LAB B2 · BLOCK TABLE + METADATA

连续 K/V 太简单了。
现在把它切成 block，再放进任意物理槽位。

上一实验只证明“远端 KV 可以继续 Decode”。这一层开始接近 vLLM 的真正问题：请求携带 metadata；KV 按固定 token block 传输；Consumer 把逻辑 block 放进任意物理 KV pool slot；attention 依靠 block table 找回正确顺序。这里第一次把“逻辑序列”和“物理显存位置”明确分开。

01 · TWO PLANES

先分控制信息，再分真正的大 tensor。

CONTROLrequest metadatarequest_id、seq、hidden、block_size、num_blocks。Consumer 先知道“接下来要收什么”。
DATAK/V wire blocks每个 logical block 带 valid-token count，再发送固定 shape 的 K block 与 V block。
LOCAL MEMORYphysical KV poolConsumer 自己决定 physical block id；这与 Producer 的逻辑编号没有一一同址关系。

这就是为什么真实 KV Connector 不可能只有一个 send(tensor)：Scheduler / metadata 解决“应该搬什么”，Worker / transport 解决“字节怎么搬”。

02 · LOGICAL ≠ PHYSICAL

故意把 0,1,2 三个逻辑 block 放到 7,6,5。

REQUEST VIEWlogical blocks[0] [1] [2]
block table →
GPU-POOL VIEWphysical slots[7] [6] [5]

最后一个 block 只有 2 个有效 token，但 wire block 仍是固定的 4-token shape；多出来的位置被 padding。Consumer 另外记录 valid_tokens，重建逻辑 K/V 时只取有效部分。这让 block 管理与 tensor shape 保持简单，但会引入 padding / fragmentation 成本。

05 · STILL MISSING

离 NIXL/RDMA 还有四个值得单独学的台阶。

① Prefix lookup：Consumer 不应该总收完整 prompt，要先告诉 Scheduler“远端到底命中了多少 token”。
② Async transfer：metadata 决策与实际 K/V load 不能把整个 engine step 阻塞住。
③ Layer-by-layer：每层 KV 的 load/save 可以与模型执行流水，而不是全部搬完再 forward。
④ Memory registration + remote handles：进入 NIXL 后，传的不再只是 Python tensor 引用，而是可远程访问的 memory region 描述。
