LAB B7 · RELEASE WITHOUT CORRUPTION OR LEAKS

远端 KV 释放太早会读坏。
永远不释放又会把显存慢慢吃光。

B5 解决“transfer 没完成前不能复用 memory”，B6 解决“哪块 allocation / region 真正在被传”。最后还缺一个生产系统必须回答的问题：如果 消费端 挂了、网络断了，生产端 难道永远把 blocks 钉住吗？租约 给 memory 生命周期 加上一个有期限的承诺；心跳 表示“我还需要它”，完成确认 表示“我已经用完”，expiry 则是失联后的 leak-safe fallback。

01 · THE STATE MACHINE

一块远端 KV 只有两条安全释放路径：明确完成，或者租约到期。

PINNED租约 starts生产端 暂时不能把这些 blocks 还给 allocator；同时记录一个 expiry deadline。
ALIVE心跳 renews消费端 仍在使用远端 KV 时周期性续约，把安全窗口继续向后推。
RELEASEcomplete OR expire正常完成可以提前释放；失联时则等 deadline 到期后回收，避免永久泄漏。

这里最重要的不是某个固定 TTL 数字，而是不变量：在仍可能有合法远端读取时不能释放；在对端永久消失时又必须最终能够回收。

03 · STALE MESSAGE

旧请求的 心跳 不能把已经复用的新 memory 又“续活”。

OLD OWNER请求 501 · generation 0late heartbeat arrives
must not mutate →
CURRENT OWNERgeneration 1lease remains unchanged

脚本用 generation 显式演示这个 ABA-style 风险。generation 是教学字段，不是说当前 vLLM 就用同样的 generation protocol。真正要记住的是：异步系统里的 完成确认 / 心跳 必须绑定到正确的 请求 / block 生命周期，迟到消息不能影响已经被重新分配的资源。

04 · MAP TO CURRENT VLLM NIXL

当前代码已经能找到这套 生命周期 机制的几个关键锚点。

租约kv_lease_duration当前 NIXL 调度器 默认读取 30 秒 租约，并把 心跳 interval 设成 lease_duration // 6。
PINrequest_finished()需要远端读取的 请求 会延迟释放 blocks，并记录基于 perf_counter() 的 expiry deadline。
心跳heartbeat_by_engine调度器 按 remote 推理引擎 聚合仍需续约的 请求，并节流后把 心跳 元数据 交给 worker。

正常 receive 完成后，调度器 还会停止对应 请求 的 心跳。换句话说，租约 不是“定时器小功能”，而是 请求 lifecycle、block allocator 与远端 transfer 完成确认 之间的资源所有权协议。

05 · CLOCK DOMAIN TRAP

perf_counter() 是进程本地时钟，不能把另一个进程的 deadline 原样拿来比较。

CURRENT SOURCE IDEAcontrol plane
scheduler: stamp expiry in its perf_counter domain
           + attach scheduler_clock

handshake: estimate peer clock offset from round trip

worker: rebase / reason about lifetime in its own clock domain

这是一个非常典型的分布式坑：即使两个数都叫“seconds”，也不代表零点相同。当前 vLLM 的 connector 元数据 明确携带 scheduler_clock，NIXL handshake 还会用往返时间估计 peer clock offset。B7 的 virtual clock 故意只有一个时间域，避免把这个工程问题藏在 toy 代码里。

06 · INFERENCE SOFTWARE CAPSTONE

到这里，KV Connector 的软件心智模型已经闭合。

① 调度器 决定远端 KV 是否可用、需要哪些 blocks。
② 块表 / region 描述符 决定逻辑 KV 对应哪块可传输 memory。
③ Handshake 检查兼容性并交换远端 agent/layout 信息。
④ 异步 / layer-wise transfer 追踪“什么时候发起、什么时候真正需要”。
⑤ 完成确认 + 租约 / 心跳 / expiry 决定“什么时候可以安全释放”。

再往后就不是继续发明 toy 协议，而是把同一套问题放到真实 NIXL / UCX / RDMA / GPUDirect 环境里验证 transport、带宽、并发与失败恢复。没有对应硬件时，网站会停在源码级解释，不伪造 benchmark。
