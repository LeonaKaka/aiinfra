首页/Labs/KV Handshake + 生命周期
LAB B5 · RDMA 前先解决控制面

高速搬内存之前，双方必须先回答：
“你是谁、这块数据是什么、我能不能接、什么时候才能复用？”

B4 已经能 layer-by-layer 地搬 KV，但仍默认两边天然兼容。真实跨实例传输不能这么乐观：模型/KV 布局/协议不兼容就不能直接读；远端还要知道 block/地址相关元数据；生产端也不能在消费端尚未完成读取时把同一块 KV 内存提前复用。本实验先用一个很小的 control-plane protocol 把这些约束跑通，再对照 NIXL 源码。

01 · 先控制，再传数据

Handshake 不是“多余的小包”，它决定大 tensor 能不能安全开始传。

描述符version · 请求 · shape · bytes生产端先描述本次交接。消费端检查协议版本、shape/capacity 等是否兼容。
ACCEPTcompatible?只有控制面验证通过，消费端才接受后续 K/V data plane。
DATAK/V 传输真正的大 tensor 在后面走；control 元数据和 data bytes 是两条不同职责的路径。

toy 脚本的描述符只是几个整数，故意不使用真实地址、rkey 或 NIXL 描述符。它只负责教学：先协商语义，再搬字节。

02 · 完成确认也是内存安全规则

“send() 已经调用”不等于 source KV 现在就能被覆盖。

GENERATION 1region 7 owns 请求 501descriptor → accept → transfer
must 等待 →
完成确认消费端 doneack(request, region, generation)

生产端只有收到完成确认后，才把 toy region 从 generation 1 推进到 generation 2。这里的 region_id / generation 是我们人为设计的教学协议，但它表达的生命周期约束是真实的：异步传输尚未结束时，源/目标内存不能被 allocator 当成普通空闲空间随意复用。

这不是 RDMA 内存注册模拟器。

真实 NIXL registration 会把可传输内存 region 注册给实际 transport，并产生真实 agent/描述符信息。这里没有 rkey、NIC、UCX、GPU Direct，也不尝试伪装成它们；只把 handshake 与生命周期的必要性变成可执行状态机。

04 · 当前 vLLM 真正交换什么

现在看 NIXL 元数据，字段不再是一堆莫名其妙的工程噪声。

COMPATIBILITYNixlHandshakePayload先带 compatibility hash，再带 encoded agent 元数据；源码明确用两阶段解码避免不兼容 schema 直接炸掉。
内存 / 布局NixlAgentMetadata包含推理引擎 id、agent 元数据、KV base addresses、device、block 数量/长度/stride、KV 布局、block size 等。
请求RemoteMeta / ReqMeta把 remote block ids、推理引擎/请求 identity、host/port、expiry 与本地 block mapping 连到某次请求。

注意这里的关键升级：B2 的块表解决“逻辑 KV 放在本机哪里”；B5 开始回答“远端哪个推理引擎的哪些 blocks、以什么布局、在什么生命周期内，能被我安全地搬过来”。

05 · 源码阅读顺序

进入 NIXL 时先看元数据，再看 transport；否则很容易只剩 API 名词。

① v1/base.py：看 register_kv_caches()、get_handshake_metadata()、load/save/完成确认的抽象契约。
② nixl/metadata.py：看 compatibility hash、NixlAgentMetadata、NixlHandshakePayload、请求 remote 元数据。
③ nixl/base_worker.py：再追内存注册、peer 元数据、TP mapping、传输句柄与租约/完成确认。
④ 最后才问 UCX/RDMA/GPUDirect 怎么把这些描述符变成真正的数据移动。
