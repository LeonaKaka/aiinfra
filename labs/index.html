第一次做 Labs，按编号顺序走，不要因为课程页“概念对应”就跳号。

训练线推荐 A1 → A12，推理线推荐 B1 → B8。课程某一节可能提前链接后面的实验，只是在告诉你“这个机制最后会落到哪里”；真正执行时仍让前一个实验提供下一个实验需要的状态、通信和生命周期心智模型。

阶段 0机制先把 分片、梯度、KV block、P2P 的最小数据流看清。
阶段 1正确性关键结果与 dense autograd / recompute 参考实现 对齐。
阶段 2系统状态加入 优化器 分片、process group、元数据、async handle、已注册内存区 与 生命周期。
阶段 3性能先制造 重叠 的条件，再用 GPU profiler 判断它是否真的发生。
路线 A · 训练基础设施
LAB A1 · TP 前向

Mini Megatron TP

Column Parallel W1 + Row Parallel W2。每个 rank 只做自己的 GEMM，最后 all-reduce partial output。

核心问题为什么 前向 在这里通信？
 LAB A2 · TP 反向

Mini TP 反向

手算 dW2、dW1、dX，再和 dense autograd 对照；看清哪些 梯度 保持 sharded，哪些必须求和。

核心问题为什么 反向 的通信位置不同？
 LAB A3 · DATA PARALLEL

DP + 梯度 Accumulation

两个 rank 持有相同参数、处理不同样本；先本地累计多个 微批次，再只做一次 梯度 all-reduce。

核心问题“累积”和“同步”为什么是两件事？
 LAB A4 · 优化器 SHARDING

Mini Distributed 优化器

reduce-scatter 让 global 梯度 直接落成 分片；每个 rank 只保留本地 momentum，再 all-gather 更新后的参数。

核心问题为什么 优化器状态 不必每卡复制？
 LAB A5 · COMMUNICATION 重叠

Bucketed Async Reduce-Scatter

W2 梯度 先 ready 就先发 async reduce-scatter；反向 继续计算 W1。第一次把“梯度 readiness”和“通信启动时机”放到同一条时间线上。

核心问题为什么 bucket ready 后要尽早 launch，而不是等整个 反向？
 LAB A6 · 2D PROCESS GROUPS

TP × DP 2D Topology

4 ranks 组成 TP=2 × DP=2。TP rows 负责 layer 内 partial output/dX，DP columns 只同步相同 TP 分片 的参数梯度。

核心问题为什么同一个 rank 会同时属于多个通信 group？
 LAB A7 · PROFILER EVIDENCE

Profiler-ready 重叠

用 torch.profiler 标出 梯度-ready、async reduce-scatter、继续 反向 与 wait；CPU 验顺序，GPU/NCCL 才能证明真实 重叠。

核心问题怎样证明 async 真的隐藏了通信？
 LAB A8 · SEQUENCE PARALLEL

Mini Sequence Parallel

TP partial output 不先复制成 full activation，而是 reduce-scatter 直接落成 sequence 分片，再与 dense 参考实现 对齐。

核心问题SP 为什么通常和 TP 的 布局 transition 绑在一起？
 LAB A9 · PIPELINE PARALLEL

Mini Pipeline Parallel

两个 阶段 分别拥有模型的一半；微批次 前向 传 activation，反向 把 activation 梯度 送回来。

核心问题PP 的 阶段 boundary 到底传什么？
 LAB A10 · CONTEXT PARALLEL

Mini Context Parallel

Q 分片 保持本地，KV chunks 轮转；用 global positions 保持 causal semantics，并对齐 dense attention。

核心问题sequence 切开后，Attention 怎样仍看到全局 context？
 LAB A11 · EXPERT PARALLEL

Mini Expert Parallel

路由器 → all-to-all dispatch → local experts → reverse combine；同时验证数值和 token identity。

核心问题token 为什么必须去 expert owner，再回到原顺序？
 LAB A12 · TRAINING CAPSTONE

Mini Training System

把 TP×DP、梯度 readiness、async reduce-scatter、DP-owned parameter update 与 parameter all-gather 串成一次完整训练步骤；momentum / Adam state 分片仍由 A4 单独演示。

核心问题这些并行机制在一次 step 里如何真正接起来？
路线 B · 推理基础设施
LAB B1 · RAW KV 交接

Mini KV 交接

Rank 0 Prefill 产生连续 K/V；Rank 1 接收后直接 Decode，并与本地重算 prompt KV 的 参考实现 对齐。

核心问题远端 KV 能否等价接管模型状态？
 LAB B2 · BLOCK KV

Mini Block KV 交接

加入 请求 元数据、固定 token blocks、physical KV pool 和 logical→physical 块表。

核心问题逻辑序列如何脱离物理显存位置？
 LAB B3 · ASYNC DATA PLANE

Mini Async KV 传输

把 block 传输 拆成 isend/irecv launch → independent work → Work.wait()，先建立异步依赖模型。

核心问题什么时候可以不等 KV？
 LAB B4 · LAYER PIPELINE

逐层 KV Streaming

Prefill 每算完一层就发送 KV[L]；Decode 只在进入 layer L 前等待该层，形成 per-layer ready dependency。

核心问题为什么不必等所有层 KV 都到齐？
 LAB B5 · CONTROL PLANE

KV Handshake + 生命周期

在 NIXL/RDMA 前先跑通 compatibility 描述符 → accept → data 传输 → 完成确认；理解 元数据 与 内存 生命周期 为什么必须存在。

核心问题为什么高速搬内存之前必须先握手，结束后还要 完成确认？
 LAB B6 · 内存 REGISTRATION MODEL

已注册内存区 描述符

让多个 layer view 共享一个 存储 分配，再分开描述 region base、block length 与 block stride，理解 NIXL registration 前的内存几何。

核心问题为什么 分配 和 传输 region 不是一回事？
 LAB B7 · RESOURCE 生命周期

KV 租约 / Expiry

用 心跳、完成确认 与 expiry 状态机解决两个相反风险：远端仍在读时不能释放，对端失联后又不能永久钉住 blocks。

核心问题怎样既不提前释放，也不永久泄漏 KV？
 LAB B8 · INFERENCE CAPSTONE

Mini 推理引擎

把 local KV hit、远端 KV、cold prefill 放进同一个 调度器 token budget，再接上 块表、async load、decode 与 完成确认 生命周期。

核心问题一个 请求 从“可调度”到“可安全释放”经历哪些系统状态？
“异步”“profiler”“handshake”页面都没有把 CPU timing 当成性能结论。

20 个脚本目前的第一验收标准仍是 correctness 与依赖结构。代码会在可见 CUDA GPU 数量不少于当前实验 world size 时自动切 NCCL；要证明 communication/计算 重叠，必须在 GPU profiler 里看到时间区间真正重叠。NIXL/RDMA 仍需要对应硬件与软件栈。
