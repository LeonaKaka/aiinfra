LAB A5 · COMMUNICATION OVERLAP

真正的 overlap 不是“最后异步一下”。
而是哪个 bucket ready，就尽早把它发出去。

A4 已经知道 Distributed Optimizer 为什么喜欢 reduce-scatter，但通信仍然放在 backward 之后。这里再前进一步：两层 MLP 的 W2 gradient 会比 W1 更早 ready。W2 一算完就立刻发起 async reduce-scatter；主线程随后继续算 dH、ReLU backward 和 dW1。等 W1 bucket 也 ready，再发起第二个 collective。这样“backward 计算”和“梯度通信”第一次出现在同一条时间线里。

01 · READY ORDER

Backward 天然有顺序；bucket 就利用这个顺序。

BUCKET 0 READYdW2输出层先得到 gradient。不要等整个模型 backward 完成。
LAUNCHasync reduce-scatter W2拿到 Work handle 后调用方可以继续；底层是否真正并行 progress 要看 backend 与硬件。
KEEP COMPUTINGdH → dPre → dW1这段计算不依赖 W2 reduction 的最终结果，所以可以继续。

随后 W1 bucket ready，再启动自己的 reduce-scatter。工业实现会有很多 bucket，并由 autograd hook / grad buffer 追踪“这个 bucket 的所有参数梯度是否都 ready”。

02 · THE MINIMUM OVERLAP PATTERN

只看四个时间点，就知道“哪里有机会重叠”。

BACKWARD TIMELINEconceptual
dW2 ready
  └─ work2 = reduce_scatter(dW2, async=True)

compute dH
compute ReLU backward
compute dW1

dW1 ready
  └─ work1 = reduce_scatter(dW1, async=True)

wait(work2)
wait(work1)
optimizer can consume local shards

关键不是 async=True 这个布尔值，而是 wait 被推迟到了真正需要 gradient shard 的位置。如果 launch 后立刻 wait，逻辑上仍然是同步执行。
