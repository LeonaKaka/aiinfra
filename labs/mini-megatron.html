LAB A · TENSOR PARALLEL

先别读几千行 Megatron。
亲手把一个 MLP 切成两半。

这一步要验证的只有一个事实：如果第一层按输出维切、第二层按输入维切，那么每个 rank 可以独立完成自己的 GEMM，最后只需要把 partial output 相加。Megatron 的 ColumnParallelLinear / RowParallelLinear，核心就是这件事的工业化版本。

01 · THE CONTRACT

一张图先定清楚：每个 rank 到底拥有什么。

W1 · COLUMN SPLIT[H,F] → [H,F/2]每个 rank 算一半 FFN hidden features。
W2 · ROW SPLIT[F,O] → [F/2,O]W2 的 row shard 正好吃对应的 local hidden。
COLLECTIVEall-reduce SUM两个 partial output 相加，得到与 dense MLP 相同的 Y。

注意这里没有 all-gather hidden。第一层切出来的 local hidden 可以直接喂给第二层对应 shard，所以通信被推迟到第二层输出。这个组合为什么常见，现在就不再是“框架规定”，而是 shape 自己推出来的。

02 · RUN

先用 CPU 跑。命令和 2 GPU 完全一样。

TERMINAL2 processes
torchrun --standalone --nproc-per-node=2 \
  labs/code/mini_megatron_tp.py --steps 50

脚本会检查本机是否至少有 2 张 CUDA GPU：有则自动选 NCCL + 每 rank 一张 GPU；没有则使用 Gloo + CPU。这样第一遍学习可以先排除 CUDA/NCCL 配置干扰。

03 · WHAT COUNTS AS PASS

不要因为程序“能跑”就算成功。

SHAPEW1 [8,12] → [8,6]world_size=2 时每 rank 只持有一半 FFN 输出列。
COMMall-reduce Ycollective buffer 就是 local output，而不是完整 W1/W2。
NUMERICSmax error < 1e-5TP 路径必须与 dense reference 数值一致。
EXAMPLE OUTPUTCPU / Gloo
W1 dense shape      : [8, 12]
W1 shard / rank     : [8, 6]
W2 shard / rank     : [6, 6]
all-reduce buffer   : 96 bytes / rank
max |TP - dense|    : 1.192e-07
PASS
这里的 step time 不是性能结论。

默认矩阵太小，Python、进程同步和 collective launch 开销会淹没 GEMM。这个 timing 只用来建立“计算 → 通信 → 下一步”的时间感。真正 benchmark 应把 hidden/ffn/batch 放大，并用 profiler 看 timeline。

05 · UPGRADE PATH

把这个 80 行实验逐步推向真正的训练 Infra。

① 把 ReLU MLP 换成 SwiGLU：观察 gate/up 两个 projection 应该怎么切。
② 加 backward 和 optimizer：检查 gradient 的 collective 在哪里出现。
③ 把 world_size 改成 4：记录 shard shape 和 collective buffer 如何变化。
④ 用 torch.profiler / Nsight Systems：把 GEMM 和 all-reduce 放到同一条 timeline。
⑤ 再进入 Megatron Sequence Parallel：思考为什么 activation 也需要减少复制。
