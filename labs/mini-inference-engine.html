LAB B8 · INFERENCE CAPSTONE

B1–B7 是 KV 数据面的零件。
这一节第一次让多个 request 在同一个 engine 生命周期里竞争资源。

2 个 ranks 分别扮演 remote KV Producer 与 Inference Consumer。Consumer 同时面对 local KV hit、remote KV request 和 cold miss：scheduler 必须分配 model-compute token budget，block table 必须把 logical KV 映射到 physical pool，remote transfer 必须在 decode 真正需要前完成，最后 completion 才允许 Producer 释放那一代 KV。

01 · THREE REQUEST PATHS

推理系统不是“一条 prompt 顺序跑到底”，而是在不同状态的 request 之间不断做选择。

REQ 201 · LOCAL HITKV already local → decode不需要重新 prefill；只消耗 1 个 decode token 的 model-compute budget。
REQ 202 · REMOTE KVdescriptor → blocks → async load先验证远端对象兼容性并预留 physical blocks；KV 到达后才能进入 decode。
REQ 203 · COLD MISSno reusable KV → prefill远端 KV 仍在传输时，本地可以把计算预算用在另一个 cold request 的 prefill 上。

这里真正要看的不是三个固定 request id，而是状态不同 → 下一步资源需求不同。这正是 continuous batching / scheduler 思维和普通“batch 一次算完”最大的差别。

02 · TOKEN BUDGET ≠ NETWORK BYTES

远端 KV 在搬，并不等于它正在消耗 model-compute token budget。

DEFAULT TEACHING SCHEDULEtoken budget = 6
1 token  → request 201 local-KV decode
4 tokens → request 203 cold prefill
           [request 202 KV transfer is in flight]
1 token  → request 202 remote-KV decode after data is ready

remaining model-compute budget = 0

这个区分非常重要：scheduler 的 token budget 约束模型这一步准备计算多少 token；KV transfer 同时占用的是另一类 data-plane / memory / network 资源。真实 vLLM 还有更丰富的 scheduling policy，但“计算预算”和“外部状态到达”不是同一个量。

03 · LOGICAL REQUEST, PHYSICAL KV POOL

request 只需要知道自己的逻辑 block 顺序，不应该绑定某个固定显存地址。

LOGICALrequest 202 blocks [0, 1]prompt order
block table →
PHYSICALpool slots [7, 3]allocator-owned storage

Consumer 在 bulk payload 完成前先建立 block table，然后把收到的 KV blocks 写进对应 physical slots；真正做 attention 时再按 logical order 取回。B2 的“逻辑序列与物理位置解耦”在这里第一次进入 scheduler + remote-transfer 生命周期。

04 · CONTROL PLANE BEFORE DATA, COMPLETION BEFORE RELEASE

高速搬 KV 之前先确认“这是谁、长什么样”；搬完以后还要确认“现在真的可以释放”。

REMOTE REQUEST 202lifetime contract
Producer: descriptor(request / shape / generation / bytes)
              │
Consumer: validate → allocate physical blocks → irecv(payload)
              │
          independent local scheduling / prefill
              │
          wait only when remote decode needs KV
              │
          decode → completion(request, generation)
              │
Producer: safe to release this source generation

request_id、generation、model_signature 和 block IDs 都是教学字段，不是当前 vLLM / NIXL 协议逐字段复刻。要记的是 invariant：兼容性必须在消费前成立，source memory 又必须活到远端完成为止。

05 · RUN + REFERENCE

真正的验收：remote handoff 后的 decode，必须等价于本地重新计算同一份 prompt KV。

TERMINAL2 ranks
torchrun --standalone --nproc-per-node=2 \
  labs/code/mini_inference_engine.py

脚本故意在 Consumer 端额外重算 prompt KV 作为 correctness-only reference；生产系统不会为了“验证 handoff”每次重算。默认条件下还要求 token budget 恰好用完、descriptor 兼容、completion/release 成功，并且 remote decode 最大误差小于 1e-5。

06 · SOURCE READING PAYOFF

现在可以把 vLLM 看成一条跨 subsystem 的 request lifecycle，而不是只盯 Scheduler 一个 class。

OUR CAPSTONErequest state → token budget → block table → remote KV → decode → completionscheduler · allocator · transfer · lifetime
maps to →
VLLMScheduler + KVCacheManager / block pool + model runner + KVConnector具体 class / 文件拆分会随版本演化

真正源码里，这些职责不会都待在一个文件。B8 的作用就是给你一个稳定的阅读问题清单：谁决定 request 现在能不能跑？谁分配 KV blocks？谁启动/等待外部 KV？谁知道 decode 已完成？谁最终允许资源回收？
