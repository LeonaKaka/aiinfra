LAB A10 · CONTEXT PARALLEL

长 context 被切开以后，Attention 仍然要看见全局历史。
这个 Lab 让 Q 留在本地，让 KV 去“找”它。

两个 ranks 各持一段 sequence。每个 rank 的 Query shard 始终留在本地；Key/Value chunk 则按 ring 顺序轮转。每一轮，本地 Q 都和当前 KV chunk 计算一部分 attention scores。把所有轮次合起来以后，输出必须和单卡 dense causal attention 完全一致。

01 · WHAT STAYS / WHAT MOVES

Context Parallel 的第一层直觉不是“每张卡独立做半段 Attention”。

2-RANK VIEWQ local · KV rotates
Rank 0 owns Q0, KV0        Rank 1 owns Q1, KV1

round 0: Q0 × KV0          Q1 × KV1
round 1: Q0 × KV1          Q1 × KV0

Q0 / Q1 stay local
KV chunks circulate so every local query can see the required global context

如果每张卡只看自己的 KV chunk，跨 chunk 的 Attention 关系就直接丢了。CP 必须在“sequence 被分片”和“Attention 仍具有全局语义”之间建立通信。

02 · GLOBAL POSITIONS STILL MATTER

KV 搬到另一张卡以后，它的全局 token 位置不能跟着“重编号”。

LOCAL Qglobal positions 0…3rank 0 的 query chunk 仍知道自己在整条序列里的位置。
REMOTE KVglobal positions 4…7remote chunk 到达 rank 0 后仍保留原始 key positions；causal mask 用全局位置比较。
MERGEsoftmax over all valid keys每轮 score chunk 拼成同一个 key 维度，再得到本地 query 的最终输出。

这正好呼应 02.3 的 position/RoPE 桥：分布式搬运可以改变数据“在哪张卡”，不能改变它在模型语义里的位置。

03 · RUN + VERIFY

正确性标准只有一个：每个 local Q shard 的输出都等于 dense causal attention 的对应切片。

TERMINAL2 ranks
torchrun --standalone --nproc-per-node=2 \
  labs/code/mini_context_parallel.py

CPU/Gloo 只验证 ring dependency、P2P 和数学结果。真实 CP 性能取决于 sequence partition、KV exchange algorithm、FlashAttention integration、topology 与 overlap；这个 Lab 不做这些性能声明。

05 · CHECKPOINT

三个问题决定你是否真的理解 CP。

① 为什么 sequence 已经分片后，本地 Q 仍然需要 remote KV？
② remote KV 到达新 rank 后，为什么 causal mask 仍必须使用它原来的 global position？
③ 这个 Lab 为什么能说明 CP 的语义，却不能证明某种 CP 算法性能最好？
