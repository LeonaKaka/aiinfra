LAB A4 · REDUCE-SCATTER + ALL-GATHER

不要把完整梯度发给每个人。
让 reduction 的结果直接落到各自的 shard。

普通 DP all-reduce 之后，每个 rank 都拿到完整 gradient；如果每个 rank 还保存完整 momentum、Adam m/v、FP32 master params，显存会重复很多份。这个实验做一个最小“Distributed Optimizer 骨架”：gradient 用 reduce-scatter 直接变成 shard；每个 rank 只维护自己的 momentum shard；更新后再 all-gather 参数，供下一次 forward 使用。

01 · MEMORY CONTRACT

计算时需要完整参数，不代表 optimizer state 也必须完整复制。

FORWARD / BACKWARDfull parameter replica这个教学版本仍让每个 DP rank 用完整参数做计算，并得到完整 local gradient。
GRADIENTreduce-scatter先跨 rank 求和，再把结果按参数区间切开；Rank r 只接收属于自己的 global grad shard。
OPTIMIZERlocal state shard只更新本 rank 的 parameter shard 与 momentum；之后 all-gather 新 parameter shards。

这和“先 all-reduce 完整 gradient，再每张卡都做同样 optimizer.step()”的数学结果可以一致，但状态复制量不再一样。world size 越大，optimizer-state sharding 的价值越明显。

02 · ONE STEP

把一轮更新压成四行，就能看清两次 collective 各自负责什么。

DISTRIBUTED OPTIMIZER SKELETONDP dimension
local_full_grad = backward(local_batch)

grad_shard = reduce_scatter_sum(local_full_grad) / DP
state_shard = momentum * state_shard + grad_shard
param_shard = param_shard - lr * state_shard

full_param = all_gather(param_shard)
# next forward uses full_param

reduce-scatter 的“reduce”解决不同 DP 样本的梯度合并，“scatter”顺便决定哪个 rank 负责哪一段 optimizer update；all-gather 则把更新后的 shards 重新 materialize 成下一轮计算需要的参数视图。

04 · MAP TO MEGATRON

现在再打开 distrib_optimizer.py，先沿 buffer/range 找 shard，而不是试图一口气理解 15 万行工程细节。

LABflat param → shard rangereduce_scatter → local momentum → all_gather
same idea →
MEGATRONoptimizer/distrib_optimizer.pybuffers · ranges · main params · reduce-scatter · all-gather

真实 Megatron 还要处理 mixed precision、FP32 main params、bucket alignment、checkpoint、overlap、TP/PP/CP/EP 组合与多种 optimizer。这个实验不是它的简化复制品，而是用最少状态把“为什么 reduce-scatter + local optimizer shard + all-gather”这条主因果链固定下来。

不要把这个实验直接叫 ZeRO-3。

这里只有 optimizer-state / update sharding 的核心数据流；参数在 forward 前仍被完整 materialize，且没有实现完整 ZeRO stage 语义、prefetch、offload 或真实 Megatron buffer 管理。
