下面不是百科全书式定义，而是这门课里的“工作定义”。当你在 Megatron / vLLM 源码里撞到一个词，先用这一句恢复上下文，再回对应课程页深挖。总站只精选跨课程反复出现、容易混淆或会影响源码阅读的核心词；完整课内术语仍以每课末尾术语表为准。遇到版本相关实现时，以当前源码为准，不把一个版本的细节背成永久定义。

HOW TO USE先找类别，再找词。模型与张量 → GPU → 分布式 → Megatron → 推理 → vLLM / KV Connector。重点看每项最下面那句“别混淆什么”。
Tensor / ModelGPUDistributedTrainingInferenceKV / Network

Tensor / Model

SHAPE[B, S, H]

Batch、Sequence、Hidden 三个最常见维度；后面几乎所有切分、显存和通信分析都从 shape 开始。

先问：哪个维度被切了？
GEMMGeneral Matrix Multiply

大多数 Linear / MLP 的核心矩阵乘；LLM 训练与 Prefill 的大量算力最终都落成 GEMM。

不要把“模型层”与“GPU kernel”混成一个层级。
ATTENTIONQ / K / V

Query 表示当前查询，Key 用来匹配，Value 提供被聚合的信息；自回归推理的 KV Cache 保存历史 token 的 K/V。

概念上 Q/K/V 分开，高性能实现可能把 QKV projection 融合。
GQAGrouped-Query Attention

多个 Q heads 共享更少的 KV heads，用更窄的 K/V 表示降低 KV Cache 与 KV 数据移动成本。

影响 KV Cache 大小，也会影响 TP / KV layout；不要默认 K/V heads 与 Q heads 一样多。

GPU Systems

DEVICE MEMORY / VRAMGPU 可直接访问的主设备内存

权重、activation、KV Cache 等通常常驻这里。VRAM 常被当作 GPU 显存的泛称，但它不指定具体物理内存技术。

“GPU 显存”是角色；HBM / GDDR 是具体实现。
DRAMDynamic Random-Access Memory

主机内存最常见的易失性存储技术之一；host staging、CPU memory 与设备注册讨论里经常会遇到。

DRAM 是存储技术，不等于“CPU 上所有 memory”的抽象角色；GPU device memory 也要看具体硬件实现。
HBMHigh Bandwidth Memory

一种高带宽显存技术，常见于数据中心 GPU / AI 加速器。它不是所有 GPU device memory 的通用名称。

消费级 GPU 很多使用 GDDR；先确认具体硬件再谈带宽。
GDDRGraphics Double Data Rate memory

另一类常见 GPU 显存技术，很多消费级/工作站显卡使用它。容量、带宽与 HBM 产品线不同。

不能因为代码写着 cuda 就假设显存一定是 HBM。
KERNELCUDA kernel

真正被 GPU 执行的一段并行程序。一个 PyTorch op 可能触发一个或多个 kernel，也可能由库调用走融合路径。

Python function 不等于一次 GPU kernel。
COMPUTE BOUND算力受限

瓶颈主要在数学运算吞吐，例如大型 GEMM 已经把主要计算单元吃满。

加显存带宽不一定有用。
MEMORY BOUND数据移动/带宽受限

GPU 大量时间花在取数和写回，而不是算术；Decode 小 batch 常更容易接近这一类瓶颈。

“显存够用”和“显存带宽够快”是两个问题。

Distributed

RANK进程在某个通信域中的编号

global rank 与 TP/DP/PP/CP/EP group 内的 rank 可能不同；同一个进程也可能同时属于多个 process group。

看到 rank 先问：“在哪个 group 里？”
ALL-REDUCE聚合后每个 rank 都拿到结果

典型用途是普通 DP 梯度同步，或不启用 sequence-parallel output sharding 时的 Row Parallel partial-output 求和。

通信结果是 replicated；具体算子不必永远使用它。
ALL-GATHER把各 rank 的 shard 拼回来

每个 rank 提供一块，最后参与者得到拼接后的完整结果。

完整结果会提高瞬时数据量/显存压力。
REDUCE-SCATTER聚合后只保留各自 shard

适合“数学上需要归约，但结果不需要在每个 rank 完整复制”的场景，例如 distributed optimizer 与 sequence parallel。

语义上同时做 reduction + sharding，不只是“更快的 all-reduce”。
ALL-TO-ALL每个 rank 给不同 rank 发不同数据

MoE token dispatch 的典型模式，因为不同 token 会被路由到不同 expert。

流量可以高度不均匀，负载均衡比单纯总字节数更重要。
NCCLNVIDIA Collective Communications Library

GPU 系统里常用的 collective / P2P 通信库，PyTorch distributed 与 Megatron 大量依赖它。

NCCL 是通信软件库，不是 NVLink、InfiniBand 或以太网本身。

Megatron / Training

SGDStochastic Gradient Descent

按梯度更新参数的经典优化方法；基础课用它把 autograd 产生的 gradient 与 optimizer step 接起来。

SGD 是优化算法；Data Parallel、Distributed Optimizer、ZeRO 讨论的是训练状态怎样跨 ranks 组织。
DPData Parallel

不同 replica 处理不同数据，再让模型更新保持一致。

主要分数据；单层权重是否再切由 TP/EP 等其它维度决定。
TPTensor Parallel

把一个 layer 内的大矩阵/计算按维度分给多个 ranks，让单层也能分摊参数和 GEMM。

collective 的位置取决于相邻算子和是否启用 SP，不能背成“每层一次 all-reduce”。
PPPipeline Parallel

把不同层放到不同 stage，通过 microbatch 让多个 stage 流水工作。

核心问题是 stage 间依赖、bubble 与 activation/gradient P2P。
VPPVirtual Pipeline Parallelism

一个物理 pipeline rank 承载多个模型分段，并通过更细的 interleaving 缩短部分 pipeline bubble。

VPP 是 PP schedule/layout 的扩展，不是再乘一个独立的物理通信域就能解释完。
SPSequence Parallel

在 TP group 内沿 sequence 维分片一部分原本会重复的 activation，并把 all-gather / reduce-scatter 放到合适边界。

它主要减少 TP 区域之间的 activation replication，不等于把 Attention 本身做 context parallel。
CPContext Parallel

让 Attention 也沿 context/sequence 维跨 ranks 工作；local Q 需要通过通信获得其它 context chunks 的 K/V 信息。

Megatron 当前可选 p2p ring、all_gather、a2a、a2a+p2p 等通信方式，不要把 CP 永久等同于 ring。
EPExpert Parallel

MoE 的 experts 分布在不同 ranks，router 决定 token 去哪个 expert，再完成 dispatch、expert compute 和 combine。

All-to-All 很典型，但 Megatron 也有 allgather / flex 等 dispatcher；EP 不等于“固定只能 A2A”。
1F1BOne Forward One Backward

Pipeline steady state 里交替推进 forward / backward microbatch，降低 bubble 与 activation 峰值。

这是 pipeline schedule，不是新的并行维度。
ZeROZero Redundancy Optimizer

通过 Data Parallel ranks 分片 optimizer state、gradient 或 parameter，减少训练状态冗余的一类方法族。

Megatron Distributed Optimizer 与 ZeRO 思路相关，但不要直接用某个 ZeRO stage 名替代当前 Megatron 的实际 buffer/collective 生命周期。
GTPGeneralized Tensor Parallelism

当前 Megatron 中新增的广义张量并行路径，带有自己的 remat、replica 与通信生命周期。

这是版本敏感的当前实现概念；不要把 GTP 当成经典 TP 的永久同义词，也不要把 gtp_remat 随手塞进旧的 world-size 乘法口诀。
DISTRIBUTED OPTIMIZER沿 DP 域分片训练状态与更新责任

每个 DP rank 只负责一部分 reduced gradients、main parameters / optimizer states 的更新范围，再通过参数同步恢复下一轮需要的一致模型视图。

与 ZeRO 思路相关，但具体哪些 bytes 被 shard、何时 all-gather 要看 Megatron 当前实现与 dtype。

Inference / vLLM

PREFILL处理 prompt tokens、建立上下文状态的阶段

大量 prompt tokens 可以并行计算，通常更偏 GEMM/compute-heavy，并产生后续 Decode 要复用的 KV。

不一定“一次吃完整个 prompt”：vLLM V1 的 chunked prefill 在可用时默认启用，可把长 prefill 拆成多个调度 chunk。
DECODE基线自回归生成阶段

经典逐 token 模型里，每个 active sequence 每一步推进一个新 token，并反复读取历史 KV，因此容易受 memory bandwidth 与 batching 影响。

这是基础心智模型；speculative decoding 等机制可能一次接受多个 token，别把“一步一个”当成所有实现的铁律。
TTFTTime To First Token

从请求进入系统到第一个输出 token 可见的端到端延迟。

可能包含 queue、Prefill、P/D handoff、Decode admission 等，不只是模型 forward 时间。
ITLInter-Token Latency

流式生成时，相邻可见 output tokens 之间的时间间隔；它天然是一组逐 token / 逐请求的延迟样本。

看交互顺滑度时要关心分布和 p95/p99，不应与 TPOT 当成同一个定义。
TPOTTime Per Output Token

常用来概括生成阶段平均每个输出 token 的耗时；具体 benchmark 的分母和是否排除首 token 要看定义。

TPOT 是聚合指标；ITL 是相邻 token 的实际间隔，两者相关但不等价。
CONTINUOUS BATCHING每个调度 step 动态组合活跃请求

请求不用等固定 batch 整体结束；新请求可加入，完成/抢占的请求可退出。

因此 Scheduler、token budget 与 KV capacity 会直接影响吞吐和尾延迟。
PAGED KV把 KV Cache 按 block 管理

请求的逻辑 token 序列不要求占一大段连续 GPU device memory，而是映射到物理 KV blocks。

借鉴分页思想，但不是操作系统页表本身。
APC / PREFIX CACHEAutomatic Prefix Caching

用 prefix hash identity 复用已经计算过的 KV，减少共享前缀的重复 Prefill。

普通 full-attention 路径可先用“完整 hash block 命中”建立心智模型；当前 hybrid full-attention + Mamba align 已存在 fine-grained partial-hit 例外，不能把完整 physical block 命中当全局不变量。
PREEMPTIONKV capacity 不足时让请求暂时退出运行

vLLM V1 当前默认使用 RECOMPUTE：释放 KV 后，资源足够时重新计算被抢占请求所需状态。

不要沿用旧 V0/SWAP 心智模型；preemption 会增加端到端延迟和重复计算。

KV Connector / Network

KV CONNECTOR外部 KV 的控制面 + Worker 传输接口层

把 Scheduler 的“哪些 tokens/blocks 可从外部获得”与 Worker 的“怎样实际 load / save / complete”连接起来。

Connector 不等于某一种 transport，也不只是一条 memcpy。
P/D DISAGGREGATIONPrefill / Decode 分离

让不同实例专门处理 Prefill 与 Decode，再通过 KV handoff 衔接两个阶段。

核心价值是资源隔离和 TTFT/ITL 独立调优；不会天然提高总吞吐。
IOMMUInput-Output Memory Management Unit

为设备 DMA 提供地址转换与访问隔离；GPU/NIC 直通、memory registration 与 RDMA 数据路径排障时经常需要确认这一层。

IOMMU 是地址转换/隔离硬件，不是传输协议；配置正确也不代表网络链路本身已经高效。
MTUMaximum Transmission Unit

网络链路一次可承载的数据包大小上限；RoCE/RDMA 环境里端到端配置不一致会直接制造性能或连通性问题。

MTU 是网络参数，不决定 KV block、NIXL descriptor 或 application chunk 的逻辑大小。
RDMARemote Direct Memory Access

让一台机器直接访问另一台机器预先注册的内存区域，减少远端 CPU 参与的数据路径。

它是一类远程内存访问机制，不是单一产品名。
GPUDIRECT RDMA让 NIC 数据路径直接触达 GPU memory

减少经 host staging 的额外拷贝，使跨节点 GPU tensor / KV 传输更直接。

需要 GPU、NIC、拓扑、驱动与软件栈共同支持；有 RDMA NIC 不代表自动拥有 GPUDirect RDMA。
UCXUnified Communication X

统一多种高速 transport 的通信框架，NIXL 可以使用它作为传输后端之一。

UCX 与 NCCL 的抽象层次和使用模式不同。
NIXLNVIDIA Inference Xfer Library

为 inference data transfer 提供 agent metadata、memory registration、异步 transfer 等能力；vLLM NixlConnector 在其上再实现 request/KV 协议。

NIXL 解决数据传输基础设施，不替 vLLM Scheduler 决定 request 生命周期。
PULL / PUSHREAD-based 与 WRITE-based KV transfer mode

Pull 由接收侧发起读取，Push 由发送侧写向对端。当前 vLLM NIXL 会把 transfer mode 纳入兼容性检查，因为两种协议不能混着握手。

“谁拥有 KV”与“谁发起数据动作”是两个不同问题。
HANDSHAKE传输前交换兼容性与远端 agent / memory 信息

双方先确认协议版本、模型/KV 相关兼容因素与远端 transfer metadata，再建立后续数据路径。

握手成功只说明控制面允许继续，不代表某次实际 transfer 已完成。
LEASE / TTL远端 KV blocks 的有限生命周期

Producer 不能在 Consumer 仍可能读取时提前 free，也不能在对端失联后永久 pin 住 blocks；heartbeat、completion 与 expiry 一起解决这两个方向的风险。

跨进程/节点时钟不能随便直接比较本地 perf_counter() deadline，需要显式的时钟/TTL 处理。
