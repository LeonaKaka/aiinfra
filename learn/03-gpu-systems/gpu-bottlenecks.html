LESSON 03.3 · GPU SYSTEMS约 55 min

GPU 到底在等什么：计算、访存还是通信？

“GPU 利用率 95%”并不等于“代码已经最优”，“算力翻倍”也不保证程序快一倍。真正做推理 Infra 时，要先判断当前工作到底被什么上限卡住：计算单元、显存带宽、跨设备通信，还是更碎的 kernel launch / CPU 调度开销。优化方向必须跟瓶颈对上。

这节课结束时，你应该能做到：
  • 用自己的话解释 compute-bound（计算受限：性能主要受计算吞吐限制）、memory-bound（内存带宽受限：性能主要受数据读写带宽限制）、communication-bound（通信受限：性能主要受跨设备通信限制）。
  • 理解 arithmetic intensity（算术强度：衡量每搬运 1 byte 数据能完成多少计算）为什么是判断瓶颈的重要指标。
  • 看懂一个极简 Roofline（屋顶线模型：把计算吞吐上限和内存带宽上限放在同一张图里比较），知道斜坡区和平台区代表什么。
  • 理解通信带宽与 latency（延迟：一次操作从开始到完成所花的时间）是两个不同问题，以及为什么小消息和大消息的优化方向不同。
  • 理解 overlap（重叠执行：让计算与通信并行以隐藏部分等待时间）的收益上限，并把它连接到 Megatron。
  • 解释为什么 LLM 的 Prefill 和 Decode 常有不同的性能压力，并把它连接到 vLLM。
01 · 三种不同上限

先把“慢”拆成三种完全不同的慢。

计算受限算不过来数据已经喂得上，主要上限是 Tensor Core / ALU 能做多少计算。
带宽受限数据喂不够快计算单元有空，但 HBM / cache 的数据搬运速度先到上限。
通信受限其它设备的数据没到多 GPU / 多节点时，本地计算要等 collective（集合通信：一组 GPU 或进程共同参与的数据通信操作）、P2P 或网络传输。

这三种情况看起来都可能表现成“程序很慢”，但解决办法完全不同：compute-bound 更关注更快的 GEMM、精度策略和 kernel；memory-bound 更关注少搬数据、kernel fusion 和复用；communication-bound 更关注通信量、topology（拓扑：描述 GPU、CPU、网络接口卡与网络之间的连接关系）、collective 算法和 overlap。

第一原则：先定位瓶颈，再优化。不要拿“更高 FLOPs”去治一个本质上在等 HBM 或网络的问题。

02 · 算术强度

判断计算还是内存，一个很重要的视角是：每搬 1 byte，做了多少计算？

ARITHMETIC INTENSITY算术强度 = FLOPs / bytes moved

这里的 bytes moved 指某个分析层级上的数据流量。严格 profiler 会区分 DRAM（动态随机存取存储器：主机内存和部分设备内存常用的易失性存储技术）、L2、L1 等 memory hierarchy；我们先用“从显存搬多少数据”建立直觉。

LOW INTENSITY搬很多，算很少例如某些逐元素操作、拷贝、简单归一化步骤，往往更容易受内存带宽限制。
HIGH INTENSITY同一批数据反复参与很多乘加足够大的 GEMM 往往能做很多计算，更有机会把 Tensor Core 吃满并进入compute-bound 区域。

“某类算子永远memory-bound”也不是绝对规律。shape、批次、dtype、kernel 实现、缓存命中和硬件都会改变实际位置。Infra 工程师要养成用测量确认的习惯。

03 · 一个最小 Roofline 心智模型

Roofline 只是把两个上限画在一张图上。

横轴是算术强度，纵轴是能达到的计算性能。极简版可以想成：

内存带宽 roof
计算 roof
左边 · memory-bound每 byte 做的计算太少，性能上限随带宽和 arithmetic intensity 增长。
右边 · compute-bound数据复用足够高后，计算单元吞吐成为更硬的上限，曲线进入平台。

这张图不是为了让你现在学性能建模数学，而是建立一个非常实用的判断：同一块 GPU 同时有“算力屋顶”和“带宽屋顶”。你的 kernel 先撞到谁，谁就是更值得优先处理的限制。

官方延伸阅读：NVIDIA Nsight Compute（kernel 性能分析器：下钻单个 GPU kernel 的计算、内存和占用率指标）的 Roofline Charts。正式分析会比这里的教学版更细，会加入不同内存层级的上限。
04 · compute-bound

计算受限时，你真的在“吃计算单元”。

想象一个足够大的 Linear：[M,K] @ [K,N]。如果矩阵尺寸合适、数据复用高、底层库能充分使用 Tensor Cores，kernel 可能更接近compute-bound。

你观察什么可能意味着什么常见方向
Tensor Core / SM 高忙算术执行资源接近上限更优 kernel、精度策略、shape、kernel fusion 或减少 FLOPs
HBM 还没到顶不是“喂不动”先卡住继续盯计算效率
大 GEMM 占主时间主耗时集中在矩阵乘cuBLAS（CUDA 线性代数库：NVIDIA 提供的 GPU 基础线性代数高性能库）、CUTLASS（CUDA 模板线性代数库：NVIDIA 提供的高性能矩阵乘与相关 kernel 模板库）、Transformer Engine（Transformer 加速库：NVIDIA 提供的 Transformer 低精度训练与推理加速库）等实现质量很重要

这也是为什么 Megatron 会如此关心 TP 之后的 local GEMM shape：切得太碎，可能让每张 GPU 上的 GEMM 变小，计算效率反而下降。

05 · memory-bound

带宽受限时，减少“搬”往往比减少“算”更重要。

如果一个操作只对每个元素做很少计算，却必须把大量数据从 HBM 读进来再写回去，那么 Tensor Cores 再强也帮不了太多。典型优化思路是：

kernel fusion多个算子合并，减少中间 tensor 写回 HBM 再读出的次数。
提高局部性让数据更多在寄存器、shared memory（共享内存：同一线程块内线程可快速共享的片上存储）和 cache 层级复用。
减少 bytes更低精度、压缩、只搬真正需要的数据。
批处理让一次 weight 读取服务更多 token / request，提高复用。
改善 layout合适的 data layout 能帮助连续合并访存并改善底层 kernel 效率。
减少 copy不必要的 tensor 实体化或 device copy 会直接消耗带宽。

后面读 FlashAttention 时，你会看到一个经典例子：它不是简单把 attention 数学公式改掉，而是重新组织数据流，减少昂贵的 HBM 读写。

06 · kernel launch overhead

有时既没吃满计算，也没吃满带宽：工作可能太碎了。

每次 CUDA kernel launch 都有调度/提交 overhead。大量非常短的小 kernel 会让 GPU timeline（时间线：按时间展示 CPU、GPU 和通信活动的性能视图）出现很多缝隙；CPU、Python、调度器也可能来不及持续喂工作。

这也是 CUDA Graphs（CUDA 图：把一组固定 GPU 工作预先记录后重复提交以减少 launch 开销）、kernel fusion、continuous batching（连续批处理：每个调度轮次都可以重新组成执行 batch）等技术有价值的一部分原因：它们不一定只是在“让某个 kernel 更快”，也可能是在减少碎片化调度和空档。

07 · 通信受限

一旦跨 GPU，就多了一份“必须把数据送到别人那里”的时间。

单 GPU 里主要盯计算和 memory hierarchy；多 GPU 还要把 GPU↔GPU、节点↔节点的通信加进账本。最简单的传输时间直觉：

IDEALIZED TRANSFER MODELtime ≈ latency + bytes / bandwidth（带宽：单位时间内链路能够传输的数据量）

小消息时固定 latency 更显眼；大消息时有效 bandwidth 更关键。collective 通信还会包含多轮传输、topology 和算法因素，所以不能直接把链路峰值带宽当实际 collective 吞吐量。

这里先认几个后面会反复出现的链路名：PCIe 是常见主机互连；RoCE（基于融合以太网的 RDMA：在以太网上承载 RDMA 语义的网络技术）在以太网上承载 RDMA；InfiniBand（高性能网络互连：数据中心常用的低延迟高带宽网络技术）则是另一类常见高性能网络。它们和 NVLink 分别处在不同硬件/网络路径上。

SMALL MESSAGElatency matters消息很小时，几十微秒级的固定开销都可能占很大比例。
LARGE MESSAGEbandwidth matters数据量大时，NVLink / PCIe / InfiniBand / RoCE 的有效吞吐决定搬完要多久。

后面学 all-reduce（全归约：归约各 GPU/进程的数据并把结果返回给所有参与者）、all-gather（全收集：收集各 GPU/进程的分片并让所有参与者得到完整结果）、reduce-scatter（归约分散：先归约，再让每个参与者只保留一份分片）时，我们会把“需要搬多少 bytes、走几轮、哪些参与者互相交换”算得更具体。

08 · 把通信藏到计算后面

Megatron 很多优化的关键词：不要傻等通信。

假设一次执行有 60ms 计算和 40ms 通信。如果完全串行，就是 100ms。若依赖关系允许把一部分通信和计算同时进行，理想上总时间可以更接近两者较大的那个，而不是简单相加。

现实不可能凭空把所有通信隐藏掉：通信可能依赖前面的结果，也会争抢 GPU、copy engine（拷贝引擎：GPU 中负责异步数据搬运的硬件引擎）、内存带宽或网络资源。但这个思路非常重要——通信与计算 overlap 是把“不得不做的通信”藏进原本就要做的计算时间里。

以后看到 Megatron 的 gradient reduce overlap（梯度归约重叠：让 gradient 通信与后续计算并行）、parameter gather overlap（参数收集重叠：让 parameter gather 与计算并行）、pipeline P2P overlap（流水线点对点重叠：让 pipeline P2P 通信与计算并行），都可以先用这个 timeline 直觉理解。

09 · 为什么 vLLM 很在意批处理

LLM 推理里，Prefill 和 Decode 常常不是同一种性能问题。

PREFILL很多 token 一起算prompt 一次送进大量 token，大矩阵乘更容易形成高效 GEMM，通常更有机会把计算吃起来。
DECODE每个 request 每步只新增少量 token单 request 很难形成足够大的矩阵；model weight 需要反复被读取，常更容易受到内存带宽、batch 大小、KV 访问等因素限制。

这不是“Prefill 永远 compute-bound、Decode 永远 memory-bound”的绝对定律。batch 大小、模型结构、quantization、硬件、kernel 都会改变瓶颈。但它给了我们一个极其重要的 vLLM 直觉：

continuous batching 的价值之一：把多个 request 的 Decode token 聚起来，让一次 weight 读取服务更多 token，提高 GPU 的有效工作量与数据复用。

10 · 怎样分析真实系统

不要靠猜，用不同 profiler 回答不同层级的问题。

timeline 里你会频繁看到 NCCL 发起的 collective / P2P；它是通信软件层，不是 NVLink、InfiniBand 或以太网链路本身。

TIMELINENsight Systems（系统性能分析器：用 timeline 查看 CPU、GPU、CUDA 和通信活动）看 CPU、CUDA kernels、NCCL、streams、空档和 overlap：系统“什么时候在等”。
KERNELNsight Compute看某个 kernel 的计算 / 内存吞吐、occupancy（占用率：表示 GPU 执行资源上可驻留工作的利用程度）和 Roofline：它“为什么慢”。
FRAMEWORKPyTorch Profiler（PyTorch 性能分析器：把框架算子与 CPU/CUDA 活动对应起来）把 Python/PyTorch op（算子：框架里一个可独立记录和执行的计算操作）和 CUDA 活动对起来，定位模型级热点。

真正的性能工作通常是从宏观 timeline 找热点，再下钻到关键 kernel，而不是打开源码随机找“看起来可以优化”的循环。

11 · 下一步去哪里

GPU Systems 到这里结束，下一模块开始研究“通信到底怎么发生”。

推理侧后面还会遇到 P/D（Prefill/Decode 分离：把 Prefill 与 Decode 放到不同资源池/实例并协调 KV 交接）：把两阶段放到不同资源池后，除了调度，还要为 KV 交接支付新的通信成本。

TRAINING · MEGATRON计算 + 通信TP / Pipeline Parallel / DP 把工作拆开；NCCL collective 搬数据；overlap 尽量把通信藏起来；并行规模还会改变 local GEMM 效率。
INFERENCE · vLLM内存 + 调度 + 通信continuous batching 提高利用率；分页式 KV 管 HBM；P/D 与 KV Connector 再引入跨设备/节点数据传输。

因此 04 Distributed 不会从抽象“分布式系统理论”起步，而会直接从你已经遇到的问题开始：两张 GPU 到底如何知道自己是谁、如何建立通信组、all-reduce 又到底搬了什么？

CHECKPOINT03.3

优化之前，先说出你认为瓶颈在哪。

1. 一个 kernel 的 Tensor Core 很空闲，但 HBM 吞吐量已经很高，更应该先怀疑计算还是内存？
更应该先怀疑memory-bound。计算单元没有吃满，而内存吞吐量接近上限，说明继续增加理论 FLOPs 往往帮助不大，应该优先考虑少搬数据、提高复用或 fusion。
2. 为什么“60ms 计算 + 40ms communication”不一定必须等于 100ms？
如果依赖关系和资源允许，一部分 communication 可以与仍在进行的计算并发。理想 overlap 会把一部分通信时间隐藏在计算时间内，但实际收益会受依赖和资源竞争限制。
3. 为什么 vLLM 会极其在意 continuous batching？
自回归 Decode 对单个请求每步工作量很小。把多个请求的 token 聚在一起，可以形成更大的有效批次，让权重读取服务更多 token、提高 GPU 利用率和吞吐；同时调度器还能及时补入新请求。
