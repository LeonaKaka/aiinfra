LESSON 03.3 · GPU SYSTEMS约 55 min

GPU 到底在等什么：Compute、Memory、Communication。

“Graphics Processing Unit (GPU，图形处理器) 利用率 95%”并不等于“代码已经最优”，“算力翻倍”也不保证程序快一倍。真正做 Infra 时，要先判断当前工作到底被什么上限卡住：计算单元、显存带宽、跨设备通信，还是更碎的 launch / Central Processing Unit (CPU，中央处理器) 调度开销。优化方向必须跟瓶颈对上。

这节课结束时，你应该能做到：
  • 用自己的话解释 compute-bound、memory-bound、communication-bound。
  • 理解 arithmetic intensity 为什么是“每搬 1 byte 数据做多少计算”的关键指标。
  • 看懂一个极简 Roofline 图，知道斜坡区和平台区代表什么。
  • 理解通信的 bandwidth 与 latency 是两个不同问题，以及为什么小消息和大消息的优化方向不同。
  • 理解 communication overlap 的收益上限，并把它连接到 Megatron。
  • 解释为什么 Large Language Model (LLM，大语言模型) prefill 和 decode 常有不同的性能压力，并把它连接到 vLLM。
01 · THREE DIFFERENT CEILINGS

先把“慢”拆成三种完全不同的慢。

COMPUTE-BOUND算不过来数据已经喂得上，主要上限是 Tensor Core / Arithmetic Logic Unit (ALU，算术逻辑单元) 能做多少计算。
MEMORY-BOUND数据喂不够快计算单元有空，但 High Bandwidth Memory (HBM，高带宽内存) / cache 的数据搬运速度先到上限。
COMMUNICATION-BOUND其它设备的数据没到多 GPU / 多节点时，本地计算要等 collective、Peer-to-Peer (P2P，点对点通信) 或网络传输。

这三种情况看起来都可能表现成“程序很慢”，但解决办法完全不同：compute-bound 更关注更快的 General Matrix Multiply (GEMM，通用矩阵乘法)、precision 和 kernel；memory-bound 更关注少搬数据、fusion、复用；communication-bound 更关注通信量、拓扑、collective 算法和 overlap。

第一原则：先定位瓶颈，再优化。不要拿“更高 FLOPs”去治一个本质上在等 HBM 或网络的问题。

02 · ARITHMETIC INTENSITY

判断 compute 还是 memory，一个很重要的视角是：每搬 1 byte，做了多少计算？

ARITHMETIC INTENSITYAI = FLOPs / bytes moved

这里的 bytes moved 指某个分析层级上的数据流量。严格 profiler 会区分 DRAM、L2、L1 等层级；我们先用“从显存搬多少数据”建立直觉。

LOW INTENSITY搬很多，算很少例如某些逐元素操作、拷贝、简单归一化步骤，往往更容易受 memory bandwidth 限制。
HIGH INTENSITY同一批数据反复参与很多乘加足够大的 GEMM 往往能做很多计算，更有机会把 Tensor Core 吃满并进入 compute-bound 区域。

“某类算子永远 memory-bound”也不是绝对规律。shape、batch、dtype、kernel 实现、缓存命中和硬件都会改变实际位置。Infra 工程师要养成用测量确认的习惯。

03 · A MINIMAL ROOFLINE

Roofline 只是把两个上限画在一张图上。

横轴是 arithmetic intensity，纵轴是能达到的计算性能。极简版可以想成：

compute roof
左边 · memory-limited每 byte 做的计算太少，性能上限随带宽和 arithmetic intensity 增长。
右边 · compute-limited数据复用足够高后，计算单元吞吐成为更硬的上限，曲线进入平台。

这张图不是为了让你现在学性能建模数学，而是建立一个非常实用的判断：同一块 GPU 同时有“算力屋顶”和“带宽屋顶”。你的 kernel 先撞到谁，谁就是更值得优先处理的限制。

官方延伸阅读：NVIDIA Nsight Compute 的 Roofline Charts。正式分析会比这里的教学版更细，会加入不同 memory hierarchy 的 roof。
04 · COMPUTE-BOUND

Compute-bound 时，你真的在“吃计算单元”。

想象一个足够大的 Linear：[M,K] @ [K,N]。如果矩阵尺寸合适、数据复用高、底层库能充分使用 Tensor Cores，kernel 可能更接近 compute-bound。

你观察什么可能意味着什么常见方向
Tensor Core / Streaming Multiprocessor (SM，流式多处理器) 高忙算术执行资源接近上限更优 kernel、precision、shape、算子融合或减少 FLOPs
HBM 还没到顶不是“喂不动”先卡住继续盯 compute efficiency
大 GEMM 占主时间主耗时集中在矩阵乘cuBLAS/CUTLASS/Transformer Engine 等实现质量很重要

这也是为什么 Megatron 会如此关心 Tensor Parallel (TP，张量并行) 之后的 local GEMM shape：切得太碎，可能让每张 GPU 上的 GEMM 变小，计算效率反而下降。

05 · MEMORY-BOUND

Memory-bound 时，减少“搬”往往比减少“算”更重要。

如果一个操作只对每个元素做很少计算，却必须把大量数据从 HBM 读进来再写回去，那么 Tensor Cores 再强也帮不了太多。典型优化思路是：

Kernel fusion多个操作合并，减少中间 tensor 写回 HBM 再读出的次数。
Better locality让数据更多在 register / shared memory / cache 层级复用。
Fewer bytes更低 precision、压缩、只搬真正需要的数据。
Batching让一次权重读取服务更多 token / request，提高复用。
Layout合适的数据布局能帮助 coalesced access 与底层 kernel。
Avoid copies不必要的 tensor materialization / device copy 会直接烧带宽。

后面读 FlashAttention 时，你会看到一个经典例子：它不是简单把 attention 数学公式改掉，而是重新组织数据流，减少昂贵的 HBM 读写。

06 · A FOURTH THING YOU MUST NOT FORGET

有时既没吃满 compute，也没吃满 bandwidth：工作可能太碎了。

每次 CUDA kernel launch 都有调度/提交开销。大量非常短的小 kernel 会让 GPU 时间线出现很多缝隙；CPU、Python、scheduler 也可能来不及持续喂工作。

07 · COMMUNICATION-BOUND

一旦跨 GPU，就多了一份“必须把数据送到别人那里”的时间。

单 GPU 里主要盯 compute 和 memory hierarchy；多 GPU 还要把 GPU↔GPU、node↔node 的通信加进账本。最简单的传输时间直觉：

IDEALIZED TRANSFER MODELtime ≈ latency + bytes / bandwidth

小消息时固定启动 latency 更显眼；大消息时有效 bandwidth 更关键。collective 通信还会包含多轮传输、拓扑和算法因素，所以不能直接把链路峰值带宽当实际 collective 吞吐。

SMALL MESSAGELatency matters消息很小时，几十微秒级的固定开销都可能占很大比例。
LARGE MESSAGEBandwidth matters数据量大时，NVLink / Peripheral Component Interconnect Express (PCIe，高速外设组件互连) / InfiniBand / RDMA over Converged Ethernet (RoCE，基于融合以太网的 RDMA) 的有效吞吐决定搬完要多久。

后面学 all-reduce / all-gather / reduce-scatter 时，我们会把“需要搬多少 bytes、走几轮、哪些 rank 互相交换”算得更具体。

08 · HIDE COMMUNICATION BEHIND COMPUTE

Megatron 很多优化的关键词：不要傻等通信。

假设一次 step 有 60ms compute 和 40ms communication。如果完全串行，就是 100ms。若依赖关系允许把一部分通信和计算同时进行，理想上总时间可以更接近两者较大的那个，而不是简单相加。

现实不可能凭空把所有通信隐藏掉：通信可能依赖前面的结果，也会争抢 GPU、copy engine、memory bandwidth 或网络资源。但这个思路非常重要——communication overlap 是把“不得不做的通信”藏进原本就要做的计算时间里。

以后看到 Megatron 的 gradient reduce overlap、parameter gather overlap、pipeline P2P overlap，都可以先用这个时间线直觉理解。

09 · WHY VLLM CARES ABOUT BATCHING

LLM 推理里，Prefill 和 Decode 常常不是同一种性能问题。

PREFILL很多 token 一起算Prompt 一次送进大量 token，大矩阵乘更容易形成高效 GEMM，通常更有机会把 compute 吃起来。
DECODE每个 request 每步只新增少量 token单 request 很难形成足够大的矩阵；模型权重需要反复被读取，常更容易受到 memory bandwidth、batch size、Key-Value (KV，键-值) 访问等因素限制。

这不是“prefill 永远 compute-bound、decode 永远 memory-bound”的绝对定律。batch 大小、模型结构、quantization、hardware、kernel 都会改变瓶颈。但它给了我们一个极其重要的 vLLM 直觉：

Continuous batching 的价值之一：把多个 request 的 decode token 聚起来，让一次权重读取服务更多 token，提高 GPU 的有效工作量与数据复用。

10 · HOW TO LOOK AT A REAL SYSTEM

不要靠猜，用不同 profiler 回答不同层级的问题。

TIMELINENsight Systems看 CPU、CUDA kernels、NVIDIA Collective Communications Library (NCCL，NVIDIA 集体通信库)、streams、空档和 overlap：系统“什么时候在等”。
KERNELNsight Compute看某个 kernel 的 compute / memory throughput、occupancy、roofline：它“为什么慢”。
FRAMEWORKPyTorch Profiler把 Python/PyTorch op 和 CUDA activities 对起来，定位模型级热点。

真正的性能工作通常是从宏观 timeline 找热点，再下钻到关键 kernel，而不是打开源码随机找“看起来可以优化”的 for-loop。

11 · THE ROAD AHEAD

GPU Systems 到这里结束，下一模块开始研究“通信到底怎么发生”。

TRAINING · MEGATRONcompute + communicationTP/Pipeline Parallel (PP，流水线并行)/Data Parallel (DP，数据并行) 把工作拆开；NCCL collectives 搬数据；overlap 尽量把通信藏起来；parallel size 还会改变 local GEMM efficiency。
INFERENCE · vLLMmemory + scheduling + communicationcontinuous batching 提高利用率；Paged KV 管 HBM；Prefill/Decode Disaggregation (P/D，Prefill/Decode 分离) disaggregation 与 KV Connector 再引入跨设备/节点数据传输。

因此 04 Distributed 不会从抽象“分布式系统理论”起步，而会直接从你已经遇到的问题开始：两张 GPU 到底如何知道自己是谁、如何建立通信组、all-reduce 又到底搬了什么？

CHECKPOINT03.3

优化之前，先说出你认为瓶颈在哪。

1. 一个 kernel 的 Tensor Core 很空闲，但 HBM throughput 已经很高，更应该先怀疑 compute 还是 memory？
更应该先怀疑 memory-bound。计算单元没有吃满，而 memory throughput 接近上限，说明继续增加理论 FLOPs 往往帮助不大，应该优先考虑少搬数据、提高复用或 fusion。
2. 为什么“60ms compute + 40ms communication”不一定必须等于 100ms？
如果依赖关系和资源允许，一部分 communication 可以与仍在进行的 compute 并发。理想 overlap 会把一部分通信时间隐藏在计算时间内，但实际收益会受依赖和资源竞争限制。
3. 为什么 vLLM 会极其在意 continuous batching？
自回归 decode 对单个 request 每步工作量很小。把多个 request 的 token 聚在一起，可以形成更大的有效 batch，让权重读取服务更多 token、提高 GPU 利用率和吞吐；同时 scheduler 还能及时补入新请求。
