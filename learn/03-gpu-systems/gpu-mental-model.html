LESSON 03.1 · GPU SYSTEMS约 45 min

GPU 心智模型：模型到底在哪里算、数据又在哪里放？

前面我们一直写 X @ W，但从现在开始要问更底层的问题：X 和 W 此刻在 Central Processing Unit (CPU，中央处理器) 内存还是 Graphics Processing Unit (GPU，图形处理器) 显存？是谁发起矩阵乘法？真正执行计算的是什么？为什么 GPU 明明很强却还会“等数据”？这套心智模型是后面理解 NVIDIA Collective Communications Library (NCCL，NVIDIA 集体通信库)、Tensor Parallel、vLLM 性能优化的地基。

这节课结束时，你应该能做到：
  • 区分 CPU/host memory 与 GPU device memory 的角色，并知道 High Bandwidth Memory (HBM，高带宽内存) / Graphics Double Data Rate (GDDR，图形双倍数据速率存储器) 是具体显存技术。
  • 知道 PyTorch CUDA op 最终会在 GPU 上触发 kernel，而不是 Python 自己在算矩阵。
  • 理解 Streaming Multiprocessor (SM，流式多处理器)、Tensor Core、device memory、Peripheral Component Interconnect Express (PCIe，高速外设组件互连)/NVLink 分别大致处在什么位置。
  • 知道 GPU 工作通常具有异步执行特征，为什么计时常需要 synchronize。
  • 面对“GPU 利用率不高”时不再只想到“GPU 算力不够”。
01 · ONE MACHINE, TWO MEMORY WORLDS

先把一台 AI 机器想成 CPU 世界和 GPU 世界。

HOSTCPUPython · scheduler · dataloader
SYSTEM MEMORYRandom Access Memory (RAM，随机存取存储器)
PCIe / platform interconnect
DEVICEGPUCUDA kernels · General Matrix Multiply (GEMM，通用矩阵乘法) · attention
DEVICE MEMORYHBM or GDDR

最常见的离散 GPU 机器里，CPU 和 GPU 有各自的内存。一个 CPU tensor 不能因为你“想让 GPU 算”就自动变成 GPU tensor，通常需要把数据传到 device memory：

pythondevice move
x = torch.randn(1024, 1024)   # CPU memory
x = x.to('cuda:0')              # move/copy to GPU 0
print(x.device)                    # cuda:0

“GPU 显存”是角色，HBM / GDDR 是实现。Video Random Access Memory (VRAM，显存) 常被当作 GPU device memory 的泛称；数据中心加速器常见 HBM，很多消费级 GPU 使用 GDDR。后面谈容量、带宽和拓扑时，要先确认具体 GPU，而不是把 HBM 当作所有 GPU 显存的同义词。

先别把互连记死。普通服务器/PC 常通过 PCIe 连接 CPU 与 GPU；NVLink/NVSwitch 更常用于高带宽 GPU↔GPU 互连，也存在带更紧密 CPU-GPU 互连的特定平台。后面会按具体拓扑再讲。

02 · INSIDE THE GPU

GPU 不是“一颗超级核心”，而是大量并行执行资源。

不同 NVIDIA 架构细节会变化，但为了学 Infra，可以先用下面这个抽象：

GPU
SMCUDA coresTensor Cores
SMCUDA coresTensor Cores
SMCUDA coresTensor Cores
SMCUDA coresTensor Cores
…many more
SMCUDA coresTensor Cores
GPU DEVICE MEMORYHBM / GDDR

SM（Streaming Multiprocessor）可以先理解为 GPU 上的一组计算执行资源。大量 threads/warps 被调度到各个 SM 上运行。Tensor Cores 则是其中专门加速某些矩阵乘加运算的硬件单元。

这也是为什么深度学习特别喜欢大矩阵：同一种规则计算可以拆成大量并行工作，让 GPU 的很多执行单元一起忙起来。

03 · WHAT IS A CUDA KERNEL

你写一行 PyTorch，GPU 看到的往往是一串 kernel launches。

例如：

pythonhigh level
Y = X @ W
Y = torch.nn.functional.gelu(Y)

Python 本身并没有拿一个 for-loop 去乘几十亿次。PyTorch 会调用底层 CUDA/library 实现，让 GPU 执行适合这些操作的 kernels。矩阵乘法通常会落到底层高度优化的 GEMM 实现；激活函数又可能是另一个 kernel。

PYTHON / CPUtorch.matmul
launch →
CUDA / LIBRARYGPU kernel(s)
execute →
GPUmany threads

Kernel = 在 GPU 上并行执行的函数/程序实例。以后说 kernel fusion，基本就是想把原本多个独立 kernel 的工作尽可能合并，减少中间读写与 launch 开销。

04 · WHY TENSOR CORES MATTER

大模型里的 GEMM，正好是 Tensor Cores 擅长的工作。

Tensor Cores 针对特定数据类型和矩阵乘加模式提供很高吞吐。于是模型训练/推理会大量使用 16-bit Floating Point (FP16，16 位浮点)、Brain Floating Point 16 (BF16，BF16 16 位浮点)、8-bit Floating Point (FP8，8 位浮点) 等较低精度格式，并把 Linear/Attention/Multi-Layer Perceptron (MLP，多层感知机) 尽量变成高效的大矩阵运算。

LINEARX @ W → GEMM-heavy
Query-Key-Value (QKV，查询-键-值) PROJECTIONoften a fused QKV GEMM
MLPlarge up / down projections

概念上 Q/K/V 是三组投影，但高性能实现常把它们融合成一次 QKV projection GEMM 或等价的融合路径。前面学 shape 不是纯数学：矩阵的 M/N/K 尺寸会影响底层 kernel 能不能把 Tensor Core 和内存带宽吃满。

05 · COMPUTE NEEDS DATA

算力再高，如果数据没及时到计算单元，GPU 也只能等。

权重、activation、Key-Value (KV，键-值) Cache 等大部分数据常驻在 GPU device memory；具体硬件可能使用 HBM，也可能使用 GDDR。计算前后要不断把数据在内存层级之间搬运。于是一个 kernel 的速度可能受两类完全不同的上限制约：

COMPUTE算得不够快Tensor Core / Arithmetic Logic Unit (ALU，算术逻辑单元) 是瓶颈
MEMORY喂数据不够快memory bandwidth / data movement 是瓶颈

下一节会正式学习显存账单，03.3 再把 compute-bound / memory-bound / communication-bound 分开。

06 · ASYNCHRONOUS EXECUTION

CPU 发出 GPU 工作后，很多 CUDA 操作不会原地傻等 GPU 完成。

在常见 PyTorch CUDA 工作流里，CPU 可以把工作提交到 CUDA stream，然后继续往下执行。这样 CPU launch 与 GPU execution 能重叠，但也带来一个新手最容易踩的坑：直接用 CPU 时钟包住 CUDA op，可能只量到“提交工作”的时间。

CPUlaunch Alaunch Bother work
GPUkernel Akernel B
pythonsimple timing idea
import time

torch.cuda.synchronize()   # exclude earlier queued CUDA work
start = time.perf_counter()
y = x @ w

torch.cuda.synchronize()   # wait for this queued work to finish
elapsed = time.perf_counter() - start

前面的同步让计时窗口不被更早排队的 CUDA 工作污染，后面的同步保证目标工作真的完成。正式 benchmark 更常使用 CUDA Events、warm-up、多次迭代等方法；这里先建立“GPU execution 可以和 CPU 控制流异步”的概念。

07 · TWO GPUS ARE TWO DEVICES

cuda:0 和 cuda:1 不是一个更大的共享显存池。

GPU 0device memory 0X lives here
NVLink / PCIe / fabric
GPU 1device memory 1W lives here

如果某个计算需要 GPU 1 用到 GPU 0 上的数据，就必须存在某种数据移动/通信路径。框架、NCCL、Peer-to-Peer (P2P，点对点通信)、collective 通信等会帮你完成，但代价不会凭空消失。

这就是分布式训练的核心矛盾：多 GPU 给了更多计算和显存，但只要把一个问题拆开，就必须考虑“拆完之后哪些数据还需要彼此交换”。

08 · WHY A GPU CAN LOOK IDLE

GPU 没跑满，不代表唯一答案是“模型太小”。

CPU / launchCPU 没及时提交足够工作
Memorykernel 在等 device-memory 数据
CommunicationGPU 在等其它 ranks / network
Synchronization某个 barrier / dependency 阻塞
Small kernels工作太碎，launch 开销占比高
Load imbalance不同 GPU 工作量不均

后面读 Megatron 的 communication overlap、读 vLLM 的 batching/scheduler，本质上都在想办法减少这些“昂贵 GPU 没在做有效计算”的时间。

09 · CONNECT THE ROADMAP

把今天的硬件词，放回我们的两条终点路线。

MEGATRONmany GPUs大 GEMM 分片 → local kernels → NCCL 通信 → overlap
vLLMserving GPUsmodel weights + KV in device memory → scheduler feeds kernels → KV transfer across devices/nodes

之后再看到 “NCCL all-reduce”“GPUDirect Remote Direct Memory Access (RDMA，远程直接内存访问)”“NVIDIA Inference Xfer Library (NIXL，NVIDIA 推理传输库)”，不要把它们当成凭空冒出来的新技术。它们都在解决同一个非常具体的问题：让数据在正确的时间，到正确的设备和内存位置。

CHECKPOINT03.1

先把 GPU 画成一个系统，而不是一块“加速卡”。

1. torch.randn(...) 默认在 CPU，为什么要 .to('cuda:0') 才能让 GPU 直接使用？
因为常见离散 GPU 系统里 CPU memory 与 GPU device memory 是不同的内存空间，tensor 必须位于对应 device 可使用的位置；移动数据本身也有成本。
2. 为什么一行 X @ W 不等于“Python 在做矩阵乘法”？
PyTorch 是高层入口。CUDA tensor 的矩阵乘法会调用底层 CUDA/library 实现并在 GPU 上执行 kernel；Python 主要负责组织和发起这些操作。
3. 为什么直接用 CPU timer 量一个 CUDA op 可能不准？
因为 CUDA 工作常异步提交，CPU 可能在 GPU 真正完成前就继续执行。简单计时要控制计时窗口前后的同步；严谨 benchmark 通常使用 CUDA Events、warm-up 等。
