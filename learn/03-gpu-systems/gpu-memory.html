LESSON 03.2 · GPU SYSTEMS约 50 min

显存到底花在哪：先学会给 GPU 做一张账本。

“模型 7B，为什么 24GB 显卡还训练不了？”“推理明明不反向传播，为什么上下文一长还是 Out Of Memory (OOM，内存不足/显存不足)？”这类问题都不能只看参数量。训练和推理会同时占用多种不同寿命、不同形状的数据。把这些账分清，后面你才看得懂 Megatron 为什么要 shard optimizer、vLLM 为什么如此在意 Key-Value (KV，键-值) Cache。

这节课结束时，你应该能做到：
  • 把 Graphics Processing Unit (GPU，图形处理器) 显存拆成 Parameters、Gradients、Optimizer States、Activations、Temporary/Workspace、KV Cache 等主要类别。
  • 用 元素数量 × 每元素字节数 粗算一个 tensor 或一份模型权重占多少内存。
  • 理解“16 bytes / parameter”为什么只能当某些训练配置下的粗略经验值，不能当通用真理。
  • 解释 activation checkpointing、distributed optimizer、Grouped-Query Attention (GQA，分组查询注意力) 分别在省哪一类显存。
  • 区分 PyTorch 的 memory_allocated 与 memory_reserved，不再把 nvidia-smi 的数字直接等同于活着的 tensor。
01 · THE MEMORY LEDGER

先别算数字，先把显存里的“住户”认全。

GPU MEMORY LEDGER谁会长期占着，谁只在某一阶段出现？
Parameters模型权重。训练和推理都需要，通常是最容易先估算的一类。train + infer
Gradients反向传播为可训练参数产生的梯度。训练需要，普通推理不需要。train
Optimizer statesAdam 的一阶/二阶动量等状态，有时还会有更高精度 master weights。train
Activationsforward 产生的中间结果。训练会为 backward 保留一部分；推理也会产生临时 activation，但通常不会保留 backward 所需的完整中间轨迹。both · train-heavy
Temporary / workspace算子、kernel、通信库、编译器运行时等为了执行某一步暂时申请的空间。both
KV Cache自回归推理为历史 token 保存的 Key / Value。随活跃请求和缓存 token 数增长。infer

真正程序里还会有 CUDA context、allocator 管理的缓存、NVIDIA Collective Communications Library (NCCL，NVIDIA 集体通信库) 等库自己的分配，以及框架特有的数据结构。所以上面是理解系统的主要账目，不是说显存里只有这六种对象。

02 · THE ONLY FORMULA YOU NEED FIRST

一个 tensor 占多少内存，第一步就是：元素数 × 每个元素多少 bytes。

BASIC MEMORY MATHmemory = numel × bytes_per_element

32-bit Floating Point (FP32，32 位浮点) 通常 4 bytes；16-bit Floating Point (FP16，16 位浮点) / Brain Floating Point 16 (BF16，BF16 16 位浮点) 通常 2 bytes；8-bit Floating Point (FP8，8 位浮点) / INT8 常可按 1 byte 粗算。实际模型还可能有量化 scale、metadata、padding/alignment 等额外开销。

比如一个 [8, 4096, 4096] 的 BF16 tensor：

mental mathone activation tensor
numel = 8 × 4096 × 4096
      = 134,217,728 elements

BF16 = 2 bytes / element
memory = 268,435,456 bytes
       = 256 MiB

注意：这只是一个 tensor。一个 Transformer layer 的 forward 会产生许多中间结果；几十层叠起来，activation 很快就会成为训练显存大户。

03 · PARAMETERS

“7B 模型”先能告诉你的，只是权重这一笔账。

7B 大约表示 70 亿个参数。若所有权重都用 BF16/FP16 存：

rough estimate7B weights
7,000,000,000 parameters × 2 bytes
= 14,000,000,000 bytes
≈ 14 GB  (decimal)
≈ 13.0 GiB

所以“7B × 2 bytes ≈ 14GB”只是权重常驻显存的粗估。它还没有包含训练梯度、optimizer states、activation，也没包含推理时的 KV Cache 和运行时开销。

参数量不是显存需求。它只是显存账本里的第一行。

04 · GRADIENTS

训练时，参数通常还要有一份对应的 gradient。

如果一个可训练参数 tensor 是 W，backward 后 PyTorch 通常会把对应梯度放在 W.grad。梯度 shape 与参数 shape 对应，所以数量级也常和参数相当。

PARAMWshape = [H,4H]
GRADW.gradsame shape
DTYPEnot universaldepends on setup
SHARDINGcan changeDP / ZeRO / Megatron

不要死记“gradient 永远 2 bytes/参数”或“永远 4 bytes/参数”。混合精度和分布式实现会改变保存 dtype、生命周期与分片方式。我们这里先抓住更稳定的事实：训练要为梯度付出额外显存，而普通推理没有这笔账。

05 · OPTIMIZER STATES

Adam 为什么显存贵？因为每个参数背后不只存“这个参数自己”。

以常见 Adam/AdamW 心智模型为例，优化器会为参数维护一阶动量 m 和二阶动量 v。很多混合精度训练配置会用 FP32 保存这些状态；某些实现还会保留 FP32 master weight。

MODEL WEIGHTparametere.g. BF16 · 2B
GRADIENTgrade.g. BF16 · 2B
ADAMm + voften 4B + 4B
SOME SETUPSmaster weightpossibly FP32 · 4B

于是你会经常听到“混合精度 Adam 训练大约 16 bytes/parameter”这种说法：2B weight + 2B grad + 8B Adam states + 4B master weight = 16B。这个数字只适用于某些实现假设。现代优化器、precision 策略、Fully Sharded Data Parallel (FSDP，全分片数据并行)/ZeRO/Megatron 分片方式都可能让实际账单不同。

真正应该记住的不是 16。应该记住：optimizer states 很大，而且它们天然适合在 data-parallel ranks 之间分片——这正是后面 Distributed Optimizer / ZeRO 的动机。

06 · ACTIVATIONS

Activation 的麻烦在于：它不只和模型大小有关，还和“这次喂多少 token”有关。

训练时 forward 产生的某些中间结果必须留到 backward 使用；推理同样会产生 layer output、attention / Multi-Layer Perceptron (MLP，多层感知机) 中间结果等 activation，但通常只需短暂存活，不必为 backward 跨阶段保留。batch 越大、sequence 越长、hidden 越宽、layer 越多，训练时需要保存的 activation 总量通常越大。

FORWARDproduce activations
→ keep some →
BACKWARDreuse to compute gradients
→
AFTER USEeligible to free/reuse

这也解释了 activation checkpointing 的基本交易：forward 时少保存一些中间结果，backward 真需要时再重算。你用更多计算，换更低 activation 显存。

NO CHECKPOINTINGsave more显存更高，backward 少重算
CHECKPOINTINGsave less, recompute显存更低，计算时间通常增加
07 · WHY NVIDIA-SMI CAN CONFUSE YOU

“PyTorch 没有这么多活 tensor，为什么显存看起来还没还回去？”

PyTorch 为了避免频繁向 CUDA 申请/释放显存，使用 caching allocator。已经不被 tensor 使用的一些块，可以继续留在 allocator 管理的池里，等下次快速复用。

memory_allocated()活着的 tensorPyTorch 当前由 tensor 占用的 GPU memory。
memory_reserved()allocator 管理的池包含当前 allocated，也可能包含暂时空闲、但仍被 PyTorch 保留用于复用的块。
pythonmemory inspection
print(torch.cuda.memory_allocated() / 1024**3)
print(torch.cuda.memory_reserved() / 1024**3)
print(torch.cuda.max_memory_allocated() / 1024**3)

# 更详细
print(torch.cuda.memory_summary())

nvidia-smi 看到的进程占用还可能包含 CUDA context、allocator 保留块以及其它库直接分配的内存，因此通常不会和 memory_allocated() 一模一样。

官方延伸阅读：PyTorch · Understanding CUDA Memory Usage 与 CUDA memory management。
08 · INFERENCE HAS A DIFFERENT BILL

推理省掉 gradients 和 optimizer，却多了一个会越聊越大的 KV Cache。

标准 Multi-Head Attention (MHA，多头注意力)/GQA 的 KV Cache 可以用下面这个简化公式建立数量级直觉。对单条序列：

KV bytes ≈ 2 × layers × cached_tokens × n_kv_heads × head_dim × bytes_per_element

最前面的 2 是 K 和 V 两份。真实实现还会有 block、alignment、metadata 等开销；Multi-head Latent Attention (MLA，多头潜在注意力) 等架构的缓存形式也不同。

做一个纯教学例子：32 层、4096 个 cached tokens、head_dim=128、BF16。

MHA · 32 KV HEADS≈ 2.0 GiB2 × 32 × 4096 × 32 × 128 × 2 bytes
GQA · 8 KV HEADS≈ 0.5 GiB其它条件不变，只把 KV heads 从 32 降到 8。

这就是上一模块讲 GQA 时那个“KV heads 少了，推理会更省”的具体显存账。服务系统同时跑很多 request 时，每个 request 都在占一段 KV，KV Cache 很容易从“附属开销”变成决定并发量的主资源。

09 · DEBUG AN OOM LIKE AN INFRA ENGINEER

看到 OOM，先问“哪一类账爆了”，而不是立刻把 batch 降到 1。

1Weights?模型本身就放不下？dtype / quantization / model parallel。
2Activations?batch / sequence / hidden 太大？checkpointing 是否能换计算省显存？
3Optimizer?训练 states 太大？是否需要 shard / offload / distributed optimizer？
4KV / runtime?推理 context / concurrency 太高？allocator、workspace、NCCL 是否也在占？

一个非常实用的习惯是记录峰值而不是只看某个时刻。很多 OOM 发生在 backward、optimizer step 或某个临时 workspace 峰值，而不是 forward 一开始。

10 · CONNECT TO MEGATRON AND VLLM

现在你已经能看懂两条路线为什么会选择完全不同的省显存技术。

MEGATRON · TRAININGshard model statesTensor Parallel (TP，张量并行) 切参数/General Matrix Multiply (GEMM，通用矩阵乘法)；Sequence/Context Parallel 减少部分 activation 重复；Distributed Optimizer 分片 optimizer states / gradients / parameters 的不同阶段。
vLLM · INFERENCEmanage KV as a first-class resourcePaged KV blocks、continuous batching、prefix reuse、KV transfer 都围绕“有限 High Bandwidth Memory (HBM，高带宽内存) 怎样服务更多 token / request”。

后面读源码时始终问：这个优化到底是在减少 Parameters、Gradients、Optimizer States、Activations、KV Cache，还是只是在改变它们“放在哪里”？

CHECKPOINT03.2

能把显存账算明白，再进性能瓶颈。

1. 7B BF16 模型权重大约 14GB，为什么不能因此断言“24GB 显卡一定能训练 7B”？
14GB 只是权重粗估。训练还要支付 gradients、optimizer states、activations、workspace/allocator 等显存；峰值通常远高于纯权重。
2. activation checkpointing 和 distributed optimizer 分别主要在省哪类账？
activation checkpointing 主要减少保存的 activations，用重计算换显存；distributed optimizer/ZeRO 类方法主要通过跨 data-parallel ranks 分片 optimizer states，并可进一步分片 gradients/parameters，减少每张卡重复保存的 model states。
3. 为什么 GQA 会直接影响 vLLM 的并发能力？
标准 KV Cache 的大小与 n_kv_heads 近似成正比。KV heads 更少，每个 request 的 KV 占用更低，同样 HBM 往往能容纳更多缓存 token / 活跃请求。
