LESSON 06.2 · INFERENCE约 55 min

Prefill 与 Decode：同一个 request 有两种工作负载，但 scheduler 不必切成两个“模式”。

从请求语义看，一个 request 先处理 prompt、建立 KV 状态，再进入生成阶段；这两个阶段通常叫 Prefill 与 Decode。但当前 vLLM V1 的 scheduler 源码明确写着：内部没有全局的“Decode 阶段”或“Prefill 阶段”。它按每个 request 还有多少 token 需要计算来分配本轮 token budget（token 预算：一个 scheduler iteration 最多允许安排多少 token 计算），因此长 Prefill 可以被拆成多个分块，并与正在 Decode 的请求出现在同一个 execution batch（执行批次：一次实际送进设备执行的一组 token tensors 与索引状态）里。

这节课结束时，你应该能做到：
  • 准确说出 Prefill 和 Decode 的逻辑边界，同时不把它们误当成调度器的两个全局阶段。
  • 理解 prompt 中多个位置为什么可以在causal mask约束下并行计算。
  • 知道长 Prefill 可以被分块调度拆成多个执行片段。
  • 理解基础 Decode 为什么每个请求每一步通常只新增一个 token，同时保留speculative decoding的例外意识。
  • 知道 Prefill 往往更容易形成较大的 GEMM，而 Decode 更容易受到权重/KV 读取与小批次影响。
  • 把 TTFT 主要关联到排队和 Prefill critical path，把 ITL 主要关联到生成阶段的输出节奏。
  • 理解为什么 P/D 是资源隔离策略，而不是自动吞吐加速器。
01 · 请求阶段 ≠ 调度器阶段

先用一张图把请求语义和实际调度分开。

上半部分只描述一个请求的逻辑：已知 prompt 建立历史 KV，然后 Decode 反复用“当前 token + 历史 KV”推进下一 token。下半部分换到在线推理系统：一次 scheduler iteration 可以同时包含多个 Decode token 和一个长 Prefill 的分块。

PREFILL vs DECODE · LOGICAL STATE + EXECUTION BUDGETvLLM V1 mental model
关键区别：Prefill / Decode 描述的是 token 工作与 request state（请求状态：记录一个请求当前处于等待、运行、已计算多少 token 等逻辑进度）；scheduler iteration 是资源分配单位。一个逻辑 Prefill 可以跨多个 iterations，而一个 iteration 也可以同时推进 Decode 请求和 Prefill 分块。

当前 vllm/v1/core/sched/scheduler.py 的注释直接说明：调度器没有内部的“decoding phase / prefill phase”；它根据 num_computed_tokens 与请求当前总 token 状态的差距，给请求分配本轮要计算的 token。这也是 chunked Prefill（分块预填充：把一个长 prompt 的 Prefill 工作拆到多个 scheduler iterations 执行）、prefix caching（前缀缓存：复用相同输入前缀已经计算好的 KV state）和 speculative decoding 能落进统一调度器模型的重要原因。

当前源码入口：vLLM scheduler 源码。读到 schedule() 开头时，重点看“There's no decoding phase nor prefill phase”这段注释。
02 · 为什么 Prefill 可以一次处理很多 Token

Causal 不等于“Prompt 必须一个 token 一个 token 算”。

Prompt token 都已经知道。虽然第 i 个位置不能看未来位置，但 causal mask 可以一次把依赖规则编码进 Attention。于是 GPU 能并行计算很多位置的 Q/K/V、MLP 等。

PREFILL VIEWt0t1t2t3t4t5t6t7
DECODE TIMEnew0new1new2new3new4futurefuturefuture

第二行表示基础版本 Decode 的连续 iterations，不表示 new0–new4 同时被最终确认。生成优化可以改变一次目标模型 iteration 覆盖多少候选 token，但不能把已确认前缀的条件依赖凭空删除。

03 · Chunked Prefill

长输入不一定独占一个巨大的 Prefill iteration。

例如一个 20K-token prompt，如果调度器当前 token 预算只有一部分可用，可以先处理前 4K，再在后续 iteration 继续。这样 Prefill 仍属于同一个请求，但实际执行会被拆到多个轮次。

ITER 1先安排 Decode 请求prefill 分块 A预算已满
ITER 2先安排 Decode 请求prefill 分块 B预算已满

当前 vLLM V1 优化指南明确说明：chunked Prefill 在可用时默认启用；调度先安排 待执行的 Decode 请求，再用剩余 max_num_batched_tokens 预算 安排 Prefill。若一个 Prefill 放不下，就自动切分块。

这是当前 vLLM V1 的策略说明，不是“Prefill 的数学定义”。不同 inference engine 可以采用不同调度策略；课程里需要记住的是请求阶段语义与执行分块是两层概念。
当前官方说明：docs/configuration/optimization.md · Chunked Prefill。
04 · Prefill 与 Decode 的 GEMM 形状不同

同一个 Linear，在 Prefill 和 Decode 的 M 维可以差很多。

把 token 维展平，Linear 可以看成 [M,K] @ [K,N]。一个 Prefill 执行分块的 M 与本轮安排的 input token count 相关；基础 Decode 的 M 则大约与本轮 active Decode token count 相关。continuous batching 会让两者的 M 动态变化。

Prefill chunk: M ≈ scheduled prompt tokensvsDecode: M ≈ active decode tokens

因此常见经验是：Prefill 更容易形成计算密集的大 GEMM；Decode 在批次较小时更容易受权重读取、KV 访问和 kernel overhead 影响。这不是绝对分类：具体瓶颈要看模型、批次、硬件、量化、attention 后端，并用性能分析工具验证。

05 · TTFT 与 ITL

用户等“第一个 token”和读后续流式输出，背后是两条不同关键路径。

队列等待调度器分配资源高负载时排队 甚至会主导 尾延迟。
TTFT队列 + 处理输入路径 + 首次输出长 prompt、分块、Prefill 批处理、P/D 交接都可能影响首 token 时间。
ITLGeneration 输出节奏生成开始后，相邻可见 token 的间隔受调度、KV access 与 decode execution 影响。

06.1 已把 ITL 与 TPOT 分开：这里讨论 P/D 时更关心逐 token 输出节奏，所以使用 ITL。

06 · Prefill 与 Decode 为什么会互相干扰

同一张 GPU 服务两种工作负载，调度不当时会互相伤害。

长 PREFILL可能形成较大的计算分块如果不分块 / 不控制预算，可能让已有 Decode 请求更久拿不到下一轮执行机会，拉高 尾部 ITL。
DECODE 流需要频繁、稳定被调度单轮工作可能较小，但用户对 token 间停顿很敏感。
调度器决定谁先算、每轮算多少 token吞吐、TTFT、ITL、公平性之间没有免费的最优解。

这就是 vLLM 调度器 / chunked Prefill 的直接问题域。

07 · 为什么要做 P/D 分离

既然两种工作负载的资源需求和延迟目标不同，可以把它们放到不同 GPU pool（GPU 资源池：由一组 GPU 实例组成、承担同类推理工作负载的资源集合）。

PREFILL 工作进程负责 prompt → KV state可围绕 TTFT、长 prompt 与计算密集型工作负载调优。
DECODE 工作进程接收 KV → 继续生成可围绕 ITL、Decode batching 与 KV capacity 调优。

一拆开就产生新问题：Prefill 工作进程已经算好的每层 KV，怎样交给 Decode 工作进程？这就是最终 KV Connector 章节的直接问题。

P/D 分离不是自动提高吞吐的魔法。它主要提供资源隔离、TTFT/ITL 独立调优与尾延迟控制，同时新增 KV 传输、路由、容量与故障处理复杂度。

CHECKPOINT06.2

把“逻辑阶段”和“调度粒度”分开回答。

1. 为什么 prompt 有 1000 token 时，不必串行跑 1000 次目标模型？
因为 prompt token 已知，causal mask可以让许多位置在同一次 batched execution 中并行计算。
2. “Prefill 是一次”与chunked Prefill 矛盾吗？
不矛盾。一个请求有一段逻辑处理输入工作负载，但调度器可以把它拆成多个 execution 分块，逐步让 num_computed_token 追上 prompt state。
3. 为什么说当前 vLLM V1 调度器没有全局 Prefill/Decode 两阶段？
因为它按每个请求还需要计算多少 token 来安排本轮 token budget；同一 iteration 可以同时安排已有 Decode token 与 Prefill 分块。Prefill/Decode 是工作负载语义，不是调度器必须切换的全局模式。
4. P/D 分离为什么一定会引出 KV 传输？
Prefill 工作进程已经建立 prompt 历史 K/V；Decode 工作进程若不想重新 Prefill，就必须获得这些状态并映射到自己的 KV 布局。
