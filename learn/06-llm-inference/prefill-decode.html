LESSON 06.2 · INFERENCE约 50 min

Prefill 与 Decode：同一个请求，其实包含两种很不一样的计算。

用户把一段 prompt 发进来时，模型先要一次性处理所有 prompt tokens；之后才进入“一次生成一个新 token”的循环。前者叫 Prefill，后者叫 Decode。它们跑的是同一套 Transformer 权重，但 tensor shapes、并行度、内存访问模式和 latency 指标都不同。

这节课结束时，你应该能做到：
  • 准确说出 Prefill 和 Decode 的边界。
  • 理解 Prefill 为什么可以同时处理 prompt 中很多 token positions。
  • 理解 Decode 为什么每个 request 每步通常只新增一个 query token。
  • 知道 Prefill 往往更容易形成大 GEMM，而 Decode 更容易受到权重/KV 读取与小 batch 影响。
  • 把 TTFT 主要关联到排队+Prefill，把 ITL 主要关联到 Decode。
  • 理解为什么现代 serving 会考虑 Prefill/Decode disaggregation。
01 · TWO PHASES

一个请求先 Prefill 一次，然后 Decode 很多次。

PREFILL · ONCE处理 prompt 的全部 S tokens在 causal mask 下，所有 prompt positions 的 hidden states 可以在一次 forward 中并行计算，并生成各层 K/V。[B, S, H]
DECODE · REPEAT每步新增一个 token / request历史 K/V 已缓存；当前 step 主要计算新 token 的 hidden state、Q/K/V，并让新 Q attend 到历史 KV。[B, 1, H] + KV history

这里的 B 是当前一起执行的 requests 数。真实 serving 会动态 batching，所以 B 会随 scheduler 变化。

02 · WHY PREFILL CAN PROCESS MANY TOKENS AT ONCE

Causal 不等于“训练/Prefill 必须一个 token 一个 token 算”。

Prompt tokens 都已经知道。虽然第 i 个位置不能看未来位置，但 causal mask 可以一次把这种依赖规则编码进 attention matrix。于是 GPU 能同时计算很多 positions 的 Q/K/V、MLP 等。

PREFILLt0t1t2t3t4t5t6t7
DECODEnew0new1new2new3new4futurefuturefuture

第二行不是说 new0–new4 同时执行，而是表示它们发生在连续的 decode iterations：new1 必须等 new0 被选定后才开始。

03 · DIFFERENT GEMM SHAPES

同一个 Linear，在 Prefill 和 Decode 的 M 维可以差很多。

把 token 维展平，Linear 可以看成 [M,K] @ [K,N]。Prefill 中 M 大约与 batch×prompt tokens 成正比；单个 decode request 中每步只有一个新 token，M 很小。Dynamic batching 可以把很多 requests 的 decode tokens 拼起来增加 M，但它仍与长 prompt prefill 的形状不同。

Prefill: M ≈ B×SvsDecode: M ≈ active requests

因此常见经验是：Prefill 更容易形成 compute-dense 的大 GEMM；Decode 在 batch 较小时更容易受权重读取、KV 访问和 kernel overhead 影响。这不是绝对分类：具体是否 compute-bound / memory-bound 要看模型、batch、硬件、量化、attention backend，并用 profiler 验证。

04 · TTFT VS ITL

用户等“第一个字”和读后续文字，背后是两条不同关键路径。

QUEUE等待被 scheduler 接纳Prefill 和 Decode 都可能排队，服务负载越高越重要。
TTFTQueue + Prefill + first sample长 prompt、prefill batching、排队策略直接影响首 token 时间。
ITLDecode step cadence生成开始后，每轮 scheduling、KV access、decode compute 决定流式速度。
05 · PREFILL AND DECODE CAN INTERFERE

同一张 GPU 同时服务两种 workload，调度不当时会互相伤害。

LONG PREFILL一次占用较大 compute chunk可能让已有 decode requests 更久拿不到下一轮执行机会，拉高 tail ITL。
DECODE STREAM需要频繁、稳定被调度单轮小，但用户对 token 间停顿很敏感。
SCHEDULER决定谁先算、算多少 tokens吞吐、TTFT、ITL、公平性之间没有免费的最优解。

这正是 vLLM scheduler、chunked prefill 等机制后面会处理的问题。

06 · WHY PREFILL / DECODE DISAGGREGATION EXISTS

既然两种 workload 的最佳资源配置不同，可以把它们放到不同 GPU pool。

PREFILL WORKERS负责 prompt → KV Cache可针对 TTFT、大 GEMM、长 prompt batching 调优。
DECODE WORKERS接收 KV → 继续逐 token 生成可针对 ITL、decode batching、KV capacity 调优。

但一拆开就产生一个新问题：Prefill GPU 已经算好的每层 KV Cache，怎么交给 Decode GPU？这就是最终 KV Connector 章节的直接问题。

P/D 分离不是自动提高吞吐的魔法。它主要提供资源隔离、独立调优 TTFT/ITL 的能力，同时新增 KV transfer、路由和系统复杂度。

CHECKPOINT06.2

用 shape 而不是名词回答。

1. 为什么 prompt 有 1000 tokens 时，Prefill 不需要串行跑 1000 次模型？
因为所有 prompt tokens 已知，causal mask 可以在一次 batched forward 中保证每个位置只看允许的历史。GPU 可并行处理这些 positions。
2. Decode 每个 request 每轮为什么通常只有一个新 token？
自回归依赖要求先确定当前 token，才能得到下一个 token 的条件分布。因此一个 request 每个 decode iteration 通常只推进一个位置。
3. P/D 分离为什么一定会引出 KV transfer？
Prefill workers 已经计算并保存了 prompt 历史的 K/V；Decode worker 要避免重新 Prefill，就必须获得这些 K/V，才能让新 query attend 到历史。
