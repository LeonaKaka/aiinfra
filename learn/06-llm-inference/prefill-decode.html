LESSON 06.2 · INFERENCE约 55 min

Prefill 与 Decode：同一个请求有两种 workload，但 scheduler 不必切成两个“模式”。

从请求语义看，一个请求先处理 prompt、建立 KV 状态，再进入生成阶段；这两个 workload 通常叫 Prefill 与 Decode。但当前 vLLM V1 的 scheduler 源码甚至明确写着：内部没有一个全局的“decoding phase”或“prefill phase”。它按每个 request 还欠多少 token 计算来分配本轮 token budget，因此长 Prefill 可以被切成 chunks，并与正在 Decode 的 requests 出现在同一次 execution batch 里。

这节课结束时，你应该能做到：
  • 准确说出 Prefill 和 Decode 的逻辑边界，同时不把它们误当成 scheduler 的两个全局状态。
  • 理解 prompt positions 为什么可以在 causal mask 下并行计算。
  • 知道长 Prefill 可以被 chunked scheduling 拆成多个 execution chunks。
  • 理解 baseline Decode 为什么每个 request 每步通常只新增一个 token，同时保留 speculative decoding 的例外意识。
  • 知道 Prefill 往往更容易形成大 GEMM，而 Decode 更容易受到权重/KV 读取与小 batch 影响。
  • 把 TTFT 主要关联到 queue + prompt-building critical path，把 ITL 主要关联到生成阶段 cadence。
  • 理解为什么 P/D disaggregation 是资源隔离方案，而不是自动吞吐加速器。
01 · LOGICAL PHASE ≠ SCHEDULER PHASE

先用一张图把“请求语义”和“实际调度”分开。

上半部分只描述一个 request 的逻辑：已知 prompt 建立历史 KV，然后 Decode 反复用“当前 token + 历史 KV”推进下一 token。下半部分换到 serving 系统：一次 scheduler iteration 可以同时包含多个 Decode token 和一个长 Prefill 的 chunk。

PREFILL vs DECODE · LOGICAL STATE + EXECUTION BUDGETvLLM V1 mental model
关键区别：Prefill / Decode 是描述 token work 与 request state 的语义；scheduler iteration 是资源分配单位。一个逻辑 Prefill 可以跨多个 iterations，而一个 iteration 也可以同时推进 Decode requests 和 Prefill chunk。

当前 vllm/v1/core/sched/scheduler.py 的注释直接说明：scheduler 没有内部的“decoding phase / prefill phase”；它根据 num_computed_tokens 与请求当前总 token state 的差距，给 request 分配本轮要计算的 tokens。这也是 chunked prefill、prefix caching、speculative decoding 能落进统一 scheduler 模型的重要原因。

当前源码入口：vllm/v1/core/sched/scheduler.py。读到 schedule() 开头时，重点看“There's no decoding phase nor prefill phase”这段注释。
02 · WHY PREFILL CAN PROCESS MANY TOKENS AT ONCE

Causal 不等于“Prompt 必须一个 token 一个 token 算”。

Prompt tokens 都已经知道。虽然第 i 个位置不能看未来位置，但 causal mask 可以一次把依赖规则编码进 attention。于是 GPU 能并行计算很多 positions 的 Q/K/V、MLP 等。

PREFILL VIEWt0t1t2t3t4t5t6t7
DECODE TIMEnew0new1new2new3new4futurefuturefuture

第二行表示 baseline decode 的连续 iterations，不表示 new0–new4 同时被最终确认。生成优化可以改变一次 target-model step 覆盖多少候选 token，但不能把已确认前缀的条件依赖凭空删除。

03 · CHUNKED PREFILL

长 prompt 不一定独占一个巨大 Prefill step。

例如一个 20K-token prompt，如果 scheduler 当前 token budget 只有一部分可用，可以先处理前 4K，再在后续 iterations 继续。这样 Prefill 仍是同一个 request 的 prompt-building workload，但 execution 被拆开。

ITER 1decode reqs firstprefill chunk Abudget full
ITER 2decode reqs firstprefill chunk Bbudget full

当前 vLLM V1 优化指南明确说明：chunked prefill 在可用时默认启用；调度先安排 pending decode requests，再用剩余 max_num_batched_tokens budget 安排 Prefill。若一个 Prefill 放不下，就自动切 chunk。

这是当前 vLLM V1 的策略说明，不是“Prefill 的数学定义”。不同 serving engine 可以采用不同 scheduling policy；课程里需要记住的是 workload 语义与 execution chunk 是两层概念。
当前官方说明：docs/configuration/optimization.md · Chunked Prefill。
04 · DIFFERENT GEMM SHAPES

同一个 Linear，在 Prefill 和 Decode 的 M 维可以差很多。

把 token 维展平，Linear 可以看成 [M,K] @ [K,N]。一个 Prefill execution chunk 的 M 与本轮安排的 prompt tokens 数量相关；baseline Decode 的 M 则大约与本轮 active decode tokens 数相关。Continuous batching 会让两者的 M 动态变化。

Prefill chunk: M ≈ scheduled prompt tokensvsDecode: M ≈ active decode tokens

因此常见经验是：Prefill 更容易形成 compute-dense 的大 GEMM；Decode 在 batch 较小时更容易受权重读取、KV 访问和 kernel overhead 影响。这不是绝对分类：具体瓶颈要看模型、batch、硬件、量化、attention backend，并用 profiler 验证。

05 · TTFT VS ITL

用户等“第一个 token”和读后续流式输出，背后是两条不同关键路径。

QUEUE等待 scheduler 分配资源高负载时 queueing 甚至会主导 tail latency。
TTFTQueue + prompt-building path + first output长 prompt、chunking、prefill batching、P/D handoff 都可能影响首 token 时间。
ITLGeneration cadence生成开始后，相邻可见 tokens 的间隔受 scheduling、KV access 与 decode execution 影响。

06.1 已把 ITL 与 TPOT 分开：这里讨论 P/D 时更关心逐 token cadence，所以使用 ITL。

06 · PREFILL AND DECODE CAN INTERFERE

同一张 GPU 服务两种 workload，调度不当时会互相伤害。

LONG PREFILL可能形成较大的 compute chunk如果不 chunk / 不控制 budget，可能让已有 decode requests 更久拿不到下一轮执行机会，拉高 tail ITL。
DECODE STREAM需要频繁、稳定被调度单轮工作可能较小，但用户对 token 间停顿很敏感。
SCHEDULER决定谁先算、每轮算多少 tokens吞吐、TTFT、ITL、公平性之间没有免费的最优解。

这就是 vLLM scheduler / chunked prefill 的直接问题域。

07 · WHY PREFILL / DECODE DISAGGREGATION EXISTS

既然两种 workload 的资源需求和 latency 目标不同，可以把它们放到不同 GPU pool。

PREFILL WORKERS负责 prompt → KV state可围绕 TTFT、长 prompt 与 compute-heavy workload 调优。
DECODE WORKERS接收 KV → 继续生成可围绕 ITL、decode batching 与 KV capacity 调优。

一拆开就产生新问题：Prefill worker 已经算好的每层 KV，怎样交给 Decode worker？这就是最终 KV Connector 章节的直接问题。

P/D 分离不是自动提高吞吐的魔法。它主要提供资源隔离、TTFT/ITL 独立调优与尾延迟控制，同时新增 KV transfer、路由、容量与故障处理复杂度。

CHECKPOINT06.2

把“逻辑阶段”和“调度粒度”分开回答。

1. 为什么 prompt 有 1000 tokens 时，不必串行跑 1000 次 target model？
因为 prompt tokens 已知，causal mask 可以让许多 positions 在同一 batched execution 中并行计算。
2. “Prefill 是一次”与 chunked prefill 矛盾吗？
不矛盾。一个 request 有一段逻辑 prompt-building workload，但 scheduler 可以把它拆成多个 execution chunks，逐步让 num_computed_tokens 追上 prompt state。
3. 为什么说当前 vLLM V1 scheduler 没有全局 Prefill/Decode 两阶段？
因为它按每个 request 还需要计算多少 tokens 来安排本轮 token budget；同一 iteration 可以同时安排已有 Decode tokens 与 Prefill chunk。Prefill/Decode 是 workload 语义，不是 scheduler 必须切换的全局 mode。
4. P/D 分离为什么一定会引出 KV transfer？
Prefill workers 已经建立 prompt 历史 K/V；Decode worker 若不想重新 Prefill，就必须获得这些状态并映射到自己的 KV layout。
