LESSON 06.1 · INFERENCE约 45 min

自回归生成：训练结束以后，一个 token 是怎么一个个冒出来的？

前五个模块大多站在训练视角：一批 tokens 进入模型，forward、loss、backward、optimizer。现在切到推理。先从最基础的 decoder-only 自回归路径学起：根据当前上下文得到下一个 token 的分布，选出 token，把它接回上下文，再推进下一步。后面再补 speculative decoding 等“让一次模型步骤处理/接受多个候选 token”的优化。

这节课结束时，你应该能做到：
  • 解释 baseline autoregressive generation 的逐 token 条件依赖。
  • 知道模型输出 logits，不是直接输出一句中文。
  • 理解 greedy / sampling 只是“从 logits 选 token”的策略，不改变 Transformer 主体。
  • 知道普通逐 token decode 存在串行依赖，同时也知道 speculative decoding 等技术可以减少昂贵 target-model steps，不能把“严格 N 次大模型 forward”当成永恒定律。
  • 区分 TTFT、ITL 与 TPOT，而不是把 ITL / TPOT 当成同一个指标。
  • 为下一课 Prefill / Decode 的分裂建立直觉。
01 · TEXT BECOMES TOKENS

模型不是直接处理“句子”，而是处理 token IDs。

假设输入是“AI infra 很重要”。Tokenizer 会先把它切成模型词表中的 tokens，再映射成整数 IDs。这里不讨论具体 tokenizer 算法，只抓住推理系统真正看到的对象：

AIinfra很重要→[id₀][id₁][id₂][id₃]

这些 IDs 经过 embedding 变成前面熟悉的 [B,S,H] hidden states，然后穿过一层层 Transformer Block。

02 · THE MODEL OUTPUT IS A DISTRIBUTION

最后一层不会直接吐出“答案”，而是给词表中的每个 token 一个分数。

最后 hidden state 经过输出投影，得到 vocabulary-size 维 logits。Softmax 后可以把它看成下一个 token 的概率分布：

LAST POSITIONlogits ∈ R^V

如果词表有 V 个 token，这里就有 V 个分数。

Greedy decoding 选概率最大的 token；temperature、top-k、top-p 等 sampling 方法改变“怎样从这个分布选 token”。无论哪种 selection policy，基础 target model 都先产生 logits。

03 · THE AUTOREGRESSIVE LOOP

Baseline 路径里，选出的 token 会成为下一步条件的一部分。

1current contextprompt + generated tokens
2Transformer forward得到当前位置 hidden state
3logits词表分数
4sample token选下一个 token
5append & repeat直到 EOS / length limit
AIinfra很重要因为它决定…

最关键的数学事实是：下一个 token 的条件分布依赖已经确认的前缀。因此未来 token 之间存在因果依赖。普通 decode 是一步一步确认；speculative decoding 则可以先用 draft 产生多个候选，再让 target model 一次验证一段候选，从而减少昂贵 target-model iterations，但它没有消除自回归分布本身的条件依赖。

04 · TRAINING AND INFERENCE WANT DIFFERENT THINGS

同一个 Transformer，训练时和在线生成时是两种系统 workload。

TRAINING大批 tokens，一起 forward + backward目标通常是最大化训练吞吐 / MFU；需要保存 activation、gradient、optimizer state；大量矩阵可以做得很大。
INFERENCE用户请求持续到来，生成状态不断演化没有普通 training backward/optimizer；更关心 latency、throughput、KV Cache 容量、request scheduling 和服务公平性。

这也是为什么“训练框架很快”并不能直接推出“拿它做在线 serving 也很快”。推理系统面对的是动态请求、不同 prompt/output 长度，以及高频 decode/scheduling 的问题。

05 · A NAIVE IMPLEMENTATION RECOMPUTES TOO MUCH

如果每推进一步都把整段历史重新算一遍，会非常浪费。

假设 prompt 已有 1000 tokens。生成第一个 token 时，需要处理这 1000 tokens；生成第二个 token 时，如果从零计算，又会重新处理前面 1000 个旧 tokens；第三步继续重复。

step 1oldoldold…oldnew₁——
step 2 naiveoldoldold…oldnew₁new₂—

但 02.1 Attention 已经给了一个关键观察：历史 token 在每层产生的 Key / Value 不会因为末尾多了一个新 token 就全部失效。于是这些 K/V 可以保存下来复用。

这就是 KV Cache 的动机。不过在真正讲 KV Cache 前，我们还需要先把一次请求拆成计算性质非常不同的 Prefill 与 Decode 阶段。

06 · INFERENCE HAS MORE THAN ONE LATENCY

“这个请求用了 2 秒”还不够描述用户体验。

TTFTTime To First Token请求进入系统到第一个输出 token 可见的时间；queue、Prefill、路由/hand-off 都可能贡献。
ITLInter-Token Latency流式输出里相邻可见 tokens 之间的实际时间间隔；它天然形成一组逐 token latency samples。
TPOTTime Per Output Token生成阶段常用的平均每输出 token 耗时；具体分母、是否排除首 token 要看 benchmark 定义。

ITL 和 TPOT 相关，但不是同一个定义。ITL 更适合描述逐 token cadence 和 tail；TPOT 是聚合后的平均指标。服务吞吐（tokens/s）则又是另一条轴，和单用户最低 latency 不一定同方向。

07 · FROM MEGATRON TO VLLM

训练 Infra 的核心问题是“怎么并行算大模型”，推理 Infra 多了“怎么服务很多动态请求”。

STILL THE SAMETensor、GEMM、Attention、GPU device memory、TP、NCCL 这些基础仍然有效。
NEW OBJECT每个 request 都有自己的 prompt、生成长度、KV Cache 和生命周期。
NEW SCHEDULERGPU 下一轮到底算哪些 requests / tokens，需要在线决定。
NEW MEMORY PROBLEM模型权重相对固定，但 KV Cache 随活跃请求动态增长、释放和复用。
CHECKPOINT06.1

先确认“生成”不是一次普通 forward。

1. LLM 每一步直接输出的是一段文字吗？
不是。模型产生 vocabulary logits；解码策略从分布中选择 token ID，再由 tokenizer 映射回文本。
2. Speculative decoding 是否说明未来 token 已经没有自回归依赖？
不是。它用 draft 先猜一段候选，再让 target model 高效验证；被接受的序列仍必须符合 target autoregressive distribution。优化的是昂贵 target-model iteration 数，不是删除条件依赖。
3. ITL 和 TPOT 为什么不能写成一个词？
ITL 是相邻输出 tokens 之间的实际间隔，可以看分布和 p95/p99；TPOT 通常是生成阶段的平均每输出 token 时间。两者数值可能相关，但定义和用途不同。
