LESSON 06.1 · INFERENCE约 50 min

自回归生成：为什么“下一个 token”会把整个 serving 系统变成状态机？

训练时我们常把很多已知 tokens 一次送进模型；在线生成则有一个新的硬约束：未来 token 还不存在。模型只能根据已经确认的前缀产生下一个 token 的分数，解码策略选出一个 token，把它加入前缀，然后下一步才有了新的条件。后面的 Prefill / Decode、Key-Value (KV，键-值) Cache、Scheduler，本质上都在围绕这条状态演化链做系统优化。

这节课结束时，你应该能做到：
  • 解释 baseline decoder-only autoregressive generation 的条件依赖。
  • 知道 target model 输出 logits；greedy / temperature / top-p 等是 logits 之后的 decoding policy。
  • 理解为什么普通 target-model decode step 之间存在串行依赖。
  • 知道 speculative / multi-token 技术能减少昂贵 target-model iterations，但没有删除 target autoregressive distribution。
  • 从“重复计算历史 K/V”自然推导出 KV Cache 的必要性。
  • 区分 Time To First Token (TTFT，首 Token 延迟)、Inter-Token Latency (ITL，Token 间延迟)、Time Per Output Token (TPOT，每输出 Token 时间) 与吞吐，并知道 benchmark 定义必须看清。
01 · TEXT BECOMES TOKENS

推理引擎真正调度的不是“句子”，而是一串 token IDs 和它们对应的运行时状态。

假设输入是“Artificial Intelligence (AI，人工智能) infra 很重要”。Tokenizer 会先把文本编码成模型词表中的 token IDs。具体 tokenizer 怎么切不是这节重点；系统层先抓住对象：

AIinfra很重要→[id₀][id₁][id₂][id₃]

IDs 经过 embedding 变成 hidden states，再穿过 Transformer。对生成任务而言，真正关键的是：这些 prompt tokens 和之后已经接受的 generated tokens，一起构成当前 confirmed prefix。

02 · THE TARGET MODEL PRODUCES LOGITS

模型不会直接“决定一句话”，而是对下一个 vocabulary token 给出一组 raw scores。

最后位置的 hidden state 经过 Language Model (LM，语言模型) head，得到 V 维 logits。为了建立第一层直觉，可以把 softmax 后的值看成候选 token 概率；真实 sampling path 还可能先应用 logit processors、temperature、top-k/top-p 等变换。

LAST POSITIONlogits ∈ R^V

词表有 V 个 token，就有 V 个 raw scores；系统只需要从这些候选里决定下一 token。

Greedy 取最大分数对应 token；sampling 则从处理后的分布采样。Transformer 主体负责产生 logits，decoding policy 负责“如何选”。这两层不要混在一起。

03 · THE AUTOREGRESSIVE STATE MACHINE

一个 token 被选中以后，它才成为下一步可以依赖的真实状态。

用概率语言写，就是第 t 个输出来自 p(y_t | x, y_1, …, y_{t-1})。未来的 y_{t+1} 要以已经确认的 y_t 为条件，所以 baseline target-model steps 之间有数据依赖。

AUTOREGRESSIVE GENERATION · DATAFLOWconfirmed prefix → logits → select → append → repeat
这里的“串行”指逻辑依赖，不等于 Graphics Processing Unit (GPU，图形处理器) 一次只能算一个 request。单个 request 的下一 token 要等自己的前一个 token 确认；serving engine 可以同时把许多 requests 的当前 step 组成 batch，这正是后面 Continuous Batching 的入口。
Speculative decoding 的精确 caveat：draft model 可以先猜多个候选，target model 一次验证多个位置，从而减少昂贵 target-model iterations；但最终被接受的 tokens 仍要保持 target model 所定义的 autoregressive distribution。不要把“逻辑依赖”误写成“生成 N 个 token 永远必须有 N 次完整大模型 forward”。
04 · TRAINING AND SERVING EXPOSE DIFFERENT BOTTLENECKS

同一个 Transformer，训练时的数据组织和在线生成时的运行时状态完全不同。

TRAINING已知 token batch → forward + backward更关注训练吞吐 / MFU；需要 activation、gradients、optimizer state；通过大 batch / sequence 构造大 General Matrix Multiply (GEMM，通用矩阵乘法)。
SERVING动态 requests → 状态持续增长普通生成没有 training backward/optimizer；更关注 latency、吞吐、KV Cache 容量、排队、scheduler 与请求生命周期。

所以“训练 kernel 很快”并不能自动推出 serving 很快。serving 还必须解决一个训练里弱很多的问题：请求在时间上不断到达、不断结束，而且每个请求当前可计算的 token 数不同。

05 · NAIVE GENERATION RECOMPUTES HISTORY

如果每生成一个 token 都从头重新算整个前缀，绝大多数历史 attention 投影都会重复。

假设 prompt 长 1000 tokens。第一步处理 prompt；得到 y₁ 后，如果第二步又把这 1001 个 token 全部从头走一遍 Transformer，旧 token 对应的每层 Key / Value 会被再次计算。第三步又重复一次。

step 1x₀x₁…x₉₉₉→ y₁———
step 2 naivex₀x₁…x₉₉₉y₁→ y₂——

Attention 给了一个关键不变量：历史 token 已经计算出的 K/V 在后续普通 decode 中仍然可复用。于是系统自然会问：为什么不把历史 K/V 留在 GPU memory 里？

这就是 KV Cache 的来源。但在 06.3 之前，下一课先把请求分成 Prefill 与 Decode，因为“第一次处理整个 prompt”和“之后推进一个新 token”在 shape、算术强度与 latency 目标上很不一样。

06 · USER EXPERIENCE HAS MULTIPLE CLOCKS

端到端 2 秒不能告诉你：用户是在等第一字，还是后面输出一卡一卡。

TTFTTime To First Token请求发出/进入测量范围到第一个输出 token 的时间。queue、Prefill、路由等都可能贡献；具体起点看 benchmark。
ITLInter-Token Latency相邻输出 token 到达之间的时间间隔，可以形成 p50 / p95 / p99 等分布，直接描述流式 cadence。
TPOTTime Per Output Token生成阶段平均每个输出 token 的时间。常见 benchmark 会单独报告 mean / median / percentiles；具体计算方式仍应看工具定义。

当前 vLLM serving benchmark 也把 TTFT、TPOT、ITL 分成三组统计，同时另外报告 request throughput、output-token throughput 和 end-to-end latency。这个区分很重要：latency 是用户侧体验，throughput 是系统整体产能，它们常常存在 trade-off。

当前 vLLM benchmark 源码：vllm/benchmarks/serve.py，BenchmarkMetrics 分别维护 TTFT / TPOT / ITL 的 mean、median、std 与 percentiles。
07 · THE NEW OBJECT IS REQUEST STATE

从这里开始，推理 Infra 不只优化模型，还要管理“活着的 requests”。

STATIC-ishmodel weights模型权重加载后通常长期驻留。
PER REQUESTconfirmed prefix + generated state每个 request 的长度和完成时间不同。
DYNAMIC MEMORYKV Cache随 request token 数持续增长，完成后释放。
SCHEDULERwhich tokens run next?每轮要在线选择哪些 requests / tokens 占 GPU。

所以后面的路线会自然变成：Autoregressive state → Prefill/Decode → KV Cache → Scheduler → Continuous Batching → Paged KV → KV Connector。

CHECKPOINT06.1

先确认你已经把“模型计算”和“request 状态演化”分开。

1. Target model 每一步真正输出的是什么？
输出的是 vocabulary logits（经过 decoding policy 处理后用于选择 token），不是直接输出整句文字。选中的 token ID 才会被追加进 confirmed prefix。
2. 为什么单个普通 request 的 y₂ 不能在 y₁ 尚未确认时按 baseline 精确计算？
因为 y₂ 的 target conditional distribution 是 p(y₂ | x, y₁)。y₁ 尚未确认，就缺少它所依赖的条件状态。Speculative decoding 可以猜并批量验证，但不会改变最终 target distribution 的这层条件关系。
3. 单 request 有串行依赖，为什么 GPU 仍然可以一次处理很多 decode tokens？
因为不同 requests 彼此独立。每个 request 当前只推进自己的下一 step，但 serving scheduler 可以把许多 requests 的“当前 token”合到同一个 GPU batch，这就是 Continuous Batching 的基础。
4. ITL 和 TPOT 为什么不能当成同一个名字？
ITL 是逐相邻 token 的实际时间间隔，天然是一组 samples；TPOT 是生成阶段聚合后的每输出 token 时间指标。它们相关，但统计对象和使用方式不同。
