LESSON 06.4 · PERFORMANCE约 55 min

推理性能：先估算，再测；先问“快在哪里”，再看一个吞吐数字。

到这里你已经知道自回归生成、Prefill / Decode 和键-值（KV）缓存。现在补上进入 vLLM 前最重要的一层工程能力：先用容量、计算量和图形处理器（GPU）显存带宽做数量级估算，再用一致的workload（工作负载：系统实际接收的一组 request 规模与分布特征）测TTFT、ITL、TPOT、throughput和tail latency。没有这一步，“优化了 30%”通常只是一个缺少上下文的数字。

这节课结束时，你应该能做到：
  • 区分“放得下”“算得动”“服务得快”三个不同问题。
  • 估算模型weights 与 per-request KV Cache 的数量级。
  • 用“数据量 ÷ 有效带宽”理解显存带宽给出的理想下界。
  • 知道为什么提高concurrency 和 batch size可能增加throughput，却同时恶化user latency。
  • 设计一个可比较的推理benchmark，而不是只记录一个孤立的吞吐数字。
  • 读到performance claim时，主动检查workload、分位数、cache state和SLO（服务级目标：系统希望达到的延迟、可用性或吞吐目标）。
01 · “更快”不是一个指标

同一个优化，可以让系统吞吐更高，也可以让某些用户等得更久。

TTFT首 Token 延迟从客户端发出请求，到收到第一个非空输出。长输入、排队和 Prefill 都会影响它。
ITLToken 间延迟streaming之间的时间间隔。它更接近用户看到文字连续出现时的“顺不顺”。
TPOT每输出 Token 时间按请求把第一个 token 之后的生成时间摊到剩余输出 token 上。

当前 vLLM 的 vllm bench serve 会同时报告请求throughput、输出 token throughput、总 token throughput，以及 TTFT、TPOT、ITL 的均值、中位数和高分位数。更重要的是，vLLM 文档明确提醒：不同工具对这些指标的命名和测量点并不完全统一，跨工具比较时要看公式和采样位置，不能只看缩写。

第一条规则：以后看到“性能提高 40%”，先问：提高的是throughput、TTFT、ITL，还是单位成本？其它指标有没有变差？

当前口径：vLLM · Benchmark CLI。本站按 2026-09 的文档复查本节的指标定义。
02 · 先算容量账

“模型权重能塞进显存”只说明第一关过了。

最粗的权重占用可以先按下面这条式子心算：

权重字节数 ≈ 参数量 × 每个参数的字节数

例如 70B 参数模型如果仅按 BF16 权重估算，每个参数约 2 bytes，仅权重就是约 140 GB。NVIDIA 当前 H200 的标称显存是 141 GB。这个数字看起来“刚好能装”，但真实服务还需要 KV Cache、临时张量、运行时工作区、内存碎片和框架本身的占用，所以“140 < 141”绝不等于“单卡 H200 可以舒服地服务这个 70B 模型”。

KV Cache 则要从模型结构和上下文长度估：

KV bytes ≈ 2 × layers × tokens × KV heads × head_dim × bytes/element

前面的 2 表示 K 和 V 两份状态。举一个只用于练心算的例子：32 层、8 个 KV heads、head_dim=128、32K tokens、每个元素 2 bytes，那么per-request KV Cache 大约就是 4 GiB。concurrent requests一多，动态 KV 占用很快就会和权重一样成为容量问题。

WEIGHTS模型的静态大块占用
KV CACHE随请求数与上下文长度增长
RUNTIME临时张量、工作区、碎片等不能忽略
硬件锚点：NVIDIA H200 当前规格页给出 141 GB GPU 显存与 4.8 TB/s 显存带宽。这里用它做数量级例子，不把理论规格当成实测服务性能。
03 · 再算“搬数据”的账

Decode 很慢，不一定是算力不够；也可能是在等权重和 KV 从显存里被读出来。

一个非常有用的理想下界是：

时间下界 ≳ 需要搬的数据量 ÷ 有效显存带宽

仍然拿上面的 140 GB 权重做极端简化：如果某一步真的需要把这 140 GB 权重完整读一遍，而硬件带宽按 H200 标称 4.8 TB/s 计算，光“搬完这些数据”的理论时间下界就约 29 ms。真实程序还会受到 kernel 效率、KV 访问、调度、通信以及没有跑满标称带宽等因素影响，因此实际值只会更复杂。

不要把 29 ms 当成 70B 模型的真实每-token 延迟。这是故意粗糙的 roofline 式数量级练习：它的用途是判断“带宽有没有可能成为主要瓶颈”，而不是替代 profiler 或 benchmark。

这也解释了为什么批次会改变 Decode 的效率。同一批里有更多 token 一起经过模型时，读取一次权重可以服务更多计算工作，单位 token 分摊到的权重读取成本会下降；但批次更大通常也意味着更多请求同时竞争资源，user latency未必一起变好。

04 · 计算量只是另一半

先判断“更像算力瓶颈还是带宽瓶颈”，再决定该优化哪里。

对普通 dense Transformer，可以把每个 token 的前向计算量先粗略记成和参数量同阶，常见心算会用 ≈ 2 × parameters FLOPs/token 来估线性层主导部分。它不是精确公式：长上下文 Attention、混合专家模型、量化、融合 kernel 和并行策略都会改变实际成本。

计算算力更紧大 Prefill、大矩阵乘更容易把计算单元吃满；这时更高的有效浮点计算能力很重要。
内存带宽更紧小批次 Decode 常更容易受权重/KV 读取影响；这时只看峰值浮点计算能力会误判。
COMMUNICATION多卡通信更紧张量并行等方案能分摊容量和计算，却会引入跨卡通信；“卡更多”不保证线性加速。

所以性能分析不是找一个万能公式，而是先建立几条数量级上界/下界，再用 profiler 和真实benchmark确认哪一项真的在主导。

05 · 跑benchmark前先写测试合同

两个结果只有在workload可比时，才有资格放进同一张表。

至少固定并记录下面这些条件：

MODEL模型、权重精度/量化方式、框架与版本
HARDWAREGPU 型号、数量、并行配置
INPUTinput-token length或真实输入分布
OUTPUToutput-token length或真实输出分布
LOADconcurrency、request arrival rate、benchmark duration
FEATURESPrefix Cache（前缀缓存：复用相同输入前缀已经计算好的 KV state）、Chunked Prefill、投机解码等开关

还要说明是否streaming、有没有预热、数据集是什么、采样参数是否一致。否则“系统 A 比系统 B 快 20%”很可能只是输入更短、并发更高或缓存命中了。

06 · 用当前 vLLM 的benchmark工具落地

vllm bench serve 测的是在线服务，不是一个孤立 kernel 的速度。

shell示意命令 · 参数按你的模型与数据集调整
vllm bench serve \
  --backend vllm \
  --model YOUR_MODEL \
  --dataset-name sharegpt \
  --dataset-path YOUR_DATASET.json \
  --num-prompts 100 \
  --save-result

当前 vLLM 会从benchmark客户端测量 TTFT，并分别统计 ITL 与 TPOT。标准逐 token 解码时两者通常接近；但投机解码可能在一次流式返回里带回多个 token，这时 ITL 记录“流式返回之间的间隔”，TPOT 则把解码时间按所有输出 token 摊开，因此两者不应该被强行当成同一个量。

一个很容易踩的坑：反复对同一个server instance跑同一组 prompt，可能命中前一次留下的 Prefix Cache，从而把throughput测得虚高。当前 vLLM 文档明确建议：如果你不想测缓存收益，就改变 seed、重置/重启server instance，或使用会在 sweep 间重置服务端缓存的工具。

当前实现与命令入口：vLLM Benchmark CLI 与 vLLM bench serve 接口文档。
07 · 不要只找“最高吞吐”

真正的部署问题通常是：在latency target不被破坏时，最多能服务多少流量？

LOW LOAD低延迟GPU 可能没吃满
USEFUL RANGE吞吐持续上升延迟仍在目标内
SATURATION排队增长p95 / p99 延迟恶化

因此更有意义的比较方式，是扫一组并发或request arrival rate，画出“throughput—延迟”曲线，再在同一个 SLO 下比较方案。NVIDIA 的推理 benchmark 指南也强调这种延迟–throughput trade-off，而不是只汇报单个峰值数字。

补充阅读：NVIDIA · 推理benchmark基础概念。这篇适合核对指标与测试口径，不作为本站当前 vLLM 实现细节的权威来源。
08 · 以后看到performance claim，按这张清单拆

“优化了 30%”至少要追问七件事。

① 提高的是请求throughput、token throughput，还是 TTFT / ITL？
② 输入和输出 token 分布是否相同？
③ concurrency或request arrival rate是否相同？
④ GPU、精度、并行度、框架版本是否相同？
⑤ 平均值之外，p95 / p99 有没有恶化？
⑥ Prefix Cache、Chunked Prefill、投机解码等功能是否改变？
⑦ 在同一个 SLO 下，哪一个方案能承载更多真实流量？

做到这里，你才真正具备进入 vLLM 的前置视角：07 模块不再只是“这个调度器有哪些功能”，而是去追问这些机制究竟在改容量、计算、带宽、调度还是tail latency。

CHECKPOINT06.4

能把“估算”和“实测”分开，才进入 vLLM。

1. 70B BF16 权重约 140 GB，而 GPU 标称显存 141 GB，为什么不能直接说“能单卡部署”？
因为服务还需要 KV Cache、临时张量、运行时工作区与内存碎片等；权重刚好放得下只通过了容量账的第一关。
2. 为什么“throughput提高”不能自动推出“用户体验更好”？
更高并发和更大批次常能提高设备利用率与总吞吐，但也可能增加排队和每个请求等待时间，所以必须同时看 TTFT、ITL 和tail latency。
3. 为什么重复跑同一套 prompt 可能让benchmark失真？
如果服务端保留了 Prefix Cache，同样的前缀可能直接复用历史 KV，测到的是“带缓存复用”的性能，而不是原本想比较的冷启动workload。
4. 比较两个推理方案时，最少要把哪些条件固定？
模型与精度、硬件与并行配置、输入/输出长度分布、并发或请求速率、关键缓存/调度功能、流式与采样设置，以及相同的benchmark duration/预热口径。
