LESSON 06.3 · INFERENCE约 60 min

KV Cache：到底缓存了什么，为什么它会成为推理显存的大头？

02.1 学 Attention 时，我们已经知道每层会从 hidden states 投影出 Q、K、V。自回归 Decode 里，历史 token 的 K/V 可以复用，所以系统把它们留在 Graphics Processing Unit (GPU，图形处理器) memory 中。这个看似简单的优化，最后会变成 vLLM 最核心的内存管理对象，也是 Key-Value (KV，键-值) Connector 真正要搬运的数据。

这节课结束时，你应该能做到：
  • 解释为什么缓存 K/V，而不是缓存历史 Q。
  • 从 layers × tokens × KV heads × head_dim × 2 推导 KV Cache 大小。
  • 理解 Grouped-Query Attention (GQA，分组查询注意力)/Multi-Query Attention (MQA，多查询注意力) 为什么能显著减少 KV memory。
  • 知道每个 request 的 KV Cache 会随 prompt + generated tokens 线性增长。
  • 理解请求结束、抢占、prefix reuse 时 KV blocks 的生命周期问题。
  • 看出“动态 KV 内存”为什么会自然引出 vLLM 的 block/page 管理。
01 · WHY CACHE K AND V?

新 token 只需要新的 Q；历史 K/V 会在未来每一步继续被读取。

Decode 第 t 步时，这一层只为新增 token 计算新的 Q、K、V。下面先不背接口和类名，只看数据流：哪些向量只服务当前 step，哪些状态会跨 step 留下来？

ONE TOKEN · ONE ATTENTION LAYERarchitecture-first mental model
一句话：Query 是当前 token 的“问题”；Key / Value 是未来 token 仍然要查询的历史状态，所以 KV 才值得缓存。

这张图只放大一个 Attention layer。真实 Transformer 的每个 Attention layer 都有自己的一份历史 K/V；到了后面的 vLLM，我们会进一步把这些逻辑位置映射到 paged KV blocks。

02 · THERE IS A CACHE FOR EVERY ATTENTION LAYER

KV Cache 不是模型外面的一张表，而是每层 Attention 都有自己的历史 K/V。

假设 32 层 Transformer。Prompt 的 token 0 在 layer 1 产生一份 K/V，在 layer 2 又产生另一份 K/V……一路到 layer 32。Decode 时，每一层都需要自己的历史。

ONE REQUEST · MANY LAYERS
L1 K/VL2 K/VL3 K/VL4 K/V…L31L32

所以 KV memory 同时和 layer 数、缓存 token 数、KV head 宽度、dtype 成正比。

03 · THE KV MEMORY FORMULA

先用一个不考虑 padding/metadata 的理论公式。

ONE REQUEST · FULL MODEL · IDEALIZEDKV bytes = 2 × L × T × Nkv × Dhead × bytes_per_element

其中 2 是 K 和 V 两份；L 是 attention layers；T 是这个 request 已缓存的 tokens；Nkv 是 KV heads 数；Dhead 是每个 head 的维度。

例如 L=32、T=4096、Nkv=8、Dhead=128、Brain Floating Point 16 (BF16，BF16 16 位浮点)=2 bytes：

memory mathtoy GQA model
2 × 32 × 4096 × 8 × 128 × 2 bytes
= 536,870,912 bytes
= 512 MiB

也就是说，仅一个 4K-token request 就可能占约 512 MiB KV Cache。100 个同规模活跃请求的理论 KV 需求已经非常大——这就是 serving 系统必须认真管理 KV memory 的原因。

真实实现还要考虑 Tensor Parallel (TP，张量并行) 分片、block size、alignment、metadata、不同 attention 架构/precision 等。公式的价值是让你知道每个变量怎么影响量级。

04 · GQA CHANGES THE MEMORY LINEARLY

KV heads 从 32 降到 8，理论 KV Cache 就直接降到四分之一。

Multi-Head Attention (MHA，多头注意力) EXAMPLENq=32 · Nkv=32每个 query head 有自己的 K/V head，KV 宽。
GQA EXAMPLENq=32 · Nkv=84 个 query heads 共享一个 KV head，KV bytes ≈ MHA 的 1/4。

这就是为什么前面一直强调 GQA 不是一个孤立的模型架构名词：它同时影响训练 Context Parallel (CP，上下文并行) 通信、推理 KV capacity，以及以后 KV Connector 的网络 transfer bytes。

05 · KV GROWS WITH THE CONFIRMED CONTEXT

请求越长，缓存越长；Prompt 和生成 token 都会占 KV。

REQUEST LIFETIME
P0P1P2P3…G0G1G2G3

Prefill 阶段会逐步建立 prompt 的 KV；一次逻辑 Prefill 可以被 scheduler 拆成多个 execution chunks，而不是必须一次 GPU iteration 吃完整个 prompt。随后在 baseline 自回归 decode 中，每个 request 每轮通常再 append 一个新位置的 K/V；speculative decoding 等机制则可能让一次 target-model step 最终接受多个 token。

因此，一个 request 的 KV 使用量仍然主要由已经建立缓存的上下文 token 数决定，通常可用 prompt_tokens + accepted_generated_tokens 建立近似线性增长的直觉。在线服务同一时刻有多少请求、每个请求已经走到多长、谁结束释放、谁刚来建立 prompt KV，都会让显存需求持续变化。

06 · MODEL WEIGHTS ARE STATIC; KV CAPACITY IS A SERVING RESOURCE

权重加载后相对固定，剩余显存决定“同时能养多少上下文”。

WEIGHTSmostly static模型加载后常驻 GPU，大小主要由参数量、dtype、TP 决定。
KV CACHEdynamic capacity被所有活跃 requests 竞争，随 token 数动态分配/释放。
WORKSPACEruntime headroomkernel、temporary buffers、CUDA graphs 等仍需留空间。

这就是 vLLM 启动时为什么必须考虑“多少显存留给 model，多少可以成为 KV cache blocks”。KV capacity 直接影响可并发 sequences / tokens。

07 · WHY CONTIGUOUS PER-REQUEST BUFFERS ARE AWKWARD

如果每个请求一开始就预留“最大可能长度”的连续 KV，浪费会非常严重。

请求 A 可能 prompt 100 tokens 只生成 20；请求 B 可能跑到 8K；请求 C 中途取消。若为每个 request 预分一大段连续显存，要么过度预留，要么长度增长时需要搬家/重新申请，还容易产生碎片。

REQUEST Ausedusedreservedreservedreservedreservedreservedreserved
REQUEST Busedusedusedusedusedgrow?grow?grow?

于是会自然想到操作系统虚拟内存的思路：逻辑上一个 sequence 连续增长，物理 GPU memory 不要求它连续。把 KV 切成固定大小 blocks/pages，按需分配。

08 · KV BLOCKS HAVE A LIFECYCLE

真正的 serving engine 要管理的不只是“申请”和“释放”。

ALLOCATEPrefill / append新 tokens 需要新 KV slots。
HOLDrunning requestDecode 每步持续读取历史。
REUSE / SHAREprefix cache相同前缀可能复用已经计算的 KV。
FREE / EVICTfinish / pressure请求结束或缓存策略淘汰后归还 blocks。

当显存不够时，scheduler 甚至可能需要暂停/抢占某些 sequences，或者在不同策略中选择是否重算/交换缓存。到这里，“KV Cache Manager”这个名字已经不再抽象。

09 · THE ROAD TO VLLM

下一模块的四个关键词，现在都有了问题来源。

SCHEDULER哪些 requests 下一轮能占用 GPU 和 KV capacity？
CONTINUOUS BATCHING有人结束后，怎样立刻把新 request 塞进执行批次？
KV CACHE MANAGER逻辑 token positions 怎样映射到物理 KV blocks？
PAGED ATTENTIONAttention kernel 怎样读取不连续的物理 KV blocks，同时表现得像连续 sequence？
CHECKPOINT06.3

能算账，才算真的理解 KV Cache。

1. 为什么历史 K/V 要缓存，而历史 Q 不需要？
未来 decode step 的新 query 需要和所有历史 K 比较并读取对应 V；旧 query 已完成它当时的 attention，不会作为未来 token 的 key/value context 被再次使用。
2. 如果 Nkv 减半，其它变量不变，理论 KV memory 怎么变？
线性减半。KV bytes 公式对 Nkv 是一次方，所以 GQA/MQA 减少 KV heads 会直接降低缓存大小。
3. 为什么固定-size blocks 比每请求一段最大连续 buffer 更适合动态 serving？
不同请求长度和生命周期高度动态。blocks 可以按需逐步分配、释放和复用，避免为短请求过度预留，也不要求一个长 sequence 的物理 KV 地址连续。
