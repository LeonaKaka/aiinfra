LESSON 07.5 · VLLM约 70 min

Prefix Cache 与 Preemption：KV block 不只会“分配和释放”，还会被复用、共享、缓存和淘汰。

到 07.4 为止，我们已经能解释一个 request 怎样申请 blocks、怎样用 block table 做 attention。但 serving 还有两个非常现实的问题：多个请求可能共享相同前缀；KV 池又不可能无限大。于是 block 需要 identity、hash、reference count、free/eviction order，scheduler 也需要在资源压力下 preempt 请求。这里补齐 vLLM 本地 KV 生命周期，下一模块再把问题扩展到“KV 在另一台机器上”。

这节课结束时，你应该能做到：
  • 解释 prefix caching 为什么能省 prefill compute，而不是“凭空减少模型权重”。
  • 理解 full/cached blocks 为什么需要 hash，shared blocks 为什么需要 ref count。
  • 知道 cached block 可以不属于任何 running request，却仍然留在 free/evictable cache 中等待复用。
  • 理解 eviction 与 preemption 的区别：一个回收 cache block，一个改变 request 的运行状态/进度安排。
  • 知道当前 V1 RequestStatus 已经包含 WAITING_FOR_REMOTE_KVS，说明 remote KV 已经进入 scheduler 状态机。
  • 从“本机 block table”自然推导出 KV Connector 的问题。
01 · WHY PREFIX CACHE EXISTS

两个请求前 1000 个 tokens 一模一样，第二个请求没必要再算一遍相同 Prefill。

例如很多用户都以同一段 system prompt 开头，或者同一个长文档被重复问不同问题。若某段完整 prefix 的 KV 已经存在，后续请求可以直接把这些 token 视作“already computed”，只计算未命中的 suffix。

REQUEST Asystem prompt + question A第一次计算，完整 prefix blocks 被缓存。
REQUEST Bsame system prompt + question B相同 prefix 命中，直接复用 KV blocks，只算后面的不同部分。
REQUEST Cdifferent prefixhash 不同，不能误复用；需要正常 prefill。

因此 prefix cache 的收益主要是减少重复 Prefill compute 和 TTFT；它并不让同一份 KV 数据完全“零占显存”。共享 block 仍然是物理 KV memory，只是多个请求可以引用同一份。

03 · REFERENCE COUNT

一块 prefix KV 可能同时被多个 running requests 引用，所以不能谁结束就立刻覆盖。

#42
ref=3#17
A only#21
B only#9
free#12
free#31
cached#7
C only#5
free

如果 A、B、C 都共享 block #42，A 完成只能让 ref count 减 1；只有没有活跃引用时，这个 block 才可能进入可回收/可淘汰状态。ref_cnt 就是把“物理 block 的生命周期”从某个单独 request 解耦出来。

04 · FREE DOES NOT ALWAYS MEAN EMPTY

一个 block 可以不再被 running request 使用，但仍保留有效 cached KV，等待下一次 prefix hit。

这是很容易混淆的一点。BlockPool 的 free queue 既承担“可被分配”的资源池，也涉及 cached blocks 的 eviction ordering。一个 cached block 可以暂时没有活跃引用，但内容仍有复用价值；直到容量压力要求真正覆盖它。

ACTIVEref_cnt > 0正在被 request 使用，不能随便重用。
CACHED / EVICTABLEref_cnt = 0 + valid hash可命中 prefix，也可能在需要空间时被 eviction。
REUSEDold hash invalidated真正拿去存新 KV 时，旧 cache identity 必须被清理。
05 · EVICTION

KV pool 满了时，系统首先要问：有没有不再被引用、但只是“为了缓存”留着的 block 可以覆盖？

当前 free-block queue 的源码注释描述了 eviction order：前部是更适合先被回收的 block，包含 LRU 语义和同一 sequence 下的额外排序考虑。你不需要背实现细节，但要理解 cache 的基本 trade-off：

KEEP CACHE未来 prefix hit 更快保留更多历史 KV，可以减少未来重复 prefill，但会占用本来可服务新 token 的 KV capacity。
EVICT CACHE立即腾出 block新请求获得空间，但未来若再次出现同 prefix，需要重新 prefill。
06 · PREEMPTION IS A REQUEST-LEVEL DECISION

如果光淘汰无引用 cache 还不够，scheduler 可能必须让正在运行的 request 暂时退出。

Preemption 和 eviction 不在同一个层级。Eviction 是“这个 cached physical block 还值不值得保留”；preemption 是“这个 request 现在还能不能继续占资源运行”。当前 scheduler 在 block allocation 失败时存在明确的 preempt path。

RUNNINGreq A已有 KV blocks，准备继续。
PRESSUREno new block本轮无法满足增长。
PREEMPTrelease / reschedule请求被移出当前 running 路径。
WAITPREEMPTED稍后重新获得机会。
RESUMErecompute/load as needed恢复成本取决于当前系统路径。

Serving 质量不只看“有没有 OOM”。如果系统频繁 preempt，GPU 可能反复重算，ITL/TTFT tail 也会恶化。所以 KV capacity 和 scheduler policy 必须一起评估。

07 · REQUEST STATUS IS BECOMING A DISTRIBUTED STATE MACHINE

现在看当前 V1 的 RequestStatus，已经能提前看到 KV Connector。

LOCALWAITING → RUNNING → finished
RESOURCE PRESSUREPREEMPTED
REMOTE KVWAITING_FOR_REMOTE_KVS
OTHER MODESstructured output / streaming 等还有自己的等待状态。

这很关键：一旦 KV 可以来自外部节点，scheduler 不能只问“本地有没有 block”。它还要知道远端命中了多少 tokens、数据是否已到、什么时候才能把 request 放进 runnable batch。

当前状态枚举可见 vllm/v1/request.py。其中明确包含 WAITING_FOR_REMOTE_KVS 与 PREEMPTED。
08 · THE LIMIT OF LOCAL PAGING

到这里，本机 KV 管理已经完整；但 P/D 分离会把“物理 block 在哪”扩展到另一台机器。

PREFILL NODEGPU APrompt 已算完，KV 存在 A 的 physical blocks。
KV must move →
metadata must agree →
DECODE NODEGPU B要继续生成，B 必须得到等价 KV，并在自己的 block layout 中可寻址。

注意这已经不是简单 torch.copy 问题：你要决定哪些 tokens 命中、传哪些 layers/blocks、什么时候发起、怎样知道完成、scheduler 在等待期间是什么状态、接收端 block IDs 怎么对应本地 KV layout。

这就是 08 · KV Connector 的起点：把我们在本机学会的“KV 生命周期 + block metadata + scheduler state”跨进程、跨 GPU、跨节点延伸。

CHECKPOINT07.5

完成这一关，你已经具备读 KV Connector 的地基。

1. Prefix cache 命中主要省的是什么？
主要省重复的 prefill compute：相同 prefix 已经有有效 KV，就可以把这些 tokens 当作已计算。共享 KV block 本身仍占物理 KV memory。
2. Eviction 和 preemption 为什么不是一回事？
Eviction 是 block/cache 层的资源回收，常针对没有活跃引用的 cached blocks；preemption 是 request 层的调度决定，会改变正在运行请求的状态和后续恢复/重算。
3. 为什么出现 WAITING_FOR_REMOTE_KVS 后，scheduler 已经不再是纯本机问题？
因为 request 是否可运行还取决于外部 KV 是否存在、是否开始传输、是否完成。远端数据传输状态已经进入 request 的调度状态机。
