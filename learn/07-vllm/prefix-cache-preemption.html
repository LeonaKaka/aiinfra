LESSON 07.5 · VLLM约 75 min

前缀缓存与抢占：KV 块不只会“分配和释放”，还会被复用、共享、缓存和淘汰。

到 07.4 为止，我们已经能解释一个请求怎样申请键-值（KV）块、怎样用块表做 Attention。但在线推理还有两个非常现实的问题：多个请求可能共享相同前缀；KV 池又不可能无限大。于是块需要标识、哈希、引用计数、空闲/淘汰顺序，调度器也需要在资源压力下抢占请求。这里补齐 vLLM 本地 KV 生命周期，下一模块再把问题扩展到“KV 在另一台机器上”。

这节课结束时，你应该能做到：
  • 解释前缀缓存为什么能减少 Prefill 计算，而不是“凭空减少模型权重”。
  • 理解自动前缀缓存（APC）如何用哈希标识识别可复用前缀，并知道普通全注意力的完整哈希块心智模型在当前 hybrid/Mamba 路径存在细粒度部分命中例外。
  • 知道缓存块可以暂时不属于任何运行中的请求，却仍留在可淘汰的空闲缓存中等待复用。
  • 理解淘汰与抢占的区别：前者决定某个缓存标识何时失效，后者改变请求的运行状态或进度安排。
  • 知道当前 V1 默认抢占恢复方式是 RECOMPUTE，而不是 SWAP。
  • 知道当前 V1 RequestStatus 已包含 WAITING_FOR_REMOTE_KVS，说明远端 KV 已进入调度器状态机。
01 · WHY PREFIX CACHE EXISTS

两个请求前 1000 个 tokens 一模一样，第二个请求没必要再算一遍相同 Prefill。

例如很多用户都以同一段 system prompt 开头，或者同一个长文档被重复问不同问题。若某段可缓存 prefix 的 KV 已经存在，后续请求可以直接把这些 token 视作“already computed”，只计算未命中的 suffix。

先把这一课最容易混淆的三种生命周期放到同一张图里：prefix 标识 决定能不能复用，物理块归属关系 决定现在谁还在引用，请求调度 决定资源不够时是否需要 preempt。

VLLM V1 · LOCAL KV LIFETIMEprefix cache ≠ 淘汰 ≠ 请求抢占
一张图记住三个层级：cache hit 回答“这份 KV 能不能复用”；引用计数 / free 队列回答“这个物理块现在能不能被重新分配”；抢占回答“如果可回收块仍不够，哪个运行中的请求必须退出当前调度”。
请求 Asystem prompt + question A第一次计算，可缓存 prefix 块被登记。
请求 Bsame system prompt + question B相同 prefix 命中，复用 KV 块，只算后面的不同部分。
请求 Cdifferent prefix哈希不同，不能误复用；需要正常 prefill。

因此 prefix cache 的收益主要是减少重复 Prefill 计算和首 Token 延迟（TTFT）；它并不让同一份 KV 数据“零占显存”。共享块仍然是物理 KV 内存，只是多个请求可以引用同一份。

对普通全注意力 APC，先用“命中完整哈希块”建立基础心智模型仍然最稳：块哈希会包含 parent 哈希、当前块 tokens，以及低秩适配（LoRA） / multimodal / cache salt 等必要额外信息。但这已经不能写成全局实现不变量。当前 V1 的 HybridKVCacheCoordinator 在全注意力 + Mamba align 等满足条件的混合缓存中，可以启用 enable_partial_hash_hits，让 cache-hit alignment 下放到更细的 hash_block_size；调度器还会为 Mamba partial tail 增加对齐 stop。也就是说，“必须命中完整物理分配块”现在是过度简化。当前 KVCacheBlock 记录 group-aware 哈希和 _block_hash_num_tokens，进一步说明哈希 granularity、物理分配块、调度器块与 hybrid 缓存组不应被当成永远一一等同。

先学稳定语义，不要绑死内部尺寸。“相同 prefix → 可验证哈希标识 → 找到可复用 KV”是核心；普通全注意力 APC 常以完整哈希块理解，而当前 hybrid/Mamba 的 fine-grained partial hit 是明确例外。物理 KV 块 size、哈希块 size、调度器块 size 与 attention 内核块 size 在当前 V1 可能属于不同层级。

设计说明：Automatic Prefix Caching；当前块元数据见 kv_cache_utils.py；hybrid/Mamba fine-grained hit 的当前协调逻辑见 kv_cache_coordinator.py 与 partial prefix-cache tests。
03 · REFERENCE COUNT

一块 prefix KV 可能同时被多个运行中的请求引用，所以不能谁结束就立刻覆盖。

#42

B only#9

free#31

C only#5
free

如果 A、B、C 都共享块 #42，A 完成只能让引用计数减 1；只有没有活跃引用时，这个块才可能进入可回收/可淘汰状态。ref_cnt 就是把“物理块的生命周期”从某个单独请求解耦出来。

04 · FREE DOES NOT ALWAYS MEAN EMPTY

一个块可以不再被运行中的请求使用，但仍保留有效 cached KV，等待下一次 prefix hit。

这是很容易混淆的一点。当前 BlockPool 的注释直接说明：缓存块既可能被运行中的请求使用，也可能已经位于 free_block_queue、等待未来命中或淘汰。也就是说，free 队列是“可以重新分配”的资源顺序，不等于“里面的数据已经被擦掉”。

ACTIVEref_cnt > 0正在被请求使用，不能随便重用。
CACHED / EVICTABLEref_cnt = 0 + valid 哈希可命中 prefix，也可能在需要空间时被淘汰。
REUSEDold 哈希 invalidated真正拿去存新 KV 时，旧 cache 标识必须被清理。
05 · EVICTION

KV pool 满了时，系统首先要问：有没有不再被引用、但只是“为了缓存”留着的块可以覆盖？

当前 free-块队列明确维护淘汰 order：最少最近使用的块在队头；同一次序下，哈希覆盖更多 tokens、位于块 chain 尾部的块更靠前被淘汰。你不需要背双向链表实现，但要理解 cache 的基本 trade-off：

KEEP CACHE未来 prefix hit 更快保留更多历史 KV，可以减少未来重复 prefill，但会占用本来可服务新 token 的 KV 容量。
EVICT CACHE立即腾出块新请求获得空间；旧块哈希被移除，未来若再次出现同 prefix，需要重新 prefill。
06 · 抢占 IS A 请求级 DECISION

如果可复用/可淘汰块仍不够，调度器才可能让正在运行的请求暂时退出。

抢占和淘汰不在同一个层级。Eviction 是“这个无活跃引用的 cached 物理块还值不值得保留”；抢占是“这个运行中的请求现在还能不能继续占资源运行”。当前调度器在 allocate_slots() 无法满足运行中的请求时有明确的 victim-selection / preempt path。

RUNNINGreq A已有 KV 块，准备继续。
PRESSUREno new 块本轮无法满足增长。
PREEMPTfree / reschedule请求被移出当前 running 路径。
WAITPREEMPTED稍后重新获得机会。
RESUME · V1 DEFAULTRECOMPUTE重新计算必要 KV 状态。

当前 vLLM V1 的优化文档明确写明默认抢占 mode 是 RECOMPUTE，而不是 SWAP，因为 V1 中 recomputation 的开销更合适。Serving 质量因此不能只看“有没有内存不足/显存不足（OOM）”：频繁 preempt 会反复消耗 Prefill/forward 算力，并恶化延迟 tail。

当前行为说明：Optimization and Tuning · 抢占；具体 victim/preempt 路径见 调度器.py。

08 · THE LIMIT OF LOCAL PAGING

到这里，本机 KV 管理已经完整；但 P/D 分离会把“物理块在哪”扩展到另一台机器。

DECODE NODEGPU B要继续生成，B 必须得到等价 KV，并在自己的块布局中可寻址。

注意这已经不是简单 torch.copy 问题：你要决定哪些 tokens 命中、传哪些 layers/块、什么时候发起、怎样知道完成、调度器在等待期间是什么状态、接收端块 IDs 怎么对应本地 KV 布局。

这就是 08 · KV Connector 的起点：把我们在本机学会的“KV 生命周期 + 块元数据 + 调度器 state”跨进程、跨 GPU、跨节点延伸。

CHECKPOINT07.5

完成这一关，你已经具备读 KV Connector 的地基。

1. Prefix cache 命中主要省的是什么？
主要省重复的 prefill 计算：相同 prefix 已经有有效 KV，就可以把这些 tokens 当作已计算。共享 KV 块本身仍占物理 KV 内存。
2. 当前 V1 抢占默认怎样恢复，而淘汰又是什么？
抢占是请求级调度决定，当前 V1 默认通过 RECOMPUTE 恢复被释放的 KV；淘汰是块/cache 层回收无活跃引用的缓存块。两者不是同一层级。
3. 为什么出现 WAITING_FOR_REMOTE_KVS 后，调度器已经不再是纯本机问题？
因为请求是否可运行还取决于外部 KV 是否存在、是否开始传输、是否完成。远端数据传输状态已经进入请求的调度状态机。
