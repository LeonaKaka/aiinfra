LESSON 07.3 · VLLM约 75 min

KV Cache Manager：逻辑上连续的 sequence，为什么物理显存可以散着放？

06.3 已经推导过：每个活跃 request 都有不断增长的 KV Cache。真正困难的是在线服务里请求长度未知、到达时间不同、结束时间不同。如果给每个 request 预留一整段最大连续显存，会浪费大量空间。vLLM 的关键思路是把 KV memory 管成一池固定粒度的 blocks，让逻辑 token 序列和物理地址解耦。

这节课结束时，你应该能做到：
  • 区分 logical token positions、logical block chain 与 physical KV block IDs。
  • 理解固定-size block 为什么比“每请求一大段连续 buffer”更适合动态 serving。
  • 知道 KVCacheManager 与 BlockPool 的职责差异。
  • 理解 KVCacheBlock 里 block ID、ref count、hash 等元数据为什么存在。
  • 解释一个 request append 新 token 时，什么时候需要申请新 block。
  • 知道当前 V1 已支持更复杂的 KV cache groups / hybrid cache，因此“每层永远同一种 block”只是入门模型。
01 · THE CONTIGUOUS BUFFER PROBLEM

在线请求的最终长度未知，所以“先给它一整段最大显存”很浪费。

假设最大上下文 8192 tokens。Request A 最后只用了 300 tokens，B 用了 4000，C 用了 7900。如果每个请求一开始都预留 8192-token 连续 KV 空间，A 的绝大部分 reservation 永远不会被使用。

NAIVE PER-REQUEST RESERVATION
A usedA wastedA wastedA wastedB usedB usedB reserveC reserve

而且请求长度继续增长时，如果它原来的连续区域不够，可能需要重新申请更大的区域、搬迁，或面对碎片问题。固定-size blocks 把这个问题改写成“需要时再拿下一块”。

02 · PHYSICAL BLOCK POOL

把 GPU 上可用于 KV 的内存切成很多编号 blocks。

PHYSICAL KV BLOCK POOL
#0 · A#1 · C#2 · prefix#3 · B#4 · free#5 · A#6 · free#7 · prefix

逻辑上 A 的 tokens 是连续的，但它的物理 blocks 可以是 #0 → #5 → #12 → ...。只要执行 attention 时有一张表告诉 kernel “这个 sequence 的第 0、1、2 个逻辑块分别在哪里”，物理地址就不必连续。

03 · LOGICAL CHAIN VS PHYSICAL IDS

Sequence 看见连续 token；执行层拿到的是 block table 与 physical block pool。

把 request、KVCacheManager、BlockPool、block table 和执行侧放在一张图里看，核心就是地址翻译：逻辑顺序由 logical block order 保证，物理位置由 block table 指向。

REQUEST → MANAGER → BLOCK TABLE → PHYSICAL KVblock size = 16 tokens
一句话：sequence 的连续性由 logical block order 保证；显存位置由 block table 翻译，所以 physical KV blocks 可以散着放。

假设 block size=16 tokens。A 已经有 60 个已计算 tokens 的 KV：它会占 4 个逻辑 blocks，其中最后一个只用了 12/16 个 token slots。A 再生成 4 个 token，可以继续写最后一块；再多 1 个 token，就需要申请新的 physical block。这里说的是 request 自己的 KV allocation，不代表这 60 个 tokens 都已经成为可复用的 prefix-cache entry；当前 vLLM 的常规 prefix caching 以完整 block 为基本缓存单位。

BEFORE60 tokensceil(60 / 16) = 4 blocks，最后一块还有 4 个 slots。
→ +5 tokens →
AFTER65 tokensceil(65 / 16) = 5 blocks，需要再申请一块。
04 · KVCACHEMANAGER VS BLOCKPOOL

一个面向 request 语义，一个面向 physical blocks。

KV CACHE MANAGER“这个 request 需要什么？”根据 request 已计算 tokens、prefix cache 命中、要新增的 tokens 等，组织每个 KV cache group 的 blocks，向 scheduler 提供 allocation/computed-block 结果。
BLOCK POOL“哪些 physical blocks 现在可拿？”维护实际 KVCacheBlock、free block queue、hash→block lookup、ref count 与 eviction 相关状态。

当前源码里 KVCacheManager 会借助 coordinator 和 block pool 等内部组件。不要把类关系死背成永远不变；先记住 request-level allocation policy 和 physical block resource pool 这两个层级。

05 · WHAT A KVCACHEBLOCK KNOWS

一个 block 不只是整数 ID，它还要知道自己能不能被复用、有没有人在用。

IDENTITYblock_id0 .. num_gpu_blocks-1物理 block 的稳定编号，后面 block table 就靠它指向 KV memory。
LIFETIMEref_cntreference count有多少活跃引用正在使用它；共享 prefix 时尤其重要。
PREFIX CACHEblock_hashavailable when cached完整/可缓存 block 可以带 hash，使相同 prefix 查找到已有 block。
FREE QUEUEprev / nextdoubly linked free list当前实现用自维护双向链表组织 free blocks，支持高效删除与 eviction ordering。
当前 KVCacheBlock 定义可见 vllm/v1/core/kv_cache_utils.py。源码明确包含 block_id、ref_cnt、block hash 与 free-list links。
06 · ALLOCATING SLOTS FOR NEW TOKENS

Scheduler 想推进 tokens，KV manager 要先把“逻辑增长”翻译成“需要几个新 blocks”。

1known progressrequest 已 computed N tokens。
2schedule M more本轮打算再推进 M tokens。
3reuse tail最后一个 block 有空 slot 就先继续写。
4allocate不够时从 pool 取新的 physical blocks。
5emit block IDsSchedulerOutput 把相关 block state 交给 worker。

这一步是 scheduler 和 GPU execution 的重要契约：ModelRunner 不应该自己猜“这个请求的 KV 放哪”。它拿到已经决定好的 block IDs，再把它们写入设备侧 block table / slot mapping。

07 · PAGING DOES NOT MEAN ZERO WASTE

固定 blocks 会显著减少“大段预留”和外部碎片，但最后一块仍可能没填满。

如果 block size=16，一个最终长度 33-token 的 request 要占 3 blocks，最后一块只用 1 个 token slot。这是典型内部碎片。

33 tokens→3 × 16 slots = 48 slots→15 slots unused in tail

Block 越小，尾部浪费通常越低，但 metadata / table 长度和管理开销会增加；block 越大，管理更简单，但 tail waste 可能增大。实际系统还要适配 attention backend 的 block-size 约束。

08 · CURRENT V1 IS MORE GENERAL THAN THE TOY MODEL

现代 vLLM 不只处理“所有层统一一种标准 Attention KV”。

当前 V1 代码里有 KVCacheConfig、多个 KV cache groups、HybridKVCacheCoordinator 等抽象，也要处理 sliding-window attention、Mamba state、cross attention 等不同 cache specs。因此源码中你会看到“group”“coordinator”“spec”比早期 PagedAttention 教程复杂很多。

学习顺序不要被复杂度反过来劫持。

先用“固定 block → block pool → request block chain → block table”理解标准 decoder attention；等这条线稳定，再理解不同 cache groups 为什么需要 coordinator。

CHECKPOINT07.3

把 sequence 和 physical memory 分开想。

1. 为什么一个 request 的逻辑 KV sequence 可以连续，但 physical blocks 不连续？
因为系统维护 block IDs / block table，把逻辑块索引映射到任意 physical KV blocks。Attention backend 按映射读取，所以物理地址不必连续。
2. KVCacheManager 和 BlockPool 的职责有什么差别？
KVCacheManager 更面向 request：计算命中/需要多少 blocks、组织 allocation；BlockPool 更面向物理资源：哪些 block 空闲、谁被引用、hash 对应谁、谁可以被回收。
3. Paging 是否完全没有内存浪费？
不是。它显著减少为最大长度预留和外部碎片，但 request 的最后一个 block 可能未填满，形成内部碎片；block size 本身就是 trade-off。
