LESSON 07.4 · VLLM约 75 min

ModelRunner 与 Paged Attention：scheduler 给出的 block IDs，最后怎样变成 GPU attention？

上一课停在控制层：Request A 的逻辑 blocks 被映射到 physical IDs，例如 [8, 2, 19, 5]。但 GPU attention kernel 不会自己去问 Python 的 KVCacheManager。执行层必须把这些信息整理成设备侧的 block table、slot mapping、input tensors 和 attention metadata。这个转换过程正是读 GPUModelRunner 的关键入口。

这节课结束时，你应该能做到：
  • 理解 SchedulerOutput 到 GPU execution 之间还需要一次“元数据压缩/搬运”。
  • 知道 GPUInputBatch、BlockTable、slot mapping 各自在标准 Attention KV 路径里解决什么。
  • 解释 paged KV attention 如何让 attention 读取不连续 physical KV blocks。
  • 知道“PagedAttention”是核心思想，但当前 vLLM 会根据平台/模型选择不同 attention backends，不能把系统等同于一个固定 kernel。
  • 理解新 token 的 K/V 怎样写入分配好的 slot，Q 又怎样按 block table 读取历史 KV。
  • 知道 Mamba/GDN 一类 recurrent-state cache group 并不一定使用 token-to-KV slot mapping。
  • 知道当前上游同时存在 V1/V2 GPU ModelRunner 路径，先从 gpu_worker.py 看本配置实际选择哪一个。
01 · THE EXECUTION CONTRACT

SchedulerOutput 是逻辑计划，ModelRunner 要把它翻译成设备可以直接消费的结构。

Scheduler 视角req A 本轮 1 token，req B 本轮 1 token，req C 继续 prefill 128 tokens；各自对应哪些 KV blocks。
GPU 视角一批 token IDs / positions / request indices、连续 input buffers、block table tensor、slot mapping、attention metadata。

这个转换不能每层都临时用 Python list 做一遍，否则 CPU overhead 和 CPU→GPU metadata copy 会变成新的瓶颈。因此 vLLM 会维护长期复用的 batch buffers 与 block-table buffers。

02 · GPUINPUTBATCH

动态 requests 最终要被压成一个 GPU batch。

当前 V1 有 vllm/v1/worker/gpu_input_batch.py。它的角色可以先理解为：维护“当前 GPU batch 里有哪些 requests，以及这些 request-level 状态在 batch tensor 中放在哪里”。

logical reqsA d1B d1C p0C p1C p2…D d1—
GPU tokenstok Atok BC0C1C2…tok Dpad/unused

模型最终并不关心“这是用户 Alice 的请求”。它需要的是 tensor positions、batch offsets、KV addresses 和 sampling metadata。

03 · BLOCKTABLE

BlockTable 是“每个 request 的逻辑块 → physical block ID”的设备可用表示。

REQ A · BLOCK TABLE ROW
logical 0 → #8logical 1 → #2logical 2 → #19logical 3 → #5
REQ B · BLOCK TABLE ROW
logical 0 → #11logical 1 → #4logical 2 → #7

当前 BlockTable 源码维护一个二维 block table buffer，也维护标准 Attention 路径使用的 slot mapping。它还处理 allocation block size 与 attention kernel block size 不一致时的虚拟拆分逻辑。入门先只记住：block table 告诉执行后端“这个 request 的 cache/state blocks 在哪里”。

当前实现：vllm/v1/worker/block_table.py。构造参数里能直接看到 block_size、kernel_block_size、slot_mapping_mode，以及 PCP/DCP 相关状态。
04 · SLOT MAPPING

对标准 Attention KV Cache：block table 解决“读哪些块”，slot mapping 解决“本轮新 KV 写到哪个 token slot”。

假设 physical block #5 有 16 个 token slots，而 Request A 当前已经占用了前 12 个。本轮 decode 的新 token 应该写入 #5 的第 12 个 slot。系统需要把当前 scheduled token 映射到这个具体 KV storage slot。

WRITE PATH · STANDARD ATTENTION
new K/V本轮 token 在某层算出的 Kₜ / Vₜ
→
slot mappingreq A → block #5 → offset 12
→
physical KV写进已分配好的 cache storage

这就是为什么 scheduler 的 allocation 与 ModelRunner 的 slot mapping 必须严格一致：如果 block ID 或 offset 错一位，attention 读到的历史上下文就直接错了。

但别把 slot mapping 当成所有 cache group 的统一真理。当前 BlockTable 有 SlotMappingMode.NONE：Mamba/GDN 这类 recurrent-state cache group 可以把 block table 当状态索引使用，不做逐 token 的 KV slot mapping。我们这里的“写 slot”心智模型专指标准 token-indexed Attention KV Cache。

05 · PAGED ATTENTION MENTAL MODEL

Q 逻辑上 attend 一段连续历史，底层却可以按 block table 从散落的 physical blocks 取 K/V。

READ PATH · SIMPLIFIED
Qₜ当前 token 的 query
→
block table[#8, #2, #19, #5]
→
K/V pages从这些 physical blocks 读取历史 K/V

从数学上看，Attention 仍然是在对 token 0…t 的 K/V 做同一个 causal attention。变化的是存储层：K/V 不要求物理连续，而是由映射表间接寻址。

“Paged”改变的是内存管理与寻址方式，不改变 Transformer 的 Attention 数学定义。

06 · PAGEDATTENTION IS NOT ONE ETERNAL KERNEL

现代 vLLM 有 attention backend 抽象，实际 kernel 会随硬件、模型和配置变化。

早期介绍 vLLM 时，经常把“PagedAttention kernel”当成整个系统的代表。这个历史直觉很有价值，但读当前源码时必须升级：V1 有 attention/backend.py、attention/backends/ 和 selector；不同平台可以使用 FlashAttention、FlashInfer 或其它 backend 路径。

不要学成“vLLM = 一个 PagedAttention CUDA kernel”。

更稳定的核心是：KV 是 block/page 管理的；执行层提供 block table/slot mapping 等 metadata；具体 attention backend 以相应方式消费这些信息。

07 · ONE DECODE ITERATION END TO END

现在把一次标准 Attention decode 从 scheduler 串到 GPU。

1 · SCHEDULEA gets 1 tokenScheduler 决定 req A 本轮推进 1。
2 · KVblock #5 slot 12KV manager 已保证有可写 slot。
3 · PREPAREbatch + tablesModelRunner 更新 batch state、BlockTable、slot mapping。
4 · FORWARDmodel + attention新 K/V 写入 slot；Q 按 block table 读取历史 KV。
5 · SAMPLEnext token结果返回 scheduler，A 的进度 +1。

你之后读 ModelRunner 时，任何一段复杂代码都先塞回这五步之一。这样即使具体 runner 文件随版本重构，也不会完全失去方向。

08 · WHY MODELRUNNER ALSO CARES ABOUT SHAPES

Serving batch 很动态，但 GPU 喜欢稳定、足够大的工作。

ModelRunner 不只是“调用 model.forward”。它还要处理 padded batch sizes、CUDA Graph capture/replay、attention backend metadata、TP/PP、spec decode 等执行优化。核心矛盾是：上层 requests 高度动态，底层 GPU kernel 又希望输入 shape 可预测、开销低。

DYNAMIC FRONT每轮 request 数、token 数都变continuous batching 带来利用率，但也让 execution shape 变化。
STABLE GPUgraphs / kernels 喜欢规则 shape框架会用 padding、capture sizes、backend-specific metadata 等方式把动态性压到可执行范围。

CHECKPOINT07.4

能解释“写哪、读哪”，Paged KV 才真正落地。

1. 对标准 Attention KV，BlockTable 和 slot mapping 分别解决什么？
BlockTable 主要告诉 attention 一个 request 的逻辑历史块对应哪些 physical blocks，用于读取历史 KV；slot mapping 把本轮 scheduled tokens 映射到具体 KV 写入位置。
2. Paged KV 会改变 Attention 数学吗？
不会。Attention 仍对逻辑上的历史 K/V 做相同计算；改变的是这些 K/V 在 GPU memory 中的存储与寻址方式。
3. 为什么不能说“所有 vLLM cache group 都需要 token slot mapping”？
因为当前 BlockTable 明确支持 SlotMappingMode.NONE；Mamba/GDN 一类 recurrent-state cache group 可以不使用 token-to-KV-slot 映射。标准 Attention KV 才对应这一课的逐 token slot 心智模型。
