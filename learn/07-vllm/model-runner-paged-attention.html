LESSON 07.4 · VLLM约 80 min

ModelRunner 与 Paged Attention：scheduler 给出的 block IDs，最后怎样变成 GPU attention？

上一课停在控制层：Request A 的逻辑 blocks 被映射到 physical IDs，例如 [8, 2, 19, 5]。但 GPU attention kernel 不会自己去问 Python 的 KVCacheManager。执行层必须把这些信息整理成设备侧的 batch tensors、block tables、slot mappings 和 attention metadata。这个转换过程正是读 GPUModelRunner 的关键入口。

这节课结束时，你应该能做到：
  • 理解 SchedulerOutput 到 GPU execution 之间还需要一次“元数据压缩/搬运”。
  • 知道 InputBatch/GPUInputBatch、BlockTable/BlockTables、slot mapping 在执行路径里分别解决什么。
  • 解释 paged KV attention 如何让 attention 读取不连续 physical KV blocks。
  • 知道“PagedAttention”是核心思想，但当前 vLLM 会根据平台/模型选择不同 attention backends，不能把系统等同于一个固定 kernel。
  • 理解新 token 的 K/V 怎样写入分配好的 slot，Q 又怎样按 block table 读取历史 KV。
  • 知道“所有 cache group 都必须用同一套 token-to-KV-slot API”不是稳定事实；不同 cache/state 类型会有不同寻址语义。
  • 知道当前上游同时存在 V1/V2 GPU ModelRunner 路径，先从 gpu_worker.py 看本配置实际选择哪一个。
01 · THE EXECUTION CONTRACT

SchedulerOutput 是逻辑计划，ModelRunner 要把它翻译成设备可以直接消费的结构。

Scheduler 视角req A 本轮 1 token，req B 本轮 1 token，req C 继续 prefill 128 tokens；各自对应哪些 KV blocks。
GPU 视角一批 token IDs / positions / request indices、连续 input buffers、block-table tensors、slot mappings、attention metadata。

这个转换不能每层都临时用 Python list 做一遍，否则 CPU overhead 和 CPU→GPU metadata copy 会变成新的瓶颈。因此 vLLM 会维护可复用的 input buffers、request/batch state 与 block-table buffers。

02 · INPUT BATCH

动态 requests 最终要被压成 GPU 能连续消费的一批 tensors；但当前两条 runner 路径的类与目录不完全相同。

当前上游的旧 V1 runner 路径使用 vllm/v1/worker/gpu_input_batch.py 中的 InputBatch，它维护 request state、sampling 状态以及与 block table 相关的执行信息。新的 V2 runner 路径则从 vllm/v1/worker/gpu/input_batch.py 导入 InputBatch / InputBuffers，把 input_ids、positions、query start、sequence lengths、request index mapping 等显式整理成执行批次。

logical reqsA d1B d1C p0C p1C p2…D d1—
GPU tokenstok Atok BC0C1C2…tok Dpad/unused

所以不要把“GPUInputBatch”当成永久类名。更稳定的心智模型是：动态 request-level 状态必须被压成 batch-level tensors 与索引映射，ModelRunner 才能高效进入设备执行。

当前 V2：vllm/v1/worker/gpu/input_batch.py；当前仓库仍保留旧 V1 路径 vllm/v1/worker/gpu_input_batch.py。
03 · BLOCK TABLE / BLOCK TABLES

无论类名是单数还是复数，核心职责都是把 request 的逻辑 cache blocks 变成执行后端可使用的 physical addressing。

REQ A · LOGICAL VIEW
logical 0 → #8logical 1 → #2logical 2 → #19logical 3 → #5
REQ B · LOGICAL VIEW
logical 0 → #11logical 1 → #4logical 2 → #7

旧 V1 路径的 vllm/v1/worker/block_table.py 定义 BlockTable / MultiGroupBlockTable，会处理 allocation block size、kernel block size 与 slot mapping。V2 路径把这部分重构到 vllm/v1/worker/gpu/block_table.py 的 BlockTables：它直接维护“每个 KV cache group 一张二维 block table”，还保留对应的 device-side input tables 与 slot_mappings tensor。

代码会重构，寻址问题不会消失。Scheduler 分配的是 request/cache 语义上的 physical block IDs；执行层必须把这些 IDs 整理成 attention/state backend 能直接消费的设备结构。

当前 V2：vllm/v1/worker/gpu/block_table.py；旧 V1：vllm/v1/worker/block_table.py。
04 · SLOT MAPPING

对标准 token-indexed Attention KV Cache：block table 解决“历史块在哪里”，slot mapping 解决“本轮新 KV 写到哪个 token slot”。

假设 physical block #5 有 16 个 token slots，而 Request A 当前已经占用了前 12 个。本轮 decode 的新 token 应该写入 #5 的第 12 个 slot。系统需要把当前 scheduled token 映射到这个具体 KV storage slot。

WRITE PATH · STANDARD ATTENTION
new K/V本轮 token 在某层算出的 Kₜ / Vₜ
→
slot mappingreq A → block #5 → offset 12
→
physical KV写进已分配好的 cache storage

这就是为什么 scheduler 的 allocation 与 ModelRunner 的 addressing metadata 必须严格一致：如果 block ID 或 offset 错一位，attention 读到的历史上下文就直接错了。

不要把某个版本的 slot-mapping API 当成跨所有 cache 类型的永久真理。当前旧 V1 BlockTable API 明确存在 SlotMappingMode.NONE，用于表达 Mamba-like state cache 不采用标准 token→KV-slot 映射；V2 已经重构这部分目录与数据结构。你应该记住的是“不同 cache/state backend 的寻址语义可能不同”，而不是死背某个 enum 永远存在。

05 · PAGED ATTENTION MENTAL MODEL

Q 逻辑上 attend 一段连续历史，底层却可以按 block table 从散落的 physical blocks 取 K/V。

READ PATH · SIMPLIFIED
Qₜ当前 token 的 query
→
block table[#8, #2, #19, #5]
→
K/V pages从这些 physical blocks 读取历史 K/V

从数学上看，Attention 仍然是在对 token 0…t 的 K/V 做同一个 causal attention。变化的是存储层：K/V 不要求物理连续，而是由映射表间接寻址。

“Paged”改变的是内存管理与寻址方式，不改变 Transformer 的 Attention 数学定义。

06 · PAGEDATTENTION IS NOT ONE ETERNAL KERNEL

现代 vLLM 有 attention backend 抽象，实际 kernel 会随硬件、模型和配置变化。

早期介绍 vLLM 时，经常把“PagedAttention kernel”当成整个系统的代表。这个历史直觉很有价值，但读当前源码时必须升级：V1 有 attention/backend.py、attention/backends/ 和 selector；不同平台可以使用 FlashAttention、FlashInfer 或其它 backend 路径。

不要学成“vLLM = 一个 PagedAttention CUDA kernel”。

更稳定的核心是：KV 是 block/page 管理的；执行层提供 block table / slot mapping / attention metadata；具体 attention backend 以相应方式消费这些信息。

07 · ONE DECODE ITERATION END TO END

现在把一次标准 Attention decode 从 scheduler 串到 GPU。

1 · SCHEDULEA gets 1 tokenScheduler 决定 req A 本轮推进 1。
2 · KVblock #5 slot 12KV manager 已保证有可写位置。
3 · PREPAREbatch + tablesModelRunner 更新 batch state、block tables 与 addressing metadata。
4 · FORWARDmodel + attention新 K/V 写入目标位置；Q 按 block table 读取历史 KV。
5 · SAMPLEnext token结果返回 scheduler，A 的进度 +1。

你之后读 ModelRunner 时，任何一段复杂代码都先塞回这五步之一。这样即使具体 runner、input-batch、block-table 文件随版本重构，也不会完全失去方向。

08 · WHY MODELRUNNER ALSO CARES ABOUT SHAPES

Serving batch 很动态，但 GPU 喜欢稳定、足够大的工作。

ModelRunner 不只是“调用 model.forward”。它还要处理 padded batch sizes、CUDA Graph capture/replay、attention backend metadata、TP/PP、spec decode 等执行优化。核心矛盾是：上层 requests 高度动态，底层 GPU kernel 又希望输入 shape 可预测、开销低。

DYNAMIC FRONT每轮 request 数、token 数都变continuous batching 带来利用率，但也让 execution shape 变化。
STABLE GPUgraphs / kernels 喜欢规则 shape框架会用 padding、capture sizes、backend-specific metadata 等方式把动态性压到可执行范围。

CHECKPOINT07.4

能解释“写哪、读哪”，Paged KV 才真正落地。

1. 对标准 Attention KV，block table 和 slot mapping 分别解决什么？
Block table 主要告诉 attention 一个 request 的逻辑历史块对应哪些 physical blocks，用于读取历史 KV；slot mapping / addressing metadata 则把本轮 scheduled tokens 映射到具体 KV 写入位置。
2. Paged KV 会改变 Attention 数学吗？
不会。Attention 仍对逻辑上的历史 K/V 做相同计算；改变的是这些 K/V 在 GPU memory 中的存储与寻址方式。
3. 为什么现在读源码不能只记住 gpu_input_batch.py 和 worker/block_table.py？
因为当前上游同时保留 V1/V2 runner。V2 runner 使用 worker/gpu/input_batch.py 与 worker/gpu/block_table.py；旧 V1 runner 仍使用重构前的路径。先看 gpu_worker.py 的 selector，再沿被选中的 runner imports 读。
