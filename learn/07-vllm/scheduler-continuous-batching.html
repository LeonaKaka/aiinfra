LESSON 07.2 · VLLM约 75 min

Scheduler 与 Continuous Batching：GPU 下一轮到底算谁？

在线推理的请求不会整齐地同时到达，也不会同时结束。A 还在 decode，B 刚结束，C 是 8K prompt，D 只需要生成 3 个 token。如果沿用传统“凑一个 batch → 整批跑到底”的思路，GPU 会被不同长度的请求拖住。vLLM 的核心变化之一，是把 batch 看成每个 scheduling/execution iteration 都可以重新组成的动态集合。

这节课结束时，你应该能做到：
  • 解释 static batching 为什么容易被长尾请求拖住。
  • 准确理解 continuous batching：batch membership 可以在 execution iterations 之间持续变化。
  • 知道当前 V1 Scheduler 内部并没有两套独立的 “Prefill phase / Decode phase” 调度器，而是围绕 token progress 统一推进请求。
  • 知道 Scheduler 受 scheduled-token budget、input budget、最大并发 requests、KV capacity 等多重资源约束。
  • 理解当前 V1 的 chunked prefill 与 decode-priority 策略为什么能细化调度粒度。
  • 知道当前 V1 的默认 preemption 恢复方式是 recompute，而不是旧式 SWAP。
01 · WHY STATIC BATCHES WASTE CAPACITY

请求长度不同，最慢的那一个会让固定 batch 很尴尬。

想象 4 个请求同时开始，输出长度分别是 2、4、8、20 tokens。如果你规定“这个 batch 的 4 个槽位直到全部请求结束都不换人”，前两个请求很快就完成，但它们留下的槽位会空着。

step 3idleBCD————
step 5idleidleCD————

这不是 GPU 算不动，而是调度策略没有及时把空出来的容量交给新请求。

02 · CONTINUOUS BATCHING

谁结束，下一轮就可以换新人进来。

Continuous batching 的核心不是某个神奇 kernel，而是 iteration-level scheduling：每轮执行前重新决定本轮一起执行哪些 requests / tokens。A 完成后，下一轮就可以让新来的 E 补进来。

iteration 1ABCD————
iteration 3EBCD————
iteration 5EFCD————

不要误解：continuous batching 不是“一次 kernel 里不断插 request”。更稳定的理解是：batch 在离散的 scheduling/execution iterations 之间持续更新。

03 · WAITING AND RUNNING

Scheduler 维护的是请求生命周期，而不是一张永远不变的 batch 表。

req E · long promptreq F · short promptreq G · priority ...
schedule / preempt ↔

当前 vLLM V1 的 scheduler 还处理 structured output、speculative decoding、multimodal、KV Connector 等额外状态。初学时不要一次吃完；先抓住 waiting / running、token progress 与资源预算。

04 · THE SCHEDULER HAS HARD BUDGETS

“想跑谁”不够，必须同时满足本轮 token 数、输入规模、并发数和 KV 空间。

SCHEDULED-TOKEN BUDGETmax_num_scheduled_tokens当前源码先建立本轮可推进多少 tokens 的总预算；未单独配置时会回落到 max_num_batched_tokens。
REQUEST BUDGETmax_num_seqs同时处于运行资源域的 request 数不能无限增长。
KV BUDGETavailable blocks即使 token budget 还有，KV block 不够也不能继续盲目 append。

当前 schedule() 里还维护 input_budget = max_num_batched_tokens，并叠加 speculative lookahead、encoder budget 等约束。因此 scheduler 实际做的是一个受多重资源限制的在线选择问题，不是只看一个 batch size。

05 · ONE TOKEN-PROGRESS SCHEDULER

教学上可以说 Prefill 与 Decode 共享机器；源码里更准确的说法是：Scheduler 统一推进每个 request 的 token progress。

scheduledA +1B +1C +1D +chunkDDD…

当前 V1 schedule() 的源码注释明确写着：Scheduler 内部没有独立的 “decoding phase” 或 “prefill phase”。它看的是 num_computed_tokens 与当前已知 token 数之间还差多少，再在预算允许时推进。长 prompt 因此可以推进很多 tokens；普通 decode request 通常只多一个当前已知 token。

这条区别对读源码很重要。Prefill / Decode 仍然是理解 workload 的好概念，但不要进 scheduler.py 后去寻找两套独立的 phase loop。Prefix caching、chunked prefill、speculative decoding 都被统一进“还差多少 token progress”这套模型里。

06 · CHUNKED PREFILL

长 prompt 不必被当成一个不可切分的大石头。

Chunked prefill 允许一个长 prompt 分多轮推进。例如 8000-token prompt 不必在一次 scheduler iteration 中全部处理；可以只推进受当前 token/input budget 限制的一段，之后继续。

当前 vLLM V1 的优化文档说明：在条件允许时 chunked prefill 默认启用；调度策略会优先安排 pending decode work，再用剩余的 max_num_batched_tokens budget 安排 prefill，放不下的 prefill 自动切 chunk。这解释了为什么它能保护 ITL，同时又尽量利用剩余 GPU 工作量。

当前说明：vLLM · Optimization and Tuning，见 Chunked Prefill；源码主循环见 scheduler.py。
07 · WHAT HAPPENS WHEN KV IS NOT ENOUGH?

Scheduler 可能需要让已有 request 暂时退让；当前 V1 默认通过 recompute 恢复。

当前 V1 scheduler 在 running request 无法分到需要的新 blocks 时，会进入明确的 preemption 路径：根据 scheduling policy 选 victim，释放它占用的资源，并把请求重新安排。当前 V1 的优化文档明确说明默认 preemption mode 是 RECOMPUTE，而不是旧 V0 路径常见的 SWAP；恢复时会重新计算被释放的 KV 状态。

Preemption 不是异常，也不是免费的。

它是有限 KV capacity 下继续服务的资源管理策略，但频繁 recompute 会浪费算力并恶化端到端 latency。带 KV Connector 时，正在进行的可靠 handoff 还会增加额外的正确性约束，08.3 会继续拆。

08 · A TINY SCHEDULER MENTAL MODEL

把几千行 scheduler 先压成“推进 token progress + 分配 KV”的伪代码。

python-like pseudocodeone scheduling iteration
token_budget = max_scheduled_tokens

# 1. running requests first
for req in running:
    want = known_tokens(req) - req.num_computed_tokens
    want = cap_by_budgets(want, token_budget, input_budget)
    blocks = kv_manager.allocate_slots(req, want)
    if blocks is None:
        preempt_victim_and_retry()
    else:
        schedule(req, want)
        token_budget -= want

# 2. admit waiting requests if capacity remains
while waiting and token_budget > 0 and running_slots_available():
    req = choose(waiting)
    local_hit = kv_manager.find_cached_prefix(req)
    remote_hit = connector_match_if_any(req, local_hit)
    want = remaining_known_tokens(req, local_hit, remote_hit)
    chunk = cap_by_budgets(want, token_budget, input_budget)
    blocks = kv_manager.allocate_slots(req, chunk)
    if blocks is None:
        break
    schedule(req, chunk)
    token_budget -= chunk

return SchedulerOutput(...)

这仍是教学伪代码，不是逐行复刻；但它和当前源码的关键抽象一致：谁先？已计算到哪？这轮还能推进多少？缓存命中多少？要多少 blocks？预算够不够？

1. Continuous batching 最准确的心智模型是什么？
每个 scheduling/execution iteration 之间可以重新组成 batch：完成的 request 离开，新 request 可以进入，已有 request 继续推进。它不是在一个正在运行的 GPU kernel 里随时插人。
2. 当前 V1 Scheduler 为什么不需要一套 Prefill loop 再加一套 Decode loop？
它统一追踪 request 的 num_computed_tokens 与当前已知 token progress 之间的差距，再按预算推进。长 prompt 往往一次推进一段；普通 decode 往往只推进新增加的 token，因此 workload 不同，但调度抽象可以统一。
3. 当前 V1 preemption 后默认怎样恢复被释放的 KV？
默认是 RECOMPUTE：请求以后重新获得机会时重新计算必要状态，而不是默认把 KV swap 到 CPU 再 swap 回来。
