LESSON 07.2 · VLLM约 80 min

Scheduler 与 Continuous Batching：GPU 下一轮到底算谁？

在线推理的 requests不会整齐地同时到达，也不会同时结束。A 还在 Decode，B 刚结束，C 正在处理长 prompt 的一段 Prefill，D/E 又在等待。如果沿用 static batching（静态批处理：固定一组 requests 一起运行，直到这一批全部结束）的思路，空槽和长尾会浪费 GPU。vLLM 的核心变化之一，是让每个 scheduler iteration 都能根据最新状态重新组成要执行的 token 工作集合。

这节课结束时，你应该能做到：
  • 解释 static batching 为什么容易被长尾请求拖住。
  • 准确理解 continuous batching：批次成员可以在 iterations 之间持续变化。
  • 知道当前 V1 Scheduler 内部没有两套独立的 “Prefill 阶段 / Decode 阶段” 调度器，而是围绕 token 进度统一推进 requests。
  • 知道调度器同时受本轮 token 预算、输入预算、最大运行请求数和 KV 容量等资源约束。
  • 理解当前 V1 的 chunked Prefill 与运行中请求优先策略怎样细化调度粒度。
  • 知道当前 V1 的默认抢占恢复方式是重计算，而不是旧式 SWAP。

建议两遍读。第一遍只回答三个问题：哪些 requests 还活着、本轮 token budget 能推进谁、KV 空间够不够。第二遍再进入 chunked Prefill、preemption 和当前 V1 Scheduler 的具体字段。先学调度约束，再记实现名。

01 · 静态批处理为什么浪费资源

request length 不同，最慢的那一个会让 static batching 很尴尬。

想象 4 个请求同时开始，输出长度分别是 2、4、8、20 tokens。如果规定“这个 batch 的 4 个 slots 直到全部请求结束都不换人”，前两个请求很快完成，但它们留下的槽位会空着。

02 · Continuous Batching

谁结束，下一轮就可以换新人进来。

continuous batching 的核心不是某个神奇内核，而是每轮重新规划：每轮执行前根据最新 request state 决定本轮一起执行哪些 requests / tokens。A 完成后，下一轮就可以把释放出的资源给 E。

iteration 1ABCD————
iteration 3EBCD————
iteration 5EFCD————

不要误解：continuous batching不是“在一个正在跑的 GPU 内核里随时插请求”。更稳定的心智模型是：批次成员在离散的 scheduler iterations 之间持续更新。

03 · 一次 scheduler iteration

一次 schedule() 真正在做的事：从 running / waiting 状态出发，在多个预算和 KV 分配约束下生成一份可执行计划。

图里故意让 running queue 中可以同时存在 Decode requests 和仍处于 Prefill 的请求。因为当前 Scheduler 的核心抽象不是“切换 Prefill 模式 / Decode 模式”，而是：这个请求已计算到哪、还欠多少 token 工作、本轮资源允许推进多少。

vLLM V1 · 调度器运行 / 等待 → 预算 + KV → SchedulerOutput
调度器的核心不是“拼一张批次表”，而是解决一个在线资源分配问题：谁先推进、推进多少 token、cache hit 了多少、还要多少 physical blocks、这一轮总 budget 是否够。continuous batching 则是这个选择过程在每次 iteration 重新执行的直接结果。

当前源码还处理 DP prefill balancing、encoder input、LoRA（低秩适配：用低秩增量参数高效适配预训练模型的方法）、结构化输出、speculative decoding、KV Connector 远端加载等额外条件。初学时不要一次吃完；先把上图的三件事分清：request state、资源预算、KV 归属关系。

当前 scheduler.py 的 schedule() 先遍历 self.running，再在没有本轮抢占且未暂停等条件下处理 waiting queue；KV blocks 通过 kv_cache_manager.allocate_slots(...) 约束可调度量。
04 · 调度器有哪些硬预算

“想跑谁”不够，必须同时满足本轮 token 数、输入规模、并发数和 KV 空间。

SCHEDULED-TOKEN BUDGETmax_num_scheduled_tokensScheduler 初始化时若该值未单独给出，会使用 max_num_batched_tokens；每轮 token_budget 从这里开始扣。
RUNNING request limitmax_num_running_reqs当前值来自 scheduler_config.max_num_seqs；waiting admission 不能让运行资源域无限增长。
KV BUDGETavailable blocks即使 token budget 还有，allocate_slots 失败也会改变调度甚至触发抢占。

当前 schedule() 同时维护 input_budget = max_num_batched_tokens，并叠加 speculative draft slots、encoder 计算/cache、max model length 等约束。所以调度器不是只看一个“批次 size”。

05 · 用 Token 进度统一调度

教学上可以说 Prefill 与 Decode 共享机器；源码里更准确的说法是：调度器统一推进每个请求的 token 进度。

scheduledA +1B +1C +1D +chunkDDD…

当前 V1 schedule() 的源码注释明确写着：调度器内部没有独立的 “decoding phase” 或 “prefill phase”。它看的是 num_computed_tokens 与当前已知 token state 之间还差多少，再在预算允许时推进。长 prompt 因此可以推进很多 tokens；基础 Decode 请求通常只多一个新的已知位置。

这条区别对读源码很重要。Prefill / Decode 仍然是理解工作负载的好概念，但不要进 scheduler.py 后去寻找两套独立 phase loop。Prefix caching、分块 Prefill、投机解码 都能被统一进“还差多少 token 进度”这套模型。

06 · 分块 Prefill

长 prompt 不必被当成一个不可切分的大石头。

07 · KV 不够时会发生什么？

调度器可能需要让已有请求暂时退让；当前 V1 默认通过 recompute（重计算：被抢占请求恢复时重新计算必要状态，而不是保留完整 KV）恢复。

当前 V1 调度器在 running 请求无法分到需要的新块时，会进入明确的 preemption 路径：选择被抢占请求、把它从 running 资源域移出、释放资源，再尝试让当前工作继续。当前 V1 优化文档明确说明默认抢占模式是 RECOMPUTE，而不是旧 V0 路径常见的 SWAP；恢复时 recompute 必要 KV 状态。

抢占不是异常，也不是免费的。

它是有限 KV 容量下继续服务的资源管理策略，但频繁 recompute 会浪费算力并恶化端到端延迟。带 KV Connector 时，正在进行的 KV 传输还会增加发送端/接收端的生命周期约束，08.3 会继续拆。

08 · 一个最小调度器心智模型

把几千行调度器先压成“推进 token 进度 + 分配 KV”的伪代码。

python-like pseudocodeone scheduler iteration
token_budget = max_scheduled_tokens

# 1. running requests
for req in running:
    want = known_tokens(req) - req.num_computed_tokens
    want = cap_by_budgets(want, token_budget, input_budget)
    blocks = kv_manager.allocate_slots(req, want)
    if blocks is None:
        preempt_victim_and_retry()
    else:
        schedule(req, want)
        token_budget -= want

# 2. waiting requests when admission is allowed
while waiting and token_budget > 0 and running_slots_available():
    req = choose(waiting)
    local_hit = kv_manager.find_cached_prefix(req)
    remote_hit = connector_match_if_any(req, local_hit)
    want = remaining_known_tokens(req, local_hit, remote_hit)
    chunk = cap_by_budgets(want, token_budget, input_budget)
    blocks = kv_manager.allocate_slots(req, chunk)
    if blocks is None:
        break
    schedule(req, chunk)
    token_budget -= chunk

return SchedulerOutput(...)

这仍是教学伪代码，不是逐行复刻；但它和当前源码的关键抽象一致：谁先？已计算到哪？这轮还能推进多少？缓存命中多少？要多少块？预算够不够？

CHECKPOINT07.2

能解释调度器，才算开始懂在线推理。

1. continuous batching 最准确的心智模型是什么？
每个 scheduler iteration 之间可以重新组成批次：完成的请求离开，新请求可以进入，已有请求继续推进。它不是在一个正在运行的 GPU 内核里随时插人。
2. 当前 V1 Scheduler 为什么不需要一套 Prefill loop 再加一套 Decode loop？
它统一追踪请求的 num_computed_tokens 与当前已知 token state 之间的差距，再按预算推进。长 prompt 往往一次推进一段；baseline decode 往往只推进新增加的位置，因此工作负载不同，但调度抽象可以统一。
3. KV 分配失败为什么会反过来改变调度器决策？
因为 scheduled token 如果没有物理 KV slots 就无法安全执行。当前 running path 会在 allocate_slots 失败时尝试 preempt victim 释放资源；所以 KV 归属关系是调度的硬约束，不是执行后的附属状态记录。
4. 当前 V1 抢占后默认怎样恢复被释放的 KV？
默认是 RECOMPUTE：请求以后重新获得机会时 recompute 必要状态，而不是默认把 KV swap 到 CPU 再 swap 回来。
