LESSON 07.2 · VLLM约 70 min

Scheduler 与 Continuous Batching：GPU 下一轮到底算谁？

在线推理的请求不会整齐地同时到达，也不会同时结束。A 还在 decode，B 刚结束，C 是 8K prompt，D 只需要生成 3 个 token。如果沿用传统“凑一个 batch → 整批跑到底”的思路，GPU 会被不同长度的请求拖住。vLLM 的核心变化之一，是把 batch 看成每个 iteration 都可以重新组成的动态集合。

这节课结束时，你应该能做到：
  • 解释 static batching 为什么容易被长尾请求拖住。
  • 准确理解 continuous batching：batch membership 可以在 generation iterations 之间持续变化。
  • 知道 Scheduler 受 token budget、最大并发 requests、KV capacity 等多重资源约束。
  • 理解 Prefill 和 Decode 可以在同一个 scheduling step 中竞争 token budget。
  • 理解 chunked prefill 的基本动机，而不是把长 prompt 当成不可分的大块。
  • 知道 preemption 是资源不够时的系统行为，不是“模型推理失败”。
01 · WHY STATIC BATCHES WASTE CAPACITY

请求长度不同，最慢的那一个会让固定 batch 很尴尬。

想象 4 个请求同时开始，输出长度分别是 2、4、8、20 tokens。如果你规定“这个 batch 的 4 个槽位直到全部请求结束都不换人”，前两个请求很快就完成，但它们留下的槽位会空着。

step 1ABCD————
step 3idleBCD————
step 5idleidleCD————

这不是 GPU 算不动，而是调度策略没有及时把空出来的容量交给新请求。

02 · CONTINUOUS BATCHING

谁结束，下一轮就可以换新人进来。

Continuous batching 的核心不是某个神奇 kernel，而是 iteration-level scheduling：每轮 generation 前重新决定本轮一起执行哪些 requests / tokens。A 完成后，下一轮就可以让新来的 E 补进来。

iteration 1ABCD————
iteration 3EBCD————
iteration 5EFCD————

不要误解：continuous batching 不是“一次 kernel 里不断插 request”。更稳定的理解是：batch 在离散的 scheduling/execution iterations 之间持续更新。

03 · WAITING AND RUNNING

Scheduler 维护的是请求生命周期，而不是一张永远不变的 batch 表。

WAITING还没获得本轮执行机会
req E · long prefillreq F · short promptreq G · priority ...
schedule / preempt ↔
RUNNING已有执行状态和 KV blocks
req A · decodereq B · prefill chunkreq C · decode

当前 vLLM V1 的 scheduler 还处理 structured output、speculative decoding、multimodal、KV Connector 等额外状态。初学时不要一次吃完；先抓住 waiting / running 与资源预算。

04 · THE SCHEDULER HAS HARD BUDGETS

“想跑谁”不够，必须同时满足本轮 token 数、并发数和 KV 空间。

TOKEN BUDGETmax scheduled tokens一轮里总共允许推进多少 tokens；当前源码把它作为 scheduler 的核心约束之一。
REQUEST BUDGETmax running requests同时运行的 request 数不能无限增长；会受最大 sequences 等配置限制。
KV BUDGETavailable blocks即使 token budget 还有，KV block 不够也不能继续盲目 append。

因此 scheduler 实际做的是一个受多重资源限制的在线选择问题。吞吐高的选择，不一定有最低 TTFT；最照顾 decode 的选择，也可能让新长 prompt 饿很久。

05 · PREFILL AND DECODE SHARE THE MACHINE

一轮 scheduler 可能同时面对“老请求 decode”和“新请求 prefill”。

scheduledA d1B d1C d1D p0D p1D p2D p3…

这里的关键单位是 scheduled tokens，而不是“一个 request 算一次”。Decode request 通常本轮推进少量 token；长 prompt prefill 可能一次吃掉很多 token budget。如果任由一个超长 prefill 独占大块计算，它会把已有 decode 的下一 token 推迟。

06 · CHUNKED PREFILL

长 Prefill 不必每次都被当成一个不可切分的大石头。

Chunked prefill 的思路，是允许一个长 prompt 分多轮推进。例如 8000-token prompt 不必在一次 scheduler iteration 中全部处理；可以先给它 1024 或某个受预算限制的 chunk，同时给 decode 留出执行机会。

LONG PROMPT8000 tokens
→
ITERATIONchunk 0..1023
→
NEXTcontinue later

这会改善调度粒度，但并非“越碎越好”。Chunk 太小可能增加调度/launch 开销、让大 GEMM 变差；chunk 太大又可能伤害 decode latency。实际配置要看服务目标。

07 · WHAT HAPPENS WHEN KV IS NOT ENOUGH?

Scheduler 可能需要让已有 request 暂时退让。

当前 V1 scheduler 的代码里存在明确的 preemption 路径：当一个 running request 无法获得需要的新 blocks，scheduler 可以选择 preempt request，释放资源，再把工作重新安排。之后请求可能需要恢复或重算部分进度，具体行为受当前实现与 connector 等配置影响。

Preemption 不是异常。

它是“有限 KV capacity 下如何保证整个服务继续向前”的资源管理策略。真正要关注的是 preemption 频率、重算代价，以及它对 TTFT/ITL/throughput 的影响。

08 · A TINY SCHEDULER MENTAL MODEL

把几千行 scheduler 先压成下面这个伪代码。

python-like pseudocodeone scheduling iteration
token_budget = max_scheduled_tokens

# 1. consider requests already running
for req in running:
    want = tokens_to_advance(req)
    need_blocks = kv_manager.blocks_needed(req, want)
    if fits(token_budget, need_blocks):
        schedule(req, want)
        token_budget -= want
    else:
        maybe_preempt_or_stop()

# 2. admit waiting requests if capacity remains
while waiting and token_budget > 0 and running_slots_available():
    req = choose(waiting)
    cached = kv_manager.find_cached_prefix(req)
    chunk = choose_prefill_or_decode_tokens(req, cached, token_budget)
    blocks = kv_manager.allocate(req, chunk)
    if blocks is None:
        break
    schedule(req, chunk)
    token_budget -= chunk

return SchedulerOutput(...)

真实实现复杂得多，但以后你读 schedule() 时，先不断把分支归类到这几个问题：谁先？推进多少？缓存命中多少？要多少 blocks？预算够不够？

能解释 scheduler，才算开始懂 serving。

1. Continuous batching 最准确的心智模型是什么？
每个 execution/scheduling iteration 之间可以重新组成 batch：完成的 request 离开，新 request 可以进入，已有 request 继续推进。它不是在一个正在运行的 GPU kernel 里随时插人。
2. 为什么 scheduler 有 token budget 还不够，还要看 KV blocks？
因为每个需要缓存的新 token 都要有实际 KV memory slot。算力预算允许并不等于显存容量允许。
3. Chunked prefill 主要解决什么矛盾？
长 prefill 一次占用过大的计算/token budget，会阻塞已有 decode。切成 chunks 可以提高调度粒度，在 TTFT、ITL 和吞吐之间更灵活地权衡。
