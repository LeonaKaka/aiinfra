LESSON 07.1 · VLLM约 65 min

vLLM Architecture：先顺着一个 request 走完系统，再读任何一个大文件。

vLLM 的代码量已经很大，直接打开某个 ModelRunner 或 scheduler.py 很容易迷路。最好的入口不是“哪个文件最核心”，而是先回答：一个请求进入 EngineCore 后，谁决定本轮算多少 token？谁分配 Key-Value (KV，键-值) blocks？谁把计划变成 Graphics Processing Unit (GPU，图形处理器) tensors？结果怎样回到 scheduler，让同一个请求在下一轮继续前进？

这节课结束时，你应该能做到：
  • 把 vLLM V1 粗分成请求/控制层、调度与 KV 管理层、执行层。
  • 知道 EngineCore、Scheduler、KVCacheManager、executor/worker、GPUModelRunner 的职责边界。
  • 理解 SchedulerOutput 为什么是“控制层给执行层的本轮计划”。
  • 知道 model execution 完成后，ModelRunnerOutput 还要通过 scheduler.update_from_output(...) 更新 request 状态。
  • 区分“Request 的逻辑状态”与“GPU 上真正执行的 tensor batch”。
  • 知道当前 GPU worker 会在 V2/V1 ModelRunner 实现之间选择，源码阅读先看 selector，再进 runner。
01 · ONE REQUEST THROUGH ONE ENGINE ITERATION

把 vLLM 先看成一个闭环：控制平面决定工作，执行平面把计划变成 GPU 工作，结果再回来改 request state。

下面这张图只保留第一次读源码最重要的边界。上半部分是 request state、调度与 KV ownership；下半部分是 executor/worker/runner 与 GPU execution。中间真正穿过边界的是 SchedulerOutput，而执行完成后的结果必须回到 update_from_output 才算闭环。

vLLM V1 · REQUEST LOOPcontrol plane → execution plane → state update
读源码时始终追两个对象：SchedulerOutput 向下把“这一轮要做什么”交给执行层；ModelRunnerOutput 向上把“这一轮做出了什么”交回状态机。KVCacheManager 则留在 scheduler 一侧，负责把逻辑 token 进度约束到真实 physical block capacity。

这张图故意没有把 Application Programming Interface (API，应用程序编程接口) server、tokenizer、structured output、speculative decoding、multimodal、distributed executor 的所有细节都塞进来。架构图首先回答 ownership 和调用边界；复杂 feature 以后再挂到这个骨架上。

02 · CONTROL PLANE VS GPU EXECUTION

先分清“决定算什么”和“真正把 tensor 算掉”。

CONTROL SIDERequest / Scheduler / KV metadata这里主要处理逻辑状态：谁在 waiting、谁 running、已有多少 computed tokens、需要多少新 blocks、本轮 token budget 还剩多少。
EXECUTION SIDEWorker / ModelRunner / kernels这里把 scheduler 的计划变成 GPU tensors、block tables、attention metadata，然后真正运行模型、attention backend 和采样。

这条边界很重要。以后你看到一个性能问题，要先判断它发生在 scheduler 的决策、Central Processing Unit (CPU，中央处理器)→GPU metadata 准备，还是实际 CUDA kernel 执行。三种问题的优化方向完全不同。

03 · ENGINECORE OWNS THE LOOP

EngineCore.step() 把 schedule → execute → update 串成一次 engine iteration。

当前 vLLM V1 的 vllm/v1/engine/core.py 可以直接看到：有请求时先调用 scheduler.schedule(...)，把得到的 scheduler_output 交给 model_executor.execute_model(..., non_block=True)；模型结果回来后，再调用 scheduler.update_from_output(scheduler_output, model_output)。这不是教学伪代码，而是当前主循环的实际骨架。

STEP 1has requests?EngineCore 判断 scheduler 是否还有工作。
STEP 2schedule()生成 SchedulerOutput。
STEP 3execute_model()executor / worker 运行设备工作。
STEP 4model output取得执行/采样结果。
STEP 5update_from_output()状态写回，再进入下一 iteration。
当前源码入口：vllm/v1/engine/core.py。第一次只定位 EngineCore.step() 中的 schedule → execute_model → update_from_output 三个调用。
04 · SCHEDULEROUTPUT IS A CONTRACT

Scheduler 不负责 GEMM；它负责告诉执行层“这一轮应该怎么组工作”。

Scheduler 的核心产物不是一串 CUDA kernel，而是一份本轮计划。它表达哪些 requests 是新来的/已经缓存的、每个请求要推进多少 token、KV block state、可能的 encoder input、spec decode 信息等。

REQUEST STATEwaiting / running / cached
→
SCHEDULERtoken + KV budgets
→
OUTPUTSchedulerOutput

把它理解成“控制平面与设备执行之间的 contract”最有用。之后读 ModelRunner，只需要继续追问：这份 request-level plan 怎样变成 input tensors、block tables 和 attention metadata？

05 · KVCACHEMANAGER LIVES NEXT TO THE SCHEDULER

Scheduler 想推进 token，必须先证明“有地方放这些 token 的 KV”。

当前 V1 的 KVCacheManager 是 scheduler 一侧的内存管理组件。它回答 prefix 命中、已有 computed blocks、新 block allocation 与 free；Scheduler 再据此决定本轮 request 能否真的推进。

SCHEDULER ASKS这个 request 已经缓存多少？还要推进多少？先做 prefix/computed-block 查询，再计算本轮新增 KV capacity。
KV MANAGER ANSWERS这些 physical block IDs 可以给你。如果 block 不够，scheduler 不能假装显存无限；必须改变本轮计划或进入 preemption/resource-management 路径。
当前源码：vllm/v1/core/kv_cache_manager.py。07.3 会专门把 block ownership 和 allocation 生命周期拆开。
06 · GPU WORKER SELECTS THE ACTUAL MODELRUNNER PATH

不要再把 GPUModelRunner 绑定到一个永久文件名。

当前 vllm/v1/worker/gpu_worker.py 保存 self.use_v2_model_runner = vllm_config.use_v2_model_runner。构造 runner 时，为 true 会导入 vllm/v1/worker/gpu/model_runner.py 的 GPUModelRunner；否则导入 vllm/v1/worker/gpu_model_runner.py 的旧 V1 runner。两条实现会继续演化，但稳定职责仍是：把 SchedulerOutput 变成设备执行所需 tensors/metadata 并运行模型。

输入：逻辑计划request IDs、scheduled token counts、KV block IDs、sampling/structured/spec decode 等执行信息。
输出：模型结果模型/采样结果以及让 scheduler 能继续更新 request state 的信息。
“vLLM V1 engine”与“V1/V2 GPUModelRunner”不是同一层版本名。

当前两条 runner 都位于 vllm/v1/worker/ 体系里。源码阅读必须先看 gpu_worker.py 的 selector，再进入当前配置真正使用的 runner。

08 · WALK ONE REQUEST

最后用一个 1000-token prompt，把前面的组件串一次。

ARRIVAL请求被转换成内部 Request，初始处在等待状态。
SCHEDULEScheduler 决定先给它多少 prefill tokens，并检查 token budget / KV capacity。
ALLOCATEKVCacheManager 返回这批 tokens 将写入的 blocks。
EXECUTE当前被选中的 ModelRunner 根据 SchedulerOutput 构造 input tensors 与 block-table/addressing metadata，跑本轮工作。
UPDATEModelRunnerOutput 回来后，scheduler 更新 computed-token 进度与 request state。
REPEAT下一轮可能继续 prefill chunk，也可能进入 baseline decode；spec decode 等模式会改变单步 token 数。
CHECKPOINT07.1

先会画职责边界，再继续看 scheduler。

1. Scheduler 和 GPUModelRunner 最本质的区别是什么？
Scheduler 在控制层决定本轮哪些请求各推进多少 token、需要哪些 KV blocks；GPUModelRunner 把这份计划变成 GPU tensors/metadata 并真正执行模型。
2. 为什么 Scheduler 不能只看“有请求就塞进 batch”，还必须问 KVCacheManager？
因为推进需要缓存的 token 必须有可写 KV slots。KV capacity 是硬资源约束，allocation 结果会直接限制 schedule。
3. EngineCore 的主循环可以压成哪三段？
scheduler.schedule() 生成计划 → model_executor.execute_model() 执行 → scheduler.update_from_output() 把结果写回 request state。
4. 为什么读 GPUModelRunner 前先看 gpu_worker.py？
因为当前 GPU Worker 会根据 use_v2_model_runner 在 V2 与旧 V1 runner 实现之间选择。直接背一个文件路径可能读到并非当前配置使用的实现。
