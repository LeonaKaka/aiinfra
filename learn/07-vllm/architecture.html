LESSON 07.1 · VLLM约 65 min

vLLM 架构：先顺着一个请求走完系统，再读任何一个大文件。

vLLM 的代码量已经很大，直接打开某个 ModelRunner 或 scheduler.py 很容易迷路。最好的入口不是“哪个文件最核心”，而是先回答：一个请求进入 EngineCore 后，谁决定本轮算多少 token？谁分配 KV 块？谁把计划整理成图形处理器（GPU）可执行的张量？结果怎样回到调度器，让同一个请求在下一轮继续前进？

这节课结束时，你应该能做到：
  • 把 vLLM V1 粗分成请求/控制层、调度与 KV 管理层、执行层。
  • 知道 EngineCore、Scheduler、KVCacheManager、执行器/工作进程、GPUModelRunner 的职责边界。
  • 理解 SchedulerOutput 为什么是“控制层给执行层的本轮计划”。
  • 知道模型执行完成后，ModelRunnerOutput 还要通过 scheduler.update_from_output(...) 更新请求状态。
  • 区分“请求的逻辑状态”与“GPU 上真正执行的张量批次”。
  • 知道当前 GPU 工作进程会在 V2/V1 ModelRunner 实现之间选择，源码阅读先看选择逻辑，再进入对应实现。
01 · 一个请求的一轮系统执行

把 vLLM 先看成一个闭环：控制平面决定工作，执行平面把计划变成 GPU 工作，结果再回来改请求状态。

下面这张图只保留第一次读源码最重要的边界。上半部分是请求状态、调度与 KV 归属关系；下半部分是执行器/工作进程/运行器与 GPU 执行。中间真正穿过边界的是 SchedulerOutput，而执行完成后的结果必须回到 update_from_output 才算闭环。

vLLM V1 · 请求 LOOP控制层 → 执行 plane → state update
读源码时始终追两个对象：SchedulerOutput 向下把“这一轮要做什么”交给执行层；ModelRunnerOutput 向上把“这一轮做出了什么”交回状态机。KVCacheManager 则留在调度器一侧，负责把逻辑 token 进度约束到真实物理块容量。

这张图故意没有把应用程序编程接口（API） server、tokenizer、structured output、speculative decoding、multimodal、distributed 执行器的所有细节都塞进来。架构图首先回答归属关系和调用边界；复杂 feature 以后再挂到这个骨架上。

02 · 控制面与 GPU 执行面

先分清“决定算什么”和“真正把张量算掉”。

CONTROL SIDE请求 / 调度器 / KV 元数据这里主要处理逻辑状态：谁在 waiting、谁 running、已有多少 computed tokens、需要多少新块、本轮 token budget 还剩多少。
EXECUTION SIDE工作进程 / ModelRunner / 内核s这里把调度器的计划变成 GPU 张量、块 tables、attention 元数据，然后真正运行模型、Attention 后端和采样。

这条边界很重要。以后你看到一个性能问题，要先判断它发生在调度器的决策、中央处理器（CPU）→GPU 元数据准备，还是实际 CUDA 内核执行。三种问题的优化方向完全不同。

03 · EngineCore 管理主循环

EngineCore.step() 把 schedule → execute → update 串成一次 engine 执行轮次。

当前 vLLM V1 的 vllm/v1/engine/core.py 可以直接看到：有请求时先调用 scheduler.schedule(...)，把得到的 scheduler_output 交给 model_executor.execute_model(..., non_block=True)；模型结果回来后，再调用 scheduler.update_from_output(scheduler_output, model_output)。这不是教学伪代码，而是当前主循环的实际骨架。

STEP 1has 请求?EngineCore 判断调度器是否还有工作。
STEP 2schedule()生成 SchedulerOutput。
STEP 3execute_model()执行器 / 工作进程运行设备工作。
STEP 4model output取得执行/采样结果。
STEP 5update_from_output()状态写回，再进入下一执行轮次。
当前源码入口：vllm/v1/engine/core.py。第一次只定位 EngineCore.step() 中的 schedule → execute_model → update_from_output 三个调用。
04 · SchedulerOutput 是执行契约

调度器不负责 GEMM；它负责告诉执行层“这一轮应该怎么组工作”。

调度器的核心产物不是一串 CUDA 内核，而是一份本轮计划。它表达哪些请求是新来的/已经缓存的、每个请求要推进多少 token、KV 块 state、可能的 encoder input、spec decode 信息等。

请求 STATEwaiting / running / cached
→
调度器token + KV budgets
→
OUTPUTSchedulerOutput

把它理解成“控制平面与设备执行之间的 contract”最有用。之后读 ModelRunner，只需要继续追问：这份请求-level plan 怎样变成 input 张量、块 tables 和 attention 元数据？

05 · KVCacheManager 为什么靠近调度器

调度器想推进 token，必须先证明“有地方放这些 token 的 KV”。

当前 V1 的 KVCacheManager 是调度器一侧的内存管理组件。它回答 prefix 命中、已有 computed 块、新块分配与 free；调度器再据此决定本轮请求能否真的推进。

调度器 ASKS这个请求已经缓存多少？还要推进多少？先做 prefix/computed-块查询，再计算本轮新增 KV 容量。
KV MANAGER ANSWERS这些物理块 IDs 可以给你。如果块不够，调度器不能假装显存无限；必须改变本轮计划或进入抢占/resource-management 路径。
当前源码：vllm/v1/core/kv_cache_manager.py。07.3 会专门把块归属关系和分配生命周期拆开。
06 · GPU 工作进程如何选择真正的 ModelRunner 路径

不要再把 GPUModelRunner 绑定到一个永久文件名。

当前 vllm/v1/worker/gpu_worker.py 保存 self.use_v2_model_runner = vllm_config.use_v2_model_runner。构造运行器时，为 true 会导入 vllm/v1/worker/gpu/model_runner.py 的 GPUModelRunner；否则导入 vllm/v1/worker/gpu_model_runner.py 的旧 V1 运行器。两条实现会继续演化，但稳定职责仍是：把 SchedulerOutput 变成设备执行所需张量/元数据并运行模型。

输入：逻辑计划请求 IDs、scheduled token counts、KV 块 IDs、sampling/structured/spec decode 等执行信息。
输出：模型结果模型/采样结果以及让调度器能继续更新请求状态的信息。
“vLLM V1 engine”与“V1/V2 GPUModelRunner”不是同一层版本名。

当前两条运行器都位于 vllm/v1/worker/ 体系里。源码阅读必须先看 gpu_worker.py 的选择逻辑，再进入当前配置真正使用的运行器。

08 · 跟踪一个请求

最后用一个 1000-token prompt，把前面的组件串一次。

ARRIVAL请求被转换成内部请求，初始处在等待状态。
SCHEDULE调度器决定先给它多少 prefill tokens，并检查 token budget / KV 容量。
ALLOCATEKVCacheManager 返回这批 tokens 将写入的块。
EXECUTE当前被选中的 ModelRunner 根据 SchedulerOutput 构造 input 张量与块-table/addressing 元数据，跑本轮工作。
UPDATEModelRunnerOutput 回来后，调度器更新 computed-token 进度与请求状态。
REPEAT下一轮可能继续 prefill chunk，也可能进入 baseline decode；spec decode 等模式会改变单步 token 数。
CHECKPOINT07.1

先会画职责边界，再继续看调度器。

1. 调度器和 GPUModelRunner 最本质的区别是什么？
调度器在控制层决定本轮哪些请求各推进多少 token、需要哪些 KV 块；GPUModelRunner 把这份计划变成 GPU 张量/元数据并真正执行模型。
2. 为什么调度器不能只看“有请求就塞进批次”，还必须问 KVCacheManager？
因为推进需要缓存的 token 必须有可写 KV slots。KV 容量是硬资源约束，分配结果会直接限制 schedule。
3. EngineCore 的主循环可以压成哪三段？
scheduler.schedule() 生成计划 → model_executor.execute_model() 执行 → scheduler.update_from_output() 把结果写回请求状态。
4. 为什么读 GPUModelRunner 前先看 gpu_工作进程.py？
因为当前 GPU 工作进程会根据 use_v2_model_runner 在 V2 与旧 V1 运行器实现之间选择。直接背一个文件路径可能读到并非当前配置使用的实现。
