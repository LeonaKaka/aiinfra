LESSON 07.1 · VLLM约 60 min

vLLM Architecture：先顺着一个 request 走完系统，再读任何一个大文件。

vLLM 的代码量已经很大，直接打开 gpu_model_runner.py 或 scheduler.py 很容易迷路。最好的入口不是“哪个文件最核心”，而是先回答：一个请求进来后，谁把它变成内部 Request？谁决定本轮算多少 token？谁分配 KV blocks？谁真正调用 GPU 模型？结果又怎样回到 scheduler？

这节课结束时，你应该能做到：
  • 把 vLLM V1 粗分成请求/控制层、调度与 KV 管理层、执行层。
  • 知道 EngineCore、Scheduler、KVCacheManager、executor/worker、GPUModelRunner 的职责边界。
  • 理解 SchedulerOutput 为什么是“控制层给执行层的本轮计划”。
  • 知道一次 model execution 完成后，输出还要回到 scheduler 更新 request 状态。
  • 区分“Request 的逻辑状态”与“GPU 上真正执行的 tensor batch”。
  • 有一张当前 vLLM V1 源码地图，不再从仓库根目录乱翻。
01 · ONE SENTENCE FIRST

vLLM 的核心循环可以先压成一句话：调度一批 tokens → 分好 KV → 执行模型 → 更新请求 → 再调度。

REQUESTEngine / EngineCore接收内部请求，维护 engine 循环。
PLANScheduler决定本轮哪些 requests 各算多少 token。
MEMORYKVCacheManager查 prefix、申请/回收 KV blocks。
EXECUTEExecutor / Worker把 schedule 送到实际设备执行。
GPUGPUModelRunner组 batch、准备 block table、跑模型。
UPDATEoutputs采样结果回到 scheduler，request 前进一步。

真实代码还有 API server、tokenizer、structured output、speculative decoding、multimodal、distributed executor 等很多层。但对“先读懂 vLLM”来说，上面这条数据/控制链是最值得先固定的骨架。

02 · CONTROL PLANE VS GPU EXECUTION

先分清“决定算什么”和“真正把 tensor 算掉”。

CONTROL SIDERequest / Scheduler / KV metadata这里主要处理逻辑状态：谁在 waiting、谁 running、已有多少 computed tokens、需要多少新 blocks、本轮 token budget 还剩多少。
EXECUTION SIDEWorker / ModelRunner / kernels这里把 scheduler 的计划变成 GPU tensors、block tables、attention metadata，然后真正运行模型、attention backend 和采样。

这条边界很重要。以后你看到一个性能问题，要先判断它发生在 scheduler 的决策、CPU→GPU metadata 准备，还是实际 CUDA kernel 执行。三种问题的优化方向完全不同。

03 · ENGINECORE OWNS THE LOOP

EngineCore 像调度与执行之间的总循环控制器。

当前 vLLM V1 的 vllm/v1/engine/core.py 里可以直接看到核心节奏：当 scheduler 里有请求时，先调用 scheduler.schedule(...) 生成本轮计划，再让 model_executor.execute_model(scheduler_output) 执行；拿到结果后调用 scheduler 的 update 路径，把生成 token、完成状态等写回。

STEP 1has requests?EngineCore 看 scheduler 是否还有工作。
STEP 2schedule()生成 SchedulerOutput。
STEP 3execute_model()executor / worker 真正运行 GPU。
STEP 4sample / output拿到 token 或模型结果。
STEP 5update状态写回，进入下一 iteration。
当前源码入口：vllm/v1/engine/core.py。不要一开始试图理解整个文件，只先定位 scheduler.schedule、model_executor.execute_model、scheduler output update 这条主链。
04 · SCHEDULEROUTPUT IS A CONTRACT

Scheduler 不负责 GEMM；它负责告诉执行层“这一轮应该怎么组工作”。

Scheduler 的核心产物不是一串 CUDA kernel，而是一份本轮计划。它里面会表达哪些 requests 是新来的/已经缓存的、每个请求要推进多少 token、KV block state、可能的 encoder input、spec decode 信息等。

REQUEST STATEwaiting / running / cached
→
SCHEDULERtoken + KV budgets
→
OUTPUTSchedulerOutput

把它理解成“控制平面和数据平面之间的接口”非常有用。之后读 ModelRunner 时，你只需要问：它怎样把这份计划翻译成 GPU batch？

05 · KVCACHEMANAGER LIVES NEXT TO THE SCHEDULER

Scheduler 想推进 token，必须先证明“有地方放这些 token 的 KV”。

当前 V1 的 KVCacheManager 明确是 scheduler 一侧的内存管理组件。源码里的 KVCacheBlocks 文档甚至直接写着：它是 KVCacheManager 和 Scheduler 之间的 allocation result interface。

SCHEDULER ASKS这个 request 已经缓存多少？还要推进多少？先做 prefix hit / computed-block 查询，再算本轮需要新增多少 KV slots。
KV MANAGER ANSWERS这些 physical block IDs 给你。如果 block 不够，scheduler 不能假装显存无限；必须停、跳过或触发 preemption 路径。
当前源码：vllm/v1/core/kv_cache_manager.py，其中定义了 KVCacheBlocks 与 KVCacheManager。下一课后的 07.3 会专门把这层拆开。
06 · GPUMODELRUNNER IS WHERE THE PLAN BECOMES TENSORS

真正进入 GPU 前，系统还要把 request 级元数据压成一批连续可执行的 tensor 工作。

GPUModelRunner 位于 vllm/v1/worker/gpu_model_runner.py。它会维护 GPU input batch、block table、attention metadata、模型、KV cache 等大量执行期状态。这个文件非常大，所以现在只给它一个角色定义：把 SchedulerOutput 变成可运行的 GPU batch，并执行模型。

输入：逻辑计划request IDs、scheduled token counts、KV block IDs、sampling/structured/spec decode 等执行信息。
输出：模型结果logits / sampled token / hidden or pooling results，以及让 scheduler 能继续更新状态的信息。
不要把“GPUModelRunner 很大”理解成“应该先读它”。

恰恰相反：先掌握 scheduler、KV blocks、block table 这几个输入对象，再读 ModelRunner，很多代码才有上下文。

08 · WALK ONE REQUEST

最后用一个 1000-token prompt，把前面的组件串一次。

ARRIVAL请求被转换成内部 Request，初始处在等待状态。
SCHEDULEScheduler 决定先给它多少 prefill tokens，并检查 token budget / KV capacity。
ALLOCATEKVCacheManager 返回这批 tokens 将写入的 blocks。
EXECUTEModelRunner 根据 SchedulerOutput 构造 input 与 block table，跑 prefill。
UPDATE请求的 computed-token 进度增加；下一轮可能继续 prefill chunk，也可能开始 decode。
REPEAT每个 decode iteration 再推进 token，直到 finish，然后释放/缓存对应 KV blocks。
CHECKPOINT07.1

先会画职责边界，再继续看 scheduler。

1. Scheduler 和 GPUModelRunner 最本质的区别是什么？
Scheduler 在控制层决定本轮哪些请求各推进多少 token、需要哪些 KV blocks；GPUModelRunner 把这份计划变成 GPU tensors/metadata 并真正执行模型。
2. 为什么 Scheduler 不能只看“有请求就塞进 batch”，还必须问 KVCacheManager？
因为每推进一个需要缓存的 token，都必须有可写的 KV slot。KV capacity 是硬资源约束，不够时请求就不能按原计划继续运行。
3. EngineCore 的主循环可以压成哪四步？
Schedule → Execute → Process/Sample Output → Update request/scheduler state，然后进入下一轮。
