LESSON 08.1 · KV CONNECTOR约 65 min

为什么要搬 KV：Prefill GPU 已经算完了，Decode GPU 为什么不能“直接接着生成”？

我们终于到最初的目标。06 已经知道 Prefill 和 Decode 是两种不同 workload，07 又知道 Decode 必须依赖历史 KV Cache。现在把它们放到不同 vLLM instances：Prefill 在 GPU A 完成后，真正能让 GPU B 接着 decode 的不是一句“prompt 已经算完”，而是每一层、每个已计算 token 对应的 KV 状态，以及能把这些状态装进 B 本地 paged KV buffer 的元数据。

这节课结束时，你应该能做到：
  • 从自回归 Attention 推导为什么跨实例 handoff 必须包含 KV，而不能只传最后一个 token。
  • 解释 Prefill/Decode disaggregation 的主要目标：独立调 TTFT/ITL、隔离 Prefill 对 tail ITL 的干扰。
  • 知道 vLLM 官方明确说明 disaggregated prefill 本身不自动提高 throughput。
  • 区分“请求路由”“KV 数据传输”“KV 元数据协调”三件不同的事。
  • 用 KV bytes 估算 transfer 是否可能成为关键路径。
  • 知道 producer/consumer 是 connector 里的角色，不等同于 scheduler/worker 进程角色。
01 · DECODE NEEDS STATE

Decode GPU 需要的不是“Prefill 已完成”这个事实，而是 Prefill 留下来的 Attention 状态。

对第 t+1 个 token，Attention 要用当前 Qₜ₊₁ 去访问此前 token 的 K₀…Kₜ 和 V₀…Vₜ。如果 GPU B 没有这些 K/V，它只有两个选择：重新对 prompt 做一次 Prefill，或者把 A 已经计算好的 KV 拿过来。

GPU A · PREFILLprompt → K/V for all prompt tokens每层的 KV 已经写进 A 的 paged KV blocks。
KV state→
GPU B · DECODEnew Q + historical K/V拿到历史 KV 后才可以从下一 token 接着算。

只传 token IDs 不够。Token IDs 能让 B 重新计算 KV，但那等于把 Prefill 又做了一遍；P/D 分离的意义就被抵消了。

02 · WHY DISAGGREGATE PREFILL

把两阶段拆开，首先是为了让两类 latency 目标不再互相绑死。

SHARED INSTANCEPrefill + Decode 混在同一资源池长 Prefill 进入时可能干扰正在 Decode 的请求。你用同一套 TP/PP、batching 和 GPU capacity 同时服务 TTFT 与 ITL。
DISAGGREGATEDPrefill 与 Decode 用不同 instances可以分别选择并行度、容量和调度目标；Prefill load 不必直接插进 Decode GPU 的关键路径。

当前 vLLM 官方文档给出的两个主要动机就是：分别调 TTFT 与 ITL，以及控制 tail ITL。Chunked Prefill 也能缓解干扰，但 P/D 分离提供了更强的资源隔离。

当前官方源码文档：docs/features/disagg_prefill.md。该页把功能标为 experimental，并明确列出独立调 TTFT/ITL 和控制 tail ITL 两个主要原因。
03 · NOT A FREE THROUGHPUT WIN

多一组机器 + 多一次 KV transfer，不会凭空制造更多有效计算。

vLLM 当前文档直接强调：Disaggregated prefill DOES NOT improve throughput.这句话很重要，因为 P/D 分离新增了 transfer、路由、握手、等待、额外实例利用率等成本。

YOU GAIN资源隔离、独立扩容、TTFT/ITL 独立调优空间。
YOU PAYKV 网络流量、connector bookkeeping、handoff latency、额外故障模式。
NET RESULT是否值得取决于 workload 与 SLO，而不是“架构更复杂所以一定更快”。
04 · THREE DIFFERENT PROBLEMS

“把 Prefill 交给 Decode”其实至少包含三条链。

REQUEST ROUTING同一个请求先去哪，再去哪？Proxy/router 要先发 Prefill，再把 handoff 信息带给正确的 Decode instance。
DATA PLANE真正的 KV bytes 怎么走？GPU→GPU、GPU→host→network→GPU，还是通过 NIXL/UCX/RDMA 等路径。
CONTROL / METADATADecode 怎么知道拿什么、何时可用？request identity、remote block info、engine/worker identity、layout compatibility、completion state。

这三者经常被一句“KV transfer”混在一起。读 Connector 源码时要一直区分：这是控制消息，还是大块 tensor bytes？

05 · HOW BIG IS THE HANDOFF?

先用 06.3 的公式估一遍，transfer latency 才有数量级概念。

假设 32 层、4096 prompt tokens、8 个 KV heads、head_dim=128、BF16：

2 × 32 × 4096 × 8 × 128 × 2 bytes=512 MiB KV

如果有效端到端 KV transfer bandwidth 只有 10 GiB/s，光搬 512 MiB 的理想数据时间就约 50 ms；20 GiB/s 约 25 ms。真实系统还会有握手、队列、同步、metadata、协议与拓扑开销。

这只是教学估算。

不同模型的 KV layout、GQA/MLA、TP、数据类型、只传命中部分、block 对齐等都会改变实际 bytes。正确做法是先算理论量级，再在真实链路上测 connector transfer。

06 · TWO KINDS OF ROLES

kv_producer/kv_consumer 和 SCHEDULER/WORKER 是两个正交概念。

DATA ROLEProducer / ConsumerPrefill instance 通常是 KV producer；Decode instance 通常是 KV consumer。描述“KV 从谁到谁”。
PROCESS ROLEScheduler connector / Worker connector同一个 vLLM instance 内，scheduler process 有 connector 控制部分，每个 worker process 还有 connector 执行部分。描述“控制逻辑在哪，数据操作在哪”。

所以一个 Prefill instance 里既有 producer-side scheduler connector，也有 producer-side worker connectors。下一课会把这四个角画完整。

CHECKPOINT08.1

先确认你知道为什么 Connector 必须存在。

1. Prefill GPU 把最后一个 token ID 发给 Decode GPU，够不够？
不够。Decode 的 Attention 需要整个历史 prefix 的每层 K/V。只有 token IDs 时，Decode 仍必须重新 Prefill 才能重建这些状态。
2. P/D 分离为什么不等于吞吐自动提升？
因为它主要换来资源隔离和 latency 独立调优，同时新增 KV transfer、路由和同步成本。官方文档也明确说 disaggregated prefill 本身不提高 throughput。
3. Producer/consumer 与 scheduler/worker role 有什么区别？
前者描述 KV 数据角色（谁生产、谁消费）；后者描述同一 instance 内 Connector 代码运行在哪类进程（scheduler 控制还是 worker 数据执行）。
