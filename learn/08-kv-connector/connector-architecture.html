LESSON 08.2 · KV CONNECTOR约 75 min

Connector Architecture：一套 KV transfer 为什么要同时住在 Scheduler 和 Worker 两边？

如果只看“网络传 tensor”，你很容易写出一个 send(kv) / recv(kv) demo，却接不进真实 serving。原因是 transfer 必须和 scheduler 的 request 状态、KV block allocation、ModelRunner 的逐层 attention 执行同时协作。vLLM V1 把 Connector 明确拆成 scheduler-side 控制接口和 worker-side 数据接口。

这节课结束时，你应该能做到：
  • 解释为什么 scheduler-side connector 不应该直接负责每层 GPU memcpy。
  • 理解 worker-side connector 为什么和 ModelRunner/Attention execution 贴得更近。
  • 掌握 get_num_new_matched_tokens、update_state_after_alloc、build_connector_meta 三个 scheduler-side 关键步骤。
  • 掌握 start_load_kv、wait_for_layer_load、save_kv_layer、wait_for_save 的 worker-side语义。
  • 理解 ConnectorMetadata 是控制面给执行面的“本轮 transfer plan”。
  • 知道 V1 Base API 当前仍标为 experimental，课程应学职责而不是死背签名。
01 · TWO SIDES

Scheduler 决定“该不该传、传多少、给谁”；Worker 决定“这些 bytes 具体怎么进出 GPU KV buffer”。

SCHEDULER-SIDE CONNECTORControl plane看 Request、local prefix hit、remote match、block allocation；构造本轮 ConnectorMetadata；跟踪 async transfer 是否完成。
WORKER-SIDE CONNECTORData plane绑定 metadata，注册/访问真实 KV tensors，在 forward 前/逐层/forward 后发起 load/save，向 scheduler 回报完成状态。

这是一个很自然的边界：Scheduler 本来就知道“请求逻辑”；Worker 本来就拥有 GPU memory 和 attention layer。Connector 只是把两边的职责接起来。

02 · STEP A: ASK REMOTE MATCH

get_num_new_matched_tokens()：先问外部 KV 到底能替我省掉多少本地计算。

07.5 的 local prefix cache 会告诉 scheduler “本机已经算过多少 prefix”。Connector 在此基础上还能回答：外部 KV cache 里，超过本地命中的部分还有多少 tokens 真正可用？

这是最容易被忽略的部分：Connector 不只是“搬数据”，它首先参与 scheduler 对“哪些 token 已经算过”的认知。

03 · STEP B: ALLOCATE DESTINATION FIRST

update_state_after_alloc()：知道要加载远端 KV 后，Decode 端还必须先给它分配本地 blocks。

远端可能说“我有前 1024 tokens 的 KV”，但 Decode GPU 不能把这些 bytes 悬空放着。KVCacheManager 先在本地 paged KV pool 分配目标 blocks，然后 Connector 才能建立 remote source → local destination 的 mapping。

这就是为什么 KV Connector 必须理解 07.3 的 block allocation：接收端的 block IDs 通常和发送端不一样，transfer 要保证语义对应而不是数字相等。

04 · STEP C: BUILD METADATA

build_connector_meta()：把 scheduler 的决定压成 worker 本轮可以执行的 transfer metadata。

IDENTITYWhich request / peer?request ID、engine/worker identity、producer/consumer handoff 参数。
BLOCK / SLOTWhich KV ranges?source/destination blocks、token range、KV cache groups / layout 必要信息。
OPERATIONLoad or save?哪些 request 本轮需要 load，哪些 layer/blocks 需要 save，以及 async tracking 所需标识。

具体 Metadata class 因 Connector 而异；Base 只定义抽象类型。这是刻意的：网络 backend 可以变化，但 scheduler→worker 仍需要一份明确计划。

05 · WORKER-SIDE HOOKS

Worker 接到 metadata 后，transfer 被插进 model forward 的合适位置。

API时机心智模型
start_load_kv()forward 前启动当前 forward 需要的 KV load，可异步。
wait_for_layer_load(layer)attention layer 内某层真正消费 KV 前，确保这层对应 load 已完成。
save_kv_layer(...)attention layer 内该层 KV 产生后立即启动 save/send，给 layer-by-layer overlap 留机会。
wait_for_save()forward 结束前确保必要 save 不会和 paged buffer overwrite 发生数据竞争。
get_finished()后续 step把异步 send/recv 完成的 request IDs 回报给 scheduler。

这组接口已经暴露了 Connector 真正“infra”的地方：它不是一次大拷贝，而是要和 attention layer 生命周期、异步 overlap、KV block 可覆盖时机共同工作。

06 · WHY LAYER-BY-LAYER EXISTS

不一定要等“32 层全部传完”才开始模型执行。

Base API 专门有 wait_for_layer_load 与 save_kv_layer，就是为了支持逐层 pipeline：当 layer 0 的 KV 已到，可以执行 layer 0；同时 layer 1 的 KV 还在传。

timet0t1t2t3t4t5
xferload L0load L1load L2load L3...
computewait L0run L0run L1run L2run L3...

真正能 overlap 多少取决于 connector、backend、layer compute time、传输粒度和 CUDA Graph 模式。Base class 甚至提供 requires_piecewise_for_cudagraph，因为某些逐层 Python/async hook 无法被整段 CUDA Graph 安全捕获。

08 · EXAMPLECONNECTOR BEFORE NIXL

想看懂接口怎样落地，先看 debug 版 ExampleConnector。

当前 example_connector.py 是一个简单的 debug implementation，会把 KV save/load 到共享磁盘。它性能不代表生产方案，但非常适合学习：Metadata 里直接包含 token IDs、block IDs 转成的 slot mapping，以及 store/load flag；worker 侧能看到怎样把 KV 注入 paged memory。

教学源码：example_connector.py。先把这个读懂，再进入 NIXL，会少掉大量 transport 细节干扰。
CHECKPOINT08.2

现在你应该能把 Connector 画成控制面 + 数据面。

1. 为什么 remote match 要在 scheduler-side 查询？
因为 remote match 会改变 scheduler 对“哪些 tokens 已经计算”的判断，从而决定本轮需要计算多少 token、需要申请多少本地 KV blocks。
2. 为什么 load KV 前要先分配本地 destination blocks？
接收的 KV 必须落进 Decode instance 自己的 paged KV layout。远端 source block IDs 与本地 block IDs 不必相同，必须先有目标地址再建立映射。
3. wait_for_layer_load 暗示了什么性能优化？
它允许逐层传输/计算流水：不是等全部层 KV 传完才 forward，而是某层使用前只等待该层所需 KV，从而有机会把后续层传输和当前层计算重叠。
