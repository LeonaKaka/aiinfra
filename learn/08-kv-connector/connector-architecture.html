LESSON 08.2 · KV CONNECTOR约 80 min

Connector 架构：为什么一套 KV 传输要同时存在于调度器侧和工作进程侧？

如果只把问题理解成“通过网络传张量”，你很容易写出一个 send(kv) / recv(kv) 小例子，却很难接入真实在线推理系统。因为传输必须同时配合调度器维护的请求状态、KV 块分配，以及 ModelRunner 的逐层 Attention 执行。vLLM V1 把 Connector 明确拆成调度器侧控制接口和工作进程侧数据接口。

这节课结束时，你应该能做到：
  • 解释为什么调度器侧 Connector 不应该直接负责每层 GPU 的显存拷贝。
  • 理解工作进程侧 Connector 为什么要靠近 ModelRunner/Attention 执行路径。
  • 掌握 get_num_new_matched_tokens、update_state_after_alloc、build_connector_meta 三个调度器侧核心步骤。
  • 掌握 start_load_kv、wait_for_layer_load、save_kv_layer、wait_for_save 的工作进程侧语义。
  • 知道当前基础应用程序接口（API）还包含请求到达/结束、抢占、失败、握手、统计等生命周期钩子，不应把 Connector 缩成四个拷贝函数。
  • 理解 ConnectorMetadata 是控制面交给执行面的“本轮传输计划”，而这套 API 仍处于实验阶段。
01 · Connector 为什么有两侧

调度器决定“该不该传、传多少、给谁”；工作进程决定“这些 bytes 具体怎么进出 GPU KV 缓冲区”。

Connector 横跨控制面和数据面，但两边不做同一件事。先把它们放在同一张架构图里：

KV CONNECTOR · CONTROL + 数据面one 请求 · simplified
关键边界：调度器侧 Connector 改变“哪些 tokens 已经有状态”的认知；工作进程侧 Connector 才真正接触 GPU KV 缓冲区和传输。ConnectorMetadata 是两者之间的执行契约。

这是一个很自然的边界：调度器本来就知道“请求逻辑”；工作进程本来就拥有 GPU 显存和 attention layer。Connector 只是把两边的职责接起来。

02 · 第一步：查询远端命中

get_num_new_matched_tokens()：先问外部 KV 到底能替我省掉多少本地计算。

07.5 的 local prefix cache 会告诉调度器 “本机已经算过多少 prefix”。Connector 在此基础上还能回答：外部 KV cache 里，超过本地命中的部分还有多少 tokens 现在真正可加载？

REMOTE HIT+384 tokens

计算suffix only

Base API 允许这个函数返回 None，表示 Connector 还需要时间才能判断 remote match，调度器应稍后再问；也可以标记这批 remote KV 会异步加载。它还明确要求只报告“调用时实际可加载”的最大 prefix，不能把一个已经失效的索引当成 hit。

这是最容易被忽略的部分：Connector 不只是“搬数据”，它首先参与调度器对“哪些 token 已经算过”的认知。

03 · 第二步：先分配目标 KV 块

update_state_after_alloc()：知道要加载远端 KV 后，Decode 端还必须先给它分配本地块。

远端可能说“我有前 1024 tokens 的 KV”，但 Decode GPU 不能把这些 bytes 悬空放着。KVCacheManager 先在本地 paged KV 池分配目标块，然后 Connector 才能建立 remote source → local destination 的 mapping。

REMOTE SOURCE生产端块 / regionsKV 在 Prefill 实例的地址布局中。

LOCAL DESTINATION消费端块 IDsKVCacheManager 为 remote tokens 分配本地 physical 块。

这就是为什么 KV Connector 必须理解 07.3 的块分配：接收端的块 IDs 通常和发送端不一样，传输要保证语义对应而不是数字相等。当前 Base 还特别说明：即使 blocks 非空，也要依据 num_external_tokens 判断这次到底有没有 external KV 要 load。

04 · 第三步：构造传输元数据

build_connector_meta()：把调度器的决定压成工作进程本轮可以执行的传输元数据。

IDENTITYWhich 请求 / peer?请求 ID、engine/工作进程 identity、生产端/消费端交接参数。
BLOCK / SLOTWhich KV ranges?source/destination 块、token range、KV cache groups / 布局必要信息。
OPERATIONLoad or save?哪些请求本轮需要 load/save，以及异步 tracking 所需标识。

具体元数据 class 因 Connector 而异；Base 只定义抽象类型。当前 Base 明确要求 build_connector_meta() 不修改 SchedulerOutput，并说明调用会重置 connector 的本步状态。网络后端可以变化，但调度器→工作进程仍需要一份清晰、一次性的执行计划。

05 · 工作进程侧生命周期钩子

工作进程接到元数据后，传输被插进 model forward 的合适位置。

API时机心智模型
start_load_kv()forward 前启动当前 forward 需要的 KV load，可异步。
wait_for_layer_load(layer)attention layer 内某层真正消费 KV 前，确保这层对应 load 已完成。
save_kv_layer(...)attention layer 内该层 KV 产生后立即启动 save/send，给 layer-by-layer overlap 留机会。
wait_for_save()forward context 退出前确保异步 save 不会和 paged 缓冲区 overwrite 发生数据竞争。
get_finished()后续 step把异步 send/recv 完成的请求 IDs 回报给调度器。

这组接口已经暴露了 Connector 真正“infra”的地方：它不是一次大拷贝，而是要和 attention layer 生命周期、异步 overlap、KV 块可覆盖时机共同工作。

06 · 为什么要支持逐层就绪

不一定要等“32 层全部传完”才开始模型执行。

Base API 专门有 wait_for_layer_load 与 save_kv_layer，就是为了支持逐层 pipeline：当 layer 0 的 KV 已到，可以执行 layer 0；同时 layer 1 的 KV 还在传。

timet0t1t2t3t4t5
xferload L0load L1load L2load L3...
计算wait L0run L0run L1run L2run L3...

真正能 overlap 多少取决于 connector、后端、layer 计算 time、传输粒度和 CUDA Graph 模式。Base class 甚至提供 requires_piecewise_for_cudagraph，因为某些逐层 Python/异步 hook 无法被整段 CUDA Graph 安全捕获；需要 piecewise graph 才能让这些同步点在 replay 间执行。

08 · 先读 ExampleConnector，再读 NIXL

想看懂接口怎样落地，先看 debug 版 ExampleConnector。

当前 example_connector.py 是一个简单的 debug implementation，会把 KV save/load 到共享磁盘。它性能不代表生产方案，但非常适合学习：元数据里能直接看到 token/块 mapping 与 store/load flag；工作进程侧也更容易观察怎样把 KV 注入 paged 内存。

教学源码：example_connector.py。先把协议闭环读懂，再进入 NVIDIA 推理传输库（NIXL），会少掉大量 transport 细节干扰。
CHECKPOINT08.2

现在你应该能把 Connector 画成控制面 + 数据面 + 生命周期。

1. 为什么 remote match 要在调度器侧查询？
因为 remote match 会改变调度器对“哪些 tokens 已经计算”的判断，从而决定本轮需要计算多少 token、需要申请多少本地 KV 块。
2. 为什么 request_finished() 不是一个可有可无的清理回调？
异步交接时，请求的模型计算结束并不代表 source KV 块已经可以覆盖。Connector 可以在这里接管块的异步释放责任，直到传输完成状态真正确认安全。
3. wait_for_layer_load 暗示了什么性能优化？
它允许逐层传输/计算流水：不是等全部层 KV 传完才 forward，而是某层使用前只等待该层所需 KV，从而有机会把后续层传输和当前层计算重叠。
