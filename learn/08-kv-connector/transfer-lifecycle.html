LESSON 08.3 · KV CONNECTOR约 90 min

传输生命周期：从“远端有 KV”到“这轮 Attention 可以安全读取”，中间发生了什么？

一句 remote hit = 1024 tokens 只是开始。真正的系统要保证：远端那 1024 个 token 对应的 KV 仍然有效；接收端已经分配好目标 KV 块；元数据指向正确的请求、层和 KV 块；异步传输已经启动；对应层真正读取 KV 前，传输已经完成；失败时不会把坏数据当成已计算状态；请求结束或被抢占时也不能让尚未完成的传输读写已经被重新分配的 KV 块。

这节课结束时，你应该能做到：
  • 把一次 KV 加载拆成查询 → 预留 → 规划 → 传输 → 同步 → 提交六个阶段。
  • 解释为什么异步传输需要请求级完成状态和层级就绪状态两种状态。
  • 理解 WAITING_FOR_REMOTE_KVS 的调度意义。
  • 知道生产端 KV 块在异步交接完成前不能贸然释放或覆盖。
  • 知道当前 kv_load_failure_policy 支持 fail 与 recompute，默认策略是 fail。
  • 理解重叠批次和抢占为什么会让 KV 块生命周期成为正确性问题，而不只是显存分配器细节。
01 · 六个阶段

一次远端 KV load，先用六步固定心智模型。

把控制状态、数据传输和块所有权放到同一条时间线上看，才能看清“remote hit”为什么远远不等于“Attention 现在就能读”。

REMOTE KV LOAD · END-TO-END 生命周期消费端-side view · simplified
两个就绪状态：调度器关心请求是否整体可以重新进入运行队列；工作进程关心当前层 的 KV 是否已经到达。它们是不同粒度的状态，不要混成一个“传完了”。

以后不管看 NVIDIA 推理传输库（NIXL）、LMCache、Mooncake 还是自定义 Connector，都先找这六件事分别在哪里实现。

02 · 查询必须真实可信

远端命中 的含义应该是“现在确实能加载”，不是“理论上以前存过”。

基础应用程序编程接口（API） 对 get_num_new_matched_tokens() 的注释非常严格：Connector 应只考虑当前真正可用、可加载的最大前缀。如果因为 淘汰、连通性或其它问题实际拿不到，那些 这些 token 不能算作命中。

错误声明索引声称 2048元数据记得以前存过 2048 个 token，但实际远端块已释放。
后果调度器跳过计算若仍把它当 已计算，Decode 会在未填充/错误 KV 上做 Attention。
正确只声明真正可加载的前缀Connector 必须把“缓存元数据”与“实际可交付性”统一起来。
03 · 异步加载会引入新的请求状态

目标块已经分配，不等于请求立刻可以进入模型前向计算。

如果 Connector 选择异步加载，调度器可以先分配块、发起传输，然后暂时把请求放在等待 远端 KV 的状态。当前 V1 的 RequestStatus 明确包含 WAITING_FOR_REMOTE_KVS，而调度器会在遍历 等待/跳过队列时尝试把把这类被阻塞的请求恢复为可运行状态。

调度器发现远端命中
→
异步传输WAITING_FOR_REMOTE_KVS
→
就绪调度剩余计算

这避免了一个危险竞态：请求已经被当成“前 1024 token 已计算”，但工作进程的 KV 数据 还在路上。

04 · 两级就绪状态

“整个请求传输完成”与“当前层 可以继续”不是同一个粒度。

请求级get_finished() / Connector 输出异步 发送/接收 的请求是否整体完成，用于调度器更新等待状态、释放责任或继续下一步。
层级wait_for_layer_load(layer)当前 Attention 层 是否已经拿到它自己的 KV；允许后续层还在传。

层级就绪状态是 重叠 的关键；请求级就绪状态是控制状态闭环的关键。两种都需要，才能既快又正确。

05 · 生产端 KV 块的生命周期

Prefill 完成后，那些 KV 块什么时候才可以被覆盖？

如果传输是同步拷贝，最简单：拷贝返回后 source 就可以释放。但异步远程直接内存访问（RDMA）/read/write 下，source 内存在 remote 消费端真正读取完成前不能被分配器拿去写新请求。

生产端请求 finished模型计算结束，但块可能仍承担交接 source。
异步传输 pending⏳
消费端read complete完成/通知后生产端才能安全交还块。

Base API 的 request_finished() 允许 Connector 返回“我异步接管块的释放责任”。这正是为了防止 source 被过早覆盖。

内存 lifetime 是传输正确性的一部分。网络库再快，如果 source/destination 缓冲区的所有权时序错了，结果仍然会随机损坏。

06 · 四类标识必须一一对应

KV 传输的元数据，本质上是在证明“这批 bytes 就是这个请求这一段状态”。

请求 IDENTITY谁的 KV？请求/会话以及对应生产端 engine/工作进程。
TOKEN IDENTITY覆盖哪段 prefix？token sequence/hash/范围必须对应，不能拿错 prefix。
内存 MAPPING从哪块到哪块？remote region/块/offset → local 块/slot。
布局 COMPAT字节怎样解释？K/V 布局、dtype、model/layer/张量并行（TP） 配置等必须兼容。
READINESS传完了吗？句柄/event/完成状态 state。
LIFETIME还能读多久？租约/ref count/归属关系，避免 source 过期。
07 · 传输失败不能被隐藏

某些块 load 失败时，最危险的行为是继续把它当作 cache hit。

CONNECTIVITYpeer / transport 失败握手失败、连接断开、remote engine 已重启。
内存source expired / overwrite租约到期、块被回收、mapping 过期。
COMPATIBILITY布局 / TP mismatch模型、KV 布局或并行映射不满足 connector 能力。

Base API 提供 get_block_ids_with_load_errors()，要求异步失败也必须报告。当前 KVTransferConfig.kv_load_failure_policy 有两种明确策略：fail（默认）立即以错误结束请求；recompute 则重新调度请求，把失败的 远端 KV 当作需要本地重算的状态。

注意：这是“KV load 失败 policy”，不是 07.5 的一般 KV-capacity 抢占 mode。

两者都可能导致 recompute，但触发原因不同：一个是远端 KV 加载失败，一个是本地调度因资源不足 preempt。

08 · 抢占与批次重叠会引入内存风险

当传输、前一批 GPU 写入和下一批块重用重叠时，“free”不能只看请求状态。

当前调度器初始化 Connector 时有两条很值得学习的 safety rail：

RELIABLE 交接requires_kv_delivery某些 Connector 要求交接必须可靠完成；抢占时调度器会让 connector/工作进程丢弃不再可信的 stale in-flight output，而不是让它继续写入已经释放的块。
MULTIPLE IN-FLIGHT BATCHESdefer_block_free当异步调度 / 流水线并行（PP） 允许多个批次同时在飞、且本机是 KV 消费端时，调度器会延后块 free，避免新 remote load 与旧批次对同一被重用块的写入发生竞争。

这两条看似很工程化，但其实都来自同一个不变量：一个 physical 块只有在所有仍可能访问它的 execution / 传输都结束后，才真正安全地交给下一任 owner。

当前实现入口：vllm/v1/core/sched/调度器.py 的 Connector 初始化与抢占路径；Base 协议见 KVConnectorBase_V1。

能画出状态机和归属关系，才算真的懂“异步 KV 传输”。

1. 为什么 remote hit 不能只看一个历史索引？
因为调度器会据此跳过本地计算。Connector 必须保证声称命中的 KV 当前真实可加载；否则会把未到/已失效的数据当作已计算状态。
2. 当前 远端 KV load 失败默认会自动 recompute 吗？
不会。当前 KVTransferConfig 的 kv_load_failure_policy 默认是 fail；只有显式选择 recompute 时，调度器才按重算路径恢复失败块。
3. 为什么多个 in-flight batches 时可能要延后 free KV 块？
因为请求逻辑上结束或被移出 running，不代表旧批次的 GPU 写入已经停止。若块立刻重用并同时被 remote load 填充，就可能和旧写入发生数据竞争，所以需要延迟归属关系转移。
