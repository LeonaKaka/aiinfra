LESSON 08.3 · KV CONNECTOR约 80 min

Transfer Lifecycle：从“远端有 KV”到“这轮 Attention 可以安全读它”，中间到底发生了什么？

一句 remote hit = 1024 tokens 只是开始。真正的系统要保证：远端那 1024 tokens 仍然有效；接收端已经分配目标 blocks；metadata 指向正确 request/layer/block；异步 copy 已启动；对应 layer 用到 KV 前 copy 已完成；失败时不会把坏数据当成已计算状态。把这条生命周期串起来，KV Connector 才从“网络 API”变成 serving component。

这节课结束时，你应该能做到：
  • 把一次 KV load 拆成 query → reserve → plan → transfer → synchronize → commit 六个阶段。
  • 解释为什么 async transfer 需要 request-level completion 与 layer-level readiness 两种状态。
  • 理解 WAITING_FOR_REMOTE_KVS 的调度意义。
  • 知道 producer blocks 在异步 handoff 完成前可能不能立刻 free/overwrite。
  • 理解 transfer failure 不能只打日志：scheduler 必须知道哪些 blocks 无效或需要 recompute/fail。
  • 解释 request identity、token identity、block mapping、layout compatibility 四类 metadata 为什么缺一不可。
01 · SIX STAGES

一次远端 KV load，先用六步固定心智模型。

1QUERY远端有多少 prefix KV 真正可读？
2RESERVE接收端为这些 tokens 分配本地 blocks。
3PLAN构造 source→destination metadata。
4TRANSFERworker 发起 async read/write/copy。
5WAIT使用某层 KV 前确认该层已到。
6COMMITworker/scheduler 确认完成，请求恢复正常计算。

以后不管看 NIXL、LMCache、Mooncake 还是自定义 Connector，都先找这六件事分别在哪里实现。

02 · QUERY MUST BE TRUTHFUL

Remote hit 的含义应该是“现在确实能加载”，不是“理论上以前存过”。

Base API 对 get_num_new_matched_tokens() 的注释非常严格：Connector 应只考虑当前真正可用、可加载的最大 prefix。如果因为 eviction、连通性或其它问题实际拿不到，那些 tokens 不能算进 hit。

BAD CLAIMindex says 2048元数据记得以前存过 2048 tokens，但实际远端 blocks 已释放。
CONSEQUENCEscheduler skips compute若仍把它当 computed，Decode 会在未填充/错误 KV 上做 Attention。
CORRECTclaim only loadable prefixConnector 必须把“cache metadata”与“实际可交付性”统一起来。
03 · ASYNC LOAD CREATES A NEW REQUEST STATE

目标 blocks 已经分配，不等于 request 立刻可以进 model forward。

如果 Connector 选择异步加载，scheduler 可以先分配 blocks、发起 transfer，然后暂时把 request 放在等待 remote KV 的状态。当前 V1 的 RequestStatus 明确包含 WAITING_FOR_REMOTE_KVS。

SCHEDULERremote hit found
→
ASYNC XFERWAITING_FOR_REMOTE_KVS
→
READYschedule remaining compute

这避免了一个危险竞态：request 已经被当成“前 1024 token computed”，但 worker 的 KV bytes 还在路上。

04 · TWO LEVELS OF READINESS

“整个 request transfer 完成”与“当前 layer 可以继续”不是同一个粒度。

REQUEST-LEVELget_finished()异步 send/receive 的 request 是否整体完成，用于 scheduler 更新等待状态、释放责任或继续下一步。
LAYER-LEVELwait_for_layer_load(layer)当前 attention layer 是否已经拿到它自己的 KV；允许后续层还在传。

Layer-level readiness 是 overlap 的关键；request-level readiness 是控制状态闭环的关键。两种都需要，才能既快又正确。

05 · PRODUCER BLOCK LIFETIME

Prefill 完成后，那些 KV blocks 什么时候才可以被覆盖？

如果传输是同步 copy，最简单：copy 返回后 source 就可以释放。但异步 RDMA/read/write 下，source memory 在 remote consumer 真正读取完成前不能被 allocator 拿去写新请求。

PRODUCERrequest finished模型计算结束，但 blocks 可能仍承担 handoff source。
async transfer pending⏳
CONSUMERread complete完成/通知后 producer 才能安全交还 blocks。

Base API 的 request_finished() 允许 Connector 返回“我异步接管 blocks 的释放责任”。这正是为了防止 source 被过早覆盖。

Memory lifetime 是 transfer correctness 的一部分。网络库再快，如果 source/destination buffer 的所有权时序错了，结果仍然会随机损坏。

06 · FOUR IDENTITIES MUST LINE UP

KV transfer 的 metadata，本质上是在证明“这批 bytes 就是这个请求这一段状态”。

REQUEST IDENTITY谁的 KV？请求/会话以及对应 producer engine/worker。
TOKEN IDENTITY覆盖哪段 prefix？token sequence/hash/范围必须对应，不能拿错 prefix。
MEMORY MAPPING从哪块到哪块？remote region/block/offset → local block/slot。
LAYOUT COMPAT字节怎样解释？K/V layout、dtype、model/layer/TP 配置等必须兼容。
READINESS传完了吗？handle/event/completion state。
LIFETIME还能读多久？lease/ref count/ownership，避免 source 过期。
07 · FAILURE CANNOT BE HIDDEN

某些 block load 失败时，最危险的行为是继续把它当作 cache hit。

CONNECTIVITYpeer / transport failure握手失败、连接断开、remote engine 已重启。
MEMORYsource expired / overwritelease 到期、block 被回收、mapping 过期。
COMPATIBILITYlayout / TP mismatch模型、KV layout 或并行映射不满足 connector 能力。

Base API 提供 get_block_ids_with_load_errors()，并在注释里要求异步失败也必须在规定时机报告。高层可以选择 fail request、重算或按策略处理，但不能静默使用坏 KV。

1. 为什么 remote hit 不能只看一个历史索引？
因为 scheduler 会据此跳过本地计算。Connector 必须保证声称命中的 KV 当前真实可加载；否则会把未到/已失效的数据当作已计算状态。
2. 为什么 producer request 已结束，KV blocks 仍可能不能马上 free？
异步 handoff 可能还在读取这些 source buffers。过早复用会导致远端读到被新请求覆盖的数据，所以 connector 需要管理 source memory lifetime。
3. Request-level completion 与 layer-level readiness 的区别是什么？
前者告诉 scheduler 一次请求的异步传输整体是否完成；后者只保证某个 attention layer 现在需要的 KV 已到，可用于逐层 transfer/compute overlap。
