LESSON 08.3 · KV CONNECTOR约 90 min

Transfer Lifecycle：从“远端有 KV”到“这轮 Attention 可以安全读它”，中间到底发生了什么？

一句 remote hit = 1024 tokens 只是开始。真正的系统要保证：远端那 1024 tokens 仍然有效；接收端已经分配目标 blocks；metadata 指向正确 request/layer/block；异步 copy 已启动；对应 layer 用到 Key-Value (KV，键-值) 前 copy 已完成；失败时不会把坏数据当成已计算状态；请求结束或被 preempt 时也不能让还在飞的 transfer 读写已经重用的 blocks。

这节课结束时，你应该能做到：
  • 把一次 KV load 拆成 query → reserve → plan → transfer → synchronize → commit 六个阶段。
  • 解释为什么 async transfer 需要 request-level completion 与 layer-level readiness 两种状态。
  • 理解 WAITING_FOR_REMOTE_KVS 的调度意义。
  • 知道 producer blocks 在异步 handoff 完成前可能不能立刻 free/overwrite。
  • 知道当前 kv_load_failure_policy 支持 fail 与 recompute，默认是 fail。
  • 理解 overlapping batches / preemption 为什么会让 block lifetime 成为 correctness 问题，而不只是 allocator 细节。
01 · SIX STAGES

一次远端 KV load，先用六步固定心智模型。

把控制状态、数据传输和 block 所有权放到同一条时间线上看，才能看清“remote hit”为什么远远不等于“Attention 现在就能读”。

REMOTE KV LOAD · END-TO-END LIFECYCLEconsumer-side view · simplified
两个 readiness：Scheduler 关心 request 是否整体可以重新进入运行队列；Worker 关心当前 layer 的 KV 是否已经到达。它们是不同粒度的状态，不要混成一个“传完了”。

以后不管看 NVIDIA Inference Xfer Library (NIXL，NVIDIA 推理传输库)、LMCache、Mooncake 还是自定义 Connector，都先找这六件事分别在哪里实现。

02 · QUERY MUST BE TRUTHFUL

Remote hit 的含义应该是“现在确实能加载”，不是“理论上以前存过”。

Base Application Programming Interface (API，应用程序编程接口) 对 get_num_new_matched_tokens() 的注释非常严格：Connector 应只考虑当前真正可用、可加载的最大 prefix。如果因为 eviction、连通性或其它问题实际拿不到，那些 tokens 不能算进 hit。

BAD CLAIMindex says 2048元数据记得以前存过 2048 tokens，但实际远端 blocks 已释放。
CONSEQUENCEscheduler skips compute若仍把它当 computed，Decode 会在未填充/错误 KV 上做 Attention。
CORRECTclaim only loadable prefixConnector 必须把“cache metadata”与“实际可交付性”统一起来。
03 · ASYNC LOAD CREATES A NEW REQUEST STATE

目标 blocks 已经分配，不等于 request 立刻可以进 model forward。

如果 Connector 选择异步加载，scheduler 可以先分配 blocks、发起 transfer，然后暂时把 request 放在等待 remote KV 的状态。当前 V1 的 RequestStatus 明确包含 WAITING_FOR_REMOTE_KVS，而 scheduler 会在遍历 waiting/skipped queue 时尝试把这类 blocked request promote 回可运行状态。

SCHEDULERremote hit found
→
ASYNC XFERWAITING_FOR_REMOTE_KVS
→
READYschedule remaining compute

这避免了一个危险竞态：request 已经被当成“前 1024 token computed”，但 worker 的 KV bytes 还在路上。

04 · TWO LEVELS OF READINESS

“整个 request transfer 完成”与“当前 layer 可以继续”不是同一个粒度。

REQUEST-LEVELget_finished() / connector output异步 send/receive 的 request 是否整体完成，用于 scheduler 更新等待状态、释放责任或继续下一步。
LAYER-LEVELwait_for_layer_load(layer)当前 attention layer 是否已经拿到它自己的 KV；允许后续层还在传。

Layer-level readiness 是 overlap 的关键；request-level readiness 是控制状态闭环的关键。两种都需要，才能既快又正确。

05 · PRODUCER BLOCK LIFETIME

Prefill 完成后，那些 KV blocks 什么时候才可以被覆盖？

如果传输是同步 copy，最简单：copy 返回后 source 就可以释放。但异步 Remote Direct Memory Access (RDMA，远程直接内存访问)/read/write 下，source memory 在 remote consumer 真正读取完成前不能被 allocator 拿去写新请求。

PRODUCERrequest finished模型计算结束，但 blocks 可能仍承担 handoff source。
async transfer pending⏳
CONSUMERread complete完成/通知后 producer 才能安全交还 blocks。

Base API 的 request_finished() 允许 Connector 返回“我异步接管 blocks 的释放责任”。这正是为了防止 source 被过早覆盖。

Memory lifetime 是 transfer correctness 的一部分。网络库再快，如果 source/destination buffer 的所有权时序错了，结果仍然会随机损坏。

06 · FOUR IDENTITIES MUST LINE UP

KV transfer 的 metadata，本质上是在证明“这批 bytes 就是这个请求这一段状态”。

REQUEST IDENTITY谁的 KV？请求/会话以及对应 producer engine/worker。
TOKEN IDENTITY覆盖哪段 prefix？token sequence/hash/范围必须对应，不能拿错 prefix。
MEMORY MAPPING从哪块到哪块？remote region/block/offset → local block/slot。
LAYOUT COMPAT字节怎样解释？K/V layout、dtype、model/layer/Tensor Parallel (TP，张量并行) 配置等必须兼容。
READINESS传完了吗？handle/event/completion state。
LIFETIME还能读多久？lease/ref count/ownership，避免 source 过期。
07 · FAILURE CANNOT BE HIDDEN

某些 block load 失败时，最危险的行为是继续把它当作 cache hit。

CONNECTIVITYpeer / transport failure握手失败、连接断开、remote engine 已重启。
MEMORYsource expired / overwritelease 到期、block 被回收、mapping 过期。
COMPATIBILITYlayout / TP mismatch模型、KV layout 或并行映射不满足 connector 能力。

Base API 提供 get_block_ids_with_load_errors()，要求异步失败也必须报告。当前 KVTransferConfig.kv_load_failure_policy 有两种明确策略：fail（默认）立即以错误结束请求；recompute 则重新调度请求，把失败的 remote KV 当作需要本地重算的状态。

注意：这是“KV load failure policy”，不是 07.5 的一般 KV-capacity preemption mode。

两者都可能导致 recompute，但触发原因不同：一个是远端 KV 加载失败，一个是本地调度因资源不足 preempt。

08 · PREEMPTION AND OVERLAPPING BATCHES ADD MEMORY HAZARDS

当 transfer、前一批 GPU 写入和下一批 block 重用重叠时，“free”不能只看 request 状态。

当前 Scheduler 初始化 Connector 时有两条很值得学习的 safety rail：

RELIABLE HANDOFFrequires_kv_delivery某些 Connector 要求 handoff 必须可靠完成；preemption 时 scheduler 会让 connector/worker 丢弃不再可信的 stale in-flight output，而不是让它继续写入已经释放的 blocks。
MULTIPLE IN-FLIGHT BATCHESdefer_block_free当 async scheduling / Pipeline Parallel (PP，流水线并行) 允许多个 batch 同时在飞、且本机是 KV consumer 时，scheduler 会延后 block free，避免新 remote load 与旧 batch 对同一被重用 block 的写入发生竞争。

这两条看似很工程化，但其实都来自同一个不变量：一个 physical block 只有在所有仍可能访问它的 execution / transfer 都结束后，才真正安全地交给下一任 owner。

当前实现入口：vllm/v1/core/sched/scheduler.py 的 Connector 初始化与 preemption 路径；Base 协议见 KVConnectorBase_V1。

CHECKPOINT08.3

能画出状态机和 ownership，才算真的懂“异步 KV transfer”。

1. 为什么 remote hit 不能只看一个历史索引？
因为 scheduler 会据此跳过本地计算。Connector 必须保证声称命中的 KV 当前真实可加载；否则会把未到/已失效的数据当作已计算状态。
2. 当前 remote KV load 失败默认会自动 recompute 吗？
不会。当前 KVTransferConfig 的 kv_load_failure_policy 默认是 fail；只有显式选择 recompute 时，scheduler 才按重算路径恢复失败 blocks。
3. 为什么多个 in-flight batches 时可能要延后 free KV blocks？
因为 request 逻辑上结束或被移出 running，不代表旧 batch 的 GPU 写入已经停止。若 block 立刻重用并同时被 remote load 填充，就可能和旧写入发生数据竞争，所以需要延迟 ownership 转移。
