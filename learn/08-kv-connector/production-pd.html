LESSON 08.5 · KV CONNECTOR约 110 min

Production P/D：真正上线时，优化的不是 Connector 本身，而是一整条 Prefill → KV → Decode 路径。

到这里已经能看懂 Connector 的协议和数据面。最后一课不再新增底层缩写，而是把前 7 个模块全部合回来：请求先被 Router 分配到 Prefill；Prefill 用适合自己的并行配置计算；KV handoff 占用网络并受 lease/ownership 约束；Decode 可以按自己的 serving 目标配置并持续生成；每一段都有队列、显存、拓扑和故障。生产系统真正要优化的是端到端 SLO，而不是单独把某个 RDMA benchmark 跑得好看。

这节课结束时，你应该能做到：
  • 画出 Router → Prefill pool → KV handoff → Decode pool → stream response 的完整生产路径。
  • 把 TTFT 分解成排队、Prefill compute、KV handoff、Decode admission 等部分。
  • 把 ITL 问题与 Decode utilization、batching、memory bandwidth、preemption 关联起来。
  • 理解当前 NixlConnector 明确支持若干 heterogeneous TP 场景，但并行维度与模型类型都有兼容边界，不能泛化成“P/D 任意配置都可不同”。
  • 解释 NIXL producer blocks 为什么需要 lease + heartbeat，而不是一个固定超时就够。
  • 知道必须同时观测 queue time、KV bytes/bandwidth、transfer wait、TTFT、ITL、preemption/error，而不是只看 tokens/s。
01 · ONE PRODUCTION MAP

真正的 P/D 不是“两台 GPU + 一条网线”，而是一条端到端 serving pipeline。

把路由、两边的队列、Prefill、KV handoff、Decode、lease/heartbeat 和用户指标放到同一张图里：

PRODUCTION P/D · END-TO-ENDone request · simplified
生产级主线：Router 连接两个独立资源池；P 负责建立并暂存 KV，Connector/NIXL 负责 handoff，D 把 KV 纳入自己的 paged cache 后持续 decode。TTFT 跨越整条路径，而 ITL 主要由 Decode pool 的稳定性决定。

这张图先固定两个边界：控制面负责 placement、metadata 和 ownership；bulk-data path 负责把真正的 KV bytes 送进 Decode 的本地 paged cache。两者必须协作，但排障时要分开看。

03 · DECODE POOL OWNS MOST OF THE STREAMING CADENCE

P/D 分离的价值之一，就是把 Decode 的关键路径尽量变得可预测。

Decode instance 不再直接执行大块新 Prefill，tail ITL 更容易控制；但它仍会受 continuous batching、KV memory pressure、recompute preemption、memory bandwidth、TP communication、sampling/CPU overhead 等影响。

BATCHactive seqs过小 GPU 吃不满；过大可能提高 per-token latency。
KVmemory pressure长上下文累积会让可并发 request 数下降。
COMMTP collectivesDecode TP 仍受 topology/collective latency 影响。
PREEMPTrecompute频繁资源回收会恶化 tail latency。
04 · CAPACITY RATIO

Prefill GPU 和 Decode GPU 的数量不应该默认 1:1。

Workload 决定两阶段的负载比例。长 prompt、短输出的请求更吃 Prefill；短 prompt、长输出更吃 Decode。生产 capacity planning 应从实际请求分布估算，而不是“每个 P 配一个 D”。

PREFILL-HEAVY WORKLOADlong input · short output可能需要更多 Prefill capacity / 更大的 Prefill TP，KV handoff bytes 也更大。
DECODE-HEAVY WORKLOADshort input · long outputDecode GPU 持有 KV 的时间更久，ITL 和并发 KV capacity 更关键。

Router 的任务因此不仅是“转发”，还可能需要做 queue-aware placement、P/D load balancing 和 affinity。

05 · P AND D DO NOT HAVE TO USE THE SAME TP

独立调优允许当前受支持模型使用 heterogeneous TP，但“支持 heterogeneous”有明确实现边界。

例如 Prefill 可能 TP=8，Decode 可能 TP=4。此时不同 rank 保存的 head/region slices 不完全一致；Connector 需要把 source TP layout 映射到 destination TP layout，而不能简单执行 rank i → rank i memcpy。

PREFILLTP = 8每个 rank 保存较小的 KV/head shard。
remap / split / replicate⇢
DECODETP = 4目标 rank 需要得到自己的本地 KV layout。
Dense / MoE当前 NixlConnector matrix：basic PD 与 heterogeneous TP 为支持状态。
MLAheterogeneous TP 当前是部分支持；KV replication/head-splitting 规则不同。
Hybrid SSM / Mamba当前 heterogeneous TP 仍是 WIP，要求 homogeneous TP。
Encoder-Decoder当前 NixlConnector PD matrix 标为不支持。

同时，handshake 仍要求模型语义、cache dtype、attention backend、transfer mode 等关键条件匹配。“TP 可以不同”从来不等于“其它并行维度也可以不经验证地随便不同”。

部署前应以当前 NixlConnector Compatibility Matrix 为准，不要只按这门课的抽象推测。
06 · MULTI-TURN CHANGES THE DIRECTION

第二轮对话时，最新 KV 其实在 Decode 端；让 Prefill 从零重算会浪费已有状态。

当前 vLLM NIXL 指南已经提供 bidirectional KV transfer 路径：第一轮 P→D handoff 后，D 生成的新 tokens 对应 KV 留在 D；下一轮 P 可以从 D 取得已有 KV，只 Prefill 新增内容，再把新状态交给 D。

TURN N · DECODED holds latest conversation KV包含模型刚生成的 tokens。
next turn D→P
TURN N+1 · PREFILLcompute only new suffix避免把整个多轮历史重新 Prefill。
P→D new KV
DECODEcontinue generation对话状态继续前进。

这也说明 KV Connector 最终不只是“一条 P→D 管道”，而会逐渐演化成跨实例 KV state management。

07 · LEASE + HEARTBEAT: WHO OWNS P'S BLOCKS WHILE D IS QUEUED?

固定一个很长的超时会泄漏容量；固定一个很短的超时又会误杀排队中的 Decode 请求。

当前 NIXL 设计为 P-side handoff 引入了明确的 KV lease renewal 机制。Prefill 完成后，P 给这些 source blocks 一个短 lease；只要 D 还健康、仍可能读取，它就周期性 heartbeat 续租。这样既不会因为 D 排队久就过早释放，也不会因为 D 崩溃就把几 GiB blocks 锁住几分钟。

P FINISHESinitial lease ≈ 30sKV blocks pinned，等待 D。
D ARRIVESon_new_request()request 一进入 D scheduler 就开始 heartbeat tracking，不等真正被 GPU schedule。
HEARTBEAT~ every 5s默认 interval = lease_duration // 6；一次可为同一 P 批量续约多个请求。
RENEW+ ~20s默认 extension = lease_duration × 2/3。
ENDtransfer complete OR expiry成功立刻释放；D 消失则 heartbeat 停止，lease 到期回收。

Heartbeats 复用 NIXL notification system，并在 forward loop 中发送/处理；没有单独靠后台线程精确打点。关键不变量是：D 只要仍可能合法读取，P 就不能覆盖；D 永久消失，P 又必须最终自动回收。

当前设计：NIXL KV Cache Lease Renewal。默认值属于当前实现，不应当成永久协议常量。
08 · BIDIRECTIONAL CACHE USES A DIFFERENT LIFETIME MODEL

D 端为“下一轮也许会回来”的 KV，不能靠同样的 heartbeat 无限续租。

多轮对话的下一次用户输入可能几秒、几分钟甚至永远不来。当前 bidirectional NIXL 因此给 D-side cached KV 使用单独的 decoder_kv_blocks_ttl，默认 480 秒，不通过 heartbeat 续租。过期后下一轮需要 recompute。

这里还有一个非常典型的分布式陷阱：expiry 使用进程本地 perf_counter，P 与 D 的时钟零点不相同。当前实现通过 handshake round-trip 估算 peer clock offset，再把 D 的 deadline 转换到 P 能比较的时钟域。Lab B7 会把这个坑单独跑成状态机。

10 · EXPERIMENTAL METHOD

最容易犯的错，是直接上 P/D，然后不知道收益到底来自哪里。

BASELINE单个 vLLM instance：固定模型、请求 trace、并发度，记录 TTFT/ITL/throughput。
DISAGGREGATE同样总 GPU 预算下拆 P/D；先不调奇怪参数，只确认 correctness 和 transfer size。
PROFILE分解 P queue / Prefill / KV xfer / D queue / Decode；找最大项。
TUNE ONE AXISP/D ratio、TP、chunking、transport、block/cache、routing 一次只改一类。
LOAD TEST不要只测一个 request；测不同 prompt/output distribution 与 burst QPS。
TAIL最终看 p95/p99 TTFT/ITL，而不是只看平均值。

FINAL CHECKPOINT08.5

到这里，目标不是“记住 NIXL”，而是能自己推系统。

1. TTFT 在 P/D 架构里至少应该拆成哪些主要部分？
Prefill queue + Prefill compute + KV handoff + Decode queue/admission + first decode step。不同系统还可以进一步拆 router/tokenization/metadata 等。
2. 为什么 P 的 source KV 不能只设置一个固定 30 秒 TTL 就结束？
D 可能只是排队很久而不是失联；固定短 TTL 会过早释放，固定长 TTL 又会在 D 崩溃时占住大量显存。当前 NIXL 用短初始 lease + D heartbeat 续租，在健康排队与故障回收之间兼顾。
3. 如果 NIXL bandwidth 很快，但端到端 TTFT 仍慢，下一步应该看什么？
分解 Prefill/Decode queue、Prefill compute、handshake/compatibility、实际 KV wait、Decode admission；再检查 lease/remote-wait 与 block pressure。网络带宽只是一段，不代表整个 serving pipeline 没有瓶颈。
