LESSON 04.3 · DISTRIBUTED约 60 min

NCCL 与拓扑：同一个 all-reduce，为什么换台机器就可能差很多？

上一课只讲“collective 的语义”。但真实系统还要回答：这些 bytes 到底走哪条链路？四张 Graphics Processing Unit (GPU，图形处理器) 是通过 NVLink 连着，还是绕 Peripheral Component Interconnect Express (PCIe，高速外设组件互连)？跨节点时 GPU 数据是不是要先经过 host staging？NVIDIA Collective Communications Library (NCCL，NVIDIA 集体通信库) 的价值，就是把 collective contract 映射到真实 GPU 拓扑和通信链路上，并选择合适的算法与 transport。

这节课结束时，你应该能做到：
  • 解释 NCCL 是什么，也解释它不是什么。
  • 区分 NVLink/NVSwitch、PCIe、InfiniBand/RDMA over Converged Ethernet (RoCE，基于融合以太网的 RDMA) 这些链路大致处在什么层级。
  • 把“collective 的数学语义”和“NCCL 实际怎样走硬件”分成两层思考。
  • 用 ring 的直觉理解 all-reduce 为什么能拆成 reduce-scatter + all-gather。
  • 知道 NCCL 并不永远固定用 ring；现代版本会根据 collective、拓扑、消息大小和平台选择 Ring、Tree、NVLink Sharp (NVLS，NVLink Sharp 算法) 等算法。
  • 理解 GPUDirect Remote Direct Memory Access (RDMA，远程直接内存访问) 为什么能减少跨节点 GPU 通信中的 host staging。
  • 知道如何用 nvidia-smi topo -m、NCCL_DEBUG=INFO、nccl-tests 开始定位通信问题。
01 · WHAT NCCL IS

NCCL 不是“网络”，而是一套针对 NVIDIA GPU 的通信库。

NVIDIA 官方把 NCCL 定义为 topology-aware 的 inter-GPU communication library。它提供 AllReduce、Broadcast、AllGather、ReduceScatter、AllToAll，以及 point-to-point send/recv 等 primitive。

NCCL 做什么把 collective/Peer-to-Peer (P2P，点对点通信) contract 映射成在真实 GPU 拓扑上执行的 CUDA communication kernels、算法与 transport。
NCCL 不是什么它不是完整分布式训练框架，也不是 InfiniBand、RoCE、NVLink 这些物理/网络链路本身。

PyTorch torch.distributed 使用 NCCL backend 时，你调用的是 PyTorch collective Application Programming Interface (API，应用程序编程接口)；底层 CUDA GPU 通信由 NCCL communicator 承担。最重要的是：API 的数学结果不因为物理路径改变，执行代价却会改变。

官方参考：NCCL Overview。NCCL 专注 inter-GPU collective 与 P2P primitives，不是完整 parallel programming framework。
02 · TOPOLOGY IS THE MAP

先分清“我要什么结果”，再追“这些 bytes 实际跨过哪些链路”。

同一个 all_reduce(tensor, TP group)，在程序语义上始终要求参与 ranks 得到 reduced tensor；但 NCCL 会结合 collective、message size、rank count、拓扑和平台能力选择实际执行方案。下面把逻辑 contract 与物理 data path 放在同一张图里：

NCCL · LOGICAL CONTRACT → PHYSICAL PATHsame collective · different cost
稳定心智模型：collective 名字描述“通信结束后每个 rank 应该拿到什么”；NCCL/topology 描述“为了实现这个 contract，哪些 chunks 沿哪些链路移动”。后面判断 Tensor Parallel (TP，张量并行)/Data Parallel (DP，数据并行)/Pipeline Parallel (PP，流水线并行) 是否划算时，必须同时看这两层。
GPU LOCAL
GPU device memory / Video Random Access Memory (VRAM，显存)数据首先住在某张 GPU 自己的显存；物理实现可能是 High Bandwidth Memory (HBM，高带宽内存) 或 Graphics Double Data Rate (GDDR，图形双倍数据速率存储器)，取决于具体 GPU。
INTRA-NODE
NVLink / NVSwitch / PCIe同一台机器里 GPU↔GPU 的路径可能非常不同。
GPU ↔ Network Interface Card (NIC，网络接口卡)
PCIe / platform fabric跨节点之前，GPU 数据还要到达网络接口；GPU/NIC affinity 与 direct-access 能力很关键。
INTER-NODE
InfiniBand / RoCE / Ethernet fabric跨服务器的数据最终进入网络；带宽、延迟、交换结构、routing 和拥塞都会影响 collective。

因此“8×GPU”远远不够描述一台训练机器。8 张卡之间是全连接 NVSwitch、部分 NVLink，还是只靠 PCIe，会直接改变高频 Tensor Parallel collective 的代价。

03 · RING ALL-REDUCE INTUITION

Ring 的核心：不要让一个中心节点吃下所有流量，让每个 rank 持续和邻居交换 chunks。

R0
R1
R2
R3
chunks circulate
reduce-scatter
then all-gather

可以把 ring all-reduce 先理解成两阶段：

PHASE 1reduce-scatter
→
EACH RANKone reduced shard
→
PHASE 2all-gather

每个 rank 分块发送/接收，最终既完成 reduction，又让所有 rank 得到完整结果。Ring 的一个重要直觉是链路可以持续流式搬大块数据，因此对大消息常有很好的带宽利用。

但不要记成“NCCL all-reduce = ring”。NCCL 会根据平台、拓扑、collective 和 message size 自动选择可用算法；现代版本的算法族不止 Ring/Tree，还包括 NVLS 等平台相关路径。

04 · RING VS TREE

为什么还需要 Tree？因为延迟、带宽和 rank 数的权衡不同。

RING · INTUITION很多顺序 steps，持续吃 bandwidth大 message 时能把链路持续利用起来；step 数随 ranks 增长，latency 也会累积。
TREE · INTUITION层级聚合 / 分发通信深度更接近 log-scale，某些 message size / rank count 下更适合低延迟。实际 NCCL tree 细节由实现决定。

不要自己提前指定 NCCL_ALGO=Ring 当“优化”。NCCL 默认会自动选择算法。只有 benchmark 与 topology 证据表明默认选择不理想，才有理由干预算法/协议。

当前 NCCL_ALGO 文档列出 Ring、Tree、NVLS 等可选算法，并说明默认未设置时由 NCCL 根据 topology / architecture 自动选择。
05 · THE LINKS ARE NOT INTERCHANGEABLE

同一个 GPU↔GPU 逻辑通信，可能落到完全不同的物理路径。

NVLINK / NVSWITCH高带宽 GPU fabric典型高端训练服务器里用于快速 GPU↔GPU 通信；拓扑和代际决定具体能力。
PCIE通用 I/O fabricGPU、Central Processing Unit (CPU，中央处理器)、NIC 都可能挂在 PCIe hierarchy 上；GPU↔GPU 可能经过 switch / root complex。
InfiniBand (IB，InfiniBand 高速互连) / ROCE跨节点 networkInfiniBand 或基于 Ethernet 的 RoCE 可承担 node↔node RDMA 网络通信。

这就是为什么“跨节点 TP 通常比单机高速 GPU fabric 上的 TP 贵得多”是很自然的系统结论：layer 内高频 activation shards 现在要穿过 GPU↔NIC 路径与网络。

06 · GPUDIRECT RDMA

跨节点时，一个关键问题：GPU 数据能不能更直接地到 NIC？

没有高效 GPU-direct path 的教学版直觉：

GPU MEMORYGPU A device memory
copy / staging →
HOST PATHCPU / host memory
→ network →
REMOTEGPU B

GPUDirect RDMA 的核心目标，是让第三方 PCIe device（典型是 NIC）能更直接 Direct Memory Access (DMA，直接内存访问) 访问 GPU memory，减少不必要的 host staging / CPU copy：

GPU MEMORYGPU A device memory
DMA ↔
NICRDMA capable
network →
REMOTE GPUGPU B memory

现实路径仍受 PCIe topology、GPU/NIC affinity、Input-Output Memory Management Unit (IOMMU，输入输出内存管理单元)、driver、NIC 能力与 platform 配置影响。“支持 GPUDirect RDMA”不等于任何 GPU 到任何 NIC 都能自动跑满，也不意味着网络与拓扑代价消失。

这也是以后读 vLLM Key-Value (KV，键-值) Connector / NVIDIA Inference Xfer Library (NIXL，NVIDIA 推理传输库) 时会再次遇到的基础：GPU 上已经算好的 KV，跨节点怎么直接送到另一张 GPU，而不是不必要地绕 host buffer。

09 · THIRD TOOL: NCCL-TESTS

训练慢之前，先问：机器的 collective 本身到底能跑多快？

NVIDIA 的 nccl-tests 是常见通信基准工具，最常见的就是测 all-reduce：

EXAMPLE BINARY./build/all_reduce_perf ...

关注不同 message sizes 下的时间和 bandwidth。多节点通常通过 Message Passing Interface (MPI，消息传递接口) 或集群 launcher 启动。具体命令取决于环境，不要直接照抄别人的网卡参数。

为什么先测它？如果 nccl-tests 已经明显跑不满机器应有的通信水平，那么训练框架里的 all-reduce 慢很可能只是症状；你应该先处理驱动、拓扑、NIC/RDMA、容器权限或网络配置。

源码参考：NVIDIA nccl-tests。
10 · COLLECTIVES CAN BE HIERARCHICAL

8 节点 × 8 GPU，不应该假装成 64 张卡完全等价互连。

真实集群天然有层级：

WITHIN NODENVLink / PCIe
≠
ACROSS NODESNIC + network
→
HIERARCHICALcollective strategy

NCCL 的 topology awareness 就是在利用这些差异。现代平台还可能有 NVSwitch/NVLS 等额外 collective acceleration 能力。初学阶段不用背算法名，先记住：高效 collective 必须尊重硬件层级。

11 · THIS CHANGES HOW YOU CHOOSE PARALLELISM

并行策略不是只看“有多少 GPU”，还要看哪些 GPU 彼此最接近。

Parallelism通信特征拓扑直觉
Tensor Parallellayer 内高频 collective，数据量大、延迟敏感通常更希望放在高带宽、低延迟的近邻 GPU group
Pipeline Parallel相邻 stage P2P，频率/消息取决于 microbatch schedule可以把 stage placement 与节点边界一起规划
Data Parallelgradient / param collectives，可 overlap经常需要跨节点扩展，因此 network bandwidth 与 topology 很重要

这就是为什么 Megatron 的 parallel rank mapping、communication overlap、distributed optimizer 不能脱离集群 topology 单独评价。接下来进入 05 Megatron 后，我们会把这套硬件/通信地基真正套到 TP、PP、DP 上。

CHECKPOINT04.3

看到通信慢，先画数据路径。

1. NCCL 和 InfiniBand 是同一种东西吗？
不是。NCCL 是实现 GPU collective/P2P 的通信库；InfiniBand 是跨节点网络技术/互连。NCCL 可以在支持的环境中利用 InfiniBand/RDMA transport。
2. 为什么不能把“NCCL all-reduce 永远使用 ring”当成规则？
因为 NCCL 支持多种算法，并会根据 topology、architecture、collective、message size 等自动选择。Ring 是重要理解模型，但不是所有环境里的固定实现。
3. 为什么 Tensor Parallel 特别在意 GPU 间是不是高速近邻？
TP 在一个 Transformer layer 内就会发生高频 collective。通信位于关键路径，若链路带宽低/延迟高，GPU 很容易等待通信，local General Matrix Multiply (GEMM，通用矩阵乘法) 并行带来的收益会被抵消。
