LESSON 04.3 · DISTRIBUTED约 60 min

NCCL 与拓扑：同一个 all-reduce，为什么换台机器就可能差很多？

上一课只讲 collective 的语义。但真实系统还要回答：这些字节到底走哪条链路？四张 GPU 是通过 NVLink 连着，还是绕 PCIe？跨节点时 GPU 数据是不是要先经过 host memory 中转？NCCL 的价值，就是把 collective 语义映射到真实 GPU 拓扑和通信链路上，并选择合适的通信算法与 transport（传输后端：负责底层设备或网络数据移动的实现层）。

这节课结束时，你应该能做到：
  • 解释 NCCL 是什么，也解释它不是什么。
  • 区分 NVLink/NVSwitch、PCIe、InfiniBand/RoCE 这些链路大致处在什么层级。
  • 把“collective semantics”和“NCCL 实际怎样走硬件”分成两层思考。
  • 用环形算法的直觉理解 all-reduce 为什么能拆成 reduce-scatter + all-gather。
  • 知道 NCCL 并不永远固定用 ring；现代版本会根据集合通信、拓扑、消息大小和平台选择环形、树形、NVLS（NVLink Sharp：NCCL 在支持的平台上可选择的 NVLink/NVSwitch 集合通信加速算法族）等算法。
  • 理解 GPUDirect RDMA（GPU 直连远程内存访问：让网络设备更直接地读写 GPU memory，以减少 host memory 中转）为什么能降低跨节点 GPU 通信的数据搬运开销。
  • 知道如何用 nvidia-smi topo -m、NCCL_DEBUG=INFO 和 NCCL 通信基准工具开始定位通信问题。
01 · NCCL 到底是什么

NCCL 不是“网络”，而是一套针对 NVIDIA GPU 的通信库。

NVIDIA 官方把 NCCL 定义为面向 GPU 间通信、具备拓扑感知能力的通信库。它提供 AllReduce、Broadcast、AllGather、ReduceScatter、AllToAll，以及 point-to-point send/recv 等通信原语。

NCCL 做什么把 collective / P2P 的通信语义映射成在真实 GPU 拓扑上执行的 CUDA kernels、通信算法与 transport。
NCCL 不是什么它不是完整分布式训练框架，也不是 InfiniBand、RoCE、NVLink 这些物理/网络链路本身。

PyTorch torch.distributed 使用 NCCL 后端时，你调用的是 PyTorch collective API；底层 CUDA GPU 通信由 NCCL communicator 承担。最重要的是：API 的数学结果不因为物理路径改变，执行代价却会改变。

官方参考：NCCL Overview。NCCL 专注 inter-GPU 集合通信与 P2P primitives，不是完整 parallel programming framework。
02 · 拓扑就是数据路径地图

先分清“我要什么结果”，再追“这些字节数据实际跨过哪些链路”。

同一个 all_reduce(tensor, TP group)，在程序语义上始终要求参与各个 rank 得到归约后的 tensor；但 NCCL 会结合 collective、message size（消息大小：一次 collective 中每个 rank 需要参与传输的数据量）、rank 数量、拓扑和平台能力选择实际执行方案。下面把逻辑通信语义与物理数据路径放在同一张图里：

NCCL · LOGICAL CONTRACT → PHYSICAL PATHsame collective · different cost
稳定心智模型：集合通信名字描述“通信结束后每个 rank 应该拿到什么”；NCCL/topology 描述“为了实现这套语义，哪些 chunk（数据块：把一个大 tensor 切出的较小传输单元）沿哪些链路移动”。后面判断 TP / DP / Pipeline Parallel 是否划算时，必须同时看这两层。
GPU LOCAL
GPU device memory / VRAM数据首先住在某张 GPU 自己的显存；具体硬件可能使用 HBM 或 GDDR。
INTRA-NODE
NVLink / NVSwitch / PCIe同一台机器里 GPU↔GPU 的路径可能非常不同。
GPU ↔ NIC（网络接口卡：负责主机与外部网络之间收发数据的硬件设备）
PCIe / 平台互连跨节点之前，GPU 数据还要到达网络接口；GPU/NIC affinity（亲和性：描述 GPU 与 NIC 在硬件拓扑上的距离和访问关系）与直接访问能力很关键。
INTER-NODE
InfiniBand / RoCE / Ethernet跨服务器的数据最终进入网络；带宽、延迟、交换结构、路由和拥塞都会影响集合通信。

因此“8×GPU”远远不够描述一台训练机器。8 张卡之间是全连接 NVSwitch、部分 NVLink，还是只靠 PCIe，会直接改变高频 Tensor Parallel 集合通信的代价。

03 · 环形 All-Reduce 的直觉

Ring（环形算法：让各 rank 沿一个逻辑环与邻居分块交换数据）的核心，是让每个 rank 持续参与传输，而不是把流量集中到一个中心节点。

R0
R1
R2
R3
chunks circulate
reduce-scatter
then all-gather

可以把 ring all-reduce 先理解成两阶段：

PHASE 1reduce-scatter
→
EACH RANKone reduced shard
→
PHASE 2all-gather

每个 rank 分块发送/接收，最终既完成归约，又让所有 rank 得到完整结果。Ring 的一个重要直觉是链路可以持续流式搬大块数据，因此对大消息常有很好的带宽利用。

但不要记成“NCCL all-reduce = ring”。NCCL 会根据平台、拓扑、集合通信和 message size 自动选择可用算法；现代版本的算法族不止 Ring / 树形算法，还包括 NVLS 等平台相关路径。

04 · Ring 与树形算法

为什么还需要 Tree（树形算法：按层级聚合和分发数据，以减少通信阶段数）？因为延迟、带宽和 rank 数的权衡不同。

RING · INTUITION顺序阶段较多，持续利用带宽大消息时能让链路持续工作；阶段数随 rank 增长，延迟也会累积。
TREE · INTUITION层级聚合 / 分发通信深度更接近对数增长，某些消息大小和 rank 数量下更适合低延迟。实际 NCCL Tree 细节由实现决定。

不要自己提前指定 NCCL_ALGO=Ring 当“优化”。NCCL 默认会自动选择算法。只有 benchmark 与 topology 证据表明默认选择不理想，才有理由干预算法或协议。

当前 NCCL_ALGO 文档列出 Ring、Tree、NVLS 等可选算法，并说明默认未设置时由 NCCL 根据 topology / architecture 自动选择。
05 · 不同链路不能当成一回事

同一个 GPU↔GPU 逻辑通信，可能落到完全不同的物理路径。

NVLINK / NVSWITCH高带宽 GPU 互连典型高端训练服务器里用于快速 GPU↔GPU 通信；拓扑和代际决定具体能力。
PCIE通用 I/O 互连GPU、CPU、NIC 都可能挂在 PCIe 层级上；GPU↔GPU 可能经过 switch 或 root complex。
INFINIBAND / ROCE跨节点网络InfiniBand 或基于以太网的 RoCE 可承担节点间 RDMA 网络通信；它们常见于 HPC（高性能计算：面向大规模并行科学与工程计算的计算领域）和 AI 集群。

这就是为什么“跨节点 TP 通常比单机高速 GPU fabric 上的 TP 贵得多”是很自然的系统结论：layer 内高频 activation 分片现在要穿过 GPU↔NIC 路径与网络。

06 · GPU 直连跨节点通信

GPUDirect RDMA 的关键问题：GPU 数据能不能更直接地到 NIC？

没有高效 GPU 直连路径时，可以先这样理解：

GPU device memoryGPU A 设备显存
拷贝 / 中转 →
host pathCPU / host memory
→ 网络 →
remoteGPU B

GPUDirect RDMA 的核心目标，是让第三方 PCIe 设备（典型是 NIC）能通过 DMA（直接内存访问：设备在较少 CPU 搬运参与下直接读写内存的数据移动机制）更直接地访问 GPU device memory，减少不必要的 host memory 中转和 CPU copy：

GPU device memoryGPU A 设备显存
直接传输 ↔
NIC支持 RDMA
network →
remote GPUGPU B 内存

现实路径仍受 PCIe 拓扑、GPU/NIC affinity、IOMMU（输入输出内存管理单元：为设备 DMA 提供地址转换和访问隔离的硬件单元）、驱动、NIC 能力与平台配置影响。“支持 GPUDirect RDMA”不等于任何 GPU 到任何 NIC 都能自动跑满，也不意味着网络与拓扑代价消失。

这也是以后读 vLLM KV Connector / NIXL 时会再次遇到的基础：GPU 上已经算好的 KV，跨节点怎么直接送到另一张 GPU，而不是不必要地绕 host memory 中的临时缓冲区。

09 · 第三个工具：NCCL 通信基准

训练慢之前，先问：机器的集合通信本身到底能跑多快？

NVIDIA 的 nccl-tests（NCCL 通信基准工具：独立测量 NCCL collective 的延迟和带宽）最常见的用途之一就是测 all-reduce：

EXAMPLE BINARY./build/all_reduce_perf ...

关注不同 message size 下的时间和 bandwidth。多节点通常通过 MPI（消息传递接口：HPC 中常见的进程间消息传递标准）或集群 launcher 启动。具体命令取决于环境，不要直接照抄别人的网卡参数。

为什么先测它？如果 nccl-tests 已经明显跑不满机器应有的通信水平，那么训练框架里的 all-reduce 慢很可能只是症状；你应该先处理驱动、拓扑、NIC/RDMA、容器权限或网络配置。

源码参考：NVIDIA nccl-tests。
10 · 集合通信也可以分层进行

8 节点 × 8 GPU，不应该假装成 64 张卡完全等价互连。

真实集群天然有层级：

WITHIN NODENVLink / PCIe
≠
ACROSS NODESNIC + network
→
HIERARCHICALcollective strategy

NCCL 的拓扑感知能力就是在利用这些差异。现代平台还可能有 NVSwitch/NVLS 等额外集合通信加速能力。初学阶段不用背算法名，先记住：高效集合通信必须尊重硬件层级。

11 · 这会直接影响并行策略怎么选

并行策略不是只看“有多少 GPU”，还要看哪些 GPU 彼此最接近。

并行方式通信特征拓扑直觉
Tensor Parallellayer 内高频集合通信，数据量大、延迟敏感通常更希望放在高带宽、低延迟的近邻 GPU 进程组
Pipeline Parallel相邻阶段 P2P，频率和消息大小取决于 microbatch 调度可以把 stage placement 与节点边界一起规划
Data Parallel梯度 / 参数集合通信，可 overlap经常需要跨节点扩展，因此 network bandwidth 与 topology 很重要

这就是为什么 Megatron 的并行 rank 映射、communication overlap、distributed optimizer 不能脱离集群 topology 单独评价。接下来进入 05 Megatron 后，我们会把这套硬件/通信地基真正套到 TP、流水线并行、DP 上。

CHECKPOINT04.3

看到通信慢，先画数据路径。

1. NCCL 和 InfiniBand 是同一种东西吗？
不是。NCCL 是实现 GPU 集合通信/P2P 的通信库；InfiniBand 是跨节点网络技术/互连。NCCL 可以在支持的环境中利用 InfiniBand/RDMA transport backend。
2. 为什么不能把“NCCL all-reduce 永远使用 ring”当成规则？
因为 NCCL 支持多种算法，并会根据 topology、architecture、collective、message size 等自动选择。Ring 是重要理解模型，但不是所有环境里的固定实现。
3. 为什么 Tensor Parallel 特别在意 GPU peers 是否通过高速近邻互连？
TP 在一个 Transformer layer 内就会发生高频集合通信。通信位于关键路径，若链路带宽低/延迟高，GPU 很容易等待通信，local GEMM 并行带来的收益会被抵消。
