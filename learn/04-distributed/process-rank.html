LESSON 04.1 · DISTRIBUTED约 50 min

进程、rank 与 process group：多张 GPU 先怎么“认识彼此”？

上一模块我们已经知道：cuda:0 和 cuda:1 是两个设备，数据不会自动共享。现在第一次真正进入分布式。开始时别急着学 all-reduce；先回答更基础的问题：谁在控制 GPU 0？谁在控制 GPU 1？它们如何获得唯一编号？哪些进程属于同一个通信小组？Megatron 后面所有 TP / PP / DP 通信，都建立在这套身份系统上。

这节课结束时，你应该能做到：
  • 区分 process、rank、world size、local rank。
  • 理解“常见的一进程一 GPU”模式，但知道它不是分布式的数学定义。
  • 看懂 torchrun --nproc-per-node=... 大致做了什么。
  • 理解 init_process_group() 为什么必须等 peers 加入。
  • 解释 process group 为什么是 Megatron 创建 TP / DP / PP 子通信域的基础。
  • 知道 collective 调用如果不同 rank 不一致，为什么容易 hang。
01 · FIRST: A PROCESS IS A PROGRAM INSTANCE

多 GPU 训练里，常见做法不是“一个 Python 程序神奇控制所有卡”，而是启动多个进程。

假设一台机器有 4 张 GPU。最常见的 PyTorch/NCCL 训练模式之一是：启动 4 个 Python processes，每个 process 绑定一张 GPU。

PROCESSrank 0GPU 0
PROCESSrank 1GPU 1
PROCESSrank 2GPU 2
PROCESSrank 3GPU 3

每个 process 有自己的 Python interpreter、自己的程序状态，也会持有属于自己的 tensor / model 对象。它们不是通过 Python 变量直接读彼此的 GPU memory；需要显式的 distributed communication。

不是共享一份 Python 对象rank 0 的 model 和 rank 1 的 model 是各自进程里的对象。
通信是显式系统行为想同步 tensor，必须经过 collective / P2P 等通信机制，而不是“变量名一样就自动一致”。
02 · RANK IS THE GLOBAL ID

rank 就是这个分布式 job 里，每个 process 的全局编号。

rank某个 process 在整个 process group / job 里的唯一编号，通常从 0 到 world_size-1。
world size这个通信世界里一共有多少个 processes。
local rank当前 process 在“本机”上的编号，常用于把 process 映射到本机 GPU。

单机 4 GPU 时，global rank 和 local rank 恰好都可能是 0、1、2、3，所以新手容易以为它们是一回事。多机以后就不是了。

03 · GLOBAL RANK ≠ LOCAL RANK

两台机器、每台 4 GPU 时，local rank 会重复，global rank 不会。

NODE Aglobal ranks 0–3
rank 0 · local 0rank 1 · local 1rank 2 · local 2rank 3 · local 3
NODE Bglobal ranks 4–7
rank 4 · local 0rank 5 · local 1rank 6 · local 2rank 7 · local 3

这里 WORLD_SIZE=8。node B 上的 local_rank=0 对应 global rank 4，而不是 rank 0。PyTorch 官方也特别强调：local rank 只在本机唯一，不是全局唯一 ID。

以后写“只让 rank 0 保存 checkpoint”时，应判断 global rank；而“这个 process 用本机哪张 GPU”通常看 local rank。

04 · WHAT TORCHRUN DOES FOR YOU

torchrun 的核心工作之一：把同一个脚本启动成多个 processes，并给它们分配分布式身份信息。

shellsingle node · 4 GPUs
torchrun --standalone --nproc-per-node=4 hello_dist.py

粗略看，它会启动 4 份 hello_dist.py。每个 process 都能从环境变量获得自己的身份，例如：

environmentone process might see
RANK=2
WORLD_SIZE=4
LOCAL_RANK=2
MASTER_ADDR=...
MASTER_PORT=...

多节点时 launcher / rendezvous 配置会更复杂，但“每个 process 最终需要知道自己是谁、总共有多少 peers、去哪里完成初始化”这个核心没有变。

05 · INIT_PROCESS_GROUP

启动了多个进程还不够：它们要加入同一个通信世界。

PyTorch 分布式代码通常会在开头初始化默认 process group。对 CUDA GPU 训练，NCCL 是常见 backend：

python04_hello_dist.py
import os
import torch
import torch.distributed as dist

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

dist.init_process_group(backend="nccl")

rank = dist.get_rank()
world_size = dist.get_world_size()

x = torch.tensor([rank], device=f"cuda:{local_rank}")
print(f"rank={rank}, local_rank={local_rank}, x={x.item()}")

dist.destroy_process_group()

torchrun 提供的环境变量可以让 init_process_group() 使用默认的 environment-variable initialization。初始化阶段需要 peers 彼此发现并建立通信状态；官方文档明确说明，初始化会等到相关 processes 加入。

官方参考：PyTorch · torch.distributed 与 torchrun tutorial。
06 · PROCESS ↔ DEVICE

为什么经常一进程一 GPU？因为身份和设备映射会变得非常清楚。

PROCESSglobal rank 5 · local rank 1
bind →
DEVICE ON THIS NODEcuda:1

“一进程一 GPU”不是说 CUDA 永远只能这样用。一个 process 可以看到多个 GPU，一个 GPU 也可能被多个 processes 使用。但对大规模训练，one-process-per-GPU 是非常常见、容易组合 NCCL 与 DDP/模型并行的模式。

07 · PROCESS GROUPS

最关键的一步：不是所有 rank 每次都必须一起通信。

默认 process group 可以包含全部 8 个 ranks。但你也可以创建子 group，只让某些 ranks 组成一个通信域。这正是 Megatron 组合多种 parallelism 的基础。

GLOBAL01234567
TP GROUP A01234567
TP GROUP B01234567
DP EXAMPLE01234567

上图只是为了理解“同一批 global ranks 可以按不同规则切成不同 group”，不是在定义某个特定 Megatron 配置。真正 TP/DP/PP rank layout 取决于 parallel sizes 和 rank ordering。

以后读 Megatron 源码看到 get_tensor_model_parallel_group()、data parallel group 等名字时，脑中要出现的不是抽象 class，而是一组具体 ranks。

08 · RENDEZVOUS: HOW PEERS MEET

多进程初始化，本质上还需要一个“大家去哪里碰头”的机制。

1launcher starts启动多个 processes。
2assign identityrank / world size / local rank。
3discover peers通过 rendezvous / store / env 配置找到彼此。
4build group初始化 backend 与 communicator 状态。

你现在不需要背 TCPStore、etcd 或 elastic rendezvous 的细节。先知道：分布式不是“所有进程天然知道彼此”，初始化系统必须先解决 peer discovery 和一致的 group membership。

09 · WHY DISTRIBUTED CODE HANGS

最典型的新手噩梦：一个 rank 在等，另一个 rank 根本没来。

Collective 的语义通常要求 group 里的相关 ranks 以兼容的顺序参与。如果 rank 0 调用了某个 collective，而 rank 1 走了另一条 if 分支没有调用，rank 0 很可能一直等 peer。

分布式 debugging 的第一反应之一：

每个 rank 现在走到哪一行？参与同一个 collective 的 ranks 是否一致？调用顺序、tensor shape / dtype、process group 是否一致？

后面学 NCCL 时你会发现，“hang”经常不是网络坏了，而是程序逻辑让不同 ranks 对通信顺序产生了不同理解。

10 · CONNECT TO MEGATRON AND VLLM

rank / group 是训练与推理系统共同的底层语言。

Megatron把 global ranks 组织成 tensor-parallel、pipeline-parallel、data-parallel、context/expert-parallel groups；不同 group 执行不同 collectives。
vLLM / distributed serving多 GPU tensor parallel workers、跨进程执行器、P/D 节点同样需要明确 worker 身份、device 映射和通信域。

下一课我们终于可以学真正的“数据怎么交换”：broadcast、all-reduce、all-gather、reduce-scatter、all-to-all。届时每个 collective 都只问三件事：哪些 ranks 参加？开始时每人有什么 tensor？结束时每人得到什么？

CHECKPOINT04.1

如果 rank 身份还混乱，先别进 collectives。

1. 两台机器、每台 4 GPU，global rank 6 的 local rank 可能是多少？
在常见每节点 4 processes 的连续分配例子里，rank 6 位于第二台机器，对应 local rank 2。关键不是死记 6→2，而是理解 local rank 只在本节点编号，会在不同节点重复。
2. world size=8 是否意味着每个 process 都必须使用 8 张 GPU？
不是。world size 描述通信 group 中 processes 的数量。常见 one-process-per-GPU 配置里，每个 process 通常只绑定一个 GPU，而总共有 8 个 processes。
3. 为什么 Megatron 需要很多 process groups，而不是所有通信都用 global group？
不同 parallelism 只需要特定 ranks 互相通信。例如 TP ranks 要交换一个 layer 的分片结果，DP ranks 要同步同一模型分片的梯度。子 process group 可以把通信限制在正确的 ranks 集合中。
