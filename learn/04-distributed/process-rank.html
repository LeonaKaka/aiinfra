LESSON 04.1 · DISTRIBUTED约 50 min

进程、rank 与 process group：多张 GPU 先怎么“认识彼此”？

上一模块已经知道：cuda:0 和 cuda:1 是不同设备，数据不会自动共享。现在第一次真正进入分布式。开始时别急着学 all-reduce；先回答更基础的问题：谁在控制 GPU 0？谁在控制 GPU 1？它们如何获得唯一编号？哪些进程属于同一个通信小组？Megatron 后面所有 TP / PP / DP 通信，都建立在这套身份系统上。

这节课结束时，你应该能做到：
  • 区分 process、global rank、world size、local rank。
  • 理解“常见的一进程一 GPU”是部署模式，而不是分布式数学定义。
  • 看懂 torchrun --nproc-per-node=... 大致做了什么。
  • 理解 init_process_group() 为什么需要 peers 先完成发现和初始化。
  • 解释 process group 为什么是 Megatron 创建 TP / DP / PP 子通信域的基础。
  • 知道 collective 调用如果不同 rank 对 group/顺序理解不一致，为什么容易 hang。
01 · FIRST: A PROCESS IS A PROGRAM INSTANCE

多 GPU 训练里，一个常见模式是启动多个 Python processes，每个 process 绑定一张 GPU。

假设一台机器有 4 张 GPU。常见 PyTorch/NCCL 训练部署会启动 4 个 Python processes：

PROCESSrank 0GPU 0
PROCESSrank 1GPU 1
PROCESSrank 2GPU 2
PROCESSrank 3GPU 3

每个 process 有自己的 Python interpreter、程序状态、tensor / model 对象。它们不是通过 Python 变量直接读彼此的 GPU memory；要同步 tensor，必须发生显式 distributed communication。

不是共享一份 Python 对象rank 0 的 model 和 rank 1 的 model 是各自进程里的对象。
通信是显式系统行为变量名相同不代表内容会自动同步；需要 collective / P2P 等通信。
02 · RANK IS THE GLOBAL ID

global rank 是这个分布式 world 里 process 的唯一编号。

global rank某个 process 在整个默认 world / group 里的唯一编号，通常从 0 到 world_size-1。
world size这个通信世界里一共有多少个 processes。
local rank当前 process 在本机上的编号，常用于把 process 映射到本机 GPU。

单机 4 GPU 时 global rank 和 local rank 恰好都可能是 0、1、2、3，所以新手很容易把两者当成同一件事。多机以后这个错觉立刻消失。

03 · GLOBAL RANK ≠ LOCAL RANK

两台机器、每台 4 GPU：local rank 会重复，global rank 不会。

把 launcher、rendezvous、process identity、local GPU binding 与 process groups 放在同一张图里：

PROCESS → IDENTITY → DEVICE → GROUP2 nodes · 4 processes per node
三个层级不要混：global rank 回答“整个 job 里这个 process 是谁”；local rank 回答“它在当前 node 上排第几，常绑定哪张本地 GPU”；process group 回答“这一次通信到底允许哪些 global ranks 参加”。

这里 WORLD_SIZE=8。Node B 上的 local_rank=0 可以对应 global rank 4，而不是 rank 0。local rank 只要求在本机语境里有意义，不是全局唯一 ID。

以后写“只让 rank 0 保存 checkpoint”时，应判断 global rank；而“这个 process 使用本机哪张 GPU”通常根据 local rank 做 device mapping。

04 · WHAT TORCHRUN DOES FOR YOU

torchrun 会把同一个脚本启动成多个 processes，并给它们分配分布式身份环境。

shellsingle node · 4 GPUs
torchrun --standalone --nproc-per-node=4 hello_dist.py

粗略看，它会启动 4 份 hello_dist.py。每个 process 能从环境变量看到自己的身份，例如：

environmentone process might see
RANK=2
WORLD_SIZE=4
LOCAL_RANK=2
MASTER_ADDR=...
MASTER_PORT=...

多节点时 launcher / rendezvous 配置会更复杂，但核心不变：每个 process 最终需要知道自己是谁、world 中有多少 peers，以及去哪里完成初始化。

05 · INIT_PROCESS_GROUP

启动了多个进程还不够：它们还要加入同一个通信世界。

PyTorch 分布式代码通常先初始化默认 process group。对 CUDA GPU 训练，NCCL 是常见 backend：

python04_hello_dist.py
import os
import torch
import torch.distributed as dist

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

dist.init_process_group(backend="nccl")

rank = dist.get_rank()
world_size = dist.get_world_size()

x = torch.tensor([rank], device=f"cuda:{local_rank}")
print(f"rank={rank}, local_rank={local_rank}, x={x.item()}")

dist.destroy_process_group()

torchrun 提供的环境变量可以让 init_process_group() 使用 environment-variable initialization。初始化阶段需要 peers 彼此发现并建立 group/backend 状态；这不是“每个进程独自初始化完就算成功”。

官方参考：PyTorch · torch.distributed 与 torchrun tutorial。
06 · PROCESS ↔ DEVICE

为什么经常一进程一 GPU？因为身份和设备映射会变得非常清楚。

PROCESSglobal rank 5 · local rank 1
bind →
DEVICE ON THIS NODEcuda:1

“一进程一 GPU”不是 CUDA 的硬限制。一个 process 可以看到多个 GPU，一个 GPU 也可能被多个 processes 使用。但大规模训练里 one-process-per-GPU 是非常常见、容易组合 NCCL 与 DDP/模型并行的部署方式。

07 · PROCESS GROUPS

不是所有 global ranks 每一次都必须一起通信。

默认 process group 可以包含全部 8 个 ranks。但你还可以创建子 group，只让其中一部分 ranks 形成某次通信域。这正是 Megatron 组合多种 parallelism 的基础。

GLOBAL01234567
TP GROUP A01234567
TP GROUP B01234567
DP EXAMPLE01234567

上图只是帮助理解“同一批 global ranks 可以按不同规则切成不同 groups”，不是某个特定 Megatron 配置。真正 TP/DP/PP rank layout 取决于 parallel sizes 和 rank ordering。

以后读 Megatron 源码看到 tensor/data/pipeline process group 时，脑中应该出现的是一组具体 global ranks，而不是一个抽象类名。

08 · RENDEZVOUS: HOW PEERS MEET

多进程初始化，本质上还需要一个“大家去哪里碰头”的机制。

1launcher starts启动多个 processes。
2assign identityrank / world size / local rank。
3discover peers通过 rendezvous / store / env 配置找到彼此。
4build group初始化 backend 与 communicator 状态。

现在不需要背 TCPStore、etcd 或 elastic rendezvous 细节。先记住：分布式进程不是天然知道彼此；初始化系统必须解决 peer discovery 与一致的 membership。

09 · WHY DISTRIBUTED CODE HANGS

最典型的新手噩梦：一个 rank 在等，另一个 rank 根本没来。

Collective 通常要求 group 里的相关 ranks 以兼容顺序参与。如果 rank 0 调用了某个 collective，而 rank 1 走了另一条 if 分支没有调用，rank 0 很可能一直等待 peer。

分布式 debugging 的第一反应之一：

每个 rank 现在走到哪一行？参与同一个 collective 的 ranks 是否一致？调用顺序、tensor shape / dtype、process group 是否一致？

下一课你会看到，“hang”经常不是网络坏了，而是程序让不同 ranks 对通信 contract 产生了不同理解。

10 · CONNECT TO MEGATRON AND VLLM

rank / group 是训练与推理系统共同的底层语言。

Megatron把 global ranks 组织成 tensor-parallel、pipeline-parallel、data-parallel、context/expert-parallel groups；不同 group 执行不同 collectives。
vLLM / distributed serving多 GPU TP workers、跨进程执行器、P/D 节点同样需要明确 worker 身份、device 映射和通信域。

下一课终于可以学真正的“数据怎么交换”：broadcast、all-reduce、all-gather、reduce-scatter、all-to-all。届时每个 collective 都只问三件事：哪些 ranks 参加？开始时每人有什么 tensor？结束时每人得到什么？

CHECKPOINT04.1

如果 rank 身份还混乱，先别进 collectives。

1. 两台机器、每台 4 GPU，global rank 6 的 local rank 可能是多少？
在常见每节点 4 processes、连续 global rank 分配的例子里，rank 6 位于第二台机器，对应 local rank 2。关键不是死记 6→2，而是理解 local rank 会在不同节点重复。
2. world size=8 是否意味着每个 process 都必须使用 8 张 GPU？
不是。world size 描述通信 world 中 processes 的数量。常见 one-process-per-GPU 配置里，每个 process 通常只绑定一张 GPU，总共有 8 个 processes。
3. 为什么 Megatron 需要很多 process groups，而不是所有通信都用 global group？
不同 parallelism 只需要特定 ranks 互相通信。例如 TP ranks 交换 layer 分片结果，DP ranks 同步同一模型分片对应的训练状态。子 group 把通信限制在正确的 ranks 集合。
