LESSON 05.6 · MEGATRON约 65 min

Context Parallel：当 sequence 长到一张 GPU 连 Attention activations 都放不下。

SP 已经在 LayerNorm、dropout、残差连接等区域把 token 分片存放，但 Attention 仍然需要跨 token 的全局上下文。CP 再往前一步：让不同 ranks 负责不同 sequence shards，连 Attention 本身也跨 shards 并行；至于远端上下文怎样交换，并不只有 Ring 一种实现。

这节课结束时，你应该能做到：
  • 解释 CP 和 SP 都切序列，但为什么不是同一个东西。
  • 先用“每个 rank 负责一部分 query tokens”建立序列分片视角，并知道 A2A 模式会进一步重排 head / sequence 布局。
  • 解释为什么在 P2P / all-gather 心智模型里，local Q 仍然需要整个可见上下文的 K/V 信息。
  • 理解 cp_comm_type='p2p' 时 Ring KV 交换的基本思路。
  • 知道当前 Megatron 还支持 all_gather、a2a、a2a+p2p，不能把 CP 定义成“环形通信”。
  • 知道当前 MCore 对因果 Attention 常用交错分片来平衡负载，不能把“CP rank = 单个连续 token range”当成实现不变量。
  • 知道 GQA / MQA 为什么能直接降低以 K/V 为主的数据交换量。
  • 在本课的稠密 Transformer 设定下正确计算 TP / PP / CP / DP rank 关系，并知道 MoE 的专家进程组会在下一课单独处理。
01 · 长上下文如何改变显存规模

序列从 4K 变 32K，不只是“多算八倍 token”。

训练长上下文时，大量 activations 会随 sequence length 增长；Attention 还要求每个 query 根据 mask 规则访问其它 token 的 K/V。即便 FlashAttention 避免显式物化巨大 S×S score matrix，Q/K/V 与其它 activations 的保存、计算和通信仍然随 S 增长。

0–4K4–8K8–12K12–16K16–20K20–24K24–28K28–32K

一种粗暴办法是继续增大 TP，但这会把 Linear GEMM也切得越来越小，通信占比可能上升。CP 的想法是：既然真正变长的是序列，就沿序列/上下文维增加并行度。

02 · CP 切分输入与激活

先用“每个 rank 一部分 tokens”建立数学模型，再看当前 MCore 为什么常把它做成交错分片。

最简单的教学图可以把 8K 序列直接切成两个连续 4K chunks。但对因果 Attention 来说，越靠后的 query 通常能看到越长的 prefix；如果简单连续切，后半段 rank 的 Attention 工作会更重。当前 MCore 的常见 per-sequence 路径会先切成 2 × CP 个等长 chunks，再做 zigzag partitioning（交错分片：把前后位置的 chunks 搭配分给不同 ranks，以平衡因果 Attention 的计算量）。

CP=2 · RANK 0chunk 0 + chunk 3early + late tokens
CP=2 · RANK 1chunk 1 + chunk 2middle partitions

也就是说，CP 的不变量是“每个 rank 只负责序列的一部分”，不是“每个 rank 永远拿一个连续区间”。具体分片还会随 packed sequence（打包序列：把多条不同长度样本拼入同一训练序列以减少补齐 token）、hybrid CP（混合上下文并行：把不同 CP 通信方式组合到不同拓扑层级）和 contiguous CP（连续分片上下文并行：让每个 rank 持有连续 token 区间）等路径变化。

CP 的难点不是 split 本身。难点是怎样让 local Q 获得正确的全局上下文 K/V，同时不把每张卡重新撑成“持有完整序列的单卡 Attention”。

当前 get_batch_on_this_cp_rank() 会在 per-sequence zigzag、per-document zigzag、hybrid CP 与 contiguous CP 等路径间分派；per-sequence zigzag 的源码例子明确写着 CP=2 时 (chunk0, chunk3) → GPU0、(chunk1, chunk2) → GPU1。
03 · local Q，跨分片 KV

先用 local Q + 远端 K/V 建立直觉；不要把这种布局误当成所有 CP 算法都必须遵守。

LOCAL QUERYQlocal~ [S/CP, heads, d]
attends to →
visible 上下文 KV
KV CONTEXTlocal + remote shardsstream / gather / redistribute

最容易理解的教学版是先 all-gather K/V，再算 Attention。它很直观，但会让每个 rank 临时拿到更大的 K/V view。另一类做法是流式交换 K/V；还有 Ulysses（Ulysses 上下文并行：用 all-to-all 在序列维与 attention-head 维之间重排数据）风格的 A2A 重排。因此“Q 留在本地、KV 在 ranks 间流动”只是 P2P Ring 最直观的实现心智模型，不是 CP 的定义。不同通信算法改变数据布局，但都要满足同一个数学目标：每个 query 必须获得它应该可见的上下文信息。

04 · P2P 模式：环形交换 KV

cp_comm_type='p2p'：Q 留在本地，KV 沿 Ring 流动；每收到一块，就把它并入本地 Attention 结果。

下面画的是逻辑数据流：四个 CP ranks 各自保留 local Q 与 attention accumulator（Attention 累加器：逐块合并局部 Attention 结果所需的数值状态），只把当前 K/V chunk 传给下一个 rank。Rank 0 的例子里，KV₀、KV₃、KV₂、KV₁ 依次到达；实际哪些 token pairs 需要计算、每轮工作量多少，仍由 causal/window mask 与具体 CP 分片决定。

CONTEXT PARALLEL · CP=4P2P ring · logical KV movement
Ring 的核心不是“把完整 KV all-gather 到每张卡”。它让 local Q 保持原地，远端 K/V 逐块经过；Attention kernel 对每块做局部贡献并用稳定的分块 softmax/accumulation 逻辑合并，因此完整上下文的数学结果可以在不长期常驻完整 K/V 的情况下得到。
当前 TransformerConfig.cp_comm_type 对 p2p 的源码说明仍是：在 Ring topology 中交换 KV chunks，P2P 为异步通信，并可与 Attention compute overlap。
05 · P2P 通信如何与 Attention 计算重叠

P2P ring 的系统价值之一，是给“边收下一块、边算当前块”留下空间。

NETWORK / P2Preceive KV chunk n+1async receive next KV chunk。
∥
ATTENTION计算 Qlocal × KVn当前 KV chunk 被 attention kernel 消费。
→
NEXT ROUNDKVn+1 ready继续下一块。
→
MERGEcorrect attention result用数值稳定的分块 attention 逻辑组合各 chunk 贡献。

当前 Megatron cp_comm_type='p2p' 配置说明明确写着 P2P Ring 是异步的，并可与 Attention compute overlap。能 overlap 不等于通信一定被完全隐藏；仍要看 CP 并行度、KV 数据量、互连带宽与 Attention kernel 时长。

06 · CP 到底节省哪部分显存

主要收益是：可沿 context shard 的 activations 不必在每张 GPU 完整复制。

CP = 1~ S × activations-per-token单 rank 处理整个序列。
→
CP = p~ (S/p) × activations-per-token可分片 activations 在每个 rank 上约随 CP 并行度下降。

实际峰值还包含 K/V exchange buffer、Attention 实现的 workspace、TP/PP/DP 状态等，所以不能把“整个 GPU 显存”简单除以 CP。

07 · GQA / MQA 如何降低 KV 通信量

K/V heads 越少，每个 token 的 K/V 表示越窄。

02.2 已经学过 GQA：很多 Q heads 共享较少的 KV heads。对于以 K/V 交换为主的 CP 模式，这会减少每个 context shard 需要搬的 K/V 数据量；具体收益还受 Attention 后端、TP/CP layout 和通信算法影响。

MHANkv = NqKV 最宽。
GQANkv < Nq共享 KV heads，K/V 更窄。
MQANkv = 1KV 最窄，但模型质量与实现权衡由架构决定。

这条线以后会直接通向 vLLM KV Connector。训练 CP 和推理 KV 传输的协议不同，但都必须先从 KV 张量的 shape 计算真实数据量。

08 · CP group 与 dense TP 正交

TP=4、CP=2 时，同一个稠密 Transformer 并行网格可以看成 4 个 TP coordinates × 2 个 context shards。

用 8 GPU 的 rank-group 直觉图：GPU0–3 处在一个 CP coordinate，GPU4–7 处在另一个；对应 CP peers 是相同 TP coordinate 的 ranks。这里的分片 A/B 只是 rank-grid 标签，不表示真实 token 一定连续：

TP GROUP · PARTITION AG0G1G2G3G4G5G6G7
TP GROUP · PARTITION BG0G1G2G3G4G5G6G7
CP PAIRS0↔41↔52↔63↔74↔05↔16↔27↔3

坐标感很重要：dense TP 分 hidden/features；CP 分上下文。一个 rank 会同时有 TP coordinate、CP coordinate、PP stage 和 DP replica identity。

按本课配置，额外模型分片轴都取 1，因此 parallel_state.py 中 dense rank generator 的有效模型规模就是 TP × PP × CP，再由 DP = world_size / model_size 得到数据并行度。
09 · CP 不只有一种通信算法

当前 Megatron 的 cp_comm_type 支持四类主要选择。

P2PRing KV 交换异步 P2P；可与 Attention compute overlap。
ALL_GATHERall-gather full KV先获得完整 K/V view 再计算；当前源码说明里不是异步 overlap 路径。
A2Ahead / sequence redistribution类似 Ulysses：在 CP group 内用 all-to-all 在 head 与序列分布之间重排。
A2A + P2Phierarchical CP（分层上下文并行：在不同硬件层级组合 A2A 与 P2P）把两种方式组合到不同层级的 topology 上。

TransformerConfig.cp_comm_type 当前明确列出 p2p、all_gather、a2a、a2a+p2p，而且可以按层指定列表。学习时先掌握数学不变量：local Q 必须获得正确的远端上下文信息；通信算法是实现选择。

源码配置：TransformerConfig.cp_comm_type。当前源码同时注明 p2p 可异步重叠执行，而 all_gather 不是异步重叠执行路径。
10 · 再区分一次 SP 与 CP

最稳的区别：Attention 本身是否保持 context shard。

SEQUENCE PARALLELTP 区域之间分片部分 activations重点减少 LayerNorm、dropout、residual 等区域的 replication；进入相应 TP 计算边界时通过 all-gather / reduce-scatter 配合。
CONTEXT PARALLELAttention 本身也沿序列/上下文分布network input 与 Attention activations 继续保持 context shard，并用 P2P/A2A/all-gather 等方式补齐跨分片依赖。
11 · 把配置读成物理布局

先只算 CP 所在的稠密并行网格；专家并行留到下一课。

shellconceptual Megatron setup

--tensor-model-parallel-size 4
--pipeline-model-parallel-size 1
--context-parallel-size 4
--cp-comm-type p2p

# 本课设定：没有其它额外模型分片轴
# local context capacity ≈ 32768 / 4 = 8192 tokens
# 单份模型跨 TP × PP × CP = 16 GPUs
# 若 world_size = 64，则 DP = 64 / 16 = 4

在这个教学设定里，一份稠密 Transformer 跨 TP × PP × CP 张 GPU；剩余的 world size 才形成 DP replicas。这样先把 CP 放进已经熟悉的 TP / PP / DP 坐标系就够了。不要在这里提前把 EP 机械乘进去：MoE 的 expert process groups 有单独的 rank construction，05.7 会专门解释。

本课只保留一个检查法：看到 context_parallel_size，先问“同一 TP coordinate 的哪些 ranks 构成 CP group”，再算每个 rank 负责多少上下文；涉及专家层时再切换到下一课的 expert grid。

源码阅读顺序：先在 transformer/attention.py 看 cp_comm_type 与 CP process group 怎样传给 core attention；再到 extensions/transformer_engine.py 找 TEDotProductAttention，核对 CP group 与通信模式怎样交给后端；rank 关系则回到 parallel_state.py。
CHECKPOINT05.6

确认你已经能把“数学目标”“token 分片”和“communication algorithm”分开。

1. CP=4 时，一个 rank 只负责大约 S/4 个query tokens，为什么不能只保留本地 K/V 就结束？
因为 self-attention 的 local query 仍可能按 mask 规则访问其它 context shards。必须通过某种 CP 通信获得相应 K/V 信息。
2. 为什么“CP rank 0 = 序列前半段”不能当成实现不变量？
当前 MCore 为因果 Attention 负载均衡常使用 zigzag partitioning。CP=2 的 per-sequence 例子会把 4 个 chunks 分成 (0,3) 给 rank0、(1,2) 给 rank1；packed/hybrid/contiguous CP 还可能走其它分片路径。
3. 为什么不能说“CP 就是 Ring Attention”？
Ring P2P 是当前 Megatron 的一种 CP 通信模式。cp_comm_type 还支持 all_gather、a2a、a2a+p2p。CP 定义的是 context shard 与 Attention 的跨分片正确性，不是某个固定 collective。
4. 在本课设定里，64 张 GPU、TP=4、PP=1、CP=4，且没有其它模型分片轴时，DP 是多少？
一份稠密模型占用 4 × 1 × 4 = 16 张 GPU，因此 DP = 64 / 16 = 4。如果进入 MoE 专家层，不要继续在这个式子外机械乘 EP；05.7 会单独看 expert process groups。
