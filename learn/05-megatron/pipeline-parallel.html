LESSON 05.4 · MEGATRON约 70 min

流水线并行：把 Transformer 层按深度分到不同 GPU。

张量并行是“一个层内大家一起算”，流水线并行则换了一个维度：前几层放在流水线阶段 0，中间几层放在流水线阶段 1，后几层继续往后。这样单张图形处理器（GPU）不再保存整模型深度，但代价是前向激活值要沿流水线向后续阶段传递，反向梯度则沿相反方向返回。

这节课结束时，你应该能做到：
  • 解释流水线并行（PP）与张量并行（TP）的切分维度为什么完全不同。
  • 把 24 层 Transformer 按 PP=4 切成四个流水线阶段。
  • 理解前向激活值发送与反向梯度发送的点对点通信（P2P）数据流。
  • 解释为什么不切微批次会产生严重流水线气泡。
  • 理解一前向一反向（1F1B）的预热 / 稳态 / 收尾三个阶段。
  • 知道 Megatron 的非交错 / 交错流水线调度对应哪些源码入口。
01 · 沿模型深度切分

24 层 Transformer，PP=4：每个流水线阶段先放 6 层。

阶段 0Layers 1–6
阶段 1Layers 7–12
阶段 2Layers 13–18
阶段 3Layers 19–24

每个流水线阶段只保存自己负责的 Transformer 层及相关参数/优化器状态/激活值s。这样模型深度带来的显存被分摊到多个各个 rank。

PP RANK 0L1–L6input → hidden₆
PP RANK 1L7–L12hidden₆ → hidden₁₂
PP RANK 2L13–L18hidden₁₂ → hidden₁₈
PP RANK 3L19–L24hidden₁₈ → logits/loss

和 TP 不同，PP 流水线阶段之间通常不是每一层做 all-reduce，而是在流水线阶段边界通过 point-to-point 通信传激活值。

02 · 前向传激活，反向传梯度

Pipeline 的接口就是流水线阶段边界那块激活值张量。

FORWARD阶段 0 → 阶段 1发送流水线阶段 0 的输出激活值
激活值 →
← dActivation
BACKWARD阶段 1 → 阶段 0把对边界激活值的梯度传回去

因此 PP 的核心通信 primitive 更接近 send / recv，而不是 TP 那种层-internal 集合通信。Megatron Core 当前的 P2PCommunicator 就专门管理相邻流水线流水线阶段的张量交换s。

官方应用程序编程接口（API）：core.流水线_parallel.p2p_通信。当前文档把 P2PCommunicator 定义为负责 consecutive 流水线流水线阶段之间张量交换的通信器。

05 · 1F1B

“一次 forward、一次 backward”不是口号，而是每个流水线阶段在依赖允许时形成的本地执行顺序。

下面用 PP=4、4 个微批次es、每个 forward/backward 都视为一个等长 slot 的教学模型。通信时间先忽略，只保留真正的数据依赖。绿色是 forward，蓝色是 backward，空格就是无法被消掉的等待。

NON-INTERLEAVED 1F1B · PP=4 · M=4equal-cost teaching model
1F1B 真正的意思是“每个流水线阶段的本地顺序尽量交替”，不是所有流水线阶段同步一起 F、再一起 B。最后一个流水线阶段最早拿到 loss 梯度，因此最早进入 backward；梯度再像波一样向前面的流水线阶段传播。

这个时间图是为了把依赖画清楚，不是性能预测器。真实 Megatron 里 F/B 时长可能不相等，通信也不是零成本，而且重叠执行、recompute、interleaving 都会改变实际时间线。

06 · 更多微批次如何降低相对气泡

流水线 depth 固定时，微批次es 越多，填充/排空成本占比通常越小。

用最简单的 forward-only、每流水线阶段等时长模型举例：有 p 个流水线阶段、m 个微批次es，完成所有 forward 需要大约 m + p - 1 个流水线阶段-time slots。于是理想化 utilization 可以写成：

SIMPLIFIED FORWARD-ONLY INTUITIONutilization ≈ m / (m + p - 1)

这不是完整 1F1B 训练的通用性能公式，只是用来建立直觉：流水线越深，填充成本越大；微批次es 越多，bubble 的相对占比越容易被摊薄。真实效率还会受 F/B 时长不对称、流水线阶段 imbalance、通信、recompute 等影响。

07 · 交错 / 虚拟流水线

一个物理 GPU 还可以持有多个“虚拟流水线阶段 / model chunks”。

非 interleaved PP 里，一个 physical rank 常对应一段连续层。Interleaved schedule 则把模型切成更多 chunks，让同一个 rank 持有多个不连续 chunks，并让微批次es 在这些 virtual 流水线阶段间流动。

NON-INTERLEAVED每个 rank 一段连续层
GPU0: L1–L4GPU1: L5–L8GPU2: L9–L12GPU3: L13–L16
INTERLEAVED IDEA每个 rank 多个 model chunks
GPU0: chunk AGPU0: chunk EGPU1: chunk BGPU1: chunk F…

这样可以缩小 virtual 流水线流水线阶段的粒度，增加重叠执行机会、降低某些 bubble，但 schedule 与通信会更复杂。Megatron 当前 Parallelism Guide 使用 --num-layers-per-virtual-pipeline-stage 配置 virtual 流水线。

官方指南：Parallelism Strategies Guide；当前 PP 示例包含 --pipeline-model-parallel-size 和 --num-layers-per-virtual-pipeline-stage。
08 · PP 和 TP 如何组合

一个流水线流水线阶段本身可以不是一张 GPU，而是一整个 TP 进程组。

例如 PP=4、TP=2，一份模型就需要 8 张 GPU。每个流水线阶段由两张 GPU 共同完成内部张量并行：

PP 阶段 0
TP0TP1
PP 阶段 1
TP0TP1
PP 阶段 2
TP0TP1
PP 阶段 3
TP0TP1

流水线阶段内是 TP 集合通信s，流水线阶段间是 PP P2P。于是同一个 rank 同时处在张量-model-parallel 进程组和流水线-model-parallel 进程组中。05.1 的“一个 world，多种进程组s”现在真正开始工作。

09 · PP 带来什么，又付出什么

PP 不是“免费把层分开”，它把问题从显存转成流水线调度。

维度收益代价
Parameter 内存每个流水线阶段只保存部分层。流水线阶段划分不均会导致内存 / 计算 imbalance。
计算不同流水线阶段可并行处理不同微批次es。fill / drain 会产生 bubble。
Communication不需要像 TP 那样每层频繁全组集合通信。流水线阶段 boundary 激活值 / 梯度必须 P2P 传输。
调度1F1B / interleaving 可提高利用率。微批次数、virtual 流水线阶段、recompute 都会相互影响。

CHECKPOINT05.4

确认你能把流水线当成一条真实的数据生产线。

1. TP 和 PP 最大的区别是什么？
TP 在一个层内沿张量/feature 维分工；PP 沿模型深度分层，把不同层 ranges 放在不同流水线阶段。它们因此使用不同通信：TP 更依赖集合通信s，PP 更依赖流水线阶段间 P2P。
2. 微批次为什么能减少流水线气泡？
流水线阶段 0 处理完 MB0 并发给流水线阶段 1 后，可以立刻继续 MB1；于是不同流水线阶段同时处理不同微批次es，避免只有一个流水线阶段忙而其他流水线阶段等待。
3. 1F1B 的三个阶段是什么？
Warmup 先灌流水线；稳态让各流水线阶段在依赖允许时尽量交替执行 forward/backward 微批次es；收尾在 forward 完成后排空剩余 backward。
