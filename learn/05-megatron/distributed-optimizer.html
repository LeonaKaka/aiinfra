Distributed Optimizer：Data Parallel 为什么还要把 optimizer states 再切一遍？

Data Parallel 的基本逻辑是“每个 replica 看不同数据，但最终保持同一套模型参数”。最直接的实现会让每个 Data Parallel (DP，数据并行) rank 都保存一整份 gradients、Adam states、32-bit Floating Point (FP32，32 位浮点) main parameters 等训练状态。问题是：这些状态很大，而且不同 DP ranks 上大量重复。Megatron Distributed Optimizer 就从这里下手——让 DP ranks 分工保存和更新 optimizer state。

这节课结束时，你应该能做到：
  • 解释普通 Data Parallel 为什么会复制 optimizer states。
  • 理解 Distributed Optimizer 与 Tensor Parallel 的差别：前者沿 DP replicas 分训练状态，后者沿 Tensor Parallel (TP，张量并行) group 分模型计算。
  • 看懂 gradient reduce-scatter → local optimizer step → parameter all-gather 这条主数据流。
  • 理解为什么 Megatron 会使用 contiguous parameter / gradient buffers 和 buckets。
  • 知道 --overlap-grad-reduce 与 --overlap-param-gather 分别在隐藏哪段通信。
  • 理解“省多少显存”取决于 dtype 和 DP size，不能简单记成一个固定倍数。
01 · THE DP REDUNDANCY

四个 DP ranks，如果每张卡都保存同样的 Adam 状态，就有四份重复。

先把 TP/Pipeline Parallel (PP，流水线并行) 暂时忘掉。假设现在只是 DP=4，而且每个 rank 都有相同模型副本：

DP RANK 0full training state
model paramsgradientsAdam mAdam vFP32 main params
DP RANK 1same copies
model paramsgradientsAdam mAdam vFP32 main params
DP RANK 2same copies
model paramsgradientsAdam mAdam vFP32 main params
DP RANK 3same copies
model paramsgradientsAdam mAdam vFP32 main params

这些 replicas 必须在数学上更新到相同模型，但这不意味着每个 rank 都必须永久保存每个参数对应的全部 optimizer state。只要训练过程能在需要时把结果同步回来，就可以把“更新所有参数”的工作按 DP ranks 分掉。

Distributed Optimizer 的问题域是 DP。它不是替代 TP/PP，而是在已经存在的 data-parallel replica 维度上减少训练状态重复。

02 · SHARD THE OPTIMIZER STATE

DP=4：每个 rank 只负责大约四分之一参数范围的 optimizer state 与更新。

DP RANK 0shard 0optimizer state for params 0…¼
DP RANK 1shard 1optimizer state for params ¼…½
DP RANK 2shard 2optimizer state for params ½…¾
DP RANK 3shard 3optimizer state for params ¾…1

每个 rank 在 backward 时仍会产生自己数据对应的 local gradients。但对于参数 shard 0，最终只需要 rank 0 持有“所有 DP ranks 聚合后的 shard-0 gradient”，然后 rank 0 用自己的 Adam state 更新这一段参数。

于是我们马上需要一个你已经学过的 collective：reduce-scatter。

03 · THE WHOLE UPDATE FLOW

关键不是“少存几份 Adam”，而是一次完整的 ownership 转移：full local gradients → reduced shards → local update → synchronized model params。

下面沿用 NVIDIA 当前文档里的 16-element / DP=4 教学尺度。每个 rank 从自己的数据得到完整 local gradient buffer；reduce-scatter 后，每个 rank 只拥有四个已经跨 DP 聚合的 gradient elements；它只更新自己的 FP32 main-param / Adam shard，最后再 all-gather 回下一轮 forward 使用的模型参数 buffer。

DISTRIBUTED OPTIMIZER · DP=4gradient ownership → parameter synchronization
最重要的不变量：optimizer/master state 可以长期按 DP rank 分片，但 data-parallel forward 仍需要数学上一致的模型参数。于是 reduce-scatter 把“谁负责更新哪一段”分出去，parameter all-gather 再把更新结果同步回模型参数 buffer。

这条链把之前几个模块真正串起来了：autograd 产生 gradients；DP collective 改变 gradient ownership；optimizer 在本地 shard 上更新；参数同步后下一轮 forward 才能继续。Megatron 再用 contiguous buffers、buckets 和 overlap 尽量把这两次通信隐藏进计算。

NVIDIA 当前 Distributed Optimizer 文档的 Key Steps 明确采用同一条路径：16-element gradient buffer → DP reduce-scatter → 每 rank 4 个 reduced elements → local optimizer step → 把 FP32 main-param shard 写回 compute-param buffer → all-gather 完整 updated parameter buffer。
04 · WHY REDUCE-SCATTER INSTEAD OF ALL-REDUCE

普通 DP 想让每张卡拿完整 gradient；Distributed Optimizer 只需要每张卡拿自己负责的 gradient shard。

ORDINARY DP SYNCall-reduce gradients每个 rank 最后都得到完整 reduced gradient，因此每个 rank 都可以 independently update 全部参数。
DISTRIBUTED OPTIMIZERreduce-scatter gradients每个 rank 只得到自己负责的 reduced gradient shard，正好对应自己保存的 optimizer state / main-param shard。

Megatron Core 当前 DistributedDataParallelConfig 的 use_distributed_optimizer 源码说明仍然明确：启用时用 reduce-scatter 聚合 gradients；否则走 all-reduce。当前同一个配置里也仍保留 overlap_grad_reduce 与 overlap_param_gather。

官方 Application Programming Interface (API，应用程序编程接口)：core.distributed.distributed_data_parallel_config。其中 use_distributed_optimizer、overlap_grad_reduce、overlap_param_gather 都是当前配置项。
05 · HOW MUCH MEMORY DOES IT SAVE?

不要背“除以 DP”这么一句，因为并不是所有 bytes 都能同样分片。

官方当前 Distributed Optimizer 文档给了按参数 dtype / gradient dtype 区分的理论账本。设 data-parallel size 为 d：

配置普通 optimizerDistributed Optimizer
16-bit Floating Point (FP16，16 位浮点) params + FP16 grads20 bytes / param4 + 16/d
Brain Floating Point 16 (BF16，BF16 16 位浮点) params + FP32 grads18 bytes / param6 + 12/d
FP32 params + FP32 grads16 bytes / param8 + 8/d

例如 BF16 + FP32 grads、DP=4 时，理论主模型状态从 18 B/param 降到 6 + 12/4 = 9 B/param。DP 越大，shardable optimizer 部分越薄；但那几个不随 d 消失的常驻部分仍然存在。

OFFICIAL CURRENT MODEL · BF16 PARAMS / FP32 GRADSdistributed bytes / param = 6 + 12/d

这些是官方实现模型下的理论数字，不等于 nvidia-smi 最终峰值。activation、temporary buffers、fragmentation、communication workspace、模型特殊参数等都还在账本里。

官方说明：Megatron Core · Distributed Optimizer。当前文档仍给出 20 / 18 / 16 B/param 的 non-distributed 基线，以及 4+16/d、6+12/d、8+8/d 三条 distributed 理论公式。
06 · WHY CONTIGUOUS BUFFERS AND BUCKETS?

几十亿个参数不适合一个 tensor 发一次 collective：Megatron 把它们整理进连续 buffers，再按 bucket 通信。

真实模型有成千上万个 parameter tensors。如果每个小 tensor gradient 一 ready 就单独发一个 NVIDIA Collective Communications Library (NCCL，NVIDIA 集体通信库) collective，latency / launch overhead 会非常糟糕。Megatron 使用 contiguous parameter / gradient buffers，并把其中区间组织成 buckets。

CONTIGUOUS PARAM / GRAD BUFFER
bucket 0abucket 0bbucket 1abucket 1bbucket 2abucket 2bbucket 3abucket 3b

这样做有两个系统收益：第一，大块连续通信通常比大量 tiny collectives 更容易获得带宽；第二，某个 bucket 的 gradients 一旦全部 ready，就可以提前启动 reduce-scatter，不必等整个 backward 完成。

当前 core.distributed.param_and_grad_buffer API 提供 bucket-level start_grad_sync()、start_param_sync()、finish_param_sync() 等接口。
07 · OVERLAP GRAD REDUCE WITH BACKWARD

后面的 layer 还在 backward 时，前面已经 ready 的 gradient bucket 可以开始通信。

BACKWARDLayer 6Layer 5Layer 4Layer 3Layer 2Layer 1
GRAD Reduce-Scatter (RS，归约分散)—bucket 6bucket 5bucket 4bucket 3bucket 2

图不是精确 Megatron timeline，只表达目标：通信和独立的 backward General Matrix Multiply (GEMM，通用矩阵乘法) 同时占用不同资源，让 wall-clock 中“纯等待通信”的部分变少。对应当前参数就是 --overlap-grad-reduce。

Overlap ≠ 通信免费。如果计算与通信争抢相同瓶颈、bucket 划分不合适、网络太慢，overlap 可能隐藏不了全部通信，甚至带来额外干扰。

08 · OVERLAP PARAM GATHER WITH FORWARD

optimizer step 更新完参数 shards 后，下一轮 forward 不必先停下来等“全模型 gather 完”。

Distributed Optimizer 的另一个通信方向是 updated parameter all-gather。Megatron 可以把 parameter buffers 分 bucket，并在 forward 即将需要某一层参数之前预取/启动对应 all-gather。

PARAM All-Gather (AG，全收集)bucket L1bucket L2bucket L3bucket L4bucket L5—
FORWARDwait firstLayer 1Layer 2Layer 3Layer 4Layer 5

当前配置项 --overlap-param-gather 的语义就是把 parameter all-gather 与 forward compute overlap。当前 optimizer config 里也仍存在 overlap_param_gather_with_optimizer_step，用于进一步把 parameter-gather 工作与 optimizer step 重叠。

当前 API：core.optimizer.optimizer_config；其中包含 use_distributed_optimizer 与 overlap_param_gather_with_optimizer_step。
09 · DO NOT CONFUSE THIS WITH TENSOR PARALLEL

TP 和 Distributed Optimizer 都在“shard”，但 shard 的对象和执行时机完全不同。

TENSOR PARALLELshard model computation同一个 layer 的 weights / activations 被 TP ranks 分着算；forward 本身依赖 TP collectives。没有这些 peers，这个 layer 就算不完整。
DISTRIBUTED OPTIMIZERshard DP training state不同 DP replicas 数学上仍是同一个模型副本；optimizer update ownership / optimizer states 被分开，之后再同步 updated params。

因此它们可以组合：一个 rank 先属于某个 TP shard，再在“相同 TP/PP 位置的不同 data replicas”之间形成 DP group；Distributed Optimizer 正是在这个 DP group 上工作。

CHECKPOINT05.5

确认你能从 DP 冗余自己推导这套设计。

1. Distributed Optimizer 为什么更自然地用 reduce-scatter gradient，而不是 all-reduce？
因为每个 DP rank 只负责一个 optimizer/parameter shard。它只需要拿到自己那段“已经跨 DP ranks 归约”的 gradient；reduce-scatter 正好同时完成 reduction 和 shard distribution。
2. optimizer step 完以后为什么还需要 parameter all-gather？
不同 ranks 分别更新了不同参数 shards，但下一轮 data-parallel forward 需要各 replica 使用一致的模型参数。因此必须把 updated shards 同步/gather 到需要它们的 ranks。
3. --overlap-grad-reduce 真正想隐藏什么？
当某些 gradient buckets 已经 ready 时，提前启动它们的 DP all-reduce/reduce-scatter，同时 Graphics Processing Unit (GPU，图形处理器) 继续计算其它 layers 的 backward，尽量把通信时间藏在 backward compute 后面。
