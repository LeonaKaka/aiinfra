LESSON 05.7 · MEGATRON约 70 min

Expert Parallel：Router 一旦把 token 指向远端 expert，通信为什么会变成 many-to-many？

Dense Multi-Layer Perceptron (MLP，多层感知机) 是“所有 token 都经过同一组权重”。Mixture of Experts (MoE，混合专家模型) 改成：router 给每个 token 选择少数 experts，只执行被选中的 expert MLP。Expert Parallel 再把 expert 集合分到不同 ranks。于是系统问题不再是“把同一个 tensor 求和”，而是“每个 token–expert assignment 要去哪个 expert、那个 expert 在哪”。All-to-All 会自然出现，但它是 dispatcher 的一种实现，不是 Expert Parallel (EP，专家并行) 的定义。

这节课结束时，你应该能做到：
  • 理解 MoE layer = router + experts + sparse token-to-expert assignment。
  • 区分三种不同语义：逻辑 token ownership、expert parameter ownership、temporary compute ownership。
  • 从 routing 推导 many-to-many 数据移动为什么适合 All-to-All。
  • 看懂 dispatch → local expert General Matrix Multiply (GEMM，通用矩阵乘法) → combine → restore token order 的完整生命周期。
  • 知道当前 Megatron 训练 dispatcher 支持 allgather / alltoall / flex，且 flex backend 当前包括 DeepEP / HybridEP / NVIDIA Collective Communications Library (NCCL，NVIDIA 集体通信库)-EP。
  • 理解 dense grid 与 expert grid 是两套 rank generator 视角，EP 不是无条件在 TP×PP×CP×DP 外再乘一次。
  • 知道 load balance 与 grouped GEMM 分别在解决 routing 分布和本地 expert compute 两个不同瓶颈。
01 · DENSE MLP → MIXTURE OF EXPERTS

MoE 不是很多完整模型，而是把部分 FFN/MLP 层换成一组 experts。

TOKENShidden states[num_tokens, H]
→
ROUTERscore experts + top-k每个 token 选择少数 experts，例如 top-2。
→
EXPERT FFNsE₀, E₁, …, E₇只执行被路由到的专家。

比如有 8 个 routed experts，每个 token 只走 top-2。expert 参数量可以大幅增加，但单 token 只激活其中少数 expert，因此激活计算量不会简单乘以总 expert 数。

MoE 的核心先是稀疏激活。EP 是 experts 被放到不同 ranks 后，为了执行这种稀疏选择而引入的分布式布局。

02 · SHARD EXPERTS ACROSS RANKS

教学例：EP=4、8 个 experts，每个 EP rank 持有 2 个 local experts。

EP RANK 0Expert 0 · 1local expert parameters
EP RANK 1Expert 2 · 3local expert parameters
EP RANK 2Expert 4 · 5local expert parameters
EP RANK 3Expert 6 · 7local expert parameters

router 的选择不会尊重“token 原来在哪张 Graphics Processing Unit (GPU，图形处理器)”。rank 0 上的 token 可以被分到 rank 3 的 Expert 6，因此 hidden state 必须到达拥有目标 expert 的执行位置；expert 权重本身并不会跟着每个 token 搬过去。

这张图只说明 EP 轴。真实 Megatron 还可能给 expert 使用独立的 expert tensor-parallel size，并构造 expert-Data Parallel (DP，数据并行)。不要把一个 global rank 只想成“EP rank”。

03 · ROUTING CHANGES EXECUTION OWNERSHIP

真正要分清三件事：逻辑 token ownership 保持在 source rank；hidden state 会移动；expert compute 在 expert owner 上临时执行。

下面故意把例子简化成 EP=4、expert-TP=1、top-1 routing，目的是先把 ownership 看清。每个 source rank 都有自己的原始 tokens；router 只产生 destination expert 与 routing metadata；dispatcher 把 token hidden states 发到 expert owner；本地 expert GEMM 完成后，再把输出送回原始 token 所属的 rank 与位置。

EXPERT PARALLEL · OWNERSHIP LIFECYCLElogical source stays fixed · data moves to expert compute
最重要的不变量：EP 改变的是 hidden state 所在位置与某段时间内“谁执行这个 token 的 expert FFN”；logical token ownership 本身并没有被重新分配。source rank 需要保留足够的 permutation / routing 信息，才能在 combine 后恢复原 token order。

top-k 大于 1 时，一个逻辑 token 会产生多个 token–expert assignments。这些 assignments 可以被送到不同 expert owners；combine 阶段不仅要把结果送回来，还要按 routing weights 合并多个 expert outputs。于是通信规模更接近“assignment 数”，而不是只数原始 token 数。

04 · WHAT THE CURRENT ALL-TO-ALL DISPATCHER ACTUALLY DOES

EP-only 心智图很重要，但当前 Megatron 的 All-to-All dispatcher 还明确区分 EP communication 与 expert-TP communication。

当前 MoEAlltoAllTokenDispatcher 的源码注释把 workflow 写得很清楚：preprocess / permute → A2A(EP) → 如果 expert-Tensor Parallel (TP，张量并行) 大于 1，再做 AG(TP) 并整理 local expert chunks → expert compute → combine 前做 RS(TP) → A2A(EP) → unpermute。

dispatch_preprocess本地计算 destination counts、permutation 等 metadata；尽量不要在这里偷偷混入额外通信，以便后续 overlap。
token_dispatch主跨设备 transport。All-to-All 路径先在 EP group 做 destination-specific exchange。
dispatch_postprocess必要时处理 expert-TP 的 gather / chunk sorting，并整理成 local expert 可以消费的连续 token groups。
token_combineexpert outputs 反向跨设备交换；All-to-All dispatcher 把结果送回原 source rank，随后 combine postprocess / unpermute 恢复原逻辑位置。
为什么主图标了 expert-TP=1？因为这样一张图只回答 EP 的核心问题，不把 TP 的 gather/reduce-scatter 叠在同一个画布里。真正读源码时，再把 expert-TP 当第二层通信轴加进去。
当前源码：core/transformer/moe/token_dispatcher.py。类注释明确列出 All-to-All (A2A，全对全通信)(EP)、All-Gather (AG，全收集)(TP)、Reduce-Scatter (RS，归约分散)(TP)、reverse A2A 与 unpermute 的顺序。
05 · THE LOAD-BALANCE PROBLEM

Router 分布一旦很偏，最慢 expert/rank 会拖住整层。

理想情况是 token 在 experts 之间比较均衡。现实里 router 学到的分布可能很偏：

Expert 0
92
Expert 1
28
Expert 2
41
Expert 3
19

某个 expert 还在处理大量 assignments 时，其它 ranks 可能已经空闲。系统上的因果链是：router 分布 → per-expert assignment count → communication bytes + GEMM shape → straggler time。

当前 TransformerConfig.moe_router_load_balancing_type 默认是 aux_loss，并支持 seq_aux_loss、global_aux_loss、sinkhorn、quantile_balancing、none 等策略。容量控制是另一维：moe_expert_capacity_factor=None 表示默认不因 capacity 丢 token；设置 capacity factor 后还能配合 padding 等机制。

不要把“负载均衡”理解成 dispatcher 自动把 token 平均分掉。dispatcher 必须遵守 router 的 assignment；负载均衡主要通过 router 目标/偏置/capacity 策略改变 assignment 分布，然后系统层面的 A2A 和 expert GEMM 才会跟着变。
06 · MANY EXPERTS CREATE MANY SMALL GEMMS

通信结束以后还有第二个效率问题：每个 expert 收到的 token 数可能不大。

NAIVEE0 GEMM · E1 GEMM · E2 GEMM · …很多大小不同的小矩阵运算，launch/occupancy 问题更明显。
→
GROUPED GEMMgroup expert GEMMs把多个 expert matrix multiplies 以 grouped 方式执行，提高本地硬件利用率。

--moe-grouped-gemm 解决的是 local expert compute efficiency，不是 token dispatch 网络本身。不要把“Grouped GEMM”和“通信融合”混成一件事。

07 · EP DOES NOT FIX ONE DISPATCHER

当前训练配置明确支持 allgather、alltoall、flex。

ALLGATHERallgather dispatcher当前默认值仍是 allgather；实现会跨 TP×EP domain gather token/routing data，本地挑选属于 local experts 的 assignments，combine 使用 reduce-scatter。
ALLTOALLAll-to-All dispatcher直接表达 destination-specific exchange；当前 workflow 是 A2A(EP)，并在 expert-TP>1 时配合 AG/RS(TP)。
FLEXpluggable EP backends当前 moe_flex_dispatcher_backend 支持 deepep、hybridep、ncclep，默认是 DeepEP。

因此更准确的话是：EP 产生 destination-dependent token traffic；dispatcher contract 决定怎样搬这些 assignments。All-to-All 是最直观的实现，但不是定义本身。

当前 TransformerConfig.moe_token_dispatcher_type 类型为 allgather | alltoall | flex、默认 allgather；flex backend 当前为 deepep | hybridep | ncclep。
08 · EXPERT GRID IS NOT DENSE GRID × EP

TP、CP、EP 不能靠一个“把所有缩写乘起来”的公式理解。

DENSE GRIDdense TP × Pipeline Parallel (PP，流水线并行) × Context Parallel (CP，上下文并行) → dense DPAttention/dense Transformer 部分按 dense rank generator 组织。
EXPERT GRIDexpert-TP × EP × PP → expert-DPMoE expert 部分由另一套 expert rank generator 组织；当前 expert generator 里 cp=1。

当前 parallel_state.py 会单独计算 expert_tensor_parallel_size × expert_model_parallel_size × pipeline_model_parallel_size（再考虑实验性 expert GTP remat 轴），然后用 world size 除它得到 expert-DP。随后 expert_decoder_rank_generator 以 tp=expert_tensor_parallel_size、ep=expert_model_parallel_size、dp=expert_data_parallel_size、pp=...、cp=1 构造 expert groups。

这就是为什么 EP 不能机械地在 dense 总 GPU 公式外再乘一次。一个 global rank 同时参与 dense 与 expert 两套 group 关系；真正要问的是“当前这段 layer 用哪套 process group”。

当前实现：megatron/core/parallel_state.py，分别构造 dense rank generator 与 expert rank generator。
09 · EP MAKES OVERLAP MORE IMPORTANT

Token exchange 很重，工程优化会尽量把它藏进其它可并行计算窗口。

overlap_moe_expert_parallel_comm启用 expert communication 与其它计算的 overlap 路径。
delay_wgrad_compute延后部分 weight-gradient 工作，为 communication 暴露可利用的计算窗口。
moe_shared_expert_overlap让 shared-expert compute 与支持的 alltoall/flex dispatcher communication 并发。

这些选项高度版本相关，不能只背 CLI 名称。05.8 的核心方法仍然是：先画 dependency，再看 async launch / stream / wait，最后用 profiler 证明时间区间是否真的重叠。

CHECKPOINT05.7

把 EP 的 ownership、dispatcher 和 topology 三层分开。

1. 为什么 router 会自然产生 many-to-many traffic？
每个 source rank 的不同 token–expert assignments 可以指向不同 destination experts，而这些 experts 分布在不同 ranks；因此不是对同一个 tensor 做统一 reduction，而是 destination-dependent exchange。
2. top-k=2 时，为什么网络里搬运的基本对象更应该想成 assignment，而不是原始 token？
一个逻辑 token 会产生两个 token–expert assignments，可能去两个不同 experts。combine 后还要用 routing weights 合并两个 expert outputs，再恢复这个 token 的逻辑位置。
3. “EP = All-to-All”为什么不够准确？
All-to-All 是最直观的 dispatcher，但当前 Megatron 训练配置还支持 allgather 和 flex。EP 定义 expert placement / routing 的并行语义，不定义唯一 transport implementation。
4. 为什么不能写 world_size = TP×PP×CP×EP×DP 当成统一源码公式？
当前 Megatron 分别构造 dense grid 与 expert grid。dense grid 和 expert grid 使用不同 TP/EP/CP/DP 关系；expert generator 当前把 CP 轴设为 1，所以必须看具体 process-group construction。
