LESSON 05.7 · MEGATRON约 70 min

Expert Parallel：路由器一旦把 token 指向远端专家，通信为什么会变成多对多？

稠密 MLP 是“所有 token 都经过同一组权重”。MoE 则由 router（路由器：根据规则决定 token 应被送往哪个 expert）给每个 token 选择少数 expert（专家：MoE 中可被 router 独立选择的一套 FFN/MLP 参数与计算），只执行被选中的 expert MLP。Expert Parallel 再把 expert set 分到不同 ranks。于是系统问题不再是“把同一个 tensor 求和”，而是“每个 token 应该发给哪个 expert，以及那个 expert 位于哪个 rank”。All-to-All 会自然出现，但它只是分发器的一种实现，不是 Expert Parallel 的定义。

这节课结束时，你应该能做到：
  • 理解 MoE 层 = router + expert + 稀疏的 token→expert 分配关系。
  • 区分三种不同语义：逻辑 token 归属、expert parameters 归属、临时计算归属。
  • 从路由推导多对多数据移动为什么适合 All-to-All。
  • 看懂 dispatch → local expert GEMM → combine → 恢复 token 顺序的完整生命周期。
  • 知道当前 Megatron 训练分发器支持 allgather / alltoall / flex，且 flex 有多种通信后端。
  • 理解 dense grid 与 expert grid 是两套 rank 生成视角，EP 不是无条件在 TP×PP×CP×DP 外再乘一次。
  • 知道负载均衡解决路由分布不均，Grouped GEMM 则优化 local expert compute；两者不是同一个问题。
01 · 从稠密 MLP 到 MoE

MoE 不是很多完整模型，而是把部分 FFN/MLP 层换成一组 experts。

TOKENShidden states[num_token, H]
→
ROUTERscore expert + top-k（前 k 选择：为每个 token 选择得分最高的 k 个 experts）每个 token 只选择少数 experts，例如 top-2。
→
EXPERT FFNsE₀, E₁, …, E₇只执行被路由到的 experts。

比如有 8 个 routed experts，每个 token 只走 top-2。expert parameters 可以大幅增加，但单 token 只激活其中少数 experts，因此激活计算量不会简单乘以总 expert 数。

MoE 的核心先是稀疏激活。EP 是 experts 被放到不同 ranks 后，为了执行这种稀疏选择而引入的分布式布局。

02 · 把 experts 分到不同 ranks

教学例：EP=4、8 个 experts，每个 EP rank 持有 2 个 local experts。

EP RANK 0Expert 0 · 1local expert parameters
EP RANK 1Expert 2 · 3local expert parameters
EP RANK 2Expert 4 · 5local expert parameters
EP RANK 3Expert 6 · 7local expert parameters

router 的选择不会受“token 原来在哪张 GPU”限制。rank 0 上的 token 可以被分到 rank 3 的 Expert 6，因此 hidden state 必须到达拥有目标 expert 的执行位置；expert 权重本身并不会跟着每个 token 搬过去。

这张图只说明 EP 轴。真实 Megatron 还可能给 expert 使用独立的 expert TP（专家张量并行：在单个 expert 内再用 Tensor Parallel 分摊权重和计算），并构造 expert DP。不要把一个 global rank 只想成“EP rank”。

03 · 路由如何改变计算归属

真正要分清三件事：logical token ownership 保持在 source rank；hidden state 会移动；expert 计算在 expert owner 上临时执行。

下面故意把例子简化成 EP=4、expert-TP=1、top-1 路由，目的是先把归属关系看清。每个 source rank 都有自己的原始 token；router 只产生 destination expert 与 routing metadata（路由元数据：记录 token 应去哪个 expert 以及后续恢复顺序所需的控制信息）；dispatcher（分发器：按 routing result 把 token hidden states 送到目标 expert，再把结果送回）执行跨 rank 数据移动；local expert GEMM 完成后，再把输出送回原始 token 所属的 rank 与位置。

EXPERT PARALLEL · OWNERSHIP LIFECYCLElogical source stays fixed · data moves to expert compute
最重要的不变量：EP 改变的是 hidden state 所在位置与某段时间内“谁执行这个 token 的 FFN”；logical token 归属关系本身并没有被重新分配。source rank 需要保留足够的 permutation（排列映射：记录 token 数据被重排前后的位置对应关系）与 routing metadata，才能在合并后恢复原 token order。

top-k 大于 1 时，一个逻辑 token 会产生多个 token–expert assignment（token–expert 分配：一次“某个 token 由某个 expert 处理”的路由记录）。这些 assignments 可以被送到不同 expert owners；合并阶段不仅要把结果送回来，还要按 routing weight（路由权重：router 为被选 expert 分配的输出组合权重）合并多个 expert outputs。于是通信规模更接近 assignment count，而不是只数原始 token 数。

04 · 当前 All-to-All dispatcher 实际做什么

EP-only 心智图很重要，但当前 Megatron 的 All-to-All dispatcher 还明确区分 EP 通信与 expert TP 通信。

当前 MoEAlltoAllTokenDispatcher 的源码注释把 workflow 写得很清楚：preprocess / permute（重排：按目标 expert 重新排列 token 数据以便通信和本地计算） → A2A(EP) → 如果 expert TP 大于 1，再做 AG(TP) 并整理 local expert chunks → expert 计算 → 合并前做 RS(TP) → A2A(EP) → unpermute（逆重排：按保存的 permutation 把 expert outputs 恢复到原 token 顺序）。

dispatch_preprocess本地计算 destination counts、permutation 等 metadata；尽量不要在这里混入额外通信，以便后续 overlap。
token_dispatch主跨设备 transport。All-to-All 路径先在 EP group 做 destination-specific 交换。
dispatch_postprocess必要时处理 expert TP 的 all-gather / chunk sorting，并整理成 local experts 可以消费的 contiguous token groups。
token_combineexpert outputs 反向跨设备交换；All-to-All dispatcher 把结果送回原 source rank，随后合并 postprocess / unpermute 恢复原逻辑位置。
为什么主图标了 expert TP=1？因为这样一张图只回答 EP 的核心问题，不把 TP 的 all-gather/reduce-scatter 叠在同一个画布里。真正读源码时，再把 expert TP 当第二层通信轴加进去。
当前源码：core/transformer/moe/token_dispatcher.py。类注释明确列出 A2A(EP)、AG(TP)、RS(TP)、reverse A2A 与 unpermute 的顺序。
05 · 负载均衡

load balancing（负载均衡：让 token assignments 尽量不要集中到少数 experts 或 ranks）要解决路由分布过偏的问题。

理想情况是 token 在 experts 之间比较均衡。现实里 router 学到的分布可能很偏：

Expert 0
92
Expert 1
28
Expert 2
41
Expert 3
19

某个 expert 还在处理大量 assignments 时，其它 ranks 可能已经空闲。系统上的因果链是：router distribution → per-expert assignment count → 通信数据量 + GEMM shape → straggler（拖尾者：工作量最大、迫使其它 ranks 等待的慢参与者）耗时。

当前 TransformerConfig.moe_router_load_balancing_type 默认是 aux_loss，并支持 seq_aux_loss、global_aux_loss、sinkhorn、quantile_balancing、none 等策略。容量控制是另一维：moe_expert_capacity_factor=None 表示默认不因容量限制丢 token；设置 capacity factor（容量系数：控制每个 expert 可接收 token 数量上限的倍率参数）后还能配合补齐等机制。

不要把 load balancing 理解成 dispatcher 自动把 token 平均分掉。dispatcher 必须遵守 router 的分配关系；load balancing 主要通过 router 目标、偏置和容量策略改变分配关系，然后系统层面的 A2A 和 expert GEMM 才会跟着变。
06 · 很多 experts 意味着很多小 GEMM

Grouped GEMM（分组矩阵乘：把多个独立小 GEMM 作为一组执行以提高 GPU 利用率）解决本地 expert 计算过碎的问题。

NAIVEE0 GEMM · E1 GEMM · E2 GEMM · …很多大小不同的小矩阵运算，launch/occupancy 问题更明显。
→
GROUPED GEMMGrouped GEMMs把多个 expert matrix multiplies 作为一组执行，提高本地硬件利用率。

--moe-grouped-gemm 解决的是 local expert 计算效率，不是 token 分发网络本身。不要把 Grouped GEMM 和通信融合混成一件事。

07 · EP 不绑定某一种 dispatcher

当前训练配置明确支持 allgather、alltoall、flex。

ALLGATHERallgather dispatcher当前默认值仍是 allgather；实现会跨 TP×EP domain all-gather token/路由 data，本地挑选属于 local expert 的 assignments，合并使用 reduce-scatter。
ALLTOALLAll-to-All dispatcher直接表达 destination-specific 交换；当前 workflow 是 A2A(EP)，并在 expert TP>1 时配合 AG/RS(TP)。
FLEX可插拔 EP backends当前 moe_flex_dispatcher_backend 支持 DeepEP（DeepEP 通信后端：用于 MoE token dispatch/combine 的高性能 EP 通信实现）、HybridEP（HybridEP 通信后端：在 flex dispatcher 中融合 token 重排与 all-to-all 的专家并行实现）和 NCCL-EP（NCCL 专家并行后端：通过 Transformer Engine EP API 使用 NVIDIA NCCL Expert Parallelism），默认是 DeepEP。

因此更准确的话是：EP 产生 destination-dependent token traffic；dispatcher contract 决定怎样搬这些 assignments。All-to-All 是最直观的实现，但不是定义本身。

当前 TransformerConfig.moe_token_dispatcher_type 类型为 allgather | alltoall | flex、默认 allgather；flex 后端当前为 deepep | hybridep | ncclep。
08 · expert grid 不能简单理解成稠密网格 × EP

TP、CP、EP 不能靠一个“把所有缩写乘起来”的公式理解。

DENSE GRIDdense TP × PP × CP → dense DPAttention/dense Transformer 部分按 dense rank 生成器组织。
EXPERT GRIDexpert TP × EP × PP → expert DPMoE expert 部分由另一套 expert rank generator 组织；当前 expert generator 里 cp=1。

当前 parallel_state.py 会单独计算 expert_tensor_parallel_size × expert_model_parallel_size × pipeline_model_parallel_size，再考虑实验性 expert GTP remat 轴，然后用 world size 除它得到 expert DP。随后 expert_decoder_rank_generator 以 tp=expert_tensor_parallel_size、ep=expert_model_parallel_size、dp=expert_data_parallel_size、pp=...、cp=1 构造 expert process groups。

这就是为什么 EP 不能机械地在 dense 总 GPU 公式外再乘一次。一个 global rank 同时参与 dense 与 expert 两套 process-group relationships；真正要问的是“当前这段 layer 用哪套 process group”。

当前实现：megatron/core/parallel_state.py，分别构造 dense rank 生成器与 expert rank generator。
09 · EP 为什么更依赖通信重叠

Token 交换很重，工程优化会尽量把它藏进其它可并行计算窗口。

overlap_moe_expert_parallel_comm启用 expert communication 与其它计算的 overlap 路径。
delay_wgrad_compute延后部分 weight-gradient 工作，为通信暴露可利用的计算窗口。
moe_shared_expert_overlap让 shared-expert compute 与支持的 alltoall/flex dispatcher 通信并发。

这些选项高度版本相关，不能只背 CLI（命令行界面：通过终端参数和命令配置、启动或调试程序的接口）名称。05.8 的核心方法仍然是：先画依赖关系，再看异步 launch、stream 和等待，最后用 profiler 证明时间区间是否真的重叠。

CHECKPOINT05.7

把 EP 的 ownership、dispatcher 和 topology 三层分开。

1. 为什么 router 会自然产生多对多 traffic？
每个 source rank 的不同 token–expert assignments 可以指向不同 destination experts，而这些 experts 分布在不同 ranks；因此不是对同一个 tensor 做统一 reduction，而是 destination-dependent 交换。
2. top-k=2 时，为什么网络里搬运的基本对象更应该想成 assignment，而不是原始 token？
一个逻辑 token 会产生两个 token–expert assignments，可能去两个不同 experts。合并后还要用 routing weights 合并两个 expert outputs，再恢复这个 token 的逻辑位置。
3. “EP = All-to-All”为什么不够准确？
All-to-All 是最直观的 dispatcher，但当前 Megatron 训练配置还支持 allgather 和 flex。EP 定义 expert placement / 路由的并行语义，不定义唯一 transport implementation。
4. 为什么不能写 world_size = TP×PP×CP×EP×DP 当成统一源码公式？
当前 Megatron 分别构造 dense grid 与 expert grid。两套 grid 使用不同 TP/EP/CP/DP 关系；expert generator 当前把 CP 轴设为 1，所以必须看具体 process-group construction。
