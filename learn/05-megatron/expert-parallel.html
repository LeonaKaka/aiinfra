LESSON 05.7 · MEGATRON约 70 min

Expert Parallel：Router 一旦把 token 指向远端 expert，通信为什么会变成 many-to-many？

Dense MLP 是“所有 token 都经过同一组权重”。MoE 改成：router 给每个 token 选择少数 experts，只执行被选中的 expert MLP。Expert Parallel 再把 expert 集合分到不同 ranks。于是系统问题不再是“把同一个 tensor 求和”，而是“每个 token 要去哪个 expert，那个 expert 在哪”。All-to-All 会自然出现，但它是 dispatcher 的一种实现，不是 EP 的定义。

这节课结束时，你应该能做到：
  • 理解 MoE layer = router + experts + sparse token-to-expert assignment。
  • 解释 EP 为什么切 expert set，而 TP 切单个矩阵/hidden dimension。
  • 从 token routing 推导 many-to-many 数据移动为什么适合 All-to-All。
  • 理解 dispatch → local expert GEMM → combine 的生命周期。
  • 知道 Megatron 当前 dispatcher 支持 allgather / alltoall / flex，不能把 EP 背成固定 A2A。
  • 理解 dense grid 与 expert grid 是两套 rank generator 视角，EP 不是无条件在 TP×PP×CP×DP 外再乘一次。
  • 知道 load imbalance 与 grouped GEMM 分别优化“分得不均”和“本地 GEMM 太碎”两个不同问题。
01 · DENSE MLP → MIXTURE OF EXPERTS

MoE 不是很多完整模型，而是把部分 FFN/MLP 层换成一组 experts。

TOKENShidden states[num_tokens, H]
→
ROUTERscore experts + top-k每个 token 选择少数 experts，例如 top-2。
→
EXPERT FFNsE₀, E₁, …, E₇只执行被路由到的专家。

比如有 8 个 routed experts，每个 token 只走 top-2。expert 参数量可以大幅增加，但单 token 只激活其中少数 expert，因此激活计算量不会简单乘以总 expert 数。

MoE 的核心先是稀疏激活。EP 是当 experts 被放到不同 ranks 后，为了执行这种稀疏选择而引入的分布式布局。

02 · SHARD EXPERTS ACROSS RANKS

教学例：EP=4、8 个 experts，每个 EP rank 持有 2 个 local experts。

EP RANK 0Expert 0 · 1local expert parameters
EP RANK 1Expert 2 · 3local expert parameters
EP RANK 2Expert 4 · 5local expert parameters
EP RANK 3Expert 6 · 7local expert parameters

router 的选择不会尊重“token 原来在哪张 GPU”。rank 0 上的 token 可以被分到 rank 3 的 Expert 6，因此 hidden state 必须到达拥有目标 expert 的执行位置。

这张图只说明 EP 轴。真实 Megatron 还可能给 expert 使用独立的 expert tensor-parallel size，并构造 expert-DP。不要把一个 global rank 只想成“EP rank”。

04 · DISPATCH → EXPERT COMPUTE → COMBINE

先用 All-to-All dispatcher 建立最清楚的数据流。

1 · ROUTER / PERMUTEgroup by destination experttop-k + routing weights，把 tokens 排成适合传输与 expert GEMM 的顺序。
→
2 · DISPATCHAll-to-All path把 token hidden states 发到拥有目标 experts 的 ranks。
→
3 · EXPERTSlocal GEMMs每个 rank 对收到的 token groups 执行 local experts。
→
4 · COMBINEreverse exchangeexpert outputs 回到对应 token logical positions，再按 routing weights 合并。

当前 MoEAlltoAllTokenDispatcher 的代码/文档就实现这条路径。但这是具体 dispatcher class，不应反过来定义 EP。

源码入口：core/transformer/moe/token_dispatcher.py。
05 · THE LOAD-BALANCE PROBLEM

Router 分布一旦很偏，最慢 expert/rank 会拖住整层。

理想情况是 token 在 experts 之间比较均衡。现实里 router 学到的分布可能很偏：

Expert 1

Expert 2
41
Expert 3

某个 expert 还在处理大量 tokens 时，其它 ranks 可能已经空闲。于是 MoE 既要解决 routing correctness，也要处理 load balancing、capacity / drop 策略等算法约束。系统上最重要的因果链是：router 分布 → per-expert token count → communication volume + GEMM size → straggler time。

06 · MANY EXPERTS CREATE MANY SMALL GEMMS

通信结束以后还有第二个效率问题：每个 expert 收到的 token 数可能不大。

NAIVEE0 GEMM · E1 GEMM · E2 GEMM · …很多大小不同的小矩阵运算，launch/occupancy 问题更明显。
→
GROUPED GEMMgroup expert GEMMs把多个 expert matrix multiplies 以 grouped 方式执行，提高本地硬件利用率。

--moe-grouped-gemm 解决的是 local expert compute efficiency，不是 token dispatch 网络本身。不要把“Grouped GEMM”和“通信融合”混成一件事。

07 · EP DOES NOT FIX ONE DISPATCHER

当前训练配置明确支持 allgather、alltoall、flex。

ALLGATHERallgather dispatcher当前 TransformerConfig.moe_token_dispatcher_type 默认值仍是 allgather；先 gather token information，再做本地选择/处理。
ALLTOALLAll-to-All dispatcher直接表达 destination-specific token exchange，是理解 EP many-to-many 数据流最直观的路径。
FLEXpluggable EP backends当前 flex 路径可接 DeepEP / HybridEP / NCCL-EP 等更专门实现，并带自己的能力与约束。

因此一句更准确的话是：EP 产生 destination-dependent token traffic；All-to-All 是典型实现，但 Megatron 的 dispatcher contract 允许其它实现。

当前配置源码：TransformerConfig.moe_token_dispatcher_type，类型为 allgather | alltoall | flex，默认 allgather。
08 · EXPERT GRID IS NOT DENSE GRID × EP

TP、CP、EP 不能靠一个“把所有缩写乘起来”的公式理解。

DENSE GRIDdense TP × PP × CP → dense DPAttention/dense Transformer 部分按 dense rank generator 组织。
EXPERT GRIDexpert-TP × EP × PP → expert-DPMoE expert 部分由另一套 expert rank generator 组织；当前实现里 expert grid 的 CP 轴为 1。

当前 parallel_state.py 会先从 world size 和 dense TP×PP×CP 得到 dense DP，再单独用 expert_tensor_parallel_size × expert_model_parallel_size × PP 得到 expert-DP（忽略实验性额外轴时）。因此 EP 不是无条件在 dense 总 GPU 公式外再乘一次。

TP 与 EP 也可以同时存在：一个 expert 自己可以再做 expert tensor parallel。Megatron 对不同组合还有 Sequence Parallel 等配置约束，所以真正调配置时要回 parallel_state.py 和当前验证逻辑，而不是背简化乘法口诀。

当前实现：megatron/core/parallel_state.py，分别构造 dense RankGenerator 与 expert_decoder_rank_generator。
09 · EP MAKES OVERLAP MORE IMPORTANT

Token exchange 很重，工程优化会尽量把它藏进其它可并行计算窗口。

overlap_moe_expert_parallel_comm制造/启用 expert communication 与其它计算的 overlap 路径。
delay_wgrad_compute延后部分 weight-gradient 工作，为 communication 暴露计算窗口。
moe_shared_expert_overlap让 shared-expert compute 与支持的 dispatcher communication 并发。

这些选项高度版本相关，不能只背 CLI 名称。05.8 的核心方法仍然是：先画 dependency，再看 async launch / stream / wait，最后用 profiler 证明时间区间是否真的重叠。

CHECKPOINT05.7

把 EP 语义、dispatcher 和 topology 三层分开。

1. 为什么 router 会自然产生 many-to-many traffic？
每个 source rank 的不同 tokens 可以被路由到不同 destination experts，而这些 experts 又分布在不同 ranks；因此不是对同一个 tensor 做统一 reduction，而是 destination-dependent exchange。
2. “EP = All-to-All”为什么不够准确？
All-to-All 是最直观的 dispatcher，但当前 Megatron 训练配置还支持 allgather 和 flex。EP 定义 expert placement / routing 的并行语义，不定义唯一 transport implementation。
3. 为什么不能写 world_size = TP×PP×CP×EP×DP 当统一公式？
当前 Megatron 分别构造 dense grid 与 expert grid。dense grid 用 TP/PP/CP 和 dense DP；expert grid用 expert-TP/EP/PP 和 expert-DP。EP 不是简单叠加在同一套 dense grid 外的独立乘数。
