Expert Parallel：MoE 为什么把通信从 All-Reduce 变成 All-to-All？

Dense Transformer 的 MLP 是“所有 token 都经过同一组权重”。Mixture-of-Experts 把这件事改成：先由 router 给每个 token 选少数 experts，再只执行被选中的 expert MLP。这样模型可以拥有大量 expert 参数，却只激活其中一小部分。Expert Parallel 的难点也随之出现：token 此刻在哪张 GPU，expert 又在哪张 GPU？

这节课结束时，你应该能做到：
  • 理解 MoE layer = router + many experts + sparse token-to-expert assignment。
  • 解释 EP 为什么是“切 experts”，而不是切 hidden dimension。
  • 从 token 路由推导为什么 All-to-All 会自然出现。
  • 理解 dispatch → local expert GEMM → combine 的完整数据流。
  • 知道负载不均衡为什么会让最快的 GPU 也必须等最慢 expert rank。
  • 看懂 Megatron 当前 allgather / alltoall / flex token dispatcher 的基本定位。
01 · DENSE MLP → MIXTURE OF EXPERTS

MoE 不是很多完整模型，而是把某些 FFN/MLP 层换成一组 experts。

TOKENShidden states[num_tokens, H]
→
ROUTERscore experts + top-k每个 token 选择少数 experts，例如 top-2。
→
EXPERT FFNsE₀, E₁, …, E₇只执行被路由到的专家。

比如有 8 个 experts，但每个 token 只走 top-2。模型参数可以因为 8 份 expert MLP 大幅增加，但单个 token 只激活其中 2 个，因此计算量不会简单变成 dense MLP 的 8 倍。

MoE 的核心不是“并行”本身，而是稀疏激活。Expert Parallel 是把这些 experts 分布到不同 GPU 上之后，为了真正执行这种稀疏路由而产生的系统方案。

02 · SHARD EXPERTS ACROSS GPUS

EP=4、8 个 experts：每个 EP rank 可以持有 2 个 local experts。

EP RANK 0Expert 0 · 1只保存/计算本地 experts。
EP RANK 1Expert 2 · 3只保存/计算本地 experts。
EP RANK 2Expert 4 · 5只保存/计算本地 experts。
EP RANK 3Expert 6 · 7只保存/计算本地 experts。

这能把大量 expert parameters 分摊到多张 GPU。但 router 选 expert 时并不会尊重“token 原来在哪张卡”。rank 0 上的 token 完全可能被分给 Expert 6，而 Expert 6 在 rank 3。

因此必须把 token hidden state 真正送到拥有目标 expert 的 GPU。

04 · DISPATCH → EXPERT COMPUTE → COMBINE

一个 MoE layer 的系统数据流可以压成四步。

1 · ROUTER / PERMUTEgroup by destination expert计算 top-k、probabilities，并把 tokens 排成适合通信/专家计算的顺序。
→
2 · DISPATCHAll-to-All把 token hidden states 发到 expert 所在 EP ranks。
→
3 · EXPERTSlocal GEMMs每张 GPU 对收到的 token groups 执行自己的 experts。
→
4 · COMBINEreverse communicationexpert outputs 回到 token 原来的 logical positions，再按 routing weights 合并。

当前 Megatron Core 的 MoEAlltoAllTokenDispatcher 文档就是按类似流程组织：preprocess / permute → EP All-to-All dispatch → local postprocess/expert work → combine 前处理 → EP All-to-All → unpermute。

官方 API：core.transformer.moe.token_dispatcher。其中 MoEAlltoAllTokenDispatcher 明确描述 EP A2A dispatch / combine 流程。
05 · THE LOAD-BALANCE PROBLEM

如果 router 把太多 token 发给同一个 expert，整个 MoE layer 会被它拖慢。

理想情况是 token 在 experts 之间比较均衡。现实里 router 学到的分布可能很偏：

Expert 0
92
Expert 1
28
Expert 2
41
Expert 3
19

rank 0 的 Expert 0 还在处理大量 tokens 时，其它 ranks 可能已经空闲。于是 MoE 不只需要“把 token 发对地方”，还需要 router load balancing、capacity 策略、expert bias / auxiliary loss 等算法机制。

Megatron 当前 router 配置支持 aux_loss、sinkhorn、seq_aux_loss、none 等负载均衡类型，并有 capacity / token drop 相关选项。初学阶段只要抓住系统因果：router 分布 → 每个 expert 的 token count → local GEMM size 与最慢 rank 时间。

06 · MANY EXPERTS CREATE MANY SMALL GEMMS

通信结束以后还有第二个效率问题：每个 expert 收到的 token 数可能不大。

NAIVEE0 GEMM · E1 GEMM · E2 GEMM · …很多大小不同的小矩阵运算，kernel launch 和低 occupancy 问题更明显。
→
GROUPED GEMMgroup expert GEMMs把多个 expert matrix multiplies 以 grouped 方式执行，提高硬件利用率。

这就是 Megatron 的 --moe-grouped-gemm 为什么会出现在性能建议里。它不是改变 MoE 数学，而是让 local expert compute 更像 GPU 擅长的大批量工作。

07 · CURRENT MEGATRON HAS MULTIPLE DISPATCHERS

“EP = All-to-All”是最重要的基础，但真实框架已经有多种 token transport。

ALLGATHERallgather dispatcher把 token 信息 gather 到更大通信域，再在本地选择/处理；当前默认 dispatcher 类型仍可为 allgather。
ALLTOALLNCCL All-to-All标准 EP>1 的直接方案：token 只发送到目标 expert ranks，最适合建立 EP 心智模型。
FLEXDeepEP / HybridEP / NCCL EP当前 Megatron 还提供 flex dispatcher，可选择更专门的跨节点/高性能 expert-parallel backend。

当前 TransformerConfig.moe_token_dispatcher_type 支持 allgather、alltoall、flex。MoE guide 对标准 EP>1 推荐 NCCL-based alltoall，并列出了 DeepEP / HybridEP 等更现代 backend。

官方说明：Megatron Core · Mixture of Experts；配置 API：TransformerConfig。
08 · EP AND TP CUT DIFFERENT THINGS

TP 把一个 expert/Linear 横着切，EP 把很多 experts 分到不同设备。

TENSOR PARALLELsplit one matrix多个 TP ranks 一起完成同一个 Linear / expert。通信常是 all-reduce、all-gather、reduce-scatter。
EXPERT PARALLELsplit expert set不同 EP ranks 持有不同 experts。router 决定 token 应去哪里，因此 token dispatch/combine 常表现为 all-to-all。

两者也可以组合：每个 expert 自己再用 expert tensor parallel。但当前 Megatron MoE 指南特别提醒，细粒度 MoE 常更倾向 EP 而不是把 expert TP 设很大，因为本地 GEMM 过小会损伤效率。

官方 Parallelism Guide 还要求：TP 与 EP 同时使用时启用 Sequence Parallel。这是一个配置约束，后面真正跑 Megatron 时要记得。

09 · EP MAKES COMMUNICATION OVERLAP EVEN MORE IMPORTANT

All-to-All 很重，真正工程优化会想办法把 token transfer 藏进其它计算。

Megatron 当前 MoE 性能指南明确把 EP All-to-All 视作重要通信瓶颈，并提供：

--overlap-moe-expert-parallel-comm把相邻 microbatches 的 expert communication 与其它计算重叠。
--delay-wgrad-compute配合拆开/延后部分 weight-gradient 计算，制造可与 A2A overlap 的计算窗口。
--moe-shared-expert-overlap共享 expert compute 与 token dispatch communication 并发。

下一课不再增加一种 parallelism，而是把前面所有“通信税”统一放到 timeline 上看：Megatron 的高级性能优化，本质上是在 dependency 允许的地方，把 communication 与 compute 同时跑。

CHECKPOINT05.7

确认你能从 router 自己推导出 All-to-All。

1. 为什么 EP 不能只做 All-Reduce？
因为不同 token 被 router 指定到不同 experts，而 experts 分布在不同 ranks。需要把不同 token 发送到不同目的地；这不是“所有 rank 对同一个 tensor 求和”的 All-Reduce 语义，而是 many-to-many 的 token exchange。
2. 为什么 load imbalance 会直接降低 MoE throughput？
某些 experts 收到过多 tokens 时，它们对应 rank 的 expert GEMM 更久；其它 ranks 即使先完成也要等待整体 layer 的依赖继续，因此 step 时间被最慢部分拖住。
3. Grouped GEMM 在解决通信问题吗？
不是。它主要优化 dispatch 后的本地 expert compute，把多个较小 expert GEMMs 以 grouped 方式执行，提高 GPU 利用率。通信仍由 token dispatcher 处理。
