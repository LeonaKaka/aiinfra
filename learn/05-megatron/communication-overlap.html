Communication Overlap：Megatron 怎么让 NCCL 和 GEMM 同时发生？

前面每加一种并行，都会出现一种新的通信税：TP 有 All-Gather / Reduce-Scatter，DP 有 gradient reduce 和 parameter gather，PP 有 stage P2P，EP 有 token All-to-All。真正的大规模训练不能只“把通信做快”，还要问：通信时 GPU 是否有另一段独立计算可以同时做？Communication overlap 就是在依赖允许的地方，把等待时间藏起来。

这节课结束时，你应该能做到：
  • 区分“通信时间存在”和“通信时间暴露在 step wall-time 上”是两回事。
  • 理解 overlap 的前提是数据依赖允许，而不是简单开两个 CUDA streams。
  • 把 DP grad-reduce / param-gather、TP AG/RS、PP P2P、EP A2A 分别对应到当前 Megatron 的优化开关。
  • 理解 buckets / chunks 为什么既影响通信效率，也影响 overlap 启动时机。
  • 知道 overlap 可能因为资源竞争、消息过小、load imbalance 等原因失效。
  • 建立用 Nsight Systems / timeline 验证 overlap 的基本思路。
01 · THE GOAL IS TO HIDE, NOT DELETE

Overlap 不会让 10 ms NCCL 凭空消失，它只想让这 10 ms 和别的工作重叠。

SERIALcompute 完 → 等 communication → 再 compute
GEMMGEMMNCCLNCCLGEMMGEMM
OVERLAPPEDcommunication 与独立 compute 同时推进
GEMMGEMMGEMMGEMMGEMMGEMM
—NCCLNCCL———

如果 communication 完全落在 compute 的时间窗口里，那么它对 step time 的“暴露部分”可能很小；如果通信比可重叠计算更长，超出来的尾巴仍然必须等待。

HIDDEN COMM被计算覆盖的部分它仍然占网络/NVLink 资源，只是不额外拉长关键路径。

EXPOSED COMM覆盖不住的尾巴这部分真正出现在 timeline gap / step wall-time 中。
02 · DEPENDENCIES DECIDE WHAT CAN OVERLAP

最重要的不是“有没有两个 stream”，而是下一段计算到底需不需要这次通信结果。

COMPUTE Aproduce tensor X
→ communication X →
COMPUTE Bneeds X
dependency
COMPUTE Cdoes not need X

Compute B 必须等 communication X 完成，无法靠“异步”绕过数学依赖；但 Compute C 如果使用别的数据，就可能和通信并发。优秀的 schedule、bucket order、microbatch interleaving 都是在主动寻找这种独立工作。

Overlap 是调度问题，也是数据布局问题。你如何 shard tensors、什么时候某个 bucket ready、哪层参数下一刻才会被使用，都会决定可重叠窗口有多大。

03 · CUDA / NCCL ASYNCHRONY IS THE MECHANISM

计算 kernel 和通信 collective 可以被异步提交，但能否并行还要看硬件资源。

COMPUTE WORKGEMM / attention kernels主要使用 SM、Tensor Cores、HBM bandwidth 等 GPU 资源。
COMM WORKNCCL / P2P使用 NVLink/PCIe/NIC 等数据路径，也会占用 GPU copy/communication engine、SM 或 memory bandwidth，具体取决于算法/平台。

因此两个 stream “时间上可以并发”不代表性能一定相加。若两者都强烈争抢 HBM bandwidth 或其它共享资源，compute 可能变慢，通信也可能变慢。

情况看起来可 overlap实际可能发生
Compute-bound GEMM + network comm资源更互补通常更有隐藏通信的空间。
Memory-bound kernel + heavy comm两个任务异步可能争 HBM / fabric，互相拖慢。
Tiny compute chunks有很多空隙窗口太短，通信 launch/latency 反而更显眼。
04 · FOUR PARALLELISMS, FOUR OVERLAP TARGETS

前面学过的通信，现在统一放到一张表里。

DPgrad RS/AR + param AGBackward 时提前 reduce gradient buckets；forward 前预取 parameter buckets。
TPactivation AG / RSSequence Parallel 下把 Linear GEMM 与 TP collectives 做 bulk / pipelined overlap。
PPP2P activation / gradient1F1B/VPP schedule 中把 stage send/recv 与其它 microbatch compute 交错。
EPtoken All-to-All通过相邻 microbatch / shared expert / delayed wgrad 等制造可覆盖 A2A 的计算。

当前 Megatron 文档对应的主要开关分别是 --overlap-grad-reduce、--overlap-param-gather、--tp-comm-overlap、--overlap-p2p-comm、--overlap-moe-expert-parallel-comm 等。

当前 Megatron MoE/performance guide 汇总了 DP、TP、PP、EP 的 communication overlap 配置：Megatron Core · Mixture of Experts / Performance Tips。
05 · DP OVERLAP: BUCKETS CREATE EARLY STARTS

Backward 不必全部结束，某个 gradient bucket ready 就可以开始 reduce。

BACKWARDL7L6L5L4L3L2L1
GRAD REDUCE—B7B6B5B4B3B2

这也是 05.5 为什么强调 contiguous buffers / buckets。bucket 太大，通信启动晚，可 overlap 窗口变小；bucket 太小，又会产生更多 collective launch / latency overhead。bucket size 本身就是性能调参的一部分。

当前 param_and_grad_buffer API 中，start_grad_sync() 在开启 overlap 时会发起异步 all-reduce/reduce-scatter，finish_grad_sync() 再在真正需要完成时等待。

API：core.distributed.param_and_grad_buffer。
06 · TP OVERLAP: PIPELINE COLLECTIVE CHUNKS WITH GEMM

TP 的挑战更难：通信就在 Linear 的数据依赖附近。

Sequence Parallel 下，TP Linear 周围常有 activation all-gather / reduce-scatter。某些通信和 GEMM 存在直接依赖，不能整块同时跑；于是实现可以把 tensor/GEMM/collective 切成更小 chunks，让“AG 一部分 → GEMM 一部分”形成流水。

ALL-GATHERchunk 0chunk 1chunk 2chunk 3———
GEMMwaitchunk 0chunk 1chunk 2chunk 3——

Megatron 当前 ModelParallelConfig 中，tp_comm_overlap 会尝试在 forward/backward Linear 上 overlap TP collectives；还有 bulk wgrad/dgrad、AG/RS pipelining 等更细的控制项。

当前 API：core.model_parallel_config，见 tp_comm_overlap 及相关配置。

08 · WHY OVERLAP CAN FAIL

开了 flag 以后 throughput 没涨，不代表 flag 没生效。

DEPENDENCY可重叠窗口太短下一段关键计算很快就需要通信结果，异步也必须立刻 wait。
RESOURCE CONFLICTcompute / comm 互相抢资源同时跑以后每个任务都变慢，净收益变小。
MESSAGE SIZEbucket 太碎latency / launch overhead 过大，难以跑到高带宽。
TOPOLOGY跨慢链路通信尾巴太长，可用 compute 根本盖不住。
IMBALANCE某些 ranks 更慢PP stage / MoE expert 负载不均，其他 ranks 仍然会在同步点等待。
CPU LAUNCH主机跟不上GPU timeline 本身出现空洞时，先解决 launch overhead，再谈通信 overlap。

CHECKPOINT05.8

到这里，你应该开始像 Infra 工程师一样看 timeline。

1. 一次 NCCL 操作耗时 10 ms，和 GEMM 完全重叠后，它的“真实耗时”变成 0 ms 了吗？
没有。通信仍实际执行并消耗链路/GPU资源；只是如果它完全落在原本就要执行的独立 GEMM 时间里，它对 step 关键路径新增的 exposed time 可以接近 0。
2. 为什么 bucket 太大和太小都可能不好？
太大时要等很多 gradient/参数准备好后才能启动通信，减少 overlap 窗口；太小时 collective 数量太多，launch/latency overhead 上升，带宽利用也可能变差。
3. 开启异步 stream 后为什么仍可能完全没有 overlap 收益？
可能存在立即数据依赖，必须马上 wait；也可能 compute/comm 争抢相同资源、通信远长于可覆盖计算、CPU launch 出现瓶颈等。是否有效必须靠实际 timeline 和 throughput 验证。
