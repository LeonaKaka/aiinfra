autograd 与 optimizer：梯度从哪里来，显存又花在哪里？

上一课你已经会写 loss.backward() 和 optimizer.step()。现在把这两个黑盒拆开一点：梯度到底表达什么？PyTorch 怎么沿计算关系把梯度算回来？Adam 为什么会比“只存参数”多吃很多显存？这些问题会直接通向后面的 Data Parallel、ZeRO 和 Megatron Distributed Optimizer。

这节课结束时，你应该能做到：
  • 用直觉解释“梯度”而不是只背“导数”。
  • 看懂一个最小 autograd 计算图，以及 .grad 是什么时候出现的。
  • 区分 autograd 负责“算梯度”和 optimizer 负责“用梯度更新参数”。
  • 理解 Adam 为什么需要额外 optimizer states，以及为什么它们值得被分片。
01 · WHAT A GRADIENT TELLS YOU

梯度先理解成：“参数轻轻动一下，loss 会往哪边变？”

假设只有一个参数 w。当前 loss 是由 w 决定的。梯度 dL/dw 告诉你：如果 w 增加一点，loss 大约会增加还是减少，以及变化有多敏感。

w = current parameter→gradient = dL/dwgradient > 0：把 w 往小方向推一点，通常能让 loss 降低

所以最朴素的 SGD 更新可以写成：

w_new=w_old−lr × gradient

lr 是 learning rate。它控制每次沿“降低 loss 的方向”走多大一步。

现在不需要微积分证明。你只需要建立方向感：gradient 是 optimizer 的导航信息；没有 gradient，optimizer 就不知道参数该怎么改。

02 · COMPUTATION GRAPH

autograd 为什么能知道每个参数的梯度？因为 forward 时留下了计算关系。

看一个极小例子：

PARAMETERw
→
FORWARDŷ = w × x
→
LOSS(ŷ-y)²

当参与计算的 tensor 需要梯度时，PyTorch 会跟踪这些操作之间的关系。执行 loss.backward() 后，它从 loss 往回走，利用链式法则把影响一路传回 w。

pythonautograd_minimal.py
import torch

w = torch.tensor(2.0, requires_grad=True)
x = torch.tensor(3.0)
y = torch.tensor(7.0)

prediction = w * x
loss = (prediction - y) ** 2

print(w.grad)       # None: 还没 backward
loss.backward()
print(w.grad)       # tensor(-6.)

这里 w=2、x=3，预测是 6，目标是 7。当前梯度为 -6，意味着在这个点把 w 稍微增大，会让 loss 下降；SGD 的 w -= lr * grad 也确实会把 w 往更大的方向推。

03 · WHERE GRADIENTS LIVE

.grad 是参数旁边真实存在的一块 tensor。

这件事对 Infra 很重要。梯度不是“一个抽象概念算完就没了”，训练时通常要把很多参数对应的梯度实际存下来。

parameter

例如一个 Linear 的 weight。它是模型当前学到的数值。

parameter.grad

backward 后产生的梯度 tensor，通常与对应参数有相同的 shape。

optimizer state

取决于优化器。SGD 可以很简单；带 momentum 或 Adam 会再维护额外状态。

这也解释了为什么一个“参数文件大小 14 GB”的模型，训练时绝不会只需要 14 GB 显存。参数只是账单的一部分。

04 · WHY GRADIENTS ACCUMULATE

PyTorch 默认是“加到 grad 上”，不是每次自动覆盖。

如果连续做两次 backward()，又没有清空参数的 .grad，新梯度通常会累加进去。这就是上一课为什么要写 zero_grad()。

conceptgradient accumulation
optimizer.zero_grad()

loss_batch_1.backward()   # grad = g1
loss_batch_2.backward()   # grad = g1 + g2

optimizer.step()

这不是 PyTorch 的坏习惯，而是一个有用特性：显存放不下大 batch 时，可以用多个小 microbatch 累积梯度，再更新一次参数。以后你在 Megatron 里看到 microbatch 和 gradient accumulation，这个基础会再次出现。

05 · OPTIMIZER IS A DIFFERENT JOB

autograd 算出 gradient；optimizer 决定怎么利用它。

SGD 的核心想法很简单：沿负梯度方向走一点。Adam 则会为每个参数维护关于梯度的一阶、二阶统计状态，常见地叫 m 和 v，用它们自适应调整更新。

SGD · SIMPLE VIEW

parameter + gradient 就能理解最基础的更新；若启用 momentum，还会多一份 momentum state。

ADAM · SIMPLE VIEW

除了 parameter 和 gradient，通常还会有两份与参数规模相近的状态：一阶矩 m 与二阶矩 v。

注意：实际训练的 dtype、mixed precision、master weights、optimizer 实现会改变精确显存数字。这里先建立“optimizer states 可能和参数本身一样巨大”的结构性直觉。

06 · MEMORY LEDGER

从这一刻开始，学会给训练显存记账。

一个非常粗略但重要的心智模型：

MODEL STATESparameters：模型权重本身
BACKWARD STATESgradients：参数对应的梯度
OPTIMIZER STATES例如 Adam 的 m / v，以及某些混合精度方案里的额外高精度副本
ACTIVATIONSforward 为 backward 保留的中间结果，大小强烈依赖 batch / sequence / model shape

这四类东西后面会反复被各种 Infra 技术“拆、丢、重算、分片”：activation checkpointing 在处理 activation；Data Parallel 会涉及 gradient sync；ZeRO / Distributed Optimizer 会处理 model/optimizer states 的重复存储。

07 · WHY SHARD OPTIMIZER STATES

如果每张 GPU 都存一整份 Adam 状态，重复会非常贵。

先做最朴素的 Data Parallel 思想实验：4 张 GPU 都拥有完整模型副本。

EACH GPU · NAIVE DPfull params + full optimizer states
lots of replicas
GPU 0 / 1same state copies
GPU 2 / 3same state copies

如果 optimizer state 很大，这种复制非常浪费显存。于是很自然会问：

Can we shard→optimizer statesacrossDP ranks?

答案就是后面会遇到的 ZeRO 思想与 Megatron Distributed Optimizer 的核心方向之一。现在不用学实现，只要知道它解决的根本矛盾：多卡训练需要协作，但不代表每张卡都应该重复保存全部训练状态。

CHECKPOINTFOUNDATIONS

过这一关，再进入 Transformer。

1. loss.backward() 之后，gradient 通常存在哪里？
对需要梯度的 leaf parameters 来说，梯度会累积在参数的 .grad tensor 中。它通常与对应参数具有相同 shape。
2. Adam 为什么会比只保存模型参数多占很多状态内存？
因为它通常为每个参数维护额外的一阶、二阶统计状态（常称 m、v）；实际混合精度实现还可能存在额外高精度参数副本，因此精确占用依实现而异。
3. 为什么 Distributed Optimizer / ZeRO 类思路对大模型重要？
因为普通 Data Parallel 如果让每张 GPU 都重复保存完整的参数/梯度/optimizer states，会浪费大量显存。把其中一些状态按 DP ranks 分片，可以显著减少每卡重复存储。
