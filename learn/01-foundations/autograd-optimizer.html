LESSON 01.4 · FOUNDATION约40 min

自动求导与优化器：gradient 从哪里来，显存又花在哪里？

上一课你已经会写 loss.backward() 和 optimizer.step()。现在把这两个黑盒拆开一点：autograd（自动求导：PyTorch 自动记录计算关系并计算 gradient 的机制）怎样把 gradient 算回来？gradient 到底表达什么？Adam（Adam 优化器：利用一阶和二阶动量统计更新 parameter 的常用 optimizer）为什么会比“只存 parameter”多吃很多显存？这些问题后面会自然变成一个系统问题：当训练状态大到每张设备都重复保存很浪费时，哪些状态可以安全地分片保存和更新？

这节课结束时，你应该能做到：
  • 用直觉解释“梯度”而不是只背“导数”。
  • 看懂一个最小 autograd 计算图，以及 .grad 是什么时候出现的。
  • 区分 autograd 负责计算 gradient，而 optimizer 负责用 gradient 更新 parameter。
  • 理解 Adam 为什么需要额外 optimizer state（优化器状态：optimizer 为更新 parameter 额外保存的历史量），以及为什么它们值得被分片。
01 · 梯度到底告诉你什么

梯度先理解成：“参数轻轻动一下，损失会往哪边变？”

假设只有一个参数 w。当前损失是由 w 决定的。梯度 dL/dw 告诉你：如果w增加一点，损失大约会增加还是减少，以及变化有多敏感。

w = current parameter→gradient = dL/dw梯度 > 0：把w往小方向推一点，通常能让损失降低

所以最朴素的 SGD 更新可以写成：

w_new=w_old−lr × gradient

lr 是学习率。它控制每次沿“降低损失的方向”走多大一步。

现在不需要微积分证明。你只需要建立方向感：梯度是优化器的导航信息；没有梯度，优化器就不知道参数该怎么改。

02 · 计算图

autograd 为什么能知道每个 parameter 的 gradient？因为前向计算时留下了计算关系。

看一个极小例子：

参数w
→
前向计算ŷ = w × x
→
损失(ŷ-y)²

当参与计算的 tensor 需要 gradient 时，PyTorch 会跟踪这些操作之间的关系。执行 loss.backward() 后，它从 loss 往回走，利用链式法则把影响一路传回 w。

pythonautograd_minimal.py
import torch

w = torch.tensor(2.0, requires_grad=True)
x = torch.tensor(3.0)
y = torch.tensor(7.0)

prediction = w * x
loss = (prediction - y) ** 2

print(w.grad)       # None: 还没 backward
loss.backward()
print(w.grad)       # tensor(-6.)

这里 w=2、x=3，预测是6，目标是7。当前梯度为 -6，意味着在这个点把w稍微增大，会让损失下降；SGD的 w -= lr * grad 也确实会把w往更大的方向推。

03 · 梯度存在哪里

.grad 是 parameter 旁边真实存在的一块 tensor。

这件事对Infra很重要。梯度不是“一个抽象概念算完就没了”，训练时通常要把很多参数对应的梯度实际存下来。

parameter

例如一个 Linear 的 weight。它是模型当前学到的数值。

parameter.grad

backward 后产生的 gradient tensor，通常与对应 parameter 有相同的 shape。

optimizer state

取决于 optimizer。SGD 可以很简单；带动量或 Adam 会再维护额外 state。

这也解释了为什么一个“parameter 文件大小 14 GB（十进制容量单位：1 GB = 10^9 bytes）”的模型，训练时绝不会只需要 14 GB 显存。parameter 只是账单的一部分。

04 · 为什么梯度会累积

PyTorch 默认是“累加到 .grad 上”，不是每次自动覆盖。

如果连续做两次 backward()，又没有清空 parameter 的 .grad，新 gradient 通常会累加进去。这就是上一课为什么要写 zero_grad()。

concept梯度累积
optimizer.zero_grad()

loss_batch_1.backward()   # grad = g1
loss_batch_2.backward()   # grad = g1 + g2

optimizer.step()

这不是 PyTorch 的坏习惯，而是一个有用特性：显存放不下大批次时，可以用多个小 microbatch（微批次：把一个 batch 再切小后逐个执行的小批次）累积 gradient，再更新一次 parameter。但要注意：“累积多个 microbatch”不自动等于“一次大 batch”。如果每个 microbatch 的 loss 都用均值归约，等大 microbatch 常见做法是先除以 accumulation steps 再做 backward；如果 microbatch 大小不同，则要按样本 / token 数正确加权。否则累计 gradient 的整体尺度或样本权重会和一次大 batch 不同。以后你在 Megatron 里看到 microbatch 和 gradient accumulation，这个基础会再次出现。

05 · 优化器做的是另一件事

autograd 计算 gradient；optimizer 决定怎么利用它。

SGD的核心想法很简单：沿负梯度方向走一点。Adam则会为每个参数维护关于梯度的一阶、二阶统计状态，常见地叫 m 和 v，用它们自适应调整更新。

SGD · SIMPLE VIEW

parameter + gradient 就能理解最基础的更新；若启用动量，还会多一份 momentum state（动量状态：记录历史 gradient 趋势以平滑 parameter 更新）。

ADAM · SIMPLE VIEW

除了 parameter 和 gradient，通常还会有两份与 parameter 规模相近的状态：一阶矩 m 与二阶矩 v。

注意：实际训练的数据类型、混合精度、高精度权重副本、优化器实现会改变精确显存数字。这里先建立“优化器状态可能和参数本身一样巨大”的结构性直觉。

06 · 训练状态的显存账本

从这一刻开始，学会给训练显存记账。

一个非常粗略但重要的心智模型：

模型状态parameter：模型权重本身
梯度状态gradient：parameter 对应的梯度
优化器状态例如 Adam 的 m / v，以及某些混合精度方案里的额外高精度副本
激活值前向计算为反向传播保留的中间结果，大小强烈依赖批次 / sequence / model形状

这四类东西后面会反复被系统技术“拆、丢、重算、分片”：activation（激活值：forward 产生并可能在 backward 中复用的中间结果）可以通过重算来省显存；多设备训练需要同步必要的 gradient；parameter、gradient 和 optimizer state 也可以按不同策略减少重复保存。现在先把“有哪些状态”记清，不需要提前背这些策略的名字。

07 · 为什么要分片优化器状态

如果每张GPU都存一整份Adam状态，重复会非常贵。

先做最朴素的数据并行思想实验：4 张 GPU 都拥有完整模型副本。

EACH GPU · DPfull params + full optimizer states
replica（副本：在不同进程或 GPU 上保存的同一逻辑模型或 state）
GPU 0 / 1same state copies
GPU 2 / 3same state copies

如果优化器状态很大，这种复制非常浪费显存。于是很自然会问：

Can we shard→optimizer statesacrossDP 进程?

答案就是后面会遇到的 ZeRO（零冗余优化器：通过数据并行进程分片 optimizer state、gradient 或 parameter 来减少重复存储）与 Megatron Distributed Optimizer（分布式优化器：沿数据并行域分片训练状态和更新责任）的核心方向之一。现在不用学实现，只要知道它解决的根本矛盾：多卡训练需要协作，但不代表每张卡都应该重复保存全部训练状态。

CHECKPOINTFOUNDATIONS

过这一关，再进入Transformer。

1. loss.backward() 之后，梯度通常存在哪里？
对需要 gradient 的可训练 parameter 来说，gradient 会累积在 .grad tensor 中。它通常与对应 parameter 具有相同 shape。
2. Adam为什么会比只保存模型参数多占很多状态内存？
因为它通常为每个参数维护额外的一阶、二阶统计状态（常称m、v）；实际混合精度实现还可能存在额外高精度参数副本，因此精确占用依实现而异。
3. 为什么分布式优化器 / ZeRO类思路对大模型重要？
因为普通数据并行如果让每张GPU都重复保存完整的参数/梯度/优化器状态，会浪费大量显存。把其中一些状态按 DP 进程分片，可以显著减少每卡重复存储。
